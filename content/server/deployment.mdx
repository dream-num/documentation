Server SDK is a library, not a deployable product. The application assembles Service, Endpoint, and
Transport, injects a Database Adapter, adds the conversion module when it needs import and export, and
deploys at its own scale. This page gives three shapes; each one can be the destination.

| Shape                                           | Collaboration | Import and export | Recommended scale                                   |
| ----------------------------------------------- | ------------- | ----------------- | --------------------------------------------------- |
| [Single machine](#single-machine)               | One process   | Same process      | Local applications, development, a few internal users |
| [Split services](#split-services)               | One node      | Separate process  | Multi-user online service within one node's capacity |
| [Multiple nodes](#multiple-collaboration-nodes) | Several nodes | Separate process  | Beyond one node's capacity, or node failover        |

Versions correspond to `1.1.0`; see [Environment and versions](/server/requirements). Users,
authentication, authorization, file storage, and operations belong to the application in every shape;
see [Identity and authorization](/server/collaboration/identity-and-authorization).

## Single machine

One Node.js process hosts collaboration and import and export, and the browser connects to it
directly. Storage is SQLite, or your database through a custom Database Adapter.

<Mermaid chart={"%%{init: {\"themeVariables\": {\"fontSize\": \"14px\"}, \"flowchart\": {\"nodeSpacing\": 24, \"rankSpacing\": 40, \"padding\": 12}}}%%\nflowchart LR\n    Browser([\"Browser\"]) -->|\"HTTP / WebSocket\"| App[\"Application process<br/>Collaboration + Exchange\"]\n    App --> DB[(\"Database\")]\n    classDef default rx:8,ry:8,stroke-width:1px\n    classDef actor fill:transparent,stroke:none\n    class Browser actor"} />

| Component         | Deployment              | Shares                                   |
| ----------------- | ----------------------- | ---------------------------------------- |
| Collaboration     | One process             | CPU and memory with import and export    |
| Import and export | Same process            | CPU and memory with collaboration        |
| Storage           | SQLite file or database | Only this process                        |

- SQLite persists data, creates its tables, and is backed up as a file. The Memory Adapter is for
  local verification only.
- A conversion is CPU-bound and holds the whole workbook in memory; a large file slows collaboration.
- SQLite serializes writes, so concurrent submissions queue.
- Only one replica; a restart disconnects every Session.

Move to split services when conversions affect collaboration latency, submissions queue, or the
service must stay available to many users.
Reference example: [Exchange](/server/collaboration/examples#exchange).

## Split services

A gateway forwards HTTP and WebSocket; collaboration is one node; import and export are a separate
process; both use the same database. The two splits are independent.

<Mermaid chart={"%%{init: {\"themeVariables\": {\"fontSize\": \"14px\"}, \"flowchart\": {\"nodeSpacing\": 24, \"rankSpacing\": 40, \"padding\": 12}}}%%\nflowchart LR\n    Browser([\"Browser\"]) -->|\"HTTPS / WSS\"| Gateway[\"Gateway\"]\n    Gateway -->|\"Collaboration\"| Node[\"Collaboration node<br/>Transport · Endpoint · Service\"]\n    Gateway -->|\"Upload · task · download\"| Exchange[\"Import and export<br/>Service + Exchange\"]\n    Node --> DB[(\"Database\")]\n    Exchange --> DB\n    classDef default rx:8,ry:8,stroke-width:1px\n    classDef actor fill:transparent,stroke:none\n    class Browser actor"} />

| Component         | Deployment                                         | Shares                              |
| ----------------- | -------------------------------------------------- | ----------------------------------- |
| Gateway           | Routes collaboration and exchange paths separately | —                                   |
| Collaboration     | One node                                           | Database                            |
| Import and export | Separate process, scaled on CPU and memory         | Database: Units, tasks, files       |
| Storage           | Database                                           | Every process                       |

- The Database Adapter implements the `IDatabaseAdapter` contract; the injection point does not
  change. See [Database Adapters](/server/collaboration/database-adapters). Migrations own the
  schema, the service has no DDL rights, and startup only checks that the tables exist.
- The import and export process assembles only the Database Adapter, a `UniverCollabService`, and
  the conversion module, with no Endpoint or Transport. Import creates the Unit through the Service;
  export reads the latest confirmed revision without going through the collaboration node.
- Tasks and files live in storage every replica can reach; tasks have timeouts and download links
  expire. See [File exchange integration](/server/import-export).

### Before going live

- The gateway forwards both HTTP and WebSocket; HTTPS pages use WSS.
- The gateway idle timeout is below the Node.js keep-alive timeout (`5` seconds by default), or
  occasional `502` responses appear.
- Transport caps bodies and messages at 16 MiB by default; set the gateway upload limit to what
  import needs.
- Register a health check route.
- Shutdown order: Transport → Service → Database Adapter. See [Resource cleanup](/server/collaboration/modules#resource-cleanup).
- The license is browser-side configuration, injected at build time. See [License](/server/license).
- Identity and authorization are implemented by the application; the examples' fixed users and
  allow-all rules do not ship.

Collaboration is still one node: the documents it serves are bounded by process memory, and a
restart disconnects every Session. Move to multiple nodes beyond that capacity or for failover.
Reference example: [running import and export separately](https://github.com/dream-num/univer-collaboration-examples/blob/main/examples/multi-node/README.md#run-import-and-export-separately).

## Multiple collaboration nodes

Several nodes run the same code against the same database. A pub/sub adapter relays Rooms,
Presence, and broadcasts between nodes; a ticket store shares Session Tickets.
`@univerjs-pro/collaboration-cluster-redis` provides the Redis implementation and needs Redis 6.2+.

| Component         | Deployment                                  | Shares                          |
| ----------------- | ------------------------------------------- | ------------------------------- |
| Gateway           | Routes WebSocket and submissions by unit ID | —                               |
| Collaboration     | N identical nodes                           | Database, pub/sub, ticket store |
| Import and export | Separate replicas                           | Database                        |
| Storage           | Database                                    | Every node and replica          |

- Create the pub/sub adapter and ticket store and pass them to `UniverCollabEndpoint`; nothing else
  changes. Shutdown order: Transport → pub/sub adapter and its connections → Service → Database Adapter.
- A node's process holds only its loaded Units, WebSocket Sessions, and Room members; all other state
  is in the database and Redis. Add or remove nodes freely; when a node stops, clients reconnect
  through the gateway.
- Redis must be highly available: while it is down, ticket requests fail, WebSocket upgrades return a
  retryable `503`, and new Sessions cannot start.
- The gateway does not retry a failed request on another node, and the SDK does not fail over loaded
  documents automatically.

### Route by document

Any node can handle any request, but keep one document's WebSocket and submissions on one node:
acknowledgements and broadcasts are delivered locally and only that node loads the document.
Otherwise several nodes load the same document and concurrent submissions hit CAS conflicts, then
reload and retry.

| Request                                           | Routing                       |
| ------------------------------------------------- | ----------------------------- |
| WebSocket connect, change submission              | Consistent hash by unit ID    |
| Session Ticket, snapshot, blocks, missing changes | Any node                      |
| Application pages and APIs                        | Any node                      |
| Upload, task, download                            | Any import and export replica |

The WebSocket path has no unit ID, so the browser appends a `unit` query parameter and the gateway
hashes on it.
Reference example: [multi-node example](https://github.com/dream-num/univer-collaboration-examples/blob/main/examples/multi-node/README.md).

## Going further

- **Hand conversions to workers.** Stateless API replicas, tasks in the database, files in object
  storage, and a queue dispatching to independently scaled workers with leases or timeouts.
- **Partition nodes by document.** The routing key is the unit ID, so documents can map to node
  pools by tenant or size; every pool shares the database and pub/sub.
- **Extension modules.** History, Thread Comment, and Worktree bring their own Services and Adapters
  and follow the same shapes. See [Collaboration extension modules](/server/collaboration/extensions).
