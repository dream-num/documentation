A Server SDK application has three deployment shapes, and the scale of the application determines which one to use. Begin with [Collaboration SDK](/server/collaboration/overview), [import and export](/server/import-export), and the [examples](/server/collaboration/examples) to see how the modules are assembled. Deployment only determines how many nodes run that same assembly.

| Shape                                                 | Collaboration | Import and export | Recommended scale                                     |
| ----------------------------------------------------- | ------------- | ----------------- | ----------------------------------------------------- |
| [Single machine](#single-machine)                     | One node      | Same node         | Local applications, development, a few internal users |
| [Split import and export](#split-import-and-export)   | One node      | Separate node     | Multi-user online service within one node's capacity  |
| [Multiple nodes](#multiple-collaboration-nodes)       | Several nodes | Separate node     | Beyond one node's capacity, or node failover          |

## Single machine

All components run in a single Node.js process, and the browser connects to that process directly.

<Mermaid chart={"%%{init: {\"themeVariables\": {\"fontSize\": \"14px\"}, \"flowchart\": {\"nodeSpacing\": 24, \"rankSpacing\": 40, \"padding\": 12}}}%%\nflowchart LR\n    Browser([\"Browser\"]) --> App[\"Collaboration + Exchange\"]\n    App --> DB[(\"Database\")]\n    classDef default rx:8,ry:8,stroke-width:1px\n    classDef actor fill:transparent,stroke:none\n    class Browser actor"} />

- The Database Adapter implements the `IDatabaseAdapter` contract. See [Database Adapters](/server/collaboration/database-adapters).
- Import and export are provided by Exchange Service and File Service. See [Collaboration extension modules](/server/collaboration/extensions).
- Conversion is CPU-bound, so a large file slows collaboration.

Move import and export to a separate node when conversions begin to affect collaboration latency, or when the service must remain responsive for many users.

## Split import and export

Import and export run on a dedicated node while collaboration remains on a single node. The gateway routes the two kinds of requests separately, and both sides use the same database.

<Mermaid chart={"%%{init: {\"themeVariables\": {\"fontSize\": \"14px\"}, \"flowchart\": {\"nodeSpacing\": 24, \"rankSpacing\": 40, \"padding\": 12}}}%%\nflowchart LR\n    Browser([\"Browser\"]) --> Gateway[\"Gateway\"]\n    Gateway -->|\"Collaboration requests\"| Node[\"Collaboration node\"]\n    Gateway -->|\"Import and export requests\"| Exchange[\"Import and export node\"]\n    Node --> DB[(\"Database\")]\n    Exchange --> DB\n    classDef default rx:8,ry:8,stroke-width:1px\n    classDef actor fill:transparent,stroke:none\n    class Browser actor"} />

The import and export node assembles the Database Adapter, a `UniverCollabService`, File Service, and Exchange Service, and then works directly with the database. The injection points are the same as on a single machine. Both nodes point File Service at the same file storage, and both install the same authorization Middleware on `UniverCollabService`.

Process memory limits the number of documents that one collaboration node can serve. Move to multiple nodes when that capacity is exceeded, or when failover is required.

## Multiple collaboration nodes

Several collaboration nodes run the same code against the same database. A pub/sub adapter relays Rooms, Presence, and broadcasts between the nodes, and a ticket store shares Session Tickets. `@univerjs-pro/collaboration-cluster-redis` provides the Redis implementation. Every node uses the same License, which covers the number of running nodes; see [collaboration nodes](/server/collaboration/license#nodes). For a reference implementation, see [Multi-node](/server/collaboration/examples#multi-node).

Each collaboration node passes the Redis pub/sub adapter and ticket store to the Endpoint. The rest of the assembly is unchanged:

```ts
import { createClient } from "redis";
import { RedisPubSubAdapter, RedisSessionTicketStore } from "@univerjs-pro/collaboration-cluster-redis";
import { UniverCollabEndpoint } from "@univerjs-pro/collaboration-endpoint";

const client = createClient({ url: process.env.REDIS_URL });
const subClient = client.duplicate();
await Promise.all([client.connect(), subClient.connect()]);

const pubSub = new RedisPubSubAdapter({ pubClient: client, subClient });
const ticketStore = new RedisSessionTicketStore({ client });
const endpoint = new UniverCollabEndpoint(service, { pubSub, ticketStore });
```

## Going further

One very large document slows down requests for small documents on the same node. Split the node pools by document size and let the gateway route large documents to a dedicated pool. The routing key is still the unit ID, and every pool shares the database and pub/sub.
