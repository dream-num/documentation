This page describes three deployment shapes for a Server SDK application by scale. Read
[Collaboration SDK](/server/collaboration/overview), [import and export](/server/import-export), and the
[examples](/server/collaboration/examples) first to see how the modules are assembled; deployment places
the same assembly on one or more nodes.

| Shape                                           | Collaboration | Import and export | Recommended scale                                   |
| ----------------------------------------------- | ------------- | ----------------- | --------------------------------------------------- |
| [Single machine](#single-machine)               | One node      | Same node         | Local applications, development, a few internal users |
| [Split services](#split-services)               | One node      | Separate node     | Multi-user online service within one node's capacity |
| [Multiple nodes](#multiple-collaboration-nodes) | Several nodes | Separate node     | Beyond one node's capacity, or node failover        |

## Single machine

One Node.js process hosts collaboration and import and export, and the browser connects to it
directly. Storage is SQLite, or your database through a custom Database Adapter. Reference example:
[Exchange](/server/collaboration/examples#exchange), with collaboration and import and export in one process.

| Component         | Deployment              | Shares                                   |
| ----------------- | ----------------------- | ---------------------------------------- |
| Collaboration     | One node                | CPU and memory with import and export    |
| Import and export | Same node               | CPU and memory with collaboration        |
| Storage           | SQLite file or database | This node                                |

- SQLite persists data, creates its tables, and serializes writes; the Memory Adapter is for local
  verification only.
- A conversion is CPU-bound; a large file slows collaboration.
- Runs as a single replica; a restart disconnects every Session.

Move to split services when conversions affect collaboration latency, submissions queue, or the
service must stay available to many users.

## Split services

A gateway forwards HTTP and WebSocket; collaboration is one node; import and export are a separate
node; both use the same database. The two splits are independent.

<Mermaid chart={"%%{init: {\"themeVariables\": {\"fontSize\": \"14px\"}, \"flowchart\": {\"nodeSpacing\": 24, \"rankSpacing\": 40, \"padding\": 12}}}%%\nflowchart LR\n    Browser([\"Browser\"]) -->|\"HTTPS / WSS\"| Gateway[\"Gateway\"]\n    Gateway -->|\"Collaboration\"| Node[\"Collaboration node<br/>Transport · Endpoint · Service\"]\n    Gateway -->|\"Upload · task · download\"| Exchange[\"Import and export node<br/>Service + Exchange\"]\n    Node --> DB[(\"Database\")]\n    Exchange --> DB\n    classDef default rx:8,ry:8,stroke-width:1px\n    classDef actor fill:transparent,stroke:none\n    class Browser actor"} />

| Component         | Deployment                                         | Shares                              |
| ----------------- | -------------------------------------------------- | ----------------------------------- |
| Gateway           | Routes collaboration and exchange paths separately | Forwarding only                     |
| Collaboration     | One node                                           | Database                            |
| Import and export | Separate node, scaled on CPU and memory            | Database: Units, tasks, files       |
| Storage           | Database                                           | Every node                          |

- The Database Adapter implements the `IDatabaseAdapter` contract; the injection point stays the
  same. See [Database Adapters](/server/collaboration/database-adapters).
- The import and export node assembles the Database Adapter, a `UniverCollabService`, and the
  conversion module, and works straight from the database.
- Tasks and files live in storage every replica can reach; tasks have timeouts and download links
  expire. See [File exchange integration](/server/import-export).

Collaboration is still one node, and the documents it serves are bounded by process memory. Move to
multiple nodes beyond that capacity or for failover.

## Multiple collaboration nodes

Several collaboration nodes run the same code against the same database. A pub/sub adapter relays
Rooms, Presence, and broadcasts between nodes, a ticket store shares Session Tickets, and
`@univerjs-pro/collaboration-cluster-redis` provides the Redis implementation. Reference example:
[Multi-node](/server/collaboration/examples#multi-node).

<Mermaid chart={"%%{init: {\"themeVariables\": {\"fontSize\": \"14px\"}, \"flowchart\": {\"nodeSpacing\": 24, \"rankSpacing\": 40, \"padding\": 12}}}%%\nflowchart LR\n    Browser([\"Browser\"]) -->|\"HTTPS / WSS\"| Gateway[\"Gateway\"]\n    subgraph Nodes[\"Collaboration nodes\"]\n        direction TB\n        A[\"Node A\"]\n        B[\"Node B\"]\n    end\n    Gateway -->|\"WebSocket and submissions<br/>by unit ID\"| A\n    Gateway -->|\"Other requests<br/>any node\"| B\n    Gateway -->|\"Upload · task · download\"| Exchange[\"Import and export nodes ×N\"]\n    A --- PubSub[(\"Pub/sub + ticket store\")]\n    B --- PubSub\n    A --> DB[(\"Database\")]\n    B --> DB\n    Exchange --> DB\n    classDef default rx:8,ry:8,stroke-width:1px\n    classDef actor fill:transparent,stroke:none\n    class Browser actor"} />

| Component         | Deployment                                  | Shares                          |
| ----------------- | ------------------------------------------- | ------------------------------- |
| Gateway           | Routes WebSocket and submissions by unit ID | Forwarding only                 |
| Collaboration     | N identical nodes                           | Database, pub/sub, ticket store |
| Import and export | Separate nodes                              | Database                        |
| Storage           | Database                                    | Every node                      |

- Create the pub/sub adapter and ticket store and pass them to `UniverCollabEndpoint`; the rest of the
  assembly stays the same. See [Packages](/server/collaboration/packages).
- The gateway keeps one document's WebSocket and submissions on one node and sends other requests to
  any node. See [gateway configuration](https://github.com/dream-num/univer-collaboration-examples/blob/main/examples/multi-node/README.md#configure-the-gateway).
- Run Redis highly available; when a node fails, clients reconnect through the gateway to another node.

## Going further

- Hand conversions to independently scaled workers: tasks in the database, files in object storage,
  dispatched through a queue.
- Partition node pools by tenant or document size; the routing key stays the unit ID and every pool
  shares the database and pub/sub.
- History, Thread Comment, and Worktree follow the same shapes. See [Collaboration extension modules](/server/collaboration/extensions).
