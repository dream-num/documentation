Server SDK 是库，不是可以直接部署的产品。应用自己组装 Collaboration Service、Endpoint 和
Transport，注入 Database Adapter，并在需要导入导出时加入文件转换模块。这个组装结果如何部署，
由应用决定。

本页按规模从小到大介绍三种部署形态。每一种都是完整的终点：选择与你的规模匹配的形态，只在它的
性能限制成为问题时再往前走。

| 形态                  | 协同     | 导入导出 | 推荐规模                                 |
| --------------------- | -------- | -------- | ---------------------------------------- |
| [单机](#单机)         | 一个进程 | 同一进程 | 本地应用、开发与测试、少量用户的内部使用 |
| [服务拆分](#服务拆分) | 一个节点 | 独立进程 | 面向多人的线上服务，在单节点容量以内     |
| [多节点](#多协同节点) | 多个节点 | 独立进程 | 超出单节点容量，或需要节点故障切换       |

版本以[环境与版本要求](/server/requirements)为准；本页对应 `1.1.0`。

<Callout title="SDK 留给应用的部分">
  每一种形态里，用户、认证、授权、产品接口、文件存储、密钥和运维都是应用的职责。把任何一种形态
  交给真实用户之前，先阅读[身份与授权](/server/collaboration/identity-and-authorization)。
</Callout>

## 单机

协同和导入导出在同一个 Node.js 进程里运行，浏览器直接连接它。存储是一个 SQLite 文件，或一个
满足 Database Adapter 契约的网络数据库。

| 组件                  | 部署方式                                         | 共享内容               |
| --------------------- | ------------------------------------------------ | ---------------------- |
| 协同                  | 一个进程；Transport、Endpoint、Service           | 与导入导出共享进程     |
| 导入导出              | 同一进程，由应用路由调用                         | 与协同共享 CPU 和内存  |
| 存储                  | SQLite 文件，或基于网络数据库的 Database Adapter | 只有一个进程访问       |
| Session Ticket 与广播 | 进程内默认实现                                   | 无                     |

推荐用于本地应用、开发与测试，以及少量用户的内部使用。SQLite 是最简单的起点：它会持久化数据，
并为空数据库创建 schema，按文件方式备份即可。应用已经在用网络数据库时，可以从一开始就通过
自定义 Database Adapter 接入它。Memory Adapter 只用于本地验证，进程退出后数据即丢失。选型见
[Database Adapter](/server/collaboration/database-adapters)。

### 性能特征

- 一个进程承载所有打开的文档和 WebSocket 连接，进程重启会断开所有 Session。
- 导入导出在同一进程内转换。一次转换是 CPU 密集型的，并把整个工作簿放在内存里，大文件会拖慢
  协同响应。
- 使用 SQLite 时，写入由 `BEGIN IMMEDIATE` 事务串行化，并发提交在一个写者上排队。
- 不能运行第二个副本。

当导入导出开始影响协同响应、提交明显排队，或者需要面向多人持续提供服务时，进入服务拆分。

参考示例：[Exchange](/server/collaboration/examples#exchange)。

## 服务拆分

第一个面向多人线上服务的形态。网关在前面转发 HTTP 和 WebSocket；协同是一个节点；存储是网络
数据库；导入导出在独立进程里按自己的资源画像扩缩容。两项拆分互相独立，可以只做其中一项。

<Mermaid chart={"%%{init: {\"themeVariables\": {\"fontSize\": \"14px\"}, \"flowchart\": {\"nodeSpacing\": 24, \"rankSpacing\": 40, \"padding\": 12}}}%%\nflowchart LR\n    Browser([\"浏览器\"]) -->|\"HTTPS / WSS\"| Gateway[\"网关\"]\n    Gateway -->|\"协同\"| Node[\"协同节点<br/>Transport · Endpoint · Service\"]\n    Gateway -->|\"上传 · 任务 · 下载\"| Exchange[\"导入导出<br/>Service + Exchange\"]\n    Node --> DB[(\"数据库\")]\n    Exchange --> DB\n    classDef default rx:8,ry:8,stroke-width:1px\n    classDef actor fill:transparent,stroke:none\n    class Browser actor"} />

| 组件                  | 部署方式                                  | 共享内容                        |
| --------------------- | ----------------------------------------- | ------------------------------- |
| 网关                  | 分别路由协同路径和导入导出路径            | 无                              |
| 协同                  | 一个节点；Transport、Endpoint、Service    | 数据库                          |
| 导入导出              | 独立进程；Service 与转换模块              | 数据库，用于 Unit、任务和文件   |
| 存储                  | 基于网络数据库的自定义 Database Adapter   | 每个进程都能访问                |
| Session Ticket 与广播 | 进程内默认实现                            | 无；协同仍然只有一个节点        |

### 存储离开机器

把 SQLite Adapter 换成基于网络数据库、满足 `IDatabaseAdapter` 契约的 Adapter，注入点不变。
[Database Adapter](/server/collaboration/database-adapters) 列出了 Adapter 必须实现的原子性、
CAS 和幂等语义。

在服务之外管理 schema：用迁移工具在独立的部署步骤里执行迁移，服务使用不能执行 DDL 的数据库
角色，启动时只检查需要的表存在。网络数据库也是多节点的前提。

### 导入导出离开进程

导入导出进程只组装 Database Adapter、一个 `UniverCollabService` 和转换模块，没有 Endpoint、
Transport 和 pub/sub。导入通过 Service 创建 Unit，导出通过 Service 读取最新已确认的 revision，
不经过协同节点。它按每次转换的 CPU 和内存扩缩容，一次耗时或失败的转换不再拖慢协同节点。

任务状态和文件放在每个副本都能访问的存储里，这样任何副本都能回答任务轮询或提供下载。为每个
任务设置超时，让下载链接过期，并在网关和上传路由两处限制上传大小。应用侧流程见
[文件交换集成](/server/import-export)。

### 上线前要做的事

- 网关同时转发 HTTP 和 WebSocket，HTTPS 页面使用 WSS，在网关终止 TLS。
- 网关的空闲超时低于 Node.js 的 keep-alive 超时（默认 `5` 秒），否则会偶发 `502`。
- Transport 默认把请求体和 WebSocket 消息限制在 16 MiB；网关的上传限制按导入流程设置。
- 在 Transport 挂载的同一个 HTTP server 上注册健康检查路由，由网关或平台探测。
- 按组装的相反顺序关停：Transport、Service、Database Adapter，见
  [资源释放](/server/collaboration/modules#资源释放)。进程停止前先让网关停止发送新流量。
- License 是浏览器侧配置，在构建或配置阶段注入，见 [License](/server/license)。
- 身份与授权已由应用实现，示例里的固定用户和全部放行的规则不是生产的起点。

### 性能特征

协同仍然是一个节点。它的状态在数据库里，可以快速重启，但能服务的文档数不会超过一个进程的
内存，一次重启会断开所有 Session。超出单节点容量，或需要节点故障切换时，进入多节点。

参考示例：[多节点示例中的独立运行导入导出](https://github.com/dream-num/univer-collaboration-examples/blob/main/examples/multi-node/README.zh-CN.md#独立运行导入导出)。

## 多协同节点

多个协同节点运行同一份代码，连接同一个数据库。pub/sub adapter 在节点之间中继 Room、Presence
和广播；共享的 Session Ticket store 让任何节点都能接受其他节点签发的 ticket。
`@univerjs-pro/collaboration-cluster-redis` 在 Redis 6.2 及以上提供这两者。

| 组件                  | 部署方式                               | 共享内容                        |
| --------------------- | -------------------------------------- | ------------------------------- |
| 网关                  | WebSocket 和提交按 unit ID 路由        | 无                              |
| 协同                  | N 个相同的节点                         | 数据库、pub/sub、ticket store   |
| 导入导出              | 独立副本                               | 数据库；不使用 pub/sub          |
| 存储                  | 网络数据库                             | 所有节点和副本                  |
| Session Ticket 与广播 | Redis pub/sub adapter 与 ticket store  | 所有协同节点                    |

### 应用里改什么

创建 pub/sub adapter 和 ticket store，传给 `UniverCollabEndpoint`，组装的其他部分不变。
Endpoint 不会释放这两个 adapter 及其连接，所以关停顺序变为：Transport、pub/sub adapter 及其
连接、Service、Database Adapter。

### 按文档路由

任何节点都能服务任何请求。仍然建议把同一文档的 WebSocket 和变更提交固定到一个节点：确认和
广播在本地投递，并且只有这个节点把文档加载进内存。不固定时，同一文档的提交落到多个节点，每个
节点都加载该文档，并发提交会触发 revision CAS 冲突，由 Service 重新加载并重试。

| 请求                                       | 路由方式                 |
| ------------------------------------------ | ------------------------ |
| WebSocket 连接、变更提交                   | 按 unit ID 一致性哈希    |
| Session Ticket、snapshot、block、缺失变更  | 任意节点                 |
| 应用页面与接口                             | 任意节点                 |
| 上传、任务、下载                           | 任意导入导出副本         |

提交路径本身包含 unit ID。WebSocket 路径不含，所以浏览器给 WebSocket URL 追加 `unit` 查询
参数，网关按它做哈希。

### 状态在哪里

节点进程内只有已加载的 Unit、打开的 WebSocket Session 和 Room 成员关系；共享状态在数据库和
Redis 里。snapshot、block、ticket 请求和导入导出副本都是无状态的。节点可以随意增减；一个节点
停止时丢失它的 Session，客户端经网关重连到其他节点。

### pub/sub 不可用时

Redis 要以高可用方式运行。它不可用期间，Session Ticket 请求失败，WebSocket upgrade 被拒绝并
返回可重试的 `503`，新 Session 无法建立。把 Redis 当作协同服务可用性的一部分，而不是可选缓存。

### 性能特征

网关不会把失败的请求重试到另一个节点，SDK 也不提供已加载文档的自动故障切换，由客户端重连。
数据库吞吐和单个节点常驻文档的开销是下一个限制。

参考示例：[多节点示例](https://github.com/dream-num/univer-collaboration-examples/blob/main/examples/multi-node/README.zh-CN.md)。

## 进一步

- **把转换派发给 worker。** 导入导出的 API 副本保持无状态，任务放数据库，文件放对象存储，由
  队列或工作流引擎把每个任务交给有独立扩缩容的 worker 进程。worker 需要租约或超时，这样转换
  中途停止的 worker 不会让任务卡住。见[文件交换集成](/server/import-export)。
- **按文档划分节点池。** 路由键就是 unit ID，应用可以按租户、大小或等级把文档映射到不同的
  节点池。SDK 只要求所有节点池共享同一个数据库和 pub/sub。
- **扩展模块。** History、Thread Comment 和 Worktree 自带 Service 和 Database Adapter，遵循
  同样的形态。见[协同扩展模块](/server/collaboration/extensions)。
