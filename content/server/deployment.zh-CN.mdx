Server SDK 是库，不是可部署的产品。应用组装 Service、Endpoint 和 Transport，注入 Database Adapter，
需要导入导出时加入转换模块，然后按自己的规模部署。本页给出三种形态，每一种都可以作为终点。

| 形态                  | 协同     | 导入导出 | 推荐规模                         |
| --------------------- | -------- | -------- | -------------------------------- |
| [单机](#单机)         | 一个进程 | 同一进程 | 本地应用、开发测试、少量内部用户 |
| [服务拆分](#服务拆分) | 一个节点 | 独立进程 | 多人线上服务，单节点容量以内     |
| [多节点](#多协同节点) | 多个节点 | 独立进程 | 超出单节点容量，或需要故障切换   |

版本对应 `1.1.0`，见[环境与版本要求](/server/requirements)。用户、认证、授权、文件存储和运维在每种
形态里都由应用负责，见[身份与授权](/server/collaboration/identity-and-authorization)。

## 单机

一个 Node.js 进程承载协同和导入导出，浏览器直接连接。存储用 SQLite，或通过自定义 Database Adapter
接入你的数据库。

| 组件     | 部署方式            | 共享                       |
| -------- | ------------------- | -------------------------- |
| 协同     | 一个进程            | 与导入导出共享 CPU 和内存  |
| 导入导出 | 同一进程            | 与协同共享 CPU 和内存      |
| 存储     | SQLite 文件或数据库 | 只有这个进程访问           |

- SQLite 持久化数据并自动建表，按文件备份。Memory Adapter 只用于本地验证。
- 一次转换是 CPU 密集型的，整个工作簿在内存里，大文件会拖慢协同。
- SQLite 写入串行，并发提交排队。
- 只能一个副本，重启断开所有 Session。

导入导出影响协同响应、提交排队，或要面向多人持续服务时，进入服务拆分。
参考示例：[Exchange](/server/collaboration/examples#exchange)。

## 服务拆分

网关转发 HTTP 和 WebSocket；协同一个节点；导入导出独立进程；两者连同一个数据库。两项拆分互相独立。

<Mermaid chart={"%%{init: {\"themeVariables\": {\"fontSize\": \"14px\"}, \"flowchart\": {\"nodeSpacing\": 24, \"rankSpacing\": 40, \"padding\": 12}}}%%\nflowchart LR\n    Browser([\"浏览器\"]) -->|\"HTTPS / WSS\"| Gateway[\"网关\"]\n    Gateway -->|\"协同\"| Node[\"协同节点<br/>Transport · Endpoint · Service\"]\n    Gateway -->|\"上传 · 任务 · 下载\"| Exchange[\"导入导出<br/>Service + Exchange\"]\n    Node --> DB[(\"数据库\")]\n    Exchange --> DB\n    classDef default rx:8,ry:8,stroke-width:1px\n    classDef actor fill:transparent,stroke:none\n    class Browser actor"} />

| 组件     | 部署方式                       | 共享                     |
| -------- | ------------------------------ | ------------------------ |
| 网关     | 分别路由协同和导入导出路径     | —                        |
| 协同     | 一个节点                       | 数据库                   |
| 导入导出 | 独立进程，按 CPU 和内存扩缩容  | 数据库：Unit、任务、文件 |
| 存储     | 数据库                         | 所有进程                 |

- Database Adapter 实现 `IDatabaseAdapter` 契约，注入点不变，见 [Database Adapter](/server/collaboration/database-adapters)。
- 导入导出进程只组装 Database Adapter、`UniverCollabService` 和转换模块，没有 Endpoint 和 Transport。
  导入通过 Service 创建 Unit，导出读取最新已确认的 revision，不经过协同节点。
- 任务和文件放在所有副本都能访问的存储里；任务设超时，下载链接过期。见[文件交换集成](/server/import-export)。

### 上线前

- 网关同时转发 HTTP 和 WebSocket，HTTPS 页面用 WSS。
- 网关空闲超时低于 Node.js keep-alive（默认 `5` 秒），否则偶发 `502`。
- Transport 默认限制请求体和消息 16 MiB；网关上传限制按导入需要设置。
- 注册健康检查路由。
- 关停顺序：Transport → Service → Database Adapter，见[资源释放](/server/collaboration/modules#资源释放)。
- License 在浏览器侧配置，构建时注入，见 [License](/server/license)。
- 身份与授权由应用实现，示例里的固定用户和放行规则不能上线。

协同仍是一个节点：能服务的文档数受进程内存限制，重启断开所有 Session。超出容量或需要故障切换时进入多节点。
参考示例：[独立运行导入导出](https://github.com/dream-num/univer-collaboration-examples/blob/main/examples/multi-node/README.zh-CN.md#独立运行导入导出)。

## 多协同节点

多个节点运行同一份代码，连同一个数据库。pub/sub adapter 在节点间中继 Room、Presence 和广播，
ticket store 共享 Session Ticket。`@univerjs-pro/collaboration-cluster-redis` 提供 Redis 实现，需要 Redis 6.2+。

<Mermaid chart={"%%{init: {\"themeVariables\": {\"fontSize\": \"14px\"}, \"flowchart\": {\"nodeSpacing\": 24, \"rankSpacing\": 40, \"padding\": 12}}}%%\nflowchart LR\n    Browser([\"浏览器\"]) -->|\"HTTPS / WSS\"| Gateway[\"网关\"]\n    subgraph Nodes[\"协同节点\"]\n        direction TB\n        A[\"节点 A\"]\n        B[\"节点 B\"]\n    end\n    Gateway -->|\"WebSocket 与提交<br/>按 unit ID\"| A\n    Gateway -->|\"其余请求<br/>任意节点\"| B\n    Gateway -->|\"上传 · 任务 · 下载\"| Exchange[\"导入导出 ×N\"]\n    A --- PubSub[(\"pub/sub + ticket store\")]\n    B --- PubSub\n    A --> DB[(\"数据库\")]\n    B --> DB\n    Exchange --> DB\n    classDef default rx:8,ry:8,stroke-width:1px\n    classDef actor fill:transparent,stroke:none\n    class Browser actor"} />

| 组件     | 部署方式                        | 共享                          |
| -------- | ------------------------------- | ----------------------------- |
| 网关     | WebSocket 和提交按 unit ID 路由 | —                             |
| 协同     | N 个相同节点                    | 数据库、pub/sub、ticket store |
| 导入导出 | 独立副本                        | 数据库                        |
| 存储     | 数据库                          | 所有节点和副本                |

- 创建 pub/sub adapter 和 ticket store 传给 `UniverCollabEndpoint`，其余不变。
  关停顺序：Transport → pub/sub adapter 及其连接 → Service → Database Adapter。
- 节点进程内只有已加载的 Unit、WebSocket Session 和 Room 成员，其余状态在数据库和 Redis。
  节点可随意增减，节点停止后客户端经网关重连。
- Redis 需要高可用：不可用时 ticket 请求失败，WebSocket upgrade 返回可重试的 `503`，新 Session 无法建立。
- 网关不会把失败的请求重试到其他节点，SDK 不做已加载文档的自动故障切换。

### 按文档路由

任何节点都能处理任何请求，但建议把同一文档的 WebSocket 和提交固定到一个节点：确认和广播在本地投递，
只有该节点加载文档。否则多个节点加载同一文档，并发提交触发 CAS 冲突后重载重试。

| 请求                                      | 路由                  |
| ----------------------------------------- | --------------------- |
| WebSocket 连接、变更提交                  | 按 unit ID 一致性哈希 |
| Session Ticket、snapshot、block、缺失变更 | 任意节点              |
| 应用页面与接口                            | 任意节点              |
| 上传、任务、下载                          | 任意导入导出副本      |

WebSocket 路径不含 unit ID，浏览器给 URL 追加 `unit` 参数，网关按它哈希。
参考示例：[多节点示例](https://github.com/dream-num/univer-collaboration-examples/blob/main/examples/multi-node/README.zh-CN.md)。

## 进一步

- **转换交给 worker。** API 副本无状态，任务在数据库，文件在对象存储，由队列派发给独立扩缩容的 worker，
  带租约或超时。
- **按文档划分节点池。** 路由键是 unit ID，可按租户或大小映射到不同节点池，各池共享数据库和 pub/sub。
- **扩展模块。** History、Thread Comment 和 Worktree 自带 Service 和 Adapter，遵循同样的形态。
  见[协同扩展模块](/server/collaboration/extensions)。
