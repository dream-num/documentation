Une application Server SDK a trois formes de déploiement, et l'échelle de l'application détermine celle à utiliser. Commencez par [Collaboration SDK](/server/collaboration/overview), [importations et exportations](/server/import-export) et [exemples](/server/collaboration/examples) pour voir comment les modules sont assemblés. Le déploiement détermine seulement combien de nœuds fonctionnent ce même assemblage.

| Forme | Collaboration | Import et export | Échelle recommandée |
| --- | --- | --- | --- |
| [Machine unique](#machine-unique) | Un nœud | Même nœud | Applications locales, développement et tests, quelques utilisateurs internes |
| [Séparer l’import et l’export](#séparer-limport-et-lexport) | Un nœud | Nœud distinct | Service en ligne multi-utilisateurs dans la capacité d’un nœud |
| [Plusieurs nœuds](#plusieurs-nœuds-de-collaboration) | Plusieurs nœuds | Nœud distinct | Au-delà de la capacité d’un nœud, ou basculement entre nœuds |

Pour dimensionner un nœud, comparez la taille des documents, le nombre d’éditeurs simultanés et la fréquence des envois aux mesures du rapport [Performances de l’édition collaborative](/server/collaboration/performance).

## Machine unique

Tous les composants fonctionnent dans un seul processus Node.js, et le navigateur se connecte directement à ce processus.

<Mermaid chart={"%%{init: {\"themeVariables\": {\"fontSize\": \"14px\"}, \"flowchart\": {\"nodeSpacing\": 24, \"rankSpacing\": 40, \"padding\": 12}}}%%\nflowchart LR\n    Browser([\"Navigateur\"]) --> App[\"Collaboration + Exchange\"]\n    App --> DB[(\"Base de données\")]\n    classDef default rx:8,ry:8,stroke-width:1px\n    classDef actor fill:transparent,stroke:none\n    class Browser actor"} />

- Le Database Adapter implémente le contrat `IDatabaseAdapter` ; voir [Adaptateurs de base de données](/server/collaboration/database-adapters).
- L'importation et l'exportation sont assurées par le service Exchange Service et File Service. Voir [Modules d'extension de la collaboration](/server/collaboration/extensions).
- La conversion est liée au processeur, donc un grand fichier ralentit la collaboration.

Déplacer l'importation et l'exportation vers un nœud distinct lorsque les conversions commencent à affecter la latence de la collaboration, ou lorsque le service doit rester réactif pour de nombreux utilisateurs.

## Séparer l’import et l’export

Importer et exporter fonctionne sur un nœud dédié tandis que la collaboration reste sur un seul nœud. La passerelle relie les deux types de requêtes séparément, et les deux côtés utilisent la même base de données.

<Mermaid chart={"%%{init: {\"themeVariables\": {\"fontSize\": \"14px\"}, \"flowchart\": {\"nodeSpacing\": 24, \"rankSpacing\": 40, \"padding\": 12}}}%%\nflowchart LR\n    Browser([\"Navigateur\"]) --> Gateway[\"Passerelle\"]\n    Gateway -->|\"Requêtes de collaboration\"| Node[\"Nœud de collaboration\"]\n    Gateway -->|\"Requêtes d’import et d’export\"| Exchange[\"Nœud d’import et d’export\"]\n    Node --> DB[(\"Base de données\")]\n    Exchange --> DB\n    classDef default rx:8,ry:8,stroke-width:1px\n    classDef actor fill:transparent,stroke:none\n    class Browser actor"} />

Le noeud d'importation et d'exportation assemble l'adaptateur de base de données, un `UniverCollabService`, File Service et Exchange Service, puis fonctionne directement avec la base de données. Les points d'injection sont les mêmes que sur une seule machine. Les deux nœuds pointent File Service au même stockage de fichiers, et les deux installent le même Middleware d'autorisation sur `UniverCollabService`.

La mémoire du processus limite le nombre de documents qu'un noeud de collaboration peut servir. Déplacer vers plusieurs nœuds lorsque cette capacité est dépassée, ou lorsque la panne est nécessaire.

## Plusieurs nœuds de collaboration

Plusieurs nœuds de collaboration exécutent le même code contre la même base de données. Un adaptateur pub/sub relaye les pièces, la présence et les émissions entre les nœuds, et une billetterie partage les tickets Session. `@univerjs-pro/collaboration-cluster-redis` fournit l'implémentation Redis. Chaque noeud utilise la même Licence, qui couvre le nombre de nœuds en cours d'exécution; voir [nœuds de collaboration](/server/collaboration/license#nodes). Pour une implémentation de référence, voir [Multi-noeud](/server/collaboration/examples#multi-node).

Chaque nœud de collaboration passe l'adaptateur pub/sous-adaptateur Redis et la billetterie à l'Endpoint. Le reste de l'assemblage est inchangé:

```ts
import { createClient } from "redis";
import { RedisPubSubAdapter, RedisSessionTicketStore } from "@univerjs-pro/collaboration-cluster-redis";
import { UniverCollabEndpoint } from "@univerjs-pro/collaboration-endpoint";

const client = createClient({ url: process.env.REDIS_URL });
const subClient = client.duplicate();
await Promise.all([client.connect(), subClient.connect()]);

const pubSub = new RedisPubSubAdapter({ pubClient: client, subClient });
const ticketStore = new RedisSessionTicketStore({ client });
const endpoint = new UniverCollabEndpoint(service, { pubSub, ticketStore });
```

## Pour aller plus loin

Un très grand document ralentit les demandes de petits documents sur le même noeud. Split les nœuds par taille de document et laisser la passerelle router les grands documents vers un pool dédié. La clé de routage est toujours l'ID de l'unité, et chaque pool partage la base de données et le pub/sub.
