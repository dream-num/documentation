1 つのドキュメントを複数人で編集する場合と、複数のドキュメントを同時に編集する場合を比較しました。ドキュメントのウォームアップ後、編集を続けながら、送信から確認応答までの遅延、スループット、予定した送信の達成率、共同編集プロセスの CPU・メモリ使用量を測定しました。

## 測定環境

共同編集サービスとデータベースは別々のサーバーで動作します。結果表のマシン構成は図の共同編集ノードを指します。

PostgreSQL はドキュメントのレコード、変更セット、スナップショットのレコード、ブロックへの参照を保持します。スナップショット内のセルデータのブロックは OSS に保存します。

測定結果はすべて単一ノードでの値です。同時に編集するドキュメントが単一ノードの容量を超える場合は、ノードを追加してドキュメントごとに負荷を分散できます。ノードはデータベースを共有し、Pub/Sub でルーム、プレゼンス、編集の配信を同期します。[複数の共同編集ノード](/server/deployment#複数の共同編集ノード)を参照してください。

### 共同編集サービスの設定

両構成で `runtime.maxLoadedUnits` を既定の 1,200 から 4,000 に引き上げ、単一ノードが最大 4,000 件のドキュメントをメモリに保持できるようにしました。その他の設定は既定値を使用し、ワーカースレッド数は SDK が自動で決定します。前回のスナップショット成功から 50 リビジョン経過するか、1 回の変更セットが 5 MiB に達すると、既定のポリシーでスナップショットが作成されます。

測定に使ったサービスの抜粋です。アダプターは初期化済みの PostgreSQL 接続プールと OSS クライアントを使い、トランスポートを Node.js の HTTP サーバーに接続します。

```ts
const dbAdapter = await PostgresS3DatabaseAdapter.create({
  pool,
  s3: { client, bucket, prefix },
});
const service = new UniverCollabService({
  dbAdapter,
  runtime: { maxLoadedUnits: 4000 },
});
const endpoint = new UniverCollabEndpoint(service);
const transport = createNodeTransport();
transport.register(endpoint);
transport.attach(server);
```

## テスト用スナップショット

各ドキュメントをスナップショットから初期化します。セル数はウォームアップ前に値または数式が入っているセルの数です。

| スナップショット | 入力済みセル数 | 内容 |
| --- | ---: | --- |
| `blank` | 0 | 空のワークシート |
| `10k-cells` | 約 10,000 | 数値、テキスト、数式 |
| `100k-cells` | 約 100,000 | 数値、テキスト、数式 |

データ入りのシートはいずれも 26 列で、数値が 14 列、テキストが 9 列、同じ行のデータを参照する数式が 3 列です。

## 測定方法

### 模擬クライアント

編集者数は独立したセッション数です。各セッションが 1 つのドキュメントに参加し、HTTP でセル変更を送信して WebSocket でサーバーの確認応答を受け取ります。スクリプトは共同編集 API を直接呼び出します。HTTP リクエストと確認応答の待機はどちらも 10 秒でタイムアウトします。

### ウォームアップと測定

各試行で指定のスナップショットからドキュメントを作成し、全セッションの参加後にウォームアップします。最初の編集でサーバーがドキュメントを読み込みます。単一ドキュメントでは編集を 1 回送信します。複数ドキュメントでは順に 1～49 回送信し、50 件目で 1 回に戻します。開始リビジョンがずれるため、スナップショットの保存時刻も分散します。

全ドキュメントのウォームアップが終わってから測定を開始します。初回送信の遅延はウォームアップ中に別途記録します。表中の送信統計、遅延のパーセンタイル、CPU、メモリはいずれも本測定の値です。

### 編集負荷

単一ドキュメントでは `blank` の編集者数を増やしました。複数ドキュメントでは 3 種類のスナップショットごとにアクティブなドキュメント数を増やしました。各送信には `sheet.mutation.set-range-values` が 1 件含まれ、1 つのセルに数値を書き込みます。

| 条件 | 単一ドキュメント | 複数ドキュメント |
| --- | --- | --- |
| ドキュメントあたりの編集者数 | 試行ごとに変更（結果表を参照） | 全試行で 2 人 |
| 編集内容 | 時間をずらして各自のセルに書き込み | 時間をずらして各自のセルに書き込み |
| 1 人あたりの頻度 | 6 秒に 1 回 | 2 秒に 1 回 |
| 1 試行の測定時間 | 300 秒 | 300 秒 |

## 指標の定義

| 指標 | 定義 |
| --- | --- |
| 確認応答の遅延 | クライアントが編集を送信してから確認応答を受信するまでの時間。P50、P95、P99 は送信成功分の 50%、95%、99% が確認応答を受け取るまでの時間を示します。Max は成功分の最大値です。 |
| スループット | 送信成功件数を測定時間で割った値（件/秒）。 |
| 送信達成率 | 予定送信件数に対する成功件数の割合。予定件数には失敗分と未送信分も含みます。 |
| CPU 平均 / ピーク（%） | 測定中の共同編集プロセスの平均 CPU 使用率と最大観測値。1 コアのフル稼働を 100% とするため、合計は 100% を超えることがあります。 |
| ピークメモリ（MiB） | 共同編集プロセスの常駐メモリ（RSS）の最大観測値。 |

### 合格基準

確認応答の遅延が **P99 < 1,000 ms**、送信達成率が **> 90%** で、全テストドキュメントの整合性確認が完了するまで共同編集プロセスが稼働し続けた試行を合格とします。判定には丸める前の値を使います。

各負荷段階は本報告に掲載した試行で判定します。1 回のみ測定した場合はその結果を使い、複数回測定した場合はすべての試行で合格する必要があります。測定の中断や指標の欠落は欠測とし、理由を記載します。

## 結果の適用範囲

サーバーの同時編集処理を評価するため、Node.js スクリプトが編集セッションを模擬し、API に直接変更を送ります。確認応答の遅延は送信からサーバーの応答受信までを測ったもので、ブラウザー操作やシート描画の時間は含みません。

結果は性能評価と単一ノードの容量設計の参考値です。実際の性能は構成、ネットワーク、ドキュメントサイズ、編集の種類と頻度によって変わります。

最大合格負荷は、測定した負荷段階のうち基準を満たした最大のものです。一部の合格段階でも平均 CPU 使用率がノードの上限に近づいています。**最大合格負荷は容量設計の参考値であり、本番環境の長期運用負荷としてそのまま使うことはできません。** 同時編集の集中やリソース使用量の変動に備えて余裕を確保し、対象環境で代表的な業務負荷を使って持続可能な規模を検証してください。

#### ノードプールの構成選び

[複数ノード構成](/server/deployment)ではゲートウェイがドキュメントサイズに応じて編集要求を別々のプールに振り分けられます。以下はドキュメントあたり 2 人がそれぞれ 2 秒に 1 回編集する場合の、ノード 1 台あたりの目安です。

- **小・中規模ドキュメント用には、まず 4 コア・8 GiB を検討してください。** 4 コア・16 GiB の測定で、8 GiB 構成のメモリ予算に収まる最大合格負荷は空白シート 2,100 件、約 10,000 セルのシート 1,800 件でした。
- **大規模ドキュメント用には 8 コア・16 GiB または 32 GiB を検討してください。** 約 100,000 セルの場合、8 コア・32 GiB の最大合格負荷は 750 件で、このうち 16 GiB 構成のメモリ予算に収まる最大負荷は 600 件でした。
