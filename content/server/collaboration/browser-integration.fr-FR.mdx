Collaboration relie les éditeurs de navigateurs à un service de document partagé. Lorsque deux utilisateurs ouvrent le même tableur, une modification dans un navigateur apparaît dans l'autre.

Configurez d'abord le moteur via [intégration du serveur](/server). La configuration de l'éditeur et le chargement de document décrit ci-dessous le suivent. Le serveur jumelé et le code Web sont dans [Début rapide de la collaboration](/server/collaboration/quick-start) .

## Connecter votre éditeur existant

Un éditeur différent n'est pas requis. Conservez l'éditeur Web SDK existant et suivez le [configuration du navigateur dans le démarrage rapide](/server/collaboration/quick-start) pour ajouter les plugins de collaboration, puis configurez le chargement de document, la soumission d'édition et l'adresse WebSocket. Les versions de paquets navigateur et serveur doivent rester compatibles.

Les utilisateurs d'exemples fixes et les autorisations par défaut sont destinés à la démonstration. Dans une application, envoyez des identifiants de connexion avec chaque demande afin que le moteur puisse vérifier l'identité et l'accès aux documents. [configuration de licence](/server/license).

## Configuration des plugins [#client-configuration]

### Envoi groupé et délais de réessai [#client-retry-timeouts]

`UniverCollaborationClientPlugin`

| <span data-config-options="">Option</span> | Type | Valeur par défaut | Effet |
| --- | --- | --- | --- |
| `socketService` | `Ctor<ICollaborationSocketService>` |  | Sélectionne l'implémentation de socket utilisée par l'exécution courante. |
| `sendChangesetTimeout` | `number` | `2000 ms` | Définit combien de temps les modifications locales sont tamponnées avant qu'elles ne soient envoyées. |
| `changesetAckTimeout` | `number` | `20000 ms` | Définit la durée d'attente d'un accusé de réception avant de réessayer. |
| `maxChangesetAckTimeout` | `number` | `120000 ms` | Définit la limite supérieure sur l'intervalle entre les résends. |

Le délai de batchage et le délai de reconnaissance sont des chronomètres séparés. Le plugin client par défaut est `sendChangesetTimeout: 2000`, `changesetAckTimeout: 20000` et `maxChangesetAckTimeout: 120000` en millisecondes. La demande de soumission utilise également le délai de réception. Les changements qui ne sont jamais reconnus sont ressentis avec un délai de retrait exponentiel, plafonné au maximum. La mise en place du délai de reconnaissance et le délai maximal de sortie à la même valeur produit un intervalle constant.

```ts
import { UniverCollaborationClientPlugin } from '@univerjs-pro/collaboration-client'
import { BrowserCollaborationSocketService } from '@univerjs-pro/collaboration-client-ui'

univer.registerPlugin(UniverCollaborationClientPlugin, {
  socketService: BrowserCollaborationSocketService,
  sendChangesetTimeout: 200,
  changesetAckTimeout: 20_000,
  maxChangesetAckTimeout: 120_000,
})
```

Ajoutez ces options à l'enregistrement client existant et conservez sa configuration de socket et de fin de course. Les préréglages de collaboration Sheets and Docs utilisent un délai de batch de 200 ms et n'exposent pas les options de timeout de reconnaissance, si bien que la personnalisation de ces timeouts nécessite le mode plugin.

## Configuration des préréglages [#client-preset-configuration]

`UniverSheetsCollaborationPreset / UniverDocsCollaborationPreset`

| <span data-config-options="">Option</span> | Type | Valeur par défaut | Effet |
| --- | --- | --- | --- |
| `enableDefaultConflictUI` | `boolean` | `true` | Affiche les avis de rétablissement de conflit intégrés. |

```ts
import { UniverSheetsCollaborationPreset } from '@univerjs/preset-sheets-collaboration'

const collaborationPreset = UniverSheetsCollaborationPreset({ enableDefaultConflictUI: false })
```

```ts
import { UniverDocsCollaborationPreset } from '@univerjs/preset-docs-collaboration'

const collaborationPreset = UniverDocsCollaborationPreset({ enableDefaultConflictUI: false })
```

Par défaut, l'interface utilisateur affiche un avis de conflit qui nomme la raison. L'avis offre un rechargement après le nettoyage du cache réussit, et une réessayer si le nettoyage échoue. Pour exécuter le flux de récupération dans l'application, définissez `enableDefaultConflictUI: false` dans l'initialisation existante et manipulez l'événement directement.

Ajoutez les préréglages de collaboration à l'appel `createUniver({ presets: [...] })` existant, à côté du préréglage de l'éditeur, et conservez les paramètres de fin et d'historique. Voir [charge utile événementielle](#conflict-recovery) et [configuration du client](/reference/packages/plugins/univerjs-pro/collaboration-client).

## Créer et ouvrir le même document

La création d'un document et son ouverture sont des actions distinctes:

1. Lorsqu'un utilisateur crée un document, le moteur le sauvegarde et retourne son ID.
2. Le navigateur charge cet ID. Réutiliser le même ID lorsque le document est rouvert ou partagé avec un autre utilisateur.

L'API nomme le document ID `unitId`. Ne créez pas de nouveau document local vierge à chaque visite.

Définissez l’utilisateur courant avant de charger un document. Il identifie le collaborateur et possède le cache hors ligne local ; voir [Identité et autorisations](/server/collaboration/identity-and-authorization).

Par exemple, après l'enregistrement des feuilles et des plugins de collaboration, chargez un tableur à partir du serveur :

```ts
import { UserManagerService } from '@univerjs/core'
import '@univerjs-pro/collaboration-client/facade'

univer.__getInjector().get(UserManagerService).setCurrentUser({ userID, name, avatar })

const workbook = await univerAPI.getCollaboration().loadSheetAsync('your-document-id')
if (!workbook) throw new Error('Document could not be loaded')
```

Le chargement spécifique au produit est couvert dans les guides [Feuilles](/guides/sheets/features/collaboration), [Docteurs](/guides/docs/features/collaboration), [Diapositives](/guides/slides/features/collaboration), [Conseils d ' administration](/guides/boards/features/collaboration), [Bases](/guides/bases/features/collaboration) et [PDF](/guides/pdfs/features/collaboration). Confirmez que le produit et la sortie du moteur que vous ciblez supportent la fonctionnalité.

## Vérifier synchronisation, enregistrement et autorisations

Ouvrez le même document en deux sessions indépendantes, comme une fenêtre régulière et une session privée. Editez dans une session et vérifiez ce que l'autre affiche. Ensuite, rechargez la page, reconnectez, redémarrez le serveur et confirmez que le contenu est toujours présent.

Tester en tant qu'éditeur, visionneur et utilisateur sans accès. Les paramètres de l'interface utilisateur en lecture seule ne contrôlent que ce que la page permet; le serveur doit toujours rejeter les lectures et les modifications non autorisées.

Si les documents chargent mais éditent ne se synchronisent pas, vérifiez la connexion WebSocket. Si le contenu disparaît après un redémarrage, vérifiez le stockage du moteur. Ces paramètres appartiennent à [intégration du serveur](/server).

## État de synchronisation et renvois [#sync-status]

Importer la collaboration Facade avant d'enregistrer les auditeurs. `CollaborationStatusChanged` rapporte l'état actuel de chaque unité qui collabore déjà lorsque l'auditeur est enregistré, puis les rapports changent sans répéter les statuts identiques consécutifs. `hasWritePending(unitId)` couvre les modifications en file d'attente, les modifications en attente d'accusé de réception et les modifications hors ligne. Si l'ID est omis, il vérifie l'unité focalisée.

```ts
import '@univerjs-pro/collaboration-client/facade'

const collaboration = univerAPI.getCollaboration()
const statusSubscription = univerAPI.addEvent(univerAPI.Event.CollaborationStatusChanged, (event) => {
  console.info(event.unitId, event.status, collaboration.hasWritePending(event.unitId))
})
const resendSubscription = univerAPI.addEvent(univerAPI.Event.CollaborationChangesetResend, (event) => {
  console.info(event.unitId, event.reason, event.attempt, event.unsyncedMutationCount, event.nextDelayMs)
})
```

`CollaborationChangesetResend` incendies sur réenvois, non sur la première présentation. Les motifs sont `ack_timeout`, `request_failed`, `license_editing_connections_exceeded`, `should_retry` et `reconnect`; `attempt`, `elapsedMs`, `unsyncedMutationCount` et `nextDelayMs` fournissent les données nécessaires pour un indicateur d'enregistrement ou de réessai.

`request_failed` signifie un échec de requête réutilisable, comme une erreur de réseau ou une réponse HTTP 408, 429 ou 5xx. `license_editing_connections_exceeded` indique que les connexions d'édition sous licence sont toutes utilisées et que le serveur a demandé un résend.

## Gérer les conflits dans l’application [#conflict-recovery]

`CollaborationConflict` tire une fois qu'une unité entre en conflit, après la tentative de nettoyage hors ligne-cache. Enregistrer l'auditeur avant de charger des documents. Ses `reason` sont `transform_failed`, `apply_failed`, `changeset_rejected`, `license_unit_type_rejected`, `permission_rejected` ou `remote_revert`; `message` et `revert` fournissent des détails supplémentaires lorsque disponibles.

`license_unit_type_rejected` indique que la licence du serveur ne couvre pas la collaboration pour ce type de document.

```ts
import type { IEventParamConfig } from '@univerjs/core/facade'
import '@univerjs-pro/collaboration-client/facade'

const conflicts = new Map<string, IEventParamConfig['CollaborationConflict']>()
const conflictSubscription = univerAPI.addEvent(univerAPI.Event.CollaborationConflict, (event) => {
  conflicts.set(event.unitId, event)
})
```

L'exemple conserve l'événement pour un écran de récupération d'hôte. La carte ne vit que dans la mémoire, de sorte que l'application doit enregistrer ou exporter n'importe quel `localChanges` avant un rafraîchissement. Cet événement est la seule occasion de les conserver; les données de cache qui ont déjà été effacées ne peuvent pas être récupérées par une lecture ultérieure. `awaitingChangeset` peut déjà avoir été appliqué sur le serveur, de sorte qu'il ne devrait pas être rejoué aveuglément.

`cacheCleared: false` signifie qu'un rafraîchissement rejouerait les anciennes éditions cache, de sorte que le nettoyage du cache doit être résolu avant de rafraîchir. Effacer le cache ne signifie pas que les éditions non synchronisées ont été sauvegardées. Un conflit `permission_rejected` nécessite également de résoudre l'accès; le rechargement ne permet pas.

## Motifs serveur et notifications de licence [#server-rejections]

Lorsque le serveur rejette une modification, `CollaborationConflict.message` porte la raison que le serveur a donnée, s'il en a donné un. N'analysez pas le texte de message localisé pour décider de l'action de récupération; brancher sur `reason` à la place. `license_unit_type_rejected` nécessite une licence serveur qui couvre le type de document, alors que `license_editing_connections_exceeded` est un signal de réenvoi : les modifications restent non reconnues et continuent de réessayer. `hasWritePending(unitId)` devient false ou l'application a conservé les modifications.

L'interface utilisateur par défaut affiche un avis de capacité d'édition et, sur un réenvoi au moins 20 secondes après le premier envoi, un avis d'arrêt du délai d'attente. Ceux-ci sont supprimés lorsque l'unité quitte les états en attente ou est éliminée. Un rejet de domaine a également un avis dédié. `enableDefaultConflictUI: false` désactive uniquement les avis de récupération de conflit; il ne désactive pas ces avis d'attente ou de domaine.
