Сотрудничество Univer состоит из клиента браузера и набора серверных модулей. Каждый модуль владеет одним классом ответственности. Приложения составляют модули через общедоступные интерфейсы, поэтому их код не зависит от внутренних элементов реализации OT[^operational-transformation], протокола или уровня стойкости.

## Collaboration Client

Клиент совместной работы браузера работает вместе с Web SDK и обрабатывает клиентскую сторону совместной работы:

- Он запрашивает снимки блока и любые подтвержденные изменения, которые отсутствуют.
- Он использует одноразовый билет сеанса, чтобы открыть соединение с WebSocket.
- Он присоединяется к Unit Rooms и обменивается Присутствием с другими членами.
- Он отправляет локальные мутации на сервер в виде наборов изменений.
- Он получает ACK и трансляцию, а после повторного подключения получает пропущенные изменения.

Клиент не определяет, является ли пользователь доверенным, и это не является авторитетным источником данных.Это решение принадлежит серверу, который обеспечивает идентификацию и авторизацию в соответствующем промежуточном ПО.

## Node Transport

`@univerjs-pro/collaboration-transport-node` является точкой входа Node.js для HTTP и трафика WebSocket.Он получает запросы и обновления WebSocket с сервера HTTP хоста, запускает промежуточное ПО ввода, зарегистрированное приложением, и направляет трафик в конечные точки.

Транспорт не понимает ОТ, Единичные данные или модели ACL. сборка использует три метода:

```ts
transport.use(httpMiddleware);
transport.useUpgrade(upgradeMiddleware);
transport.register(endpoint);
```

- `use()` обрабатывает обычные HTTP-запросы и может устанавливать `userID`, `customData` , журналы или следы.
- `useUpgrade()` обрабатывает рукопожатие WebSocket и может отклонить соединение до его установки.
- `register()` регистрирует протокол Endpoint, жизненный цикл которого затем управляет Transport.

## Collaboration Endpoint

`@univerjs-pro/collaboration-endpoint` реализует протокол, используемый клиентом Univer Collaboration Client, и обладает следующими возможностями:

| Возможность | Ответственность Endpoint |
| --- | --- |
| Загрузка содержимого | Снимки и блоки Returns Unit, а также любые подтвержденные изменения, которых не хватает клиенту. |
| Отправка изменений | Принимает изменения, возвращает ACK, рассылает подтверждённые изменения в Room |
| Подключение Session | Выдает одноразовые сессионные билеты, затем устанавливает и поддерживает сеансы WebSocket |
| Совместная работа Room | Обрабатывает JOIN, LEAVE, состояние участников и Presence |
| Жизненный цикл Unit | Преобразует запросы удаления и восстановления в вызовы Service |
| Несколько узлов | Ретранслирует номера, присутствие и трансляцию через узлы через дополнительный адаптер паба / суб и общий магазин билетов. |

Конечная точка не выполняет OT и не хранит сами данные о сотрудничестве. Она получает авторитетный результат от Сервиса и карты, которые приводят к обратному протоколу Клиента. Операции с продуктом, такие как создание документа, принадлежат прикладному API, который вызывает Сервис.

## Collaboration Service

`@univerjs-pro/collaboration-service` является ядром совместной работы и не зависит от сети. Он охватывает Sheet, Doc, Slide, Board, Base и PDF:

- Он считывает данные восстановления блока и подтвержденные изменения.
- Он создает блоки из данных блока или снимков.
- Отправка пакета изменений запускает OT и продвигает непрерывную редакцию [^collaboration-revision].
- Идентифицирует дубликаты сообщений через `(unitID, sid, reqId)`.
- Он удаляет, восстанавливает или навсегда удаляет блоки.
- Он запускает Service Middleware и выдает Events после подтверждения.

Сервис не имеет HTTP или WebSocket уровня, и он не знает о пользователях, ролях, ACL, иерархии или управлении файлами. Endpoint строит протокол браузера поверх Сервиса. Приложения также могут вызывать публичный API Сервиса непосредственно из бизнес-API или фоновых задач.

### Основные API

| Возможность | API Service |
| --- | --- |
| Загрузить Unit | `getUnitLoadData()`, `getUnitLoadDataWithBlocks()` |
| Прочитать приращения | `getChangesets()`, `getSheetBlock()` |
| Создать Unit | `createUnitFromData()`, `createUnitFromSnapshot()` |
| Отправить изменения | `submitChangeset()` |
| Удалить и восстановить | `deleteUnits()`, `recoverUnits()` |

## Database Adapter

Database Adapter — контракт между Service и хранилищем. Он гарантирует:

- атомарное создание начального снимка и зависимостей;
- сравнение и обмен ревизии;
- Идемпотентное изменение представления;
- возможность мгновенного снимка только после того, как все его зависимости существуют;
- пакетные операции жизненного цикла Unit по принципу «всё или ничего».

Приложение подключает хранилище через `IDatabaseAdapter`. Как выбрать встроенный адаптер или реализовать собственный, описано в разделе [Адаптеры баз данных](/server/collaboration/database-adapters).

## Четыре основных понятия

| Понятие | Значение |
| --- | --- |
| Unit | Независимо загружаемый и совместный контент Univer с уникальным `unitID` и типом |
| Snapshot | Содержание единицы сохранялось при пересмотре, а не живой изменчивый объект. |
| Changeset | Парочка мутаций, представленных вместе, с пересмотром базы и идентичностью для идемпотентности |
| Revision | Непрерывный номер версии подтвержденного состояния Unit, начиная с `1` |

Все изменения в исполняемом контенте проходят через API или команды Facade.Мутация объекта снимка не обновляет живой блок в Клиенте или Сервисе.

## Загрузка Unit

<Mermaid chart={"sequenceDiagram\n    participant Client\n    participant Transport\n    participant Endpoint\n    participant Service\n    participant Adapter\n\n    Client->>Transport: Загрузка Unit по HTTP\n    Transport->>Endpoint: Аутентифицированный Context запроса\n    Endpoint->>Service: getUnitLoadData()\n    Service->>Adapter: Снимок + изменения\n    Adapter-->>Service: Эталонные данные\n    Service-->>Endpoint: Данные загрузки Unit\n    Endpoint-->>Client: Ответ протокола"} />

`userID/customData`, созданный Transport Middleware, перемещается с текущим HTTP-запросом в Service Middleware. Приложение решает, разрешено ли чтение. Клиенту не нужно присоединяться к Комнате, прежде чем он прочитает обычный HTTP.

## Отправка правки

```text
Facade / Command
  → Mutation
  → Changeset клиента
  → отправка в Endpoint
  → Middleware Service
  → OT + CAS ревизии
  → атомарный коммит Adapter
  → подтверждённый Changeset
  → ACK / рассылка Room
```

Подтвержденная редакция в Адаптере баз данных является авторитетным состоянием. АСК и трансляции поддерживают синхронизацию онлайн-клиентов с низкой задержкой. Клиент, который пропускает сообщение, может получить подтвержденные изменения, которых ему не хватает, используя уже известную редакцию.

## Минимальная сборка сервера

```ts
import { createServer } from "node:http";

import { MemoryDatabaseAdapter } from "@univerjs-pro/collaboration-database-memory";
import { UniverCollabEndpoint } from "@univerjs-pro/collaboration-endpoint";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";
import { createNodeTransport } from "@univerjs-pro/collaboration-transport-node";

const database = new MemoryDatabaseAdapter();
const service = new UniverCollabService({ dbAdapter: database });
const endpoint = new UniverCollabEndpoint(service);
const transport = createNodeTransport();

transport.use(async (context, next) => {
  context.userID = "demo-user";
  await next();
});
transport.register(endpoint);

const server = createServer();
transport.attach(server);
server.listen(3010);
```

Жестко закодированный пользователь и адаптер памяти демонстрируют только сборку модуля.Реальные приложения устанавливают контекст через Middleware и выбирают адаптер, соответствующий их требованиям к данным.

### Создание Unit через API приложения

Приложения могут определять свои собственные конечные точки HTTP или RPC и вызывать `service`, созданный выше, после прохождения аутентификации, проверки ввода и проверки бизнеса:

```text
Бизнес-клиент
  → POST /api/units
  → аутентификация и проверка приложения
  → service.createUnitFromData()
  → Database Adapter
```

В приведенном ниже примере Express предполагается, что программа аутентификации Middleware установила `response.locals.user` и что `request.body.data` уже был подтвержден как Данные Рабочей книги:

```ts
import { randomUUID } from "node:crypto";

import { json } from "express";
import { UniverType } from "@univerjs/protocol";

app.post("/api/units", json({ limit: "1mb" }), async (request, response, next) => {
  try {
    const user = response.locals.user as { readonly userID: string };
    const unitID = randomUUID();

    const result = await service.createUnitFromData(
      {
        type: UniverType.UNIVER_SHEET,
        data: {
          ...request.body.data,
          id: unitID,
          rev: 1,
        },
      },
      {
        userID: user.userID,
        customData: { traceID: randomUUID() },
      },
    );

    response.status(result.status === "created" ? 201 : 200).json(result);
  } catch (error) {
    next(error);
  }
});
```

`POST /api/units` является маршрутом приложения и не является частью протокола Collaboration Client. Звонок `createUnitFromData()` по-прежнему выполняет `createUnit` Middleware Сервиса. Записи о продукте, ACL владельца, отображение ошибок-ответов и компенсация за сбои остаются ответственностью приложения.

## Освобождение ресурсов

`transport.dispose()` утилизирует Конечные точки, зарегистрированные в `register()`. Сервис и Адаптер базы данных, которые впрыскиваемое приложение должно быть утилизировано отдельно, в обратном порядке сборки:

```ts
await transport.dispose();
await service.dispose();
await database.dispose();
```

Если приложение поставляло адаптер паба/подложки, оно также должно утилизировать этот адаптер и его соединения после Транспорта.

Чтобы расширить поведение на этих границах модуля, продолжайте с [Промежуточное ПО и события](/server/collaboration/middleware-and-events).

[^operational-transformation]: Операционная трансформация (OT) согласует одновременные операции, созданные на разных ревизиях документа. Она обрабатывает изменения, а не заменяет весь документ последним полученным снимком.

[^collaboration-revision]: Ревизия обозначает позицию в подтверждённой истории Unit. Changeset содержит операции одной отправки; их подтверждение продвигает историю. Ревизия не является версией SDK или меткой времени.
