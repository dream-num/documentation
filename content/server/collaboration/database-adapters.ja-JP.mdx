データベースアダプタは、コラボレーションサービスが管理するコアコラボレーションデータを主張しています。このサービスは、ユニット、OT、およびリビジョンセマティクスを所有しており、アダプタはこれらのセマティクスを原子格納操作に変え、再試行が安全です。内蔵アダプタで覆われていないデータベースを接続するには、`IDatabaseAdapter`を実行し、完全な行動契約を満たします。

データベースアダプタは、Apache-2.0のオープンソースです。ソースコードは[univer-collaboration-sdk-community(ユニバー・コラボレーション)](https://github.com/dream-num/univer-collaboration-sdk-community)で利用可能で、パッケージは他のパッケージと同じ名前とバージョンを使用します。

## 再起動後の永続化を確認する [#verify-persistence]

リポジトリのルートから`pnpm example:database-adapter`を起動し、実行します。 `http://127.0.0.1:3010/?unit=persistent-sheet`を開き、セルを変更し、2番目のブラウザで変更を確認します。 その後、サーバーを停止し、再び同じコマンドを実行し、同じURLを再オープンします。 値はまだ存在する必要があります。

[サンプルのサーバー](https://github.com/dream-num/univer-collaboration-examples/blob/main/examples/database-adapter/server/main.ts)は文書を `examples/database-adapter/.data/collaboration.sqlite` に保存します。

## Adapter が保存するもの

Adapter は共同編集するドキュメント（Unit）ごとに、次の 3 種類のデータを保存します。

- **Unit レコード**には、ドキュメント ID、種類、作成者、作成日時、現在のリビジョン（`headRevision`）が含まれます。Adapter は変更セットの保存と同時にリビジョンを更新します。アプリケーションは `UnitRecord.metadata` に名前（`name`）、最終編集者の ID（`lastEditorID`）、最終更新日時（`lastModifiedAt`）などの独自の項目を保存・管理できます。
- **スナップショット**は、あるリビジョンのドキュメントの内容を保持します。指定したリビジョンを読み込むとき、Service はそのリビジョン以前の最新のスナップショットを読み込み、そこから指定リビジョンまでの変更を順に適用できます。スプレッドシートの場合は、スナップショットが参照するデータブロックも保存します。
- **変更セット**は 1 回の送信に含まれる操作をまとめたものです。Adapter は変更セットをリビジョン順に保存し、送信時の `sid` と `reqId` を保持します。Service はこの識別子でクライアントからの再送を判別し、同じ変更の二重適用を防ぎます。[^submission-idempotency] アプリケーションは `ChangesetRecord.metadata` に編集元（`source`）や関連する業務操作の ID（`operationId`）などを記録できます。

作成時や送信時の設定方法は[メタデータの永続化](/server/collaboration/middleware-and-events#persistent-metadata)を参照してください。

論理削除ではデータが保持され、復元すると編集を再開できます。完全に削除するとデータにアクセスできなくなり、元のドキュメント ID も再利用できません。

ユーザー、ロール、アクセス権限はアプリケーションが管理します。History、Thread Comment、Worktree にはそれぞれ専用の Adapter インターフェースがあります。

## Adapter の読み書きの要件

`IDatabaseAdapter` を実装するときは、操作ごとに次の要件を満たしてください。

| 操作 | 要件 |
| --- | --- |
| Unit の作成 | Unit レコード（メタデータを含む）、初期スナップショット、参照先の Sheet ブロックをアトミックに保存し、同時に読み取り可能にします。 |
| 変更セットのコミット | 現在のリビジョンが期待値と一致する場合にのみコミットします（CAS）[^revision-cas]。変更セットとそのメタデータの保存、Unit のメタデータ全体の置き換え、リビジョンの 1 加算をアトミックに実行します。不一致の場合は何も書き込まず、現在のリビジョンを返します。 |
| 変更セットの読み取り | 指定範囲の変更セットをリビジョンの昇順で欠番なく返します。Service が同じ Unit 内の再送を判別できるよう、元の `sid` と `reqId` を保持します。 |
| スナップショットの保存 | スナップショットが読み取り可能になった時点で、参照先のすべての Sheet ブロックも読み取れるようにします。 |
| 削除と復元 | バッチ内のすべての Unit に操作を適用します。1 件でも失敗した場合はバッチ全体を元の状態に保ちます。 |

## Memory Adapter

[`@univerjs-pro/collaboration-database-memory`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-memory)はNode.jsプロセスの内で動きます。それはのために適しています:

- 単体テストと結合テスト
- 一時的な開発環境
- カスタムミドルウェアまたはクライアントアセンブリの迅速なチェック

```ts
import { MemoryDatabaseAdapter } from "@univerjs-pro/collaboration-database-memory";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";

const database = new MemoryDatabaseAdapter();
const service = new UniverCollabService({ dbAdapter: database });
```

メモリアダプタは、永続的な実装として同じリビジョン、CAS、および出欠契約に従います。そのデータは、現在のNode.jsプロセスにのみ存在し、そのプロセスが終了したときに失われます。

## SQLite Adapter

[`@univerjs-pro/collaboration-database-sqlite`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-sqlite)はSQLiteファイルに保存されます。開発、テスト、ローカルアプリケーション、小規模な用途に適しています。

```ts
import { mkdir } from "node:fs/promises";

import { SQLiteDatabaseAdapter } from "@univerjs-pro/collaboration-database-sqlite";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";

await mkdir("./data", { recursive: true });

const database = new SQLiteDatabaseAdapter({
  filename: "./data/collaboration.sqlite",
  busyTimeoutMs: 5_000,
});
const service = new UniverCollabService({ dbAdapter: database });
```

データベースが空いているときにスキーマを初期化し、既に存在するスキーマだけを検証します。ファイルの場所、バックアップ方法、その他のSQLiteの設定は、アプリケーションによって決定されます。

## PostgreSQL Adapter

[`@univerjs-pro/collaboration-database-postgres`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-postgres) は、シートのスナップショットが参照するセルのデータブロックを含め、Core の共同編集データをすべて PostgreSQL に保存します。複数の共同編集ノードで同じデータベースを共有できます。

```ts
import { PostgresDatabaseAdapter } from "@univerjs-pro/collaboration-database-postgres";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";
import { Pool } from "pg";

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
const database = await PostgresDatabaseAdapter.create({ pool });
const service = new UniverCollabService({ dbAdapter: database });
```

このアプリケーションは、プールを所有し、サービスを無効にした後に閉じます。 `create()`は、空のデータベースで`collaboration`スキーマを初期化し、既存のスキーマのみを検証します。

S3 互換のオブジェクトストレージを利用できる場合は、データベースとバックアップの容量を抑えられる [PostgreSQL + S3 Adapter](#postgresql-s3-adapter) を推奨します。

## PostgreSQL + S3 Adapter [#postgresql-s3-adapter]

[`@univerjs-pro/collaboration-database-postgres-s3`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-postgres-s3) はシートのセルのデータブロックを S3 互換バケットに保存します。Unit、changeset、スナップショットのレコード、ブロックへの参照は PostgreSQL に保存します。

大きなワークブックでは、スナップショットの大半をセルデータが占めます。ブロックを S3 に保存すると、PostgreSQL のデータベースとバックアップの容量を抑えられます。ワークブックの増大に合わせて、ブロックのストレージを独立して拡張できます。

`DATABASE_URL` にデータベースの接続文字列、`S3_REGION` にバケットのリージョン、`S3_BUCKET` に既存のバケット名を設定します。

```ts
import { S3Client } from "@aws-sdk/client-s3";
import { PostgresS3DatabaseAdapter } from "@univerjs-pro/collaboration-database-postgres-s3";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";
import { Pool } from "pg";

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
const client = new S3Client({ region: process.env.S3_REGION });
const database = await PostgresS3DatabaseAdapter.create({
  pool,
  s3: { client, bucket: process.env.S3_BUCKET! },
});
const service = new UniverCollabService({ dbAdapter: database });
```

## カスタム Database Adapter

カスタムアダプタは、通常、次の場合に適しています。

- MySQL などの業務データベースを既に使っている
- コラボレーションの投稿は、アプリケーションが所有するデータベースメカニズムを使用する必要があります。
- 運用やコンプライアンス要件が 組み込み Adapter の想定範囲を超える

`IDatabaseAdapter` を実装し、組み込み Adapter と同様に Service に注入します。

```ts
const database = new ApplicationCollaborationDatabase({ pool });
const service = new UniverCollabService({ dbAdapter: database });
```

本サービスは特定のデータベースに依存しませんが、カスタム実装にトランザクション、CAS、またはデジュプリケーションを追加することはできません。このアダプタは、データベースが提供する機能を使用して、完全な契約を実行しなければなりません。[コミュニティリポジトリ](https://github.com/dream-num/univer-collaboration-sdk-community)の組み込みの実装は、異なるデータベースに同じ契約を適用し、参照として機能します。

## 業務データの保存方法

**`metadata` を使用して、文書や変更に添付された情報を使用します。** アプリケーションは、ドキュメントを作成したり、変更を提出したりするときに、これらのフィールドを設定したり、組み込みのアダプターはコラボレーションデータとともに保存することができます。 [ミドルウェアとイベント](/server/collaboration/middleware-and-events#persistent-metadata)を参照してください。

**ミドルウェアまたはイベントを使用して、ビジネステーブルを分離します。** 試みられた操作を監査するために、ミドルウェアの監査テーブルに書きます。成功したコミットの後、ビジネステーブルを更新するには、`changesetCommitted`を聞いてください。デフォルトでは、これらの書き込みはコラボレーショントランザクションの外で実行されます。リビジョンコンフリクトは、コミットステージミドルウェアが再び実行される可能性があるため、リトライは重複したレコードを作成する必要はありません。イベントは、最良の機能に基づいてプロセス内で配信されます。アプリケーションが埋め戻すか、再構築することができますデータのためにそれらを使用してください。

**アプリケーションが独自のデータベースとスキーマを必要とするとき、またはビジネスとコラボレーションデータが1つのトランザクションで書かれなければならないとき、カスタムデータベースアダプタを使用します。**サービスを呼び出すと、アプリケーションは、`customData`のビジネスオペレーションIDなどのコンテキストを渡すことができます。 アダプタは、`ctx.customData`から必要なフィールドを読み、どのテーブルが更新されるかを決めることができます。 例えば、`commitChangeset()`は、変更を保存した同じトランザクションで対応するビジネスレコードを更新するために、運用IDを使用することができます。

`customData`は現在の呼び出しにスコープ付けされます。内蔵アダプタはフィールドを自動的に主張しません。また、ビジネステーブルに書き込むために使用していません。

## 拡張モジュールのストレージ

履歴、スレッドコメント、Worktree、およびファイルなどの拡張モジュールは、それぞれ独立したデータベースアダプタインターフェイスを定義します。 それらのアダプタは、1つのデータベースを共有したり、別のストレージを使用することができます。 単一のカスタム実装は、いくつかのアダプタインターフェイスを提供し、対応するサービスに注入することができます。

これらのアダプタインターフェイスは独立したため、SDKはデフォルトでクロスモジュール取引を提供していません。複数のモジュールがデータベースを共有する場合でも、アプリケーションはクロスモジュールの一貫性戦略を所有しています。

## Adapter の選択

| Adapter         | 適した用途                                                                                | 主な制約                                                                                                                         |
| --------------- | ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Memory          | テスト、サンプル、一時的な開発                                                            | プロセス終了時にデータが失われる                                                                                                 |
| SQLite          | 開発、テスト、ローカルアプリ、小規模利用                                                  | 単一ファイル DB。設定はアプリケーションが管理                                                                                    |
| PostgreSQL + S3 | PostgreSQL とオブジェクトストレージを使うアプリケーション。特に大きなワークブックに適する | データベースとバケットの両方を管理します。S3 互換ストレージがない場合は [PostgreSQL Adapter](#postgresql-adapter) を使用します。 |
| カスタム        | 既存 DB や独自の業務データ連携                                                            | 完全な契約の実装と検証が必要                                                                                                     |

注入した Adapter はアプリケーションが所有します。Service を先に破棄し、次に Adapter を破棄します。

```ts
await service.dispose();
await database.dispose();
```

比較できる実行例は[データベースアダプターのサンプル](/server/collaboration/examples#database-adapter)を参照してください。

[^submission-idempotency]: 冪等性により、同じ送信を再試行しても編集が二重に適用されません。再試行時は送信 ID を保持します。内容が同じでも新しい ID なら新規送信になります。

[^revision-cas]: *CAS（比較交換）*は現在値が期待値と一致する場合だけ更新します。現在のリビジョン確認と次の状態の書き込みを不可分に行い、同時送信が同じリビジョンを確定しないようにします。
