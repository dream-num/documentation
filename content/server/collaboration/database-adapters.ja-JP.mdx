Database Adapter は Collaboration Service が使う基本的な共同編集データを永続化します。開発者は `IDatabaseAdapter` を実装して、完全な動作契約を満たせるデータベースに接続できます。Service は Unit、OT、リビジョンの意味を管理し、Adapter はそれをアトミックかつ安全に再試行できる永続化操作に変換します。

Database Adapter は Apache-2.0 でオープンソースです。ソースは [univer-collaboration-sdk-community](https://github.com/dream-num/univer-collaboration-sdk-community) にあり、パッケージ名とバージョンは他のパッケージと同じです。

## 再起動後の永続化を確認する [#verify-persistence]

Quick Start を停止し、ルートで `pnpm example:database-adapter` を実行します。`http://127.0.0.1:3010/?unit=persistent-sheet` を開き、セルを変更して別ブラウザーで確認します。停止後に同じコマンドと URL で再開し、値が残ることを確認します。ファイルは `examples/database-adapter/.data/collaboration.sqlite` です。再起動時に削除しないでください。サーバーは既存 Unit を読み、`UNIT_NOT_FOUND` のときだけ `createUnitFromData()` を呼びます。[server/main.ts](https://github.com/dream-num/univer-collaboration-examples/blob/main/examples/database-adapter/server/main.ts) を参照してください。

## Adapter が保存するもの

基本の共同編集 Adapter は次を保存します。

- Unit レコードと現在の最新リビジョン；
- リビジョン付きスナップショット；
- 確定済みの変更セット；
- Sheet のスナップショットが参照するブロック；
- `(unitID, sid, reqId)` をキーとする送信の冪等性[^submission-idempotency]レコード；
- Unit の論理削除、復元、完全削除の状態。

既定ではユーザー、ロール、ACL、製品メタデータを保存しません。History、Thread Comment、Worktree は独立した Adapter 契約を使います。

## 必須の意味論

`IDatabaseAdapter` は単なる CRUD インターフェースではありません。Collaboration Service が期待する正確性の契約を守る必要があります。

| 契約 | 意味 |
| --- | --- |
| アトミックな作成 | 初期スナップショットと Sheet ブロックが同時に可視化されるか、どちらも可視化されない |
| リビジョン CAS[^revision-cas] | 最新リビジョンが期待値と一致する場合のみ次の送信を確定 |
| 送信の冪等性 | 同じ `(unitID, sid, reqId)` の再試行は同じ確定結果を返す |
| 連続する変更セット | 確定した変更セットと Unit のリビジョンが連続する |
| スナップショットの可視性 | 依存データがすべて保存された後でのみ読み取り可能になる |
| アトミックなライフサイクル操作 | 一括削除・復元のすべての Unit が成功するか、どれも実行されない |
| 完全削除の墓標 | 完全削除した Unit ID を再作成できない |

この並行性と原子性を実装せずに各メソッドを通常の読み書きに対応付けると、OT と復元の動作を壊します。

## Memory Adapter

[`@univerjs-pro/collaboration-database-memory`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-memory) はプロセス内実装で、次の用途に適しています。

- 単体テストと結合テスト；
- 一時的な開発環境；
- カスタム Middleware やクライアント構成の簡易検証。

```ts
import { MemoryDatabaseAdapter } from "@univerjs-pro/collaboration-database-memory";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";

const database = new MemoryDatabaseAdapter();
const service = new UniverCollabService({ dbAdapter: database });
```

Memory Adapter は永続化実装と同じリビジョン、CAS、冪等性の契約に従いますが、データは現在の Node.js プロセス内にあり、終了時に失われます。

## SQLite Adapter

[`@univerjs-pro/collaboration-database-sqlite`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-sqlite) は開発、テスト、ローカルアプリケーション、小規模利用向けの永続化 SQLite 実装です。

```ts
import { mkdir } from "node:fs/promises";

import { SQLiteDatabaseAdapter } from "@univerjs-pro/collaboration-database-sqlite";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";

await mkdir("./data", { recursive: true });

const database = new SQLiteDatabaseAdapter({
  filename: "./data/collaboration.sqlite",
  busyTimeoutMs: 5_000,
});
const service = new UniverCollabService({ dbAdapter: database });
```

空のデータベースにはスキーマを初期化し、既存のデータベースは検証だけを行います。ファイルの場所、バックアップ、その他の SQLite 設定はアプリケーションが決めます。

## PostgreSQL Adapter

[`@univerjs-pro/collaboration-database-postgres`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-postgres) は node-postgres ベースの永続化実装で、複数の共同編集ノードで共有できます。

```ts
import { PostgresDatabaseAdapter } from "@univerjs-pro/collaboration-database-postgres";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";
import { Pool } from "pg";

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
const database = await PostgresDatabaseAdapter.create({ pool });
const service = new UniverCollabService({ dbAdapter: database });
```

接続プールはアプリケーションが保持し、Service を破棄した後に閉じます。`create()` は空のデータベースに `collaboration` スキーマを初期化し、既存のスキーマは検証だけを行います。

## カスタム Database Adapter

通常、次の場合に適しています。

- MySQL などの業務データベースを既に使っている；
- 共同編集の送信をアプリケーション固有の DB 機構と統合したい；
- 運用やコンプライアンス要件が 組み込み Adapter の想定範囲を超える。

`IDatabaseAdapter` を実装し、組み込み Adapter と同様に Service に注入します。

```ts
const database = new ApplicationCollaborationDatabase({ pool });
const service = new UniverCollabService({ dbAdapter: database });
```

Service は特定の DB に依存しませんが、カスタム実装にトランザクション、CAS、重複排除を補うこともできません。Adapter 自身が DB の機能で完全な契約を実装する必要があります。[コミュニティリポジトリ](https://github.com/dream-num/univer-collaboration-sdk-community)の組み込み実装は同じ契約を異なるデータベースで実装した例であり、参考にできます。

## Context とアプリケーションの境界

Service の各呼び出しは `customData` を Middleware、Database Adapter、関連する Events に渡しますが、SDK は自動保存しません。認可の判断は通常 Service Middleware に置き、Adapter の各メソッドで繰り返さないようにします。

```text
Service Middleware
  → 業務操作を許可または拒否
  → Database Adapter
  → サーバー管理の共同編集状態をアトミックに保存
```

これにより Memory、SQLite、PostgreSQL、カスタム Adapter で同じアプリケーションポリシーを共有できます。

業務データと共同編集データに強い整合性が必要なら、カスタム Database Adapter が `customData` から必要な値を読み、同じ DB トランザクションで両方を書き込めます。

同一トランザクションが不要なら、Middleware や Events から別テーブルや外部システムに書き込めます。これらは既定では Adapter の内部トランザクションを共有しません。Events は共同編集のコミット成功後に発行される、プロセス内のベストエフォート通知です。必要な冪等性、再試行、補償処理はアプリケーションの責任です。

## 拡張モジュールのストレージ

History、Thread Comment、Worktree、File などは独立した Database Adapter インターフェースを定義します。Adapter は同じ DB を共有しても別ストレージを使っても構いません。1 つのカスタム実装が複数の Adapter インターフェースを提供し、対応する Service に注入することもできます。

インターフェースは独立しているため、SDK は既定ではモジュール間トランザクションを提供しません。同じ DB を共有する場合も、モジュール間の整合性はアプリケーションが設計します。

## Adapter の選択

| Adapter | 適した用途 | 主な制約 |
| --- | --- | --- |
| Memory | テスト、サンプル、一時的な開発 | プロセス終了でデータが消える |
| SQLite | 開発、テスト、ローカルアプリ、小規模利用 | 単一ファイル DB。設定はアプリケーションが管理 |
| PostgreSQL | 複数ノードへのデプロイと既存の PostgreSQL | 接続プールと DB の運用はアプリケーションが管理 |
| カスタム | 既存 DB や独自の業務データ連携 | 完全な契約の実装と検証が必要 |

注入した Adapter はアプリケーションが所有します。Service を先に破棄し、次に Adapter を破棄します。

```ts
await service.dispose();
await database.dispose();
```

比較できる実行例は[データベースアダプターのサンプル](/server/collaboration/examples#database-adapter)を参照してください。

[^submission-idempotency]: 冪等性により、同じ送信を再試行しても編集が二重に適用されません。再試行時は送信 ID を保持します。内容が同じでも新しい ID なら新規送信になります。

[^revision-cas]: *CAS（比較交換）*は現在値が期待値と一致する場合だけ更新します。現在のリビジョン確認と次の状態の書き込みを不可分に行い、同時送信が同じリビジョンを確定しないようにします。
