Historia, Thread Comment, File y Worktree son módulos de extensión de colaboración opcionales que amplían la colaboración sin cambiar el núcleo. Cada módulo proporciona su propio Servicio, Medioware, Evento, Adaptador de bases de datos y límites de ciclo de vida, por lo que una aplicación permite sólo los módulos que el producto requiere. Los módulos todavía pueden compartir el transporte, el sistema de identidad y la misma base física.

Server-side Office Exchange se basa en el servicio de archivos y colaboración. Se convierte entre archivos de Office y Unidades colaborativas, y proporciona su propio servicio, Endpoint y Middleware.

## Historial de versiones

La historia convierte la creación de una unidad y los cambios confirmados en las entradas de historia que un usuario ve. El índice se deriva: los cambios confirmados en el Servicio de Colaboración Central siguen siendo la fuente autorizada del contenido de la unidad.

```ts
const historyService = new UniverHistoryService({
  collabService,
  dbAdapter: historyDatabase,
  userProvider,
});

transport.register(new UniverHistoryEndpoint(historyService));
```

El constructor se suscribe al servicio básico `unitCreated` y `changesetCommitted` Eventos y mantiene el índice actual, y `dispose()` elimina esas suscripciones. Por defecto, los grupos de historia cambian por ventana del tiempo y por mutaciones especiales en lugar de escribir una entrada para cada cambio.

La historia expone la lectura de Middleware para `getHistoryList`, `listHistoryCreators` y `getHistoryChangesets`. La indización tiene lugar dentro del servicio. `userProvider` sólo suministra datos de visualización como nombres y avatares, y no realiza ninguna autenticación ni autorización. Un fallo de la escucha de eventos no hace rodar un cambio básico que ya está confirmado, por lo que la historia debe ser tratado como datos derivados que siempre se pueden reconstruir

## Comentarios en hilos

El servicio de comentarios gestiona el contenido, las respuestas, la edición, la eliminación y el estado de resolución.

```ts
const commentService = new UniverCommentService({
  database: commentDatabase,
  userProvider,
});

transport.register(
  new UniverCommentEndpoint({
    service: commentService,
    roomHost: collabEndpoint,
  }),
);
```

Los cuerpos de comentarios pertenecen al adaptador de comentarios, mientras que los anclas que se mueven con el contenido de hoja o Doc siguen siendo parte de las instantáneas y cambios de núcleo. El comentario Endpoint puede publicar `comment_update` a través de la sala de unidad del punto final de colaboración principal, pero ese mensaje en tiempo real no es el estado de comentario autoritativo. Un cliente que pierde el mensaje puede recuperar enumerando los comentarios de nuevo.

El servicio de comentarios proporciona Middleware para añadir, lista, respuesta, resolver o reabrir, editar y eliminar, y publica un evento `commentCommitted`. El servicio de comentario no hereda la política de lectura o edición del Servicio básico.

## Almacenamiento de archivos

Los archivos almacenan los archivos binarios que los clientes de Univer suben: imágenes y archivos adjuntos insertados en una Unidad, y los archivos fuente y resultado de importación y exportación. Los datos de la unidad registran solamente el ID de archivo, y el cliente resuelve ese ID a una URL de descarga cuando carga la Unidad.

```ts
const fileService = new UniverFileService({
  database: fileDatabase,
  blobStore,
});

transport.register(new UniverFileEndpoint(fileService));
```

Los metadatos y el contenido son dos contratos independientes: `IFileDatabaseAdapter` almacena registros de archivos y el contenido de las tiendas `IFileBlobStore`. Los archivos de intercambio temporal son accesibles sólo al usuario que los subió, y el Servicio los elimina en un horario. Imágenes y archivos adjuntos dentro de una unidad están sujetos a permisos de unidad a través de `upload`, `signUrl` y `download` Middleware.

## Conversión Office del lado del servidor

Importaciones de servicio de intercambio Los archivos de Office como Unidades de colaboración y Unidades de exportación como archivos. Utiliza `@univerjs-pro/exchange-node` para la conversión, crea y lee Unidades a través del Servicio de Colaboración, y almacena los archivos fuente y resultado a través del servicio de archivos:

```ts
const exchangeService = new UniverExchangeService({ collabService, fileService });

transport.register(new UniverExchangeEndpoint(exchangeService));
```

Importación y exportación son tareas. El cliente crea una tarea y luego encuestas para el resultado. Importación pasa por el `createUnit` Middleware del Servicio Central, y la exportación pasa por `readUnitData`. El `import` y `export` Mediaware de los límites de la velocidad de la manija de cambio, cuotas y auditoría.

| Unit | Importación | Exportación |
| --- | --- | --- |
| Sheet | xls, xlsx, csv, tsv | xlsx, csv, tsv |
| Doc | doc, docx | docx |
| Slide | ppt, pptx | pptx |
| Base | xls, xlsx, csv, tsv | xlsx, csv |
| PDF | pdf | pdf |

## Borradores Worktree y fusión

Worktree añade borradores aislados, congelación, evaluación de fusión y fusión por Unit para una o varias Units:

```text
create → draft → ready → merging → merged
           ↑       │
           └ reopen┘

draft / ready → discarded
```

```ts
const worktreeService = new UniverCollabWorktreeService({
  trunk: {
    service: collabService,
    dbAdapter: coreDatabase,
  },
  dbAdapter: worktreeDatabase,
});
```

Worktree almacena sus propios proyectos de cambio por `(worktreeID, unitID)` y reutiliza la Unidad, OT y los motores de presentación del Servicio Central. Sólo el estado `draft` acepta nuevas ediciones. `markReady()` congela el proyecto de revisión actual, y `mergeWorktree()` fusiona Unidades en el maletero una a la vez.

Worktree Service tiene su propio ciclo de vida, su propio software de lectura, el proyecto de presentación/apply/commit Middleware, y Eventos para la creación, cambios de estado, fusionar resultados, y proyectos de cambio compromete. La escritura final al tronco todavía pasa por el Middleware del Servicio Central.

Una fusión multi-Unit no es atómica entre Units. La aplicación debe mostrar el resultado de cada Unit.

## Puntos de extensión independientes

Cuando una aplicación permite un módulo de extensión, cada límite requiere una evaluación separada:

| Límite | Principal | History | Comment | File | Worktree |
| --- | --- | --- | --- | --- | --- |
| Service | Independiente | Independiente | Independiente | Independiente | Independiente |
| Middleware | No compartido | No hereda del principal | No hereda del principal | No hereda del principal | No hereda del principal |
| Event | Ciclo de vida principal | Observa Events principales | `commentCommitted` | — | Ciclo de vida/commit de Worktree |
| Database Adapter | Adapter principal | History Adapter | Comment Adapter | File Adapter y Blob Store | Worktree Adapter |

Office Exchange reutiliza el almacenamiento de Core y File. Después de la `import` y `export` Middleware de Exchange run, importación y exportación todavía pasan a través del Core y File Middleware.

Estos Adaptadores pueden compartir una base de datos y seguir siendo objetos separados con contratos separados. Los servicios y los adaptadores también deben ser eliminados de forma independiente.

## Conectar la interfaz de historial de Web SDK [#web-history]

Mount the History Endpoint junto con los endpoints de colaboración. En el Web SDK, `historyServerUrl` es el prefijo común para `/{unitId}/list`, `/{unitId}/creators`, y `/{unitId}/cs`, y es predeterminado a `/universer-api/history`. Cuando se utiliza un prefijo diferente, el plugin de historia de host y el producto Historia plugin UI debe ser configurado con la misma URL.

Restaurar una versión pasa por el camino de mutación de colaboración; no hay historia independiente Punto final REST para restaurar. La carga de colaboración, la presentación y la autorización deben permanecer configuradas. Comparando dos instantáneas materializadas a través de `createUnitComparisonEngine()` es una operación separada que sólo lee datos. No requiere un servicio de historia de ejecución, y no persiste ni restaura versiones.
