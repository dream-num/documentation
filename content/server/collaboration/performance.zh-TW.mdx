測試涵蓋單文件多人編輯和多文件同時編輯兩種情境。文件預熱後，測試記錄持續編輯期間的提交確認延遲、吞吐量、提交達成率，以及協同服務程序的 CPU 和記憶體佔用。

### 協同服務配置

4 核和 8 核節點均將 `runtime.maxLoadedUnits` 從預設值 1,200 調至 4,000，允許單節點在記憶體中同時保留最多 4,000 份文件。其餘 SDK 執行環境參數沿用預設值，工作執行緒數由 SDK 自動確定。快照也採用預設策略：距上次成功快照累計 50 個版本，或單次變更集達到 5 MiB 時觸發。4 核與 8 核節點的協同服務程序記憶體上限分別為 14 GiB 和 29 GiB。

以下是負載測試服務的核心程式碼節選。配接器使用已初始化的 PostgreSQL 連線池和 OSS 用戶端，傳輸層掛載到 Node.js HTTP 服務。

```ts
const dbAdapter = await PostgresS3DatabaseAdapter.create({
  pool,
  s3: { client, bucket, prefix },
});
const service = new UniverCollabService({
  dbAdapter,
  runtime: { maxLoadedUnits: 4000 },
});
const endpoint = new UniverCollabEndpoint(service);
const transport = createNodeTransport();
transport.register(endpoint);
transport.attach(server);
```

| 快照名稱 | 儲存格數 | 內容 |
| --- | ---: | --- |
| `blank` | 0 | 空白工作表 |
| `10k-cells` | 約 10,000 | 數字、文字和公式 |
| `100k-cells` | 約 100,000 | 數字、文字和公式 |

`10k-cells` 和 `100k-cells` 均有 26 欄，其中 14 欄為數字、9 欄為文字、3 欄為參照同一列資料的公式。

## 測試方法

### 模擬用戶端

結果表中的「編輯人數」按獨立工作階段計數。每個工作階段加入一份文件，透過 HTTP 提交儲存格修改，並透過 WebSocket 接收伺服器端確認。測試指令碼直接呼叫協同 API。HTTP 請求與等待 WebSocket 確認的逾時時間均為 10 秒。

### 預熱與正式取樣

每輪先從指定快照創建文件，待所有工作階段加入後開始預熱。首次編輯會觸發伺服器端加載文件。單文件情境預先提交 1 次編輯。多文件情境中各文件預熱時提交不同次數的編輯，從不同版本開始正式編輯，保存快照的時刻也隨之錯開。

所有文件完成預熱後開始正式取樣。結果表中的提交統計、延遲分位數、CPU 和記憶體均取自正式取樣期間。

### 編輯負載

單文件情境使用 `blank`，逐步增加編輯人數。多文件情境分別使用上述三種快照，在每種快照下逐步增加活躍文件數。兩種情境中，每次提交都只包含一條 `sheet.mutation.set-range-values`，向一個儲存格寫入一個數值。

| 測試條件 | 單文件多人編輯 | 多文件同時編輯 |
| --- | --- | --- |
| 每份文件編輯人數 | 按測試組調整，見結果表 | 固定為 2 人，適用於全部多文件測試 |
| 每次編輯的操作 | 各自錯開時間修改自己的儲存格 | 各自錯開時間修改自己的儲存格 |
| 每人編輯頻率 | 每 6 秒 1 次 | 每 2 秒 1 次 |
| 每輪取樣時長 | 300 秒 | 300 秒 |

## 指標定義

| 指標 | 定義 |
| --- | --- |
| 提交確認延遲 | 從用戶端發出一次編輯，到該用戶端收到伺服器端確認所經過的時間。P50、P95、P99 分別表示 50%、95%、99% 的成功提交在相應時間內收到確認。Max 表示成功提交中最長的確認延遲。 |
| 吞吐量 | 正式取樣期間成功提交的次數除以取樣時長，單位為次/秒。 |
| 提交達成率 | 成功提交數佔計劃提交數的百分比。計劃提交數包含成功、失敗及未發出的提交。 |
| CPU 均值 / 峰值（%） | 協同服務程序在正式取樣期間的平均 CPU 佔用和最高取樣值。每個 CPU 核心滿載計為 100%，多核合計可超過 100%。 |
| 記憶體峰值（MiB） | 正式取樣期間協同服務程序常駐記憶體（RSS）的最大取樣值。 |

### 並行規模的判定標準

每輪同時滿足以下條件才算達標：

- 提交確認延遲 **P99 < 1,000 ms**。
- 提交達成率 **> 90%**。
- 協同服務程序持續執行，直到所有測試文件通過一致性核對。
- 正式取樣期間快照處理跟得上持續寫入，待處理快照任務沒有持續增加。持續增加時記為「快照持續積壓」。

只測一輪的負載級別取該輪結果；測了多輪的負載級別，每輪都須達標。

## 測試結果的適用範圍

為評估伺服器端處理並行編輯的能力，測試使用 Node.js 指令碼模擬編輯工作階段，直接呼叫協同 API 提交儲存格修改。提交確認延遲僅衡量指令碼從發出請求到收到伺服器端確認所用的時間，不包含使用者在瀏覽器中操作和等待表格渲染的時間。

本報告的資料僅供效能評估和單協同節點容量規劃參考。實際效能取決於部署配置、網路條件、文件大小以及編輯操作的類型和頻率。

「負載級別」指一組測試條件下的一個負載值，即編輯人數或活躍文件數。「最高達標負載級別」指在本次測試條件下滿足判定標準的最大已測負載級別。部分達標負載級別的平均 CPU 佔用已接近節點上限。**最高達標負載級別僅供容量規劃參考，不宜直接作為生產環境的長期執行負載。** 實際部署時，應為並行高峰和資源佔用波動預留安全裕度，並在目標環境中用代表性業務負載驗證可長期穩定承載的規模。

#### 節點池規格選擇建議

採用[多節點部署](/server/deployment)時，閘道可按文件大小將編輯請求分別路由到中小型文件池和大型文件池。以下為各池的單節點選型參考，測試負載為每份文件 2 人、每人每 2 秒編輯一次。

- **中小型文件池建議優先評估 4 核 8 GiB。** 按 4 核 16 GiB 的實測結果估算，在 8 GiB 規格的記憶體預算內，空白文件可參考 2,300 份，每份約 10,000 個儲存格的文件可參考 1,800 份。
- **大型文件池建議評估 8 核 16 GiB 或 8 核 32 GiB。** 每份約 100,000 個儲存格時，8 核 32 GiB 的最高達標負載級別為 700 份，記憶體峰值也在 8 核 16 GiB 的預算內。這一情境的限制因素是快照處理：750 份時提交確認延遲仍然達標，但出現快照持續積壓。
