Le Univer Collaboration SDK ne définit pas les utilisateurs, les rôles ou un modèle ACL. Une application établit une identité de confiance dans le Middleware Transport et protège ensuite les Sessions en temps réel et les données de collaboration faisant autorité avec Endpoint et Service Middlesware.

Cette page applique [Middleware et événements](/server/collaboration/middleware-and-events) à une tâche concrète : intégrer l'identité et l'autorisation par Middleware.

## Vérifier les droits [#verify-permissions]

Arrêtez l'exemple précédent et exécutez `pnpm example:permissions`. Ouvrez `http://127.0.0.1:3010` dans deux contextes de navigateurs distincts : connectez-vous comme **Alice · Éditeur** dans l'un et comme **Bob · Affichage** dans l'autre. L'éditeur peut modifier le document, et le visionneur voit le résultat synchronisé mais ne peut pas le modifier. Ouvrez [serveur/main.ts](https://github.com/dream-num/univer-collaboration-examples/blob/main/examples/permissions/server/main.ts) pour suivre le code : résolution d'identité en `transport.use()`, lisez les vérifications en `readUnitData`, vérifiez la pièce en `joinUnit` et modifiez les vérifications en `submitChangeset`. Remplacez la démo Cookie et la liste d'utilisateurs par votre propre authentification et document ACL. **Frontend en lecture seule l'état est insuffisant.**

La page fournit également un compte **Casey · Aucun accès**. Se connecter avec ce compte devrait bloquer le chargement du document, et la requête snapshot retourne HTTP 403.

## Modèle d’identité

| Identifiant | Fournisseur | Signification et vie |
| --- | --- | --- |
| `userID` | Application | Identité métier stable et auteur des jeux de modifications confirmés |
| `memberID` | Endpoint | ID du membre en ligne pour une Session WebSocket ; change après reconnexion |
| `sid + reqId` | Client | Identité d’une soumission de modifications, stable lors des nouvelles tentatives |

les champs de profil d'utilisateur soumis par le navigateur, `memberID`, et les révisions ne peuvent pas se substituer à l'authentification de l'application. `context.userID`.

## Établir l’identité dans les Middleware Transport

Le Transport exécute Middleware pour chaque requête HTTP Collaboration. Une application peut lire un cookie, une session ou un jeton porteur et joindre le résultat authentifié au Contexte :

```ts
transport.use(async (context, next) => {
  const user = await auth.requireUser(context.incomingMessage);

  context.userID = user.id;
  context.customData.user = user;
  context.customData.tenantID = user.tenantID;
  context.customData.traceID = readTraceID(context.incomingMessage);

  await next();
});
```

Lorsque l'authentification échoue, mettre fin à la réponse HTTP sans appeler `next()` :

```ts
transport.use(async (context, next) => {
  const user = await auth.findUser(context.incomingMessage);
  if (!user) {
    context.response.statusCode = 401;
    context.response.end("Authentication required");
    return;
  }

  context.userID = user.id;
  await next();
});
```

Le SDK n’impose ni noms de Cookie, ni formats de jeton, ni tables utilisateur, ni parcours de connexion.

## Transmission de l’identité à une Session WebSocket

Le chemin WebSocket ne fait pas confiance aux champs utilisateurs dans les charges utiles du client. L'Endpoint transporte un contexte HTTP authentifié dans une session en temps réel au moyen d'un ticket de session unique:

```text
Requête HTTP de Session Ticket
  → authentification par les Middleware Transport
  → l’Endpoint stocke { userID, customData }
  → renvoie un ticket opaque à usage unique
  → l’ouverture WebSocket consomme le ticket
  → crée la Session { userID, memberID, customData }
```

La chaîne de tickets ne contient ni `userID` ni `customData`. `memberID` n'identifie que la connexion actuelle, et ce n'est pas un titre d'identité indépendant. Dans un déploiement multi-nœuds avec une billetterie partagée, le `customData` stocké est sérialisé, de sorte qu'il doit rester jSON-sérializable.

## Autoriser à la bonne frontière

| Comportement à protéger | Middleware |
| --- | --- |
| Entrée HTTP de collaboration | Transport `use()` |
| Connexion WebSocket | Endpoint `connect` |
| Entrée dans une Room d’Unit | Endpoint `joinUnit` |
| Lecture des instantanés, blocs ou jeux de modifications | Service `readUnitData` |
| Soumission de modifications de contenu | Service `submitChangeset` |
| Création d’une Unit | Service `createUnit` |
| Suppression d’Units | Service `deleteUnits` |
| Restauration d’Units | Service `recoverUnits` |

Endpoint `joinUnit` contrôle uniquement si une session peut entrer dans une salle en temps réel. Les instantanés et les changements manquants peuvent être lus directement sur HTTP, de sorte qu'un contrôle JOIN ne peut pas remplacer `readUnitData`. De même, une interface utilisateur client en lecture seule est un indice de produit et ne remplace pas la politique `submitChangeset` sur le serveur.

## Protéger la lecture, JOIN et l’édition

```ts
import { CollabError } from "@univerjs-pro/collaboration-service";

endpoint.use("joinUnit", async (context, next) => {
  const allowed = await acl.canRead(context.session.userID, context.unitID);
  if (!allowed) {
    throw new CollabError("PERMISSION_DENIED", "Cannot join this Unit");
  }
  await next();
});

service.use("readUnitData", async (context, next) => {
  const allowed = await acl.canRead(context.userID, context.request.unitID);
  if (!allowed) {
    throw new CollabError("PERMISSION_DENIED", "Unit is not accessible");
  }
  await next();
});

service.use("submitChangeset", async (context, next) => {
  const unitID = context.request.changeset.unitID;
  const allowed = await acl.canEdit(context.userID, unitID);
  if (!allowed) {
    throw new CollabError("PERMISSION_DENIED", "Unit is read-only");
  }
  await next();
});
```

Une application réelle installe normalement les trois règles : lire la politique pour HTTP et JOIN, et éditer la politique pour la soumission.

## Protéger le cycle de vie des Units

Le protocole de collaboration ouvre des unités qui existent déjà. -Créer document-- est normalement une API d'application qui écrit un enregistrement de produit et une ACL avant qu'elle n'appelle `createUnitFromData()` ou `createUnitFromSnapshot()`. Le cycle de vie nécessite également la protection du service Middleware :

```ts
service.use("createUnit", async (context, next) => {
  if (!(await acl.canCreate(context.userID, context.request.snapshot.type))) {
    throw new CollabError("PERMISSION_DENIED", "Unit creation denied");
  }
  await next();
});

service.use("deleteUnits", async (context, next) => {
  for (const unitID of context.request.unitIDs) {
    if (!(await acl.canDelete(context.userID, unitID))) {
      throw new CollabError("PERMISSION_DENIED", `Cannot delete ${unitID}`);
    }
  }
  await next();
});
```

Protégez `recoverUnits` séparément. Un utilisateur qui avait une fois la permission de supprimer ne conserve pas nécessairement la permission de récupération.

## Réutiliser les recherches via customData

Middleware dans le même service d'appel peut utiliser `customData` pour éviter les requêtes dupliquées:

```ts
service.use("submitChangeset", async (context, next) => {
  const unitID = context.request.changeset.unitID;
  context.customData.role ??= await acl.getRole(context.userID, unitID);

  if (context.customData.role === "viewer") {
    throw new CollabError("PERMISSION_DENIED", "Unit is read-only");
  }
  await next();
});
```

`customData` appartient uniquement à l'appel ou à la session en cours et n'est pas maintenu automatiquement. Les rôles, les ACL et les relations locataires restent dans le stockage des applications.

## Des politiques distinctes pour les extensions

History, Thread Comment, Worktree, File et Exchange disposent chacun de leur propre middleware de service :

- La liste d'historiques et les modifications doivent vérifier que l'appelant peut lire l'unité.
- La liste des commentaires devrait vérifier l'accès à la lecture, tout en ajoutant, en répondant, en modifiant et en supprimant la politique des commentaires.
- Worktree nécessite des vérifications distinctes de la visibilité, des modifications de projet, des modifications d'état et de la fusion.
- Un Worktree fusionne dans le coffre passe toujours par le coffre Service Middleware.
- Fichier `upload` doit vérifier l'accès à l'unité cible, tandis que `signUrl` et `download` vérifient l'accès en lecture.
- Échangez `import` et `export` sont l'endroit approprié pour les contrôles des quotas et pour les contrôles d'accès à l'unité source; la création de l'unité importée et la lecture de l'Unité exportée passent toujours par le Middleware de service de base.

Les règles installées sur le service de collaboration de base ne protègent pas automatiquement ces modules. Le même service de politique d'application devrait être réutilisé plutôt qu'un modèle de données ACL séparé construit pour chaque extension.

## Définir l’utilisateur courant côté client

`UserManagerService.setCurrentUser()` définit l'identifiant utilisateur, le nom et l'avatar pour l'instance Univer actuelle, et les composants frontend lisent ces valeurs à partir de là. Le filtre --Concern me-- du panneau de commentaires, par exemple, utilise cet identifiant utilisateur pour afficher les commentaires qui impliquent l'utilisateur courant.

Appelez-le après la création de l'instance Univer et avant que le document ne soit chargé :

```ts
import { UserManagerService } from "@univerjs/core";

// currentUser is your application profile; id/name/avatar are example field names.
univer
  .__getInjector()
  .get(UserManagerService)
  .setCurrentUser({
    userID: currentUser.id,
    name: currentUser.name,
    avatar: currentUser.avatar ?? "",
  });
```

Cartez l'identifiant utilisateur stable de l'application sur `userID` et gardez-le identique à celui authentifié `context.userID` sur le serveur. Les noms de membres et les avatars partagés pendant la collaboration sont définis dans le Middleware `connect` du serveur, comme décrit dans [Présence](/server/collaboration/presence).

La [Exemple de permissions](/server/collaboration/examples#permissions) est la version d'exécution complète.
