title: 协同扩展模块
description: 理解 History、Thread Comment、Worktree、File 与服务端 Office Exchange 如何扩展核心协同服务。
---

History、Thread Comment、File 与 Worktree 是可选的协同扩展模块，可以在不修改核心的前提下扩展协同能力。每个模块都提供自己的 Service、Middleware、Event、Database Adapter 和生命周期边界，应用可以只启用产品需要的模块。这些模块仍然可以共用 Transport、身份系统和同一个物理数据库。

服务端 Office Exchange 建立在 File 与 Collaboration Service 之上。它负责在 Office 文件和协同 Unit 之间相互转换，并拥有自己的 Service、Endpoint 与 Middleware。

| 扩展模块        | 与 Core Collaboration 的关系                                       |
| --------------- | ------------------------------------------------------------------ |
| History         | 监听 Core Event，生成一份派生的历史索引                            |
| Thread Comment  | 复用 Core Unit Room；评论 anchor 仍属于 Core 内容                  |
| File            | 保存 Unit 引用的图片、附件和导入导出文件，Unit 数据只记录文件 ID   |
| Office Exchange | 通过 Core Service 创建或读取 Unit，通过 File 读写文件              |
| Worktree        | 复用 Core 的 Unit 与 OT 能力，把 draft 合入 trunk                  |

History、Thread Comment、File 与 Worktree 各自配置自己的 Middleware、Event 和 Database Adapter。

## 版本历史

History 将 Unit 创建和 confirmed changeset 整理为用户可见的历史条目。历史索引是派生数据：Unit 内容的权威来源始终是 Core Collaboration Service 中已确认的 changeset。

```ts
const historyService = new UniverHistoryService({
  collabService,
  dbAdapter: historyDatabase,
  userProvider,
});

transport.register(new UniverHistoryEndpoint(historyService));
```

构造函数会订阅 Core Service 的 `unitCreated` 和 `changesetCommitted` Event 并据此更新索引，`dispose()` 负责解除这些订阅。默认策略按时间窗口和特殊 mutation 归组，不会为每条 changeset 都生成历史条目。

History 提供 `getHistoryList`、`listHistoryCreators` 和 `getHistoryChangesets` 三个读取 Middleware，索引工作在 Service 内部完成。`userProvider` 只补全姓名、头像这类展示信息，既不参与认证，也不参与授权。Event Listener 出错不会回滚已经确认的 Core changeset，因此 History 应视为可以随时重建的派生数据。

## Thread Comment

Comment Service 管理评论正文、回复、编辑、删除和解决状态。

```ts
const commentService = new UniverCommentService({
  database: commentDatabase,
  userProvider,
});

transport.register(
  new UniverCommentEndpoint({
    service: commentService,
    roomHost: collabEndpoint,
  }),
);
```

评论正文属于 Comment Adapter，随 Sheet 或 Doc 内容移动的 anchor 仍然属于 Core snapshot 和 changeset。Comment Endpoint 可以通过主 Collaboration Endpoint 的 Unit Room 发布 `comment_update`，但这条实时消息不是评论状态的权威来源；Client 错过该消息后重新获取评论列表即可恢复。

Comment Service 提供 add、list、reply、solve/reopen、edit 和 delete 的 Middleware，并发布一个 `commentCommitted` Event。Comment Service 不继承 Core Service 的读取策略或编辑策略。

## 文件存储

File 保存 Univer 客户端上传的二进制文件，包括插入 Unit 的图片和附件，以及导入导出的源文件和结果文件。Unit 数据只记录文件 ID，客户端在加载 Unit 时用该 ID 换取下载地址，因此 snapshot 和 changeset 保持较小的体积。

```ts
const fileService = new UniverFileService({
  database: fileDatabase,
  blobStore,
});

transport.register(new UniverFileEndpoint(fileService));
```

元数据和内容是两套独立的合同：`IFileDatabaseAdapter` 存储文件记录，`IFileBlobStore` 存储内容。导入导出的临时文件只有上传者本人可以访问，由 Service 定期清理。Unit 内的图片和附件受 Unit 权限控制，由 `upload`、`signUrl`、`download` 三个 Middleware 执行校验。

## 服务端 Office Exchange

Exchange Service 将 Office 文件导入为协同 Unit，也将 Unit 导出为文件。转换由 `@univerjs-pro/exchange-node` 完成，Unit 的创建和读取通过 Collaboration Service 进行，源文件和结果文件通过 File Service 存储：

```ts
const exchangeService = new UniverExchangeService({ collabService, fileService });

transport.register(new UniverExchangeEndpoint(exchangeService));
```

导入和导出都是 task：客户端先创建 task，再轮询结果。导入经过 Core Service 的 `createUnit` Middleware，导出经过 `readUnitData`；Exchange 自己的 `import` 和 `export` Middleware 负责限流、配额和审计。

| Unit  | 导入                | 导出           |
| ----- | ------------------- | -------------- |
| Sheet | xls、xlsx、csv、tsv | xlsx、csv、tsv |
| Doc   | doc、docx           | docx           |
| Slide | ppt、pptx           | pptx           |
| Base  | xls、xlsx、csv、tsv | xlsx、csv      |
| PDF   | pdf                 | pdf            |

## Worktree 草稿与合并

Worktree 为一个或多个 Unit 提供隔离的 draft、冻结、合入评估和逐 Unit 合并：

```text
create → draft → ready → merging → merged
           ↑       │
           └ reopen┘

draft / ready → discarded
```

```ts
const worktreeService = new UniverCollabWorktreeService({
  trunk: {
    service: collabService,
    dbAdapter: coreDatabase,
  },
  dbAdapter: worktreeDatabase,
});
```

Worktree 按 `(worktreeID, unitID)` 保存自己的 draft changeset，同时复用 Core Service 的 Unit、OT 和提交引擎。只有 `draft` 状态可以继续编辑。`markReady()` 冻结当前的 draft revision，`mergeWorktree()` 将 Unit 逐个合入 trunk。

Worktree Service 拥有独立的生命周期、读取 Middleware 和 draft submit/apply/commit Middleware，以及创建、状态变化、合入结果和 draft changeset 提交这几类 Event。最终写入 trunk 时，仍然经过 Core Service 自己的 Middleware。

多个 Unit 一起合并时，跨 Unit 不具备原子性。应用应展示每个 Unit 的合入结果。

## 独立扩展点

启用扩展模块时，每一项边界都需要单独评估：

| 边界             | Core           | History         | Comment            | File                       | Worktree                  |
| ---------------- | -------------- | --------------- | ------------------ | -------------------------- | ------------------------- |
| Service          | 独立           | 独立            | 独立               | 独立                       | 独立                      |
| Middleware       | 不共享         | 不继承 Core     | 不继承 Core        | 不继承 Core                | 不继承 Core               |
| Event            | Core lifecycle | 监听 Core Event | `commentCommitted` | —                          | Worktree lifecycle/commit |
| Database Adapter | Core Adapter   | History Adapter | Comment Adapter    | File Adapter 与 Blob Store | Worktree Adapter          |

Office Exchange 复用 Core 与 File 的存储。在 Exchange 自己的 `import`、`export` Middleware 执行之后，导入导出仍然经过 Core 与 File 的 Middleware。

这些 Adapter 可以共用同一个数据库，但仍然各自是独立的对象，拥有独立的合同。Service 和 Adapter 也应分别释放。

## 选择能力

| 产品需求               | 模块                                        | 首个示例                    |
| ---------------------- | ------------------------------------------- | --------------------------- |
| 面向用户的版本历史     | History Service、Endpoint、Adapter          | `pnpm example:history`      |
| Sheet 或 Doc 批注      | Comment Service、Endpoint、Adapter          | `pnpm example:comments`     |
| 图片、附件与文件存储   | File Service、Endpoint、Adapter、Blob Store | `pnpm example:file-service` |
| 服务端 Office 导入导出 | Exchange Service、Endpoint + File           | `pnpm example:exchange`     |
| 隔离草稿、评审与合并   | Worktree Service、Endpoint、Client、Adapter | `pnpm example:worktree`     |

完整的运行命令和页面地址见[示例索引](/server/collaboration/examples)。

## 连接 Web SDK 历史界面 [#web-history]

将 History Endpoint 与协同端点一同挂载。Web SDK 的 `historyServerUrl` 是 `/{unitId}/list`、`/{unitId}/creators` 和 `/{unitId}/cs` 的共同前缀，默认值为 `/universer-api/history`。如果使用其他前缀，宿主 History 插件与品类 History UI 插件必须配置相同的地址。

恢复版本通过协同 mutation 路径完成，没有单独的历史恢复 REST 接口。协同的加载、提交与授权配置必须保持可用。使用 `createUnitComparisonEngine()` 比较两份完整快照是另一项独立操作，该操作只读，不需要历史服务运行，也不负责保存或恢复版本。
