We tested multiple editors in one document and simultaneous edits across many documents. After warming up the documents, we measured acknowledgment latency, throughput, completion rate, and the collaboration process's CPU and memory usage.

## Test environment

The collaboration service and PostgreSQL ran on separate servers. Node sizes in the results refer to the collaboration node in the diagram.

PostgreSQL stores document records, changesets, snapshot records, and block references. OSS stores snapshot cell-data blocks.

All measurements are for a single collaboration node. When concurrent documents exceed its capacity, additional nodes can handle edits to different documents. They share a database and use pub/sub to synchronize rooms, presence, and edit broadcasts. See [Multiple collaboration nodes](/server/deployment#multiple-collaboration-nodes).

### Collaboration service configuration

On both node sizes, we raised `runtime.maxLoadedUnits` from 1,200 to 4,000 so the node could keep up to 4,000 documents in memory. Other SDK runtime settings used their defaults, including automatic worker selection. The default snapshot policy triggers after 50 revisions since the last successful snapshot or when a single changeset reaches 5 MiB. The collaboration process had a memory limit of 14 GiB on the 4-core node and 29 GiB on the 8-core node.

The benchmark service uses an initialized PostgreSQL pool and OSS client. The transport attaches to the Node.js HTTP server.

```ts
const dbAdapter = await PostgresS3DatabaseAdapter.create({
  pool,
  s3: { client, bucket, prefix },
});
const service = new UniverCollabService({
  dbAdapter,
  runtime: { maxLoadedUnits: 4000 },
});
const endpoint = new UniverCollabEndpoint(service);
const transport = createNodeTransport();
transport.register(endpoint);
transport.attach(server);
```

## Method

### Simulated clients

Each editor in the results is an independent session. Each session joins one document, submits a cell edit over HTTP, and receives the acknowledgment over WebSocket. The scripts call the collaboration API directly. Both the HTTP request and the wait for acknowledgment have a 10-second timeout.

### Warm-up and sampling

Each run creates documents from the selected snapshot. Warm-up starts once all sessions have joined. The first edit loads the document on the server. A single document receives one warm-up edit. In multi-document runs, documents receive different numbers of warm-up edits, which staggers their starting revisions and snapshot writes.

Sampling starts after all documents have warmed up. Submission counts, latency percentiles, CPU, and memory in the tables come from the sampling period.

### Edit workload

For the single-document test we increased the number of editors on `blank`. For each of the three snapshots we also increased the number of active documents. Each submission contains one `sheet.mutation.set-range-values` operation that writes a number to one cell.

| Condition | One document | Multiple documents |
| --- | --- | --- |
| Editors per document | Varies by run (see results) | Two in every run |
| Edit operation | Staggered writes to each editor's own cell | Staggered writes to each editor's own cell |
| Frequency per editor | Once every 6 seconds | Once every 2 seconds |
| Sampling period per run | 300 seconds | 300 seconds |

## Metrics

| Metric | Definition |
| --- | --- |
| Acknowledgment latency | Time from sending an edit until the same client receives the server acknowledgment. P50, P95, and P99 are the times within which 50%, 95%, and 99% of successful submissions were acknowledged. Max is the longest successful acknowledgment time. |
| Throughput | Successful submissions divided by sampling time, in submissions per second. |
| Completion rate | Successful submissions as a percentage of all planned submissions, including failed and unsent ones. |
| CPU mean / peak (%) | Mean and highest sampled CPU usage of the collaboration process. One fully utilized core counts as 100%, so totals can exceed 100%. |
| Peak memory (MiB) | Highest sampled resident set size (RSS) of the collaboration process. |

### Pass criteria

A run passes only if all of the following hold:

- Acknowledgment latency **P99 < 1,000 ms**.
- Completion rate **> 90%**.
- The collaboration process stays up until every test document passes the consistency check.
- Snapshot processing keeps up with writes during the sampling period, so pending snapshot tasks do not keep growing. Continued growth is reported as a sustained snapshot backlog.

A load level tested once uses that run's result. A level tested multiple times passes only if every run passes.

## Interpreting the results

Node.js scripts simulate editing sessions and send cell changes directly to the API. Acknowledgment latency measures the round trip from the script to the server. It excludes browser interaction and spreadsheet rendering.

Use these measurements for performance assessment and single-node capacity planning. Performance depends on deployment, network conditions, document size, and edit type and frequency.

A load level is one load value under a given set of test conditions: the editor count or the number of active documents. The highest passing level is the largest tested level that met the criteria. Mean CPU usage approached node capacity at some passing levels. **Treat these levels as capacity-planning references, not sustained production targets.** Leave headroom for concurrency spikes and resource fluctuations, and validate sustained capacity with representative workloads in the target environment.

#### Sizing node pools

In a [multi-node deployment](/server/deployment), the gateway can route documents by size to separate pools. These single-node estimates assume two editors per document, each editing once every two seconds.

- **For small and medium documents, evaluate 4 cores and 8 GiB first.** Estimated from the 4-core/16-GiB results, the 8-GiB memory budget fits 2,300 blank documents or 1,800 documents with about 10,000 populated cells each.
- **For large documents, evaluate 8 cores with 16 or 32 GiB.** With about 100,000 populated cells per document, the highest passing level on 8 cores / 32 GiB was 700 documents, and its peak memory fits the 16-GiB budget. Snapshot processing is the limiting factor here: at 750 documents, acknowledgment latency still passed, but a sustained snapshot backlog developed.
