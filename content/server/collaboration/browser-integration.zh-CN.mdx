协同把浏览器中的编辑器连接到同一个共享的文档服务。两位用户打开同一份表格时，一端的修改会出现在另一端的浏览器中。

先按[服务端集成](/server)完成后端配置，再做下文的编辑器配置与文档加载。[协同快速开始](/server/collaboration/quick-start)中给出了配套的 Server 与 Web 代码。

## 连接已有编辑器

无需更换编辑器。保留现有的 Web SDK 编辑器，按[快速开始中的前端配置](/server/collaboration/quick-start)添加协同插件，再配置文档加载、修改提交和 WebSocket 地址。前端与后端的包版本必须保持兼容。

示例中的固定用户和默认权限仅用于演示。正式接入时，每个请求都需要携带应用的登录信息，由后端确认用户身份和文档访问权限。许可证配置见[使用许可证](/server/license)。

## 插件配置 [#client-configuration]

### 批量发送与重试超时 [#client-retry-timeouts]

`UniverCollaborationClientPlugin`

| <span data-config-options="">配置项</span> | 类型 | 默认值 | 作用 |
| --- | --- | --- | --- |
| `socketService` | `Ctor<ICollaborationSocketService>` |  | 指定当前运行环境使用的 Socket 实现。 |
| `sendChangesetTimeout` | `number` | `2000 ms` | 本地修改在发送前的合并缓冲时长。 |
| `changesetAckTimeout` | `number` | `20000 ms` | 等待服务端确认的时长，超时后重发。 |
| `maxChangesetAckTimeout` | `number` | `120000 ms` | 两次重发之间的最长间隔。 |

合并发送延迟与确认超时是两个不同的计时器。客户端插件默认使用 `sendChangesetTimeout: 2000`、`changesetAckTimeout: 20000` 和 `maxChangesetAckTimeout: 120000`，单位均为毫秒。提交请求同样使用确认超时。始终未获确认的修改会按指数退避重发，间隔不超过最大值。确认超时与最大超时取相同值时，重发间隔固定。

```ts
import { UniverCollaborationClientPlugin } from '@univerjs-pro/collaboration-client'
import { BrowserCollaborationSocketService } from '@univerjs-pro/collaboration-client-ui'

univer.registerPlugin(UniverCollaborationClientPlugin, {
  socketService: BrowserCollaborationSocketService,
  sendChangesetTimeout: 200,
  changesetAckTimeout: 20_000,
  maxChangesetAckTimeout: 120_000,
})
```

将这些选项并入现有的客户端注册，socket 与接口地址的配置保持不变。Sheets 和 Docs 的协同预设使用 200 ms 的合并发送延迟，并且未提供确认超时选项，因此自定义这些超时需要改用插件模式。

### 冲突恢复提示 [#client-conflict-notices]

`UniverCollaborationClientUIPlugin`

| <span data-config-options="">配置项</span> | 类型 | 默认值 | 作用 |
| --- | --- | --- | --- |
| `enableDefaultConflictUI` | `boolean` | `true` | 显示内置的冲突恢复提示。 |

```ts
import { UniverCollaborationClientUIPlugin } from '@univerjs-pro/collaboration-client-ui'

univer.registerPlugin(UniverCollaborationClientUIPlugin, { enableDefaultConflictUI: false })
```

## 预设配置 [#client-preset-configuration]

`UniverSheetsCollaborationPreset / UniverDocsCollaborationPreset`

| <span data-config-options="">配置项</span> | 类型 | 默认值 | 作用 |
| --- | --- | --- | --- |
| `enableDefaultConflictUI` | `boolean` | `true` | 显示内置的冲突恢复提示。 |

```ts
import { UniverSheetsCollaborationPreset } from '@univerjs/preset-sheets-collaboration'

const collaborationPreset = UniverSheetsCollaborationPreset({ enableDefaultConflictUI: false })
```

```ts
import { UniverDocsCollaborationPreset } from '@univerjs/preset-docs-collaboration'

const collaborationPreset = UniverDocsCollaborationPreset({ enableDefaultConflictUI: false })
```

默认情况下，UI 会显示一条注明冲突原因的提示：缓存清理成功后提供刷新，清理失败时提供重试。如果恢复流程由应用自行实现，在现有初始化中设置 `enableDefaultConflictUI: false`，并直接处理事件。

把协同预设加入现有的 `createUniver({ presets: [...] })` 配置，与编辑器预设放在一起，接口地址与历史记录的配置保持不变。事件参数见[冲突恢复事件](#conflict-recovery)，客户端插件的可选配置见[客户端插件配置](/reference/packages/plugins/univerjs-pro/collaboration-client)。

## 创建和打开同一份文档

新建文档与打开文档是两个不同的动作：

1. 用户新建文档时，业务后端负责保存，并把文档 ID 返回给前端。
2. 前端使用该 ID 加载文档。再次打开文档或分享给他人时，仍使用同一个 ID。

API 把文档 ID 称为 `unitId`。不要每次访问都新建一个本地空白文档。

先设置当前用户，再加载文档。当前用户决定协同身份，也是本地离线缓存的归属者，详见[身份与权限](/server/collaboration/identity-and-authorization)。

例如，Sheets 和协同插件都注册完成之后，可从服务端加载表格：

```ts
import { UserManagerService } from '@univerjs/core'
import '@univerjs-pro/collaboration-client/facade'

univer.__getInjector().get(UserManagerService).setCurrentUser({ userID, name, avatar })

const workbook = await univerAPI.getCollaboration().loadSheetAsync('your-document-id')
if (!workbook) throw new Error('Document could not be loaded')
```

各产品的加载方式见 [Sheets](/guides/sheets/features/collaboration)、[Docs](/guides/docs/features/collaboration)、[Slides](/guides/slides/features/collaboration)、[Boards](/guides/boards/features/collaboration)、[Bases](/guides/bases/features/collaboration) 和 [PDFs](/guides/pdfs/features/collaboration) 指南。使用前请确认目标产品与后端版本支持该能力。

## 验证同步、保存和权限

用两个相互独立的浏览器会话打开同一份文档，例如一个普通窗口和一个无痕窗口。在一端修改，观察另一端的显示结果。随后刷新页面、断开重连、重启服务，确认内容仍然存在。

分别以编辑者、查看者和无权限用户的身份进行测试。前端的只读设置只限制页面允许的操作，服务端仍须拒绝未授权的读取和修改。

文档能打开但修改不同步时，检查 WebSocket 连接；重启后内容丢失时，检查后端存储。这些配置属于[服务端集成](/server)。

## 添加导入导出、评论或历史记录

要让多人共同编辑导入的文件，需要使用转换后的数据创建协同文档，见[导入导出集成](/server/import-export)。评论和历史记录各自需要插件、服务端和权限，按 [Office 协同扩展模块](/server/collaboration/extensions)接入。

历史面板的配置按产品区分：[Sheets](/guides/sheets/features/edit-history)、[Docs](/guides/docs/features/edit-history)、[Slides](/guides/slides/features/edit-history)、[Boards](/guides/boards/features/edit-history)、[Bases](/guides/bases/features/edit-history)。PDFs 目前支持到什么程度见[历史记录说明](/guides/pdfs/features/edit-history)。

## 同步状态与重发 [#sync-status]

先导入协同 Facade，再注册监听。注册监听时，`CollaborationStatusChanged` 会先为每个已处于协同状态的文档报告当前状态，之后只报告状态变化，不会连续重复相同的状态。`hasWritePending(unitId)` 涵盖排队中的修改、等待确认的修改和离线修改；不传 ID 时检查当前聚焦的文档。WebSocket 已连接并不表示修改已经保存。

```ts
import '@univerjs-pro/collaboration-client/facade'

const collaboration = univerAPI.getCollaboration()
const statusSubscription = univerAPI.addEvent(univerAPI.Event.CollaborationStatusChanged, (event) => {
  console.info(event.unitId, event.status, collaboration.hasWritePending(event.unitId))
})
const resendSubscription = univerAPI.addEvent(univerAPI.Event.CollaborationChangesetResend, (event) => {
  console.info(event.unitId, event.reason, event.attempt, event.unsyncedMutationCount, event.nextDelayMs)
})
```

`CollaborationChangesetResend` 仅在重发时触发，首次提交不触发。原因包括 `ack_timeout`、`request_failed`、`license_editing_connections_exceeded`、`should_retry` 和 `reconnect`；`attempt`、`elapsedMs`、`unsyncedMutationCount` 和 `nextDelayMs` 为构建保存中或重试中的提示提供所需数据。移除编辑器时释放事件订阅。

`request_failed` 表示可重试的请求失败，例如网络错误，或 HTTP 408、429、5xx 响应。`license_editing_connections_exceeded` 表示授权允许的编辑连接已全部占用，服务端要求重发。

## 由应用处理冲突 [#conflict-recovery]

文档进入冲突后，`CollaborationConflict` 会在尝试清理离线缓存之后触发一次。监听器必须在加载任何文档之前注册。其 `reason` 为 `transform_failed`、`apply_failed`、`changeset_rejected`、`license_unit_type_rejected`、`permission_rejected` 或 `remote_revert`；`message` 和 `revert` 在有数据时提供补充信息。

`license_unit_type_rejected` 表示服务端许可证不覆盖该文档类型的协同。

```ts
import type { IEventParamConfig } from '@univerjs/core/facade'
import '@univerjs-pro/collaboration-client/facade'

const conflicts = new Map<string, IEventParamConfig['CollaborationConflict']>()
const conflictSubscription = univerAPI.addEvent(univerAPI.Event.CollaborationConflict, (event) => {
  conflicts.set(event.unitId, event)
})
```

示例保留该事件，供应用的恢复界面使用。该 Map 仅存在于内存中，因此在刷新之前，应用必须保存或导出所有 `localChanges`。该事件是留存这些修改的唯一机会，已清理的缓存数据无法通过后续读取恢复。`awaitingChangeset` 可能已在服务端应用，因此不要直接重放。

`cacheCleared: false` 表示刷新会重放旧的缓存修改，因此需要先完成缓存清理再刷新。清理缓存并不意味着未同步的修改已经保存。`permission_rejected` 冲突还需要解决权限问题，刷新不会授予权限。

## 服务端原因与许可证提示 [#server-rejections]

服务端拒绝修改时，如果服务端给出了原因，`CollaborationConflict.message` 会携带该原因。不要解析本地化文案来决定恢复动作，应依据 `reason` 分支处理。`license_unit_type_rejected` 需要一份覆盖该文档类型的服务端许可证；`license_editing_connections_exceeded` 是重发信号：修改仍未确认，并会继续重试。在 `hasWritePending(unitId)` 变为 false 或应用已留存这些修改之前，请保持编辑器打开。

默认 UI 会显示编辑连接容量提示；如果重发发生在首次发送之后至少 20 秒，还会显示保存超时提示。文档离开等待状态或被销毁时，这些提示会被移除。域名被拒绝时也有单独的提示。`enableDefaultConflictUI: false` 只关闭冲突恢复提示，不会关闭上述等待提示和域名提示。
