コラボレーションは、ブラウザエディタを1つの共有文書サービスに接続します。 2人のユーザーが同じスプレッドシートを開くと、別のブラウザで編集が表示されるようになります。

[サーバ統合](/server) で最初にバックエンドを設定します。 エディタの設定とドキュメントの読み込みは、以下の通りです。 ペアリングされたサーバーと Web コードは [コラボレーションクイックスタート](/server/collaboration/quick-start). にあります。

## 既存エディターへの接続

異なるエディタは必要ありません。 既存のWeb SDKエディタを保持し、[クイックスタートのブラウザ設定](/server/collaboration/quick-start)をフォローしてコラボレーションプラグインを追加し、ドキュメントの読み込み、送信の編集、WebSocketアドレスを設定します。 ブラウザとサーバーパッケージのバージョンは互換性がありません。

固定例のユーザーとデフォルト権限は、デモンストレーション用に意図されています。アプリケーションでは、各リクエストでログイン認証情報を送信して、バックエンドはアイデンティティとドキュメントアクセスを検証できます。ライセンスは[ライセンス構成](/server/license)で覆われています。

## プラグイン設定 [#client-configuration]

### 一括送信と再試行のタイムアウト [#client-retry-timeouts]

`UniverCollaborationClientPlugin`

| <span data-config-options="">オプション</span> | 型 | 既定値 | 動作 |
| --- | --- | --- | --- |
| `socketService` | `Ctor<ICollaborationSocketService>` |  | 現在のランタイムで使用されるソケットの実装を選択します。 |
| `sendChangesetTimeout` | `number` | `2000 ms` | 送信される前に、ローカル編集がバッファされる時間を設定します。 |
| `changesetAckTimeout` | `number` | `20000 ms` | 再試行する前に、受諾を待つ時間を設定します。 |
| `maxChangesetAckTimeout` | `number` | `120000 ms` | 再送間隔の上の境界を設定します。 |

バッチ処理遅延と承認タイムアウトは、別のタイマーです。クライアントプラグインのデフォルトは、`sendChangesetTimeout: 2000`、`changesetAckTimeout: 20000`および`maxChangesetAckTimeout: 120000`に、ミリ秒単位ですべて。送信リクエストは、承認タイムアウトも使用されます。承認されていない変更セットは、最大でキャプチャされた、指数関数的なバックオフで再送信されます。承認タイムアウトと、同じ値への最大タイムアウトを設定すると、一定の間隔が生成されます。

```ts
import { UniverCollaborationClientPlugin } from '@univerjs-pro/collaboration-client'
import { BrowserCollaborationSocketService } from '@univerjs-pro/collaboration-client-ui'

univer.registerPlugin(UniverCollaborationClientPlugin, {
  socketService: BrowserCollaborationSocketService,
  sendChangesetTimeout: 200,
  changesetAckTimeout: 20_000,
  maxChangesetAckTimeout: 120_000,
})
```

これらのオプションを既存のクライアント登録に追加し、ソケットとエンドポイントの設定を維持します。 シートとDocsのコラボレーションプリセットは、200 msのバッチ遅延を使用し、承認のタイムアウトオプションを露出させないため、これらのタイムアウトをカスタマイズするにはプラグインモードが必要です。

## プリセット設定 [#client-preset-configuration]

`UniverSheetsCollaborationPreset / UniverDocsCollaborationPreset`

| <span data-config-options="">オプション</span> | 型 | 既定値 | 動作 |
| --- | --- | --- | --- |
| `enableDefaultConflictUI` | `boolean` | `true` | ビルトインの衝突回復通知を表示します。 |

```ts
import { UniverSheetsCollaborationPreset } from '@univerjs/preset-sheets-collaboration'

const collaborationPreset = UniverSheetsCollaborationPreset({ enableDefaultConflictUI: false })
```

```ts
import { UniverDocsCollaborationPreset } from '@univerjs/preset-docs-collaboration'

const collaborationPreset = UniverDocsCollaborationPreset({ enableDefaultConflictUI: false })
```

デフォルトでは、UI は、理由を名前付ける矛盾した通知を示しています。 キャッシュクリーンアップが成功した後に通知が再ロードされ、クリーンアップが失敗した場合に再試行されます。 アプリケーション内の回復フローを実行するには、既存の初期化で `enableDefaultConflictUI: false` を設定し、イベントを直接処理します。

エディタプリセットの横にある既存の`createUniver({ presets: [...] })`呼び出しにコラボレーションプリセットを追加し、エンドポイントと履歴設定を維持します。 [イベントのペイロード](#conflict-recovery)と[クライアント構成](/reference/packages/plugins/univerjs-pro/collaboration-client)を参照してください。

## 同じドキュメントの作成と表示

ドキュメントの作成と開口部の操作は、別のアクションです。

1. ユーザーがドキュメントを作成するとき、バックエンドはそれを保存し、IDを返します。
2. ブラウザはIDをロードします。ドキュメントが再オープンまたは別のユーザーと共有されると、同じIDを再利用します。

ドキュメント ID `unitId` という名前の API です。 訪問ごとに新しいローカル空白のドキュメントを作成しないでください。

文書を読み込む前に現在のユーザーを設定してください。現在のユーザーは共同編集の身元とローカルのオフラインキャッシュの所有者を決めます。設定方法は[本人確認と認可](/server/collaboration/identity-and-authorization)を参照してください。

たとえば、スプレッドシートとコラボレーションプラグインを登録した後、サーバーからスプレッドシートをロードします。

```ts
import { UserManagerService } from '@univerjs/core'
import '@univerjs-pro/collaboration-client/facade'

univer.__getInjector().get(UserManagerService).setCurrentUser({ userID, name, avatar })

const workbook = await univerAPI.getCollaboration().loadSheetAsync('your-document-id')
if (!workbook) throw new Error('Document could not be loaded')
```

[シート](/guides/sheets/features/collaboration)、[ドキュメント](/guides/docs/features/collaboration)の[スライド](/guides/slides/features/collaboration)は、[ボード](/guides/boards/features/collaboration), [ベース](/guides/bases/features/collaboration)および[PDFファイル](/guides/pdfs/features/collaboration)ガイドで製品固有のロードが覆われています。 対象製品とバックエンドリリースが機能をサポートしていることを確認してください。

## 同期、保存、権限の検証

通常のウィンドウやプライベートなウィンドウなど、2つの独立したブラウザセッションで同じドキュメントを開きます。 1つのセッションで編集し、他のショーをチェックします。 その後、ページを再読み込み、サーバーを再接続し、サーバーを再起動し、コンテンツがまだ存在することを確認します。

エディタ、ビューア、およびアクセスなしのユーザーとしてテストします。 読み取り専用UI設定は、ページが許可するものだけを制御します。 サーバーは、許可されていない読み取りと変更を拒否する必要があります。

ドキュメントが読み込まれるが編集が同期しない場合は、WebSocket接続を確認してください。 コンテンツが再起動後に消えた場合、バックエンドストレージを確認します。 これらの設定は[サーバ統合](/server)に属しています。

## ファイル交換、コメント、履歴の追加

インポートしたファイルを共同編集するには、変換されたデータから共同ドキュメントを作成します。 [ファイル交換統合](/server/import-export) を参照してください。コメントと履歴は、それぞれ独自のプラグイン、サービス、および権限を必要とします。 [オフィス拡張モジュール](/server/collaboration/extensions)に従ってください。

## 同期状態と再送 [#sync-status]

リスナーを登録する前にコラボレーションファサードをインポートします。 `CollaborationStatusChanged`は、リスナーが登録されると既にすべてのユニットの現在のステータスを報告し、連続した同一の状態を繰り返すことなく変更を報告します。 `hasWritePending(unitId)` は、キュートな編集、待望の承認を編集し、オフラインで編集します。 ID が省略されている場合は、集中したユニットをチェックします。 接続されたソケットは、編集が保存されるという意味ではありません。

```ts
import '@univerjs-pro/collaboration-client/facade'

const collaboration = univerAPI.getCollaboration()
const statusSubscription = univerAPI.addEvent(univerAPI.Event.CollaborationStatusChanged, (event) => {
  console.info(event.unitId, event.status, collaboration.hasWritePending(event.unitId))
})
const resendSubscription = univerAPI.addEvent(univerAPI.Event.CollaborationChangesetResend, (event) => {
  console.info(event.unitId, event.reason, event.attempt, event.unsyncedMutationCount, event.nextDelayMs)
})
```

`CollaborationChangesetResend` 最初の投稿ではなく、再送の火災。 理由は `ack_timeout`, `request_failed`, `license_editing_connections_exceeded`, `should_retry`, と `reconnect`; `attempt`, `elapsedMs`, `unsyncedMutationCount`, と `nextDelayMs` 保存または再試行インジケータに必要なデータを提供します。 エディタが削除されたときにイベントのサブスクリプションを無効にします。

`request_failed`は、ネットワークエラーやHTTP 408、429、または5xx応答などの再試行可能なリクエストの失敗を意味します。 `license_editing_connections_exceeded` は、ライセンスされた編集接続がすべて使用中であり、サーバーは再送を要求したことを意味します。

## アプリケーションで競合を処理 [#conflict-recovery]

`CollaborationConflict` ユニットが衝突するときに一度火災, オフラインキャッシュクリーンアップの試みの後. 任意の文書をロードする前に、リスナーを登録. その `reason` です。 `transform_failed`, `apply_failed`, `changeset_rejected`, `license_unit_type_rejected`, `permission_rejected`, または `remote_revert`; `message` そして、 `revert` 利用できるとき付加的な細部を提供して下さい。

`license_unit_type_rejected` は、サーバーのライセンスがこの文書タイプの共同編集に対応していないことを示します。

```ts
import type { IEventParamConfig } from '@univerjs/core/facade'
import '@univerjs-pro/collaboration-client/facade'

const conflicts = new Map<string, IEventParamConfig['CollaborationConflict']>()
const conflictSubscription = univerAPI.addEvent(univerAPI.Event.CollaborationConflict, (event) => {
  conflicts.set(event.unitId, event)
})
```

たとえば、ホストリカバリ画面でイベントを保持します。マップはメモリにのみ住んでいます。そのため、アプリケーションはリフレッシュする前に、`localChanges`を保存またはエクスポートする必要があります。このイベントは、それらを保持する唯一の機会です。すでにクリアされたキャッシュデータが後で読むことで復元できません。`awaitingChangeset`は、既にサーバーに適用されている可能性があるため、ブラインドに再生されるべきではありません。

`cacheCleared: false` は、リフレッシュが古いキャッシュされた編集を再生することを意味します。そのため、キャッシュのクリーンアップは、さわやかな前に解決する必要があります。キャッシュをクリアすると、非同期の編集が保存されたという意味ではありません。 `permission_rejected` コンフリクトは、アクセスを解決する必要があります。リロードは許可を与えません。

## サーバーの拒否理由とライセンス通知 [#server-rejections]

サーバが変更を拒否した場合、`CollaborationConflict.message` はサーバーが与えられた理由を運ぶ。もしそれが1つを与えた場合。 回復アクションを決定するためにローカライズされたメッセージテキストを解析しないでください。 代わりに`reason`のブランチ。 `license_unit_type_rejected`は、ドキュメントタイプをカバーするサーバーライセンスを必要としますが、`license_editing_connections_exceeded` は再送信信号です。 編集は未承認のままであり、再試行を維持します。 編集者は`hasWritePending(unitId)`が偽りになるまで開いて、またはアプリケーションは編集を保持しています。

デフォルトの UI は編集容量通知を表示し、最初の送信後少なくとも 20 秒後に再送信すると、保存タイムアウト通知を表示します。 これらは、ユニットが待ち受けた状態を離れるか、または処分されるときに削除されます。 ドメイン拒否は、専用の通知を持っています。 `enableDefaultConflictUI: false` は、競合の回復通知のみを無効にします。 これらの待機またはドメイン通知を無効にしません。
