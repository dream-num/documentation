Middleware 与 Event 是 Collaboration SDK 的通用扩展点。身份与权限通过 Middleware 接入。操作执行前需要校验或限制时使用 Middleware，状态确认后需要记录变化或触发后续处理时使用 Event。两者都可用于日志、请求追踪、指标采集和派生数据更新。

## 两种不同的扩展时机

|                      | Middleware                       | Event                            |
| -------------------- | -------------------------------- | -------------------------------- |
| 运行时机             | 一次操作执行过程中               | 状态变化确认之后                 |
| 能否参与或拒绝操作   | 可以                             | 不可以                           |
| 能否补充调用 Context | 可以                             | 读取 Event 携带的 Context 和结果 |
| Listener 失败        | 可能使当前操作失败               | 被隔离，不改变已经确定的领域结果 |
| 典型用途             | 身份、权限、业务校验、日志、计时 | 派生索引、缓存、指标、进程内通知 |

判断方式如下：需要决定操作能否继续时使用 Middleware；只需确认某个状态变化已经发生时使用 Event。

## Middleware 执行模型

同一个 Action 的 Middleware 按注册顺序组成异步链。`await next()` 进入下一个 Middleware，SDK 操作在最内层执行：

```ts
service.use("submitChangeset", async (context, next) => {
  const startedAt = performance.now();
  context.customData.startedAt = startedAt;

  try {
    await next();
  } finally {
    metrics.observe("collaboration.submit.duration", performance.now() - startedAt);
  }
});
```

Middleware 可以读取该 Action 的 request，通过 `customData` 共享本次调用内的数据，在 `next()` 之前检查输入或查询业务系统，并在 `next()` 返回后记录耗时或结果。抛出 `CollabError` 可以拒绝一次预期内的协同操作。

Transport 的 HTTP Middleware 可以直接结束 HTTP response，而不调用 `next()`。Service 和 Endpoint 的 Middleware 如需拒绝操作，应抛出明确的错误，而不是静默跳过 `next()`。

## Transport Middleware

`transport.use()` 注册普通 HTTP Middleware，按注册顺序执行。调用 `await next()` 可继续处理，也可以直接结束响应。WebSocket 握手由 `transport.useUpgrade()` 处理。

以下示例先记录 HTTP 耗时，再认证请求并设置可信的 `userID`，最后注册 Collaboration Endpoint：

```ts
transport.use(async (context, next) => {
  const start = performance.now();
  context.response.once("finish", () => {
    recordHttpDuration({
      method: context.incomingMessage.method,
      route: context.route?.path ?? "unmatched",
      status: context.response.statusCode,
      durationMs: performance.now() - start,
    });
  });
  await next();
});

transport.use(async (context, next) => {
  const user = await authenticate(context.incomingMessage);
  if (!user) {
    context.response.statusCode = 401;
    context.response.end("Authentication required");
    return;
  }
  context.userID = user.userId;
  await next();
});

transport.register(collaborationEndpoint);
```

`recordHttpDuration` 和 `authenticate` 由应用提供。Endpoint 使用前序 Middleware 设置的 `userID`。耗时观测位于认证之前，因此被拒绝的请求同样会被记录。

`context.route?.path` 是匹配到的完整路由模板，执行到 Endpoint 时才可用。通过 response 的 `finish` 事件可以观测响应何时完成。路由匹配之前被拒绝的请求以及未知路径均记为 `unmatched`。

## Endpoint Middleware

Endpoint Middleware 作用于实时 Session 与 Presence 操作：

| Action            | 触发时机                                     | 常见用途                     |
| ----------------- | -------------------------------------------- | ---------------------------- |
| `connect`         | Ticket 已消费、Session 已创建，处理 HELLO 前 | 连接策略、补充成员名称与头像 |
| `joinUnit`        | Session 加入 Unit Room 前                    | Room 准入、Unit 可见性检查   |
| `receivePresence` | 已 JOIN Session 的 Presence 到达后、广播前   | 校验、过滤 Presence          |
| `sendPresence`    | Presence 发给某个 Room 成员前                | 按接收者过滤 Presence        |

```ts
endpoint.use("receivePresence", async (context, next) => {
  if (JSON.stringify(context.payload).length > 8_000) {
    throw new CollabError("INVALID_REQUEST", "Presence payload is too large");
  }
  await next();
});
```

Endpoint 的 `session.userID` 和 `session.customData` 来自签发 Session Ticket 的 HTTP request。`memberID` 由 Endpoint 为当前 WebSocket Session 创建，重连后会变化。

## Service Middleware

Service Middleware 作用于权威协同数据的生命周期：

| Action            | 操作边界                             | 常见用途                     |
| ----------------- | ------------------------------------ | ---------------------------- |
| `readUnitData`    | 读取 snapshot、block 或 changeset 前 | 读取规则、tenant、审计       |
| `createUnit`      | 原子创建 Unit 前                     | 类型检查、创建权限、业务规则 |
| `deleteUnits`     | 删除批次写入 Adapter 前              | 删除规则、逐 Unit 检查       |
| `recoverUnits`    | 恢复批次写入 Adapter 前              | 恢复规则、审计               |
| `submitChangeset` | 收到提交后，去重和 OT 之前 | 检查编辑权限，限制本次提交的大小 |
| `applyChangeset`  | OT 完成后，将 changeset 应用到文档之前 | 校验转换后的操作，例如检查它们是否涉及受保护的区域 |
| `commitChangeset` | changeset 已应用到候选状态，Adapter 写入之前 | 设置要随本次提交保存的 metadata |

```ts
service.use("createUnit", async (context, next) => {
  await creationPolicy.assertAllowed({
    userID: context.userID,
    unitID: context.request.snapshot.unitID,
    type: context.request.snapshot.type,
  });
  context.customData.creationPolicyChecked = true;
  await next();
});
```

`submitChangeset` 每次逻辑提交只运行一次。revision 发生竞争时，`applyChangeset` 和 `commitChangeset` 可能以新的 `attempt` 重新运行。这两个阶段的 Middleware 必须可重试，不能直接发送不可撤销的外部消息，也不能执行一次性扣费。

## customData 的作用域

`customData` 用于在同一次调用中共享上下文。调用方可以传入数据，Middleware 也可以在处理过程中补充，供后续 Middleware、Database Adapter 和相关 Event 读取。常见用途包括：

- 传递租户 ID、trace ID 或本次请求使用的 logger。
- 复用本次调用中的权限查询结果。
- 记录计时起点或审计标签。

内置 Database Adapter 不会持久化 `customData`。如果需要将某些字段随文档或 changeset 一起保存，请参见[持久化 metadata](#persistent-metadata)。

## 持久化 metadata [#persistent-metadata]

`metadata` 用于保存应用自定义的数据。`UnitRecord.metadata` 随文档保存，`ChangesetRecord.metadata` 随单次提交保存。

创建文档时，可以在 `createUnitFromData()` 或 `createUnitFromSnapshot()` 的输入中传入 `metadata`，也可以在 `createUnit` middleware 中设置 `context.unit.metadata`。未提供时默认为 `{}`。

提交 changeset 时，可以在 `commitChangeset` middleware 中同时更新两份 metadata。`context.unit.metadata` 初始为文档当前的值，`context.changeset.metadata` 初始为 `{}`。两者的类型分别为 `UnitMetadata` 和 `ChangesetMetadata`，都是 `Record<string, unknown>`，字段值须可序列化为 JSON。

在 `await next()` 前完成修改。例如，下面的代码更新文档的最近编辑者，并记录本次提交的来源：

```ts
service.use("commitChangeset", async (context, next) => {
  context.unit.metadata.lastEditorID = context.userID;
  context.changeset.metadata.source = "application";
  await next();
});
```

Service 将修改后的两个完整对象传给 Adapter，随本次提交一起保存。

- **版本冲突**：Service 重试时，会用最新的 Unit metadata 和空的 changeset metadata 重新执行 `commitChangeset` middleware。
- **重复提交**：如果同一次提交已经成功，服务会返回原 changeset 的 metadata。

读取文档的 metadata 时，调用 Adapter 的 `getUnit()`，取返回记录的 `metadata`。读取本次提交的 metadata 时，取 `submitChangeset()` 成功结果中的 `changeset.metadata`。要查看以往提交，调用 `getChangesets()`，返回的 `changesets` 数组中每一项都包含 `metadata`。

使用内置 SQLite 或 PostgreSQL Adapter 时，也可以直接用 SQL 查询文档或 changeset 的 metadata。具体表名和字段名以该 Adapter 的数据库结构为准。

## Event 执行模型

Service 通过 `on()` 注册进程内 Listener，该方法返回一个可释放的订阅：

```ts
const subscription = service.on("changesetCommitted", async (event) => {
  metrics.increment("collaboration.changeset.committed", {
    unitType: String(event.changeset.type),
  });
  localCache.delete(event.changeset.unitID);
});

subscription.dispose();
```

同一个 Event 的 Listener 按注册顺序依次执行，SDK 会等待前一个 Listener 完成后再执行下一个。Listener 的错误会被记录并隔离，不会影响已经确定的领域结果。例如，`changesetCommitted` 的 Listener 失败时，Adapter 已存储的 changeset 不会被回滚。

Event 因此适合进程内、可恢复或非关键的后续处理。它不与数据库 commit 共享事务边界，也不保证外部系统收到通知。

## Core Service Event

| Event                | 已确认的事实                    | 典型用途                       |
| -------------------- | ------------------------------- | ------------------------------ |
| `unitCreated`        | Unit 及其初始数据已创建         | 更新本地目录缓存、建立派生索引 |
| `changesetCommitted` | Adapter 保存变更集并更新版本号 | 广播、指标、派生索引           |
| `unitsDeleted`       | 删除批次已由 Adapter 确认       | 清理进程内关联状态             |
| `unitsRecovered`     | 恢复批次已由 Adapter 确认       | 恢复本地派生状态               |

在 `unitCreated` 监听器中，通过 `event.record.metadata` 读取文档 metadata；在 `changesetCommitted` 监听器中，通过 `event.changeset.metadata` 读取本次提交的 metadata。

Endpoint 监听同一个 Service 上的 `changesetCommitted`，把确认后的 changeset 广播给当前进程中已 JOIN 该 Unit 的 Client；配置了 pub/sub 适配器时，广播也会到达其他节点。Endpoint 自身还提供 `memberLeftUnit`，用于观察成员主动离开、断线以及 Endpoint 释放。

## 扩展模块拥有独立扩展点

History、Thread Comment 与 Worktree 不会自动继承主 Collaboration Service 的 Middleware 或 Event：

- History 为 `getHistoryList`、`listHistoryCreators`、`getHistoryChangesets` 提供读取 Middleware；
- Comment 提供 add、reply、edit、delete、solve、list 的 Middleware，以及 `commentCommitted`；
- Worktree 提供生命周期和 draft read/submit/commit 的 Middleware，以及创建、状态、合入和 draft commit 相关的 Event。

每个启用的模块都需要单独安装规则。主 Service 上的日志、tenant 或权限 Middleware 不会自动覆盖这些模块。

如需将已有的用户与 ACL 系统映射到这些通用 Middleware 边界，请阅读[身份与权限](/server/collaboration/identity-and-authorization)。
