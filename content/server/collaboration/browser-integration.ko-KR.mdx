공동 작업은 브라우저 편집기를 하나의 공유 문서 서비스에 연결합니다. 두 사용자가 같은 스프레드 시트를 열 때, 하나의 브라우저에서 편집은 다른 곳에서 나타납니다.

[서버 통합](/server)를 통해 백엔드를 설정하십시오. 아래 설명된 편집기 구성 및 문서 로딩은 다음과 같습니다. 쌍된 서버 및 웹 코드는 [협업 빠른 시작](/server/collaboration/quick-start)에 있습니다.

## 기존 편집기 연결

다른 편집기가 필요하지 않습니다. 기존 Web SDK 편집기를 유지하고 [빠른 시작의 브라우저 구성](/server/collaboration/quick-start)를 따르고 협업 플러그인을 추가하려면 문서 로딩, 편집 제출 및 WebSocket 주소를 구성하십시오. 브라우저 및 서버 패키지 버전은 호환되지 않습니다.

수정된 예 사용자 및 기본 권한은 데모를 위해 예정되어 있습니다. 응용 프로그램에서, 각 요청으로 로그인 자격 증명을 보내서, 백엔드는 정체성과 문서 액세스를 확인할 수 있습니다. 라이센스는 [인증 구성](/server/license)에서 적용됩니다.

## 플러그인 설정 [#client-configuration]

### 일괄 전송 및 재시도 시간 제한 [#client-retry-timeouts]

`UniverCollaborationClientPlugin`

| <span data-config-options="">옵션</span> | 유형 | 기본값 | 동작 |
| --- | --- | --- | --- |
| `socketService` | `Ctor<ICollaborationSocketService>` |  | 현재 런타임에 사용되는 소켓 구현을 선택합니다. |
| `sendChangesetTimeout` | `number` | `2000 ms` | 그들이 보낸 전에 얼마나 긴 로컬 편집이 완충되는지 설정한다. |
| `changesetAckTimeout` | `number` | `20000 ms` | 재발견 전에 인정을 기다리는 방법. |
| `maxChangesetAckTimeout` | `number` | `120000 ms` | resends 사이 간격에 위 경계를 놓습니다. |

일괄 처리 지연 및 승인 타임 아웃은 별도의 타이머입니다. 클라이언트 플러그인은 `sendChangesetTimeout: 2000`, `changesetAckTimeout: 20000` 및 `maxChangesetAckTimeout: 120000`에 기본적으로 밀리 초입니다. 제출 요청은 인정 타임 아웃뿐만 아니라 사용합니다. 인정되지 않은 변경은 최대에 캡핑 된 exponential 백 오프와 재흡입됩니다. 승인 시간 제한 및 동일한 값으로 최대 타임 아웃을 설정하면 일정한 간격을 생성합니다.

```ts
import { UniverCollaborationClientPlugin } from '@univerjs-pro/collaboration-client'
import { BrowserCollaborationSocketService } from '@univerjs-pro/collaboration-client-ui'

univer.registerPlugin(UniverCollaborationClientPlugin, {
  socketService: BrowserCollaborationSocketService,
  sendChangesetTimeout: 200,
  changesetAckTimeout: 20_000,
  maxChangesetAckTimeout: 120_000,
})
```

기존 클라이언트 등록에 이러한 옵션을 추가하고 소켓 및 엔드포인트 구성을 유지하십시오. 시트 및 문서 협업 미리 설정은 200 ms 일괄 처리 지연을 사용하며 승인 타임 아웃 옵션을 노출하지 않습니다. 이러한 타임 아웃을 사용자 정의하면 플러그인 모드가 필요합니다.

### 충돌 복구 알림 [#client-conflict-notices]

`UniverCollaborationClientUIPlugin`

| <span data-config-options="">옵션</span> | 유형 | 기본값 | 동작 |
| --- | --- | --- | --- |
| `enableDefaultConflictUI` | `boolean` | `true` | 내장 충돌 복구 통지를 표시합니다. |

```ts
import { UniverCollaborationClientUIPlugin } from '@univerjs-pro/collaboration-client-ui'

univer.registerPlugin(UniverCollaborationClientUIPlugin, { enableDefaultConflictUI: false })
```

## 프리셋 설정 [#client-preset-configuration]

`UniverSheetsCollaborationPreset / UniverDocsCollaborationPreset`

| <span data-config-options="">옵션</span> | 유형 | 기본값 | 동작 |
| --- | --- | --- | --- |
| `enableDefaultConflictUI` | `boolean` | `true` | 내장 충돌 복구 통지를 표시합니다. |

```ts
import { UniverSheetsCollaborationPreset } from '@univerjs/preset-sheets-collaboration'

const collaborationPreset = UniverSheetsCollaborationPreset({ enableDefaultConflictUI: false })
```

```ts
import { UniverDocsCollaborationPreset } from '@univerjs/preset-docs-collaboration'

const collaborationPreset = UniverDocsCollaborationPreset({ enableDefaultConflictUI: false })
```

기본적으로 UI는 그 이름의 충돌 통지를 보여줍니다. 이 통지는 캐시 정리가 성공한 후 다시로드를 제공하며, 정리가 실패한 경우 재스트를 제공합니다. 응용 프로그램에서 복구 흐름을 실행하려면 기존 초기화에서 `enableDefaultConflictUI: false`를 설정하고 이벤트를 직접 처리하십시오.

기존 `createUniver({ presets: [...] })` 통화에 대한 협업을 추가하고, 편집기 사전 설정 옆에, 엔드포인트와 역사 설정을 유지하십시오. [이벤트 payloads](#conflict-recovery) 및 [고객 구성](/reference/packages/plugins/univerjs-pro/collaboration-client)를 참조하십시오.

## 같은 문서 생성 및 열기

문서 작성 및 개구는 별도의 작업입니다:

1. 사용자가 문서를 만들 때, 백엔드가 저장하고 ID를 반환합니다.
2. 브라우저는 ID를 로드합니다. 문서가 다시 열릴 때 동일한 ID를 재사용하거나 다른 사용자와 공유합니다.

API는 문서 ID `unitId`를 지명합니다. 모든 방문에 새로운 지역 공백 문서를 창조하지 마십시오.

문서를 로드하기 전에 현재 사용자를 설정하세요. 현재 사용자는 공동 편집의 신원과 로컬 오프라인 캐시의 소유자를 결정합니다. 설정 방법은 [신원 확인과 권한 부여](/server/collaboration/identity-and-authorization)를 참고하세요.

예를 들어, 시트 및 협업 플러그인이 등록 된 후 서버에서 스프레드 시트를로드하십시오.

```ts
import { UserManagerService } from '@univerjs/core'
import '@univerjs-pro/collaboration-client/facade'

univer.__getInjector().get(UserManagerService).setCurrentUser({ userID, name, avatar })

const workbook = await univerAPI.getCollaboration().loadSheetAsync('your-document-id')
if (!workbook) throw new Error('Document could not be loaded')
```

제품 별 적재는 [제품정보](/guides/sheets/features/collaboration), [팟캐스트](/guides/docs/features/collaboration)의 [제품정보](/guides/slides/features/collaboration)에, [회사연혁](/guides/boards/features/collaboration)는, [기본 정보](/guides/bases/features/collaboration) 및 [PDF 파일](/guides/pdfs/features/collaboration) 가이드 덮습니다. 당신이 특징을 지원하는 제품 및 후원 방출이 확인하십시오.

## 동기화, 저장 및 권한 확인

일반 창과 개인과 같은 두 개의 독립적 인 브라우저 세션에서 동일한 문서를 엽니 다. 한 세션에서 편집하고 다른 쇼를 확인하십시오. 그런 다음 페이지를 다시로드, 다시 연결, 서버를 다시 시작, 그리고 내용을 여전히 현재 확인.

편집기, 뷰어 및 액세스가없는 사용자로 테스트하십시오. 읽기 전용 UI 설정만 페이지 허용 여부를 제어합니다. 서버는 여전히 무단 읽기 및 변경을 거부해야합니다.

문서로드하지만 편집이 동기화되지 않는 경우, WebSocket 연결을 확인하십시오. 다시 시작 후 콘텐츠가 사라지면 다시 저장을 확인하십시오. 이러한 설정은 [서버 통합](/server)에 속합니다.

## 파일 교환, 댓글 또는 기록 추가

공동으로 수입 된 파일을 편집하려면 변환 된 데이터에서 공동 문서를 작성하십시오. [파일 교환 통합](/server/import-export)를 참조하십시오. 댓글과 역사는 각각 자체 플러그인, 서비스 및 권한이 필요합니다. [Office 확장 모듈](/server/collaboration/extensions)을 따르십시오.

역사 패널 윤곽을 위해, [제품정보](/guides/sheets/features/edit-history), [팟캐스트](/guides/docs/features/edit-history)의 [제품정보](/guides/slides/features/edit-history)를, [회사연혁](/guides/boards/features/edit-history) 및 [기본 정보](/guides/bases/features/edit-history) 가이드를 보십시오. 오늘 어떤 것을 위한 [PDF의 역사](/guides/pdfs/features/edit-history)가 보십시오.

## 동기화 상태와 재전송 [#sync-status]

청취자 등록하기 전에 협력 Facade를 가져옵니다. `CollaborationStatusChanged`는 청취자가 등록되면 청취자가 연속 동일한 상태를 반복하지 않고 변경 사항을보고 이미 협력하는 모든 단위의 현재 상태를보고합니다. `hasWritePending(unitId)`은 정량 편집을 다루고, 승인 및 오프라인 편집을 편집합니다. ID가 무효한 경우, 집중된 단위를 확인합니다. 연결 소켓은 편집이 저장되지 않습니다.

```ts
import '@univerjs-pro/collaboration-client/facade'

const collaboration = univerAPI.getCollaboration()
const statusSubscription = univerAPI.addEvent(univerAPI.Event.CollaborationStatusChanged, (event) => {
  console.info(event.unitId, event.status, collaboration.hasWritePending(event.unitId))
})
const resendSubscription = univerAPI.addEvent(univerAPI.Event.CollaborationChangesetResend, (event) => {
  console.info(event.unitId, event.reason, event.attempt, event.unsyncedMutationCount, event.nextDelayMs)
})
```

`CollaborationChangesetResend`는, 첫번째 제출에 아닙니다 재판매에 불을 붙입니다. 이유는 `ack_timeout`, `request_failed`, `license_editing_connections_exceeded`, `should_retry` 및 `reconnect`입니다; `attempt`, `elapsedMs`, `unsyncedMutationCount` 및 `nextDelayMs`는 저축 또는 재출 지시자를 위해 필요로 한 자료를 제공합니다. 편집자가 제거될 때 사건 구독을 처리하십시오.

`request_failed`는 네트워크 오류 또는 HTTP 408, 429, 또는 5xx 응답과 같은 재시동할 수 있는 요청 실패를 의미합니다. `license_editing_connections_exceeded`은 라이센스 편집 연결을 모두 사용하는 것을 의미하며 서버는 재판매를 요청했습니다.

## 애플리케이션에서 충돌 처리 [#conflict-recovery]

`CollaborationConflict` 화재는 한 번 단위가 충돌을 입력 할 때, 오프라인 캐시 정리 시도 후. 모든 문서를 로딩하기 전에 청취를 등록하십시오. 그것의 `reason`는 `transform_failed`, `apply_failed`, `changeset_rejected`, `license_unit_type_rejected`, `permission_rejected` 또는 `remote_revert`입니다; `message` 및 `revert`는 추가 세부 사항을 제공 할 때 사용할 수 있습니다.

`license_unit_type_rejected`는 서버 라이선스가 해당 문서 유형의 공동 편집을 지원하지 않음을 뜻합니다.

```ts
import type { IEventParamConfig } from '@univerjs/core/facade'
import '@univerjs-pro/collaboration-client/facade'

const conflicts = new Map<string, IEventParamConfig['CollaborationConflict']>()
const conflictSubscription = univerAPI.addEvent(univerAPI.Event.CollaborationConflict, (event) => {
  conflicts.set(event.unitId, event)
})
```

예를 들어 호스트 복구 화면에 대한 이벤트를 유지. 맵은 메모리에만 살고, 그래서 응용 프로그램은 저장하거나 새로 고침하기 전에 `localChanges`을 수출해야합니다. 이 이벤트는 유지 할 수있는 유일한 기회입니다; 이미 삭제 된 캐시 데이터는 나중에 읽을 수 없습니다. `awaitingChangeset`는 이미 서버에 적용되어 있으므로 블라인드를 재생할 수 없습니다.

`cacheCleared: false`는 새로 고침이 오래된 캐시 된 편집을 재생할 수 있으므로 캐시 정리가 상쾌하기 전에 해결되어야합니다. 캐시를 정리하면 동기화되지 않은 편집이 저장되었습니다. `permission_rejected` 충돌도 해결해야합니다. 다시로드는 권한이 부여되지 않습니다.

## 서버 거부 이유와 라이선스 알림 [#server-rejections]

서버가 변경을 거부 할 때 `CollaborationConflict.message`는 서버가 주어진 이유를 수행 할 때, 하나가 주어집니다. 로컬화 된 메시지 텍스트를 파싱하지 마십시오. 복구 동작을 결정하십시오. 대신 `reason`의 지점. `license_unit_type_rejected`은 문서 유형에 포함 된 서버 라이센스를 필요로하며 `license_editing_connections_exceeded`가 재판매 신호입니다. 편집은 unacknowledged 남아 있으며 재 배포를 유지합니다. ZX`hasWritePending(unitId)`이 응용 프로그램을 유지하거나 수정할 때까지 편집기가 열립니다.

기본 UI는 편집 용량 통지를 표시하고, 첫 번째 전송 후 적어도 20 초 동안 다시 종료, 저장 시간 통지. 이 장치는 대기 상태를 나타날 때 제거 또는 처분됩니다. 도메인 거부는 전용 통지뿐만 아니라. `enableDefaultConflictUI: false`는 충돌 복구 통지 만 비활성화하지 않습니다; 이 대기 또는 도메인 통지를 비활성화하지 않습니다.
