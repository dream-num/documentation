Проверены два сценария: работа нескольких редакторов с одним документом и одновременное редактирование нескольких документов. После прогрева измерялись задержка подтверждения, пропускная способность, доля выполненных отправок, загрузка CPU и потребление памяти процессом совместного редактирования.

## Тестовая среда

Сервис совместного редактирования и база данных работали на разных серверах. Конфигурации узла в таблицах результатов относятся к узлу совместного редактирования на схеме.

PostgreSQL хранит записи документов, наборы изменений, записи снимков и ссылки на блоки. Блоки снимков с данными ячеек хранятся в OSS.

Все измерения выполнены на одном узле. Когда число одновременно редактируемых документов превышает его возможности, документы можно распределить между несколькими узлами. Узлы используют общую базу данных и механизм публикации и подписки для синхронизации комнат, присутствия и рассылки изменений. См. [развёртывание нескольких узлов](/server/deployment#несколько-узлов-совместного-редактирования).

### Настройки сервиса

В обеих конфигурациях значение `runtime.maxLoadedUnits` увеличили с 1 200 до 4 000, чтобы узел мог держать в памяти до 4 000 документов. Остальные настройки SDK оставили по умолчанию, включая автоматический выбор числа рабочих потоков. Снимок создаётся через 50 ревизий после последнего успешного снимка или при достижении одним набором изменений размера 5 МиБ. Лимит памяти процесса совместного редактирования составил 14 ГиБ на 4-ядерном узле и 29 ГиБ на 8-ядерном.

Ниже приведён фрагмент тестового сервиса. Адаптер использует инициализированный пул соединений PostgreSQL и клиент OSS. Транспорт подключён к HTTP-серверу Node.js.

```ts
const dbAdapter = await PostgresS3DatabaseAdapter.create({
  pool,
  s3: { client, bucket, prefix },
});
const service = new UniverCollabService({
  dbAdapter,
  runtime: { maxLoadedUnits: 4000 },
});
const endpoint = new UniverCollabEndpoint(service);
const transport = createNodeTransport();
transport.register(endpoint);
transport.attach(server);
```

## Методика

### Имитация клиентов

Каждый редактор — независимый сеанс. Он подключается к одному документу, отправляет правки ячеек по HTTP и получает подтверждения по WebSocket. Скрипты напрямую вызывают API совместного редактирования. Для HTTP-запроса и ожидания подтверждения действует тайм-аут 10 секунд.

### Прогрев и измерения

В каждом прогоне документы создаются из выбранного снимка. Прогрев начинается после подключения всех сеансов. Первая правка вызывает загрузку документа на сервере. При работе с одним документом предварительно отправляется одна правка. При работе с несколькими документами каждый документ получает разное число правок при прогреве, поэтому начальные ревизии и моменты сохранения снимков разнесены во времени.

Измерения начинаются после прогрева всех документов. Статистика отправок, процентили задержки, загрузка CPU и объём памяти в таблицах относятся к периоду измерений.

### Нагрузка при редактировании

Для одного документа `blank` увеличивали число редакторов. Для каждого из трёх снимков увеличивали число одновременно активных документов. В обоих сценариях каждая отправка содержит одну операцию `sheet.mutation.set-range-values`, записывающую число в одну ячейку.

| Условие | Один документ | Несколько документов |
| --- | --- | --- |
| Редакторы на документ | Зависит от прогона (см. результаты) | Два во всех прогонах |
| Операция | Каждый редактор меняет свою ячейку со сдвигом по времени | Каждый редактор меняет свою ячейку со сдвигом по времени |
| Частота на редактора | Раз в 6 секунд | Раз в 2 секунды |
| Период измерений на прогон | 300 секунд | 300 секунд |

## Показатели

| Показатель | Определение |
| --- | --- |
| Задержка подтверждения | Время от отправки правки до получения подтверждения тем же клиентом. P50, P95 и P99 — время, за которое получено подтверждение для 50%, 95% и 99% успешных отправок. Max — наибольшая задержка успешной отправки. |
| Пропускная способность | Число успешных отправок за период измерений, делённое на его длительность в секундах. |
| Доля выполненных отправок | Процент успешных отправок от запланированных. В план входят также неудавшиеся и неотправленные запросы. |
| CPU, среднее / пик (%) | Средняя и наибольшая наблюдаемая загрузка CPU процессом совместного редактирования. Полностью занятое ядро соответствует 100%, поэтому сумма может превышать 100%. |
| Пиковая память (МиБ) | Наибольшее измеренное значение резидентной памяти (RSS) процесса совместного редактирования. |

### Критерии прохождения

Прогон проходит проверку, только если выполнены все условия:

- Задержка подтверждения **P99 < 1 000 мс**.
- Доля выполненных отправок **> 90%**.
- Процесс совместного редактирования работает до успешной проверки согласованности всех тестовых документов.
- В период измерений обработка снимков успевает за записью, и число ожидающих задач сохранения снимков не растёт непрерывно. Непрерывный рост отмечается как «Очередь снимков продолжает расти».

Если уровень нагрузки проверен одним прогоном, берётся его результат. Если прогонов несколько, пройти должны все.

## Применимость результатов

Для оценки обработки параллельных изменений скрипты Node.js имитируют сеансы и направляют правки ячеек прямо в API. Задержка измеряется от отправки до получения ответа и не включает действия в браузере и отрисовку листа.

Эти данные служат ориентиром для оценки производительности и планирования ёмкости одного узла. Результат зависит от конфигурации, сети, размера документа, типа и частоты правок.

Уровень нагрузки — одно значение нагрузки при заданных условиях теста: число редакторов или активных документов. Максимальная пройденная нагрузка — наибольший из испытанных уровней, удовлетворивших критериям. На некоторых из них средняя загрузка CPU приближалась к пределу узла. **Это ориентир для планирования, а не целевая долговременная нагрузка в эксплуатации.** Оставляйте запас на пики и колебания потребления ресурсов и проверяйте устойчивую нагрузку в целевой среде на типовых документах.

#### Выбор конфигурации пулов узлов

В [многоузловой конфигурации](/server/deployment) шлюз может распределять документы по пулам в зависимости от размера. Оценки для одного узла предполагают двух редакторов на документ с одной правкой каждые две секунды от каждого.

- **Для небольших и средних документов сначала оцените 4 ядра с 8 ГиБ.** По оценке на основе измерений с 4 ядрами и 16 ГиБ, бюджет 8 ГиБ вмещает 2 300 пустых документов или 1 800 документов примерно по 10 000 заполненных ячеек.
- **Для больших документов оцените 8 ядер с 16 или 32 ГиБ.** При размере около 100 000 заполненных ячеек на документ максимальный пройденный уровень на 8 ядрах с 32 ГиБ — 700 документов, и его пиковая память укладывается в бюджет 16 ГиБ. Здесь ограничивающий фактор — обработка снимков: при 750 документах задержка подтверждения ещё укладывалась в порог, но очередь снимков продолжала расти.
