Univer Collaboration se compose d'un client de navigateur et d'un ensemble de modules côté serveur. Chaque module possède une classe de responsabilité. Les applications composent les modules à travers des interfaces publiques, de sorte que leur code ne dépend pas des internes de l'implémentation OT[^operational-transformation], du protocole ou de la couche de persistance.

## Collaboration Client

Le client de collaboration du navigateur fonctionne aux côtés du Web SDK et gère le côté client de la collaboration:

- Il demande des instantanés d'unité et tout changement confirmé qu'il manque.
- Il utilise un ticket de session unique pour ouvrir une connexion WebSocket.
- Il rejoint les salles d'unité et échange Présence avec d'autres membres.
- Il soumet des mutations locales au serveur sous forme de changements.
- Il reçoit des ACK et des émissions, et après une reconnexion il récupère les changements qu'il a manqués.

Le Client ne détermine pas si un utilisateur est fiable, et ce n'est pas la source de données faisant autorité. Cette décision appartient au serveur, qui impose l'identité et l'autorisation dans le Middleware correspondant.

## Node Transport

`@univerjs-pro/collaboration-transport-node` est le point d'entrée Node.js pour le trafic HTTP et WebSocket. Il reçoit les requêtes et les mises à jour WebSockets du serveur HTTP hôte, exécute l'entrée Middleware enregistrée par l'application, et conduit le trafic vers Endpoints.

Le Transport ne comprend pas les données OT, l'unité ou les modèles ACL. L'assemblage utilise trois méthodes :

```ts
transport.use(httpMiddleware);
transport.useUpgrade(upgradeMiddleware);
transport.register(endpoint);
```

- `use()` gère les requêtes HTTP ordinaires et peut établir `userID`, `customData` ou des traces.
- `useUpgrade()` gère la poignée de main WebSocket et peut rejeter la connexion avant qu'elle ne soit établie.
- `register()` enregistre un protocole Endpoint, dont le cycle de vie est ensuite géré par le Transport.

## Collaboration Endpoint

`@univerjs-pro/collaboration-endpoint` implémente le protocole utilisé par le client de collaboration Univer et possède les capacités suivantes:

| Fonction | Responsabilité de l’Endpoint |
| --- | --- |
| Chargement | Retourne des instantanés et des blocs unitaires, ainsi que tous les changements confirmés que le Client ne possède pas |
| Soumission | Reçoit les changements, renvoie les ACK et diffuse les changements confirmés à la Room |
| Connexion Session | Délivrance de billets de séance une fois, puis établit et maintient des sessions WebSocket |
| Collaboration Room | Traite JOIN, LEAVE, état des membres et Presence |
| Cycle de vie Unit | Convertit suppressions et restaurations en appels Service |
| Plusieurs nœuds | Relays Rooms, Présence, et des émissions à travers les nœuds à travers un adaptateur pub/sous-adaptateur optionnel et une billetterie partagée |

L'Endpoint n'exécute pas OT et ne stocke pas les données de collaboration elle-même. Il obtient le résultat faisant autorité du Service et les cartes qui résultent du protocole Client. Les opérations de produit comme la création d'un document appartiennent à une API d'application qui appelle le Service.

## Collaboration Service

`@univerjs-pro/collaboration-service` est le noyau de collaboration et ne dépend pas du réseau. Il couvre Sheet, Doc, Slide, Board, Base et PDF:

- Il lit les données de récupération de l'unité et les changements confirmés.
- Il crée des unités à partir de données d'unité ou de instantanés.
- Soumettre un jeu de modifications lance OT et avance la révision continue[^collaboration-revision].
- Il identifie les soumissions dupliquées par `(unitID, sid, reqId)`.
- Il supprime, récupère ou supprime définitivement les unités.
- Il exécute Service Middleware et émet des événements après confirmation.

Le Service n'a pas de couche HTTP ou WebSocket, et il ne connaît pas les utilisateurs, les rôles, les ACL, la hiérarchie ou la gestion de fichiers. Le point d'arrivée construit le protocole du navigateur en plus du Service. Les applications peuvent également appeler l'API publique du Service directement à partir des API d'affaires ou des tâches de fond.

### API principales

| Fonction | API Service |
| --- | --- |
| Charger une Unit | `getUnitLoadData()`, `getUnitLoadDataWithBlocks()` |
| Lire les données incrémentales | `getChangesets()`, `getSheetBlock()` |
| Créer une Unit | `createUnitFromData()`, `createUnitFromSnapshot()` |
| Soumettre des changements | `submitChangeset()` |
| Supprimer et restaurer | `deleteUnits()`, `recoverUnits()` |

## Database Adapter

Le Database Adapter est le contrat entre Service et stockage. Il garantit :

- la création atomique de l’instantané initial et de ses dépendances ;
- le compare-and-swap de révision ;
- présentation de modifications de l'idémpotent;
- visibilité instantanée seulement après l'existence de toutes ses dépendances;
- les lots de cycle de vie Unit en tout ou rien.

L’application accède au stockage via `IDatabaseAdapter`. Pour choisir un adaptateur intégré ou créer le vôtre, consultez le guide [Database Adapters](/server/collaboration/database-adapters).

## Quatre concepts centraux

| Concept | Signification |
| --- | --- |
| Unit | Contenu Univer indépendant et collaboratif, avec un `unitID` unique et un type |
| Snapshot | Le contenu unitaire a persisté lors d'une révision, pas l'objet mutable vivant |
| Changeset | Un lot de mutations soumises ensemble, avec une révision de base et une identité pour idempotency |
| Revision | Le numéro de version continue de l'état unitaire confirmé, à partir de `1` |

Toutes les modifications apportées au contenu d'exécution passent par les API ou commandes Facade. Muter un objet instantané ne met pas à jour l'unité en direct dans le Client ou le Service.

Le `userID/customData` établi par Transport Middleware voyage avec la requête HTTP en cours dans Service Middle Software. L'application décide si une lecture est autorisée. Un client n'a pas besoin de rejoindre une Chambre avant qu'il ne lise au-dessus de HTTP ordinaire.

## Soumettre une édition

```text
Facade / Command
  → Mutation
  → Changeset du Client
  → soumission Endpoint
  → Middleware Service
  → OT + CAS de révision
  → commit atomique de l’Adapter
  → Changeset confirmé
  → ACK / diffusion à la Room
```

La révision confirmée dans l'adaptateur de base de données est l'état faisant autorité. ACKs et les émissions maintiennent les clients en ligne synchronisés avec une faible latence. Un client qui manque un message peut récupérer les changements confirmés qu'il manque en utilisant la révision qu'il connaît déjà.

## Assemblage serveur minimal

```ts
import { createServer } from "node:http";

import { MemoryDatabaseAdapter } from "@univerjs-pro/collaboration-database-memory";
import { UniverCollabEndpoint } from "@univerjs-pro/collaboration-endpoint";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";
import { createNodeTransport } from "@univerjs-pro/collaboration-transport-node";

const database = new MemoryDatabaseAdapter();
const service = new UniverCollabService({ dbAdapter: database });
const endpoint = new UniverCollabEndpoint(service);
const transport = createNodeTransport();

transport.use(async (context, next) => {
  context.userID = "demo-user";
  await next();
});
transport.register(endpoint);

const server = createServer();
transport.attach(server);
server.listen(3010);
```

L'utilisateur codé en dur et l'adaptateur mémoire ne démontrent que l'assemblage du module. Les applications réelles établissent le contexte à travers Middleware et sélectionnent un adaptateur qui correspond à leurs besoins en données.

### Créer une Unit via une API applicative

Les applications peuvent définir leurs propres paramètres HTTP ou RPC et appeler le `service` créé ci-dessus après l'authentification, la validation d'entrée, et les vérifications d'entreprise passent:

```text
Client métier
  → POST /api/units
  → authentification et validation applicatives
  → service.createUnitFromData()
  → Database Adapter
```

L'exemple Express ci-dessous suppose que Middleware d'authentification a défini `response.locals.user` et que `request.body.data` a déjà été validé en tant que Workbook Data:

```ts
import { randomUUID } from "node:crypto";

import { json } from "express";
import { UniverType } from "@univerjs/protocol";

app.post("/api/units", json({ limit: "1mb" }), async (request, response, next) => {
  try {
    const user = response.locals.user as { readonly userID: string };
    const unitID = randomUUID();

    const result = await service.createUnitFromData(
      {
        type: UniverType.UNIVER_SHEET,
        data: {
          ...request.body.data,
          id: unitID,
          rev: 1,
        },
      },
      {
        userID: user.userID,
        customData: { traceID: randomUUID() },
      },
    );

    response.status(result.status === "created" ? 201 : 200).json(result);
  } catch (error) {
    next(error);
  }
});
```

`POST /api/units` est une route d'application et ne fait pas partie du protocole Collaboration Client. Appeler `createUnitFromData()` exécute toujours le Middleware `createUnit` du Service. Les enregistrements de produits, les ACL propriétaires, la cartographie erreur-réponse et la compensation d'échec restent la responsabilité de l'application.

## Libération des ressources

`transport.dispose()` élimine les Endpoints enregistrés avec `register()`. Le Service et l'Adaptateur de base de données que l'application injectée doit être éliminée séparément, au contraire de l'ordre de montage:

```ts
await transport.dispose();
await service.dispose();
await database.dispose();
```

Si l'application a fourni un adaptateur pub/sous, elle doit également disposer de cet adaptateur et de ses connexions après le transport. Le point d'arrivée ne les dispose pas.

Pour étendre le comportement à ces limites de module, continuez avec [Middleware et événements](/server/collaboration/middleware-and-events).

[^operational-transformation]: La transformation opérationnelle (OT) adapte les opérations concurrentes créées sur des révisions différentes pour les appliquer de manière cohérente. Elle traite les modifications, sans remplacer tout le document par le dernier instantané reçu.

[^collaboration-revision]: Une révision identifie une position dans l’historique confirmé d’une Unit. Un changeset contient les opérations d’une soumission ; sa confirmation fait avancer cet historique. Ce n’est ni une version du SDK ni un horodatage.
