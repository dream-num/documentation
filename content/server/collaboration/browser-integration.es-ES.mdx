La colaboración conecta los editores del navegador a un servicio de documentos compartido. Cuando dos usuarios abren la misma hoja de cálculo, aparece una edición en un navegador en el otro.

Configurar el backend primero a través de [integración del servidor](/server). La configuración del editor y la carga de documentos descritos a continuación lo siguen. El código del servidor y de la Web está en [Inicio rápido de la colaboración](/server/collaboration/quick-start) .

## Conectar el editor existente

No es necesario un editor diferente. Retenga el editor Web SDK existente y siga el [configuración del navegador en Inicio rápido](/server/collaboration/quick-start) para agregar los plugins de colaboración, luego configure la carga de documentos, la presentación de edición y la dirección WebSocket. Las versiones de paquetes de navegador y servidor deben seguir siendo compatibles.

Los usuarios de ejemplo fijo y los permisos predeterminados están destinados a la demostración. En una aplicación, enviar credenciales de inicio de sesión con cada solicitud para que el backend pueda verificar la identidad y el acceso a documentos. [configuración de licencias](/server/license).

## Configuración de plugins [#client-configuration]

### Envío por lotes y tiempos de reintento [#client-retry-timeouts]

`UniverCollaborationClientPlugin`

| <span data-config-options="">Opción</span> | Tipo | Valor predeterminado | Efecto |
| --- | --- | --- | --- |
| `socketService` | `Ctor<ICollaborationSocketService>` |  | Selecciona la implementación de socket utilizada por el tiempo de ejecución actual. |
| `sendChangesetTimeout` | `number` | `2000 ms` | Establece cuánto tiempo las ediciones locales se amortiguan antes de ser enviadas. |
| `changesetAckTimeout` | `number` | `20000 ms` | Establece cuánto tiempo esperar para un reconocimiento antes de volver a intentarlo. |
| `maxChangesetAckTimeout` | `number` | `120000 ms` | Establece el límite superior en el intervalo entre los reenvíos. |

El retraso de batido y el tiempo de reconocimiento son temporizadores separados. El plugin del cliente predetermina a `sendChangesetTimeout: 2000`, `changesetAckTimeout: 20000` y `maxChangesetAckTimeout: 120000`. La solicitud de envío utiliza el tiempo de confirmación también. Los cambios que nunca se reconocen son resentidos con retroceso exponencial, capped al máximo. Configuración del tiempo de reconocimiento y el intervalo de tiempo máximo de salida.

```ts
import { UniverCollaborationClientPlugin } from '@univerjs-pro/collaboration-client'
import { BrowserCollaborationSocketService } from '@univerjs-pro/collaboration-client-ui'

univer.registerPlugin(UniverCollaborationClientPlugin, {
  socketService: BrowserCollaborationSocketService,
  sendChangesetTimeout: 200,
  changesetAckTimeout: 20_000,
  maxChangesetAckTimeout: 120_000,
})
```

Agregue estas opciones al registro de clientes existente y mantenga su configuración de socket y endpoint. Los presets de colaboración de Sheets y Docs utilizan un retraso de bateo de 200 ms y no expongan las opciones de timeout de reconocimiento, por lo que la personalización de estos timeouts requiere modo plugin.

## Configuración de preajustes [#client-preset-configuration]

`UniverSheetsCollaborationPreset / UniverDocsCollaborationPreset`

| <span data-config-options="">Opción</span> | Tipo | Valor predeterminado | Efecto |
| --- | --- | --- | --- |
| `enableDefaultConflictUI` | `boolean` | `true` | Muestra los avisos de recuperación de conflictos incorporados. |

```ts
import { UniverSheetsCollaborationPreset } from '@univerjs/preset-sheets-collaboration'

const collaborationPreset = UniverSheetsCollaborationPreset({ enableDefaultConflictUI: false })
```

```ts
import { UniverDocsCollaborationPreset } from '@univerjs/preset-docs-collaboration'

const collaborationPreset = UniverDocsCollaborationPreset({ enableDefaultConflictUI: false })
```

Por defecto, la interfaz de usuario muestra un aviso de conflicto que indica la razón. La notificación ofrece una recarga después de que la limpieza de caché tenga éxito, y una reiniciación si la limpieza falla. Para ejecutar el flujo de recuperación en la aplicación, establecer `enableDefaultConflictUI: false` en la inicialización existente y manejar el evento directamente.

Agregue los presets de colaboración a la llamada `createUniver({ presets: [...] })` existente, junto al preset del editor, y mantenga la configuración de endpoint e historia. Ver [cargas de pago del evento](#conflict-recovery) y [configuración cliente](/reference/packages/plugins/univerjs-pro/collaboration-client).

## Crear y abrir el mismo documento

Crear un documento y abrir uno son acciones separadas:

1. Cuando un usuario crea un documento, el backend lo guarda y devuelve su ID.
2. El navegador carga ese ID. Reutilizar el mismo ID cuando el documento es reabierto o compartido con otro usuario.

La API nombra el documento ID `unitId`. No cree un nuevo documento en blanco local en cada visita.

Establece el usuario actual antes de cargar un documento. Identifica al colaborador y es propietario de la caché local sin conexión; consulta [Identidad y autorización](/server/collaboration/identity-and-authorization).

Por ejemplo, después de que las hojas y los plugins de colaboración estén registrados, cargue una hoja de cálculo del servidor:

```ts
import { UserManagerService } from '@univerjs/core'
import '@univerjs-pro/collaboration-client/facade'

univer.__getInjector().get(UserManagerService).setCurrentUser({ userID, name, avatar })

const workbook = await univerAPI.getCollaboration().loadSheetAsync('your-document-id')
if (!workbook) throw new Error('Document could not be loaded')
```

La carga específica del producto está cubierta por las guías [Hojas](/guides/sheets/features/collaboration), [Docs](/guides/docs/features/collaboration), [Diapositivas](/guides/slides/features/collaboration), [Juntas](/guides/boards/features/collaboration), [Bases](/guides/bases/features/collaboration), y [PDF](/guides/pdfs/features/collaboration). Confirme que el producto y la versión de backend que dirija soportan la función.

## Verificar sincronización, guardado y permisos

Abra el mismo documento en dos sesiones independientes del navegador, como una ventana regular y una privada. Edite en una sesión y compruebe lo que el otro muestra. A continuación, vuelva a cargar la página, vuelva a conectarse, reinicie el servidor y confirme que el contenido sigue presente.

Pruebe como editor, un espectador y un usuario sin acceso. Los ajustes de la interfaz de usuario solo controlan lo que la página permite; el servidor debe rechazar lecturas y cambios no autorizados.

Si los documentos se cargan pero las ediciones no sincronizan, compruebe la conexión WebSocket. Si el contenido desaparece después de un reinicio, revise el almacenamiento de backend. [integración del servidor](/server).

## Estado de sincronización y reenvíos [#sync-status]

Importar la colaboración Facade antes de registrar oyentes. `CollaborationStatusChanged` reporta el estado actual de cada unidad ya colaborando cuando el oyente está registrado, luego reporta cambios sin repetir los statuss idénticos consecutivos. `hasWritePending(unitId)` cubre ediciones apagadas, ediciones en espera de reconocimiento, y ediciones fuera de línea. Si el ID es omitido, comprueba la unidad enfocada. Un socket conectado no significa que las ediciones se guardan.

```ts
import '@univerjs-pro/collaboration-client/facade'

const collaboration = univerAPI.getCollaboration()
const statusSubscription = univerAPI.addEvent(univerAPI.Event.CollaborationStatusChanged, (event) => {
  console.info(event.unitId, event.status, collaboration.hasWritePending(event.unitId))
})
const resendSubscription = univerAPI.addEvent(univerAPI.Event.CollaborationChangesetResend, (event) => {
  console.info(event.unitId, event.reason, event.attempt, event.unsyncedMutationCount, event.nextDelayMs)
})
```

`CollaborationChangesetResend` incendios en reenviamientos, no en la primera presentación. Las razones son `ack_timeout`, `request_failed`, `license_editing_connections_exceeded`, `should_retry`, y `reconnect`; `attempt`, `elapsedMs`, `unsyncedMutationCount`, y `nextDelayMs` proporcionan los datos necesarios para un indicador de ahorro o reingreso.

`request_failed` significa un fallo de solicitud retráctil, como un error de red o una respuesta HTTP 408, 429 o 5xx. `license_editing_connections_exceeded` quiere decir que las conexiones de edición con licencia están en uso y el servidor solicitó un reenvío.

## Gestionar conflictos en la aplicación [#conflict-recovery]

`CollaborationConflict` incendios una vez cuando una unidad entra en conflicto, después del intento de limpieza fuera de línea. Registrar el oyente antes de cargar cualquier documento. Su `reason` es `transform_failed`, `apply_failed`, `changeset_rejected`, `license_unit_type_rejected`, `permission_rejected`, o `remote_revert`; `message` y `revert` proporcionan detalles adicionales cuando está disponible.

`license_unit_type_rejected` indica que la licencia del servidor no cubre la colaboración para este tipo de documento.

```ts
import type { IEventParamConfig } from '@univerjs/core/facade'
import '@univerjs-pro/collaboration-client/facade'

const conflicts = new Map<string, IEventParamConfig['CollaborationConflict']>()
const conflictSubscription = univerAPI.addEvent(univerAPI.Event.CollaborationConflict, (event) => {
  conflicts.set(event.unitId, event)
})
```

El ejemplo conserva el evento para una pantalla de recuperación de host. El mapa vive sólo en memoria, por lo que la aplicación debe guardar o exportar cualquier `localChanges` antes de una actualización. Este evento es la única oportunidad para retenerlos; datos de caché que ya se han limpiado no se puede recuperar por una lectura posterior. `awaitingChangeset` puede ya haber sido aplicado en el servidor, por lo tanto no debe ser repetida ciegamente.

`cacheCleared: false` significa que un refresco volvería a reproducir las ediciones de caché viejas, por lo que la limpieza de caché debe resolverse antes de refrescarse. Limpiar el caché no significa que las ediciones no sincronizadas fueron guardadas. Un conflicto `permission_rejected` también requiere la resolución de acceso; la recarga no otorga permiso.

## Motivos del servidor y avisos de licencia [#server-rejections]

Cuando el servidor rechaza un cambio, `CollaborationConflict.message` lleva la razón por la que el servidor dio, si dio uno. No parse el texto de mensaje localizado para decidir la acción de recuperación; rama en `reason` en su lugar. `license_unit_type_rejected` requiere una licencia de servidor que cubre el tipo de documento, mientras que `license_editing_connections_exceeded` es una señal de reenvío: las ediciones no se conocen y siguen reiniciando. Mantenga el editor abierto hasta `hasWritePending(unitId)` se vuelve falso o la aplicación ha retenido.

La interfaz de usuario predeterminada muestra un aviso de capacidad de edición y, en un reenvío al menos 20 segundos después del primer envío, un aviso de ahorro de tiempo. Estos son eliminados cuando la unidad deja los estados en espera o se elimina. Un rechazo de dominio tiene un aviso dedicado también. `enableDefaultConflictUI: false` deshabilita los avisos de recuperación de conflictos solamente; no deshabilita estos avisos de espera o de dominio.
