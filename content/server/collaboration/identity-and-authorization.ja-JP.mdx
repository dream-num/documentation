title: 本人確認と認可
description: Transport、Endpoint、Service の Middleware を通じて既存の認証・認可システムを接続します。
---

Univer Collaboration SDKは、ユーザー、ロール、またはACLモデルを定義しません。アプリケーションは、輸送ミドルウェアで信頼できるアイデンティティを確立し、エンドポイントとサービスミドルウェアでリアルタイムと権限のあるコラボレーションデータを保護します。

このページでは、[ミドルウェアとイベント](/server/collaboration/middleware-and-events) を 1 つの具体的なタスクに適用します。ミドルウェアによるアイデンティティと認可を統合します。

## 編集・閲覧権限を確認する [#verify-permissions]

`pnpm example:permissions` を実行し、`http://127.0.0.1:3010` を開いて、順番にアカウントを切り替えます。

1. Bob としてセルを編集します。
2. Casey に切り替え、変更が表示され、セルが読み取り専用になっていることを確認します。
3. Dana に切り替え、文書を開けないことを確認します。

シートと範囲の権限は[オブジェクト権限のサンプル](/server/collaboration/examples#object-permissions)を参照してください。

## ID モデル

| 識別子 | 提供元 | 意味と寿命 |
| --- | --- | --- |
| `userID` | アプリケーション | 安定した業務上の ID。確定した変更セットの作成者 |
| `memberID` | Endpoint | 1 つの WebSocket Session のオンラインメンバー ID。再接続すると変わる |
| `sid + reqId` | クライアント | 再試行でも変わらない変更セット送信の識別子 |

ブラウザで送信されたユーザープロファイルフィールド、`memberID`、およびリビジョンは、アプリケーション認証の代替はできません。アプリケーションは、`context.userID`に安定したユーザーキーをマップします。

## Transport Middleware で本人情報を確立する

トランスポートは、すべてのコラボレーションHTTPリクエストに対してミドルウェアを実行します。アプリケーションは、Cookie、セッション、またはベアラートークンを読み、認証結果をコンテキストに添付することができます。

```ts
transport.use(async (context, next) => {
  const user = await auth.requireUser(context.incomingMessage);

  context.userID = user.id;
  context.customData.user = user;
  context.customData.tenantID = user.tenantID;
  context.customData.traceID = readTraceID(context.incomingMessage);

  await next();
});
```

認証が失敗すると、`next()` を呼び出すことなく HTTP レスポンスを終了します。

```ts
transport.use(async (context, next) => {
  const user = await auth.findUser(context.incomingMessage);
  if (!user) {
    context.response.statusCode = 401;
    context.response.end("Authentication required");
    return;
  }

  context.userID = user.id;
  await next();
});
```

SDK は Cookie 名、トークン形式、ユーザーテーブル、ログインフローを指定しません。

## WebSocket Session への本人情報の引き継ぎ

WebSocket パスは、クライアントペイロードでユーザーフィールドを信頼しません。エンドポイントは、認証された HTTP コンテキストを 1 回セッションチケットの手段によってリアルタイムセッションに処理します。

```text
Session Ticket の HTTP リクエスト
  → Transport Middleware で認証
  → Endpoint が { userID, customData } を保存
  → 不透明な使い捨てチケットを返却
  → WebSocket 接続時にチケットを消費
  → Session { userID, memberID, customData } を作成
```

チケット文字列には`userID`と`customData`は含まれていません。 `memberID`では、現在の接続のみを識別し、独立したアイデンティティ認証ではありません。 共有チケットストアを備えたマルチノード展開では、保存された`customData`がシリアライズされているため、JSON-serializableを維持する必要があります。

## 適切な境界で認可する

| 保護する操作 | Middleware |
| --- | --- |
| 共同編集の HTTP 入口 | Transport `use()` |
| WebSocket 接続 | Endpoint `connect` |
| Unit Room への参加 | Endpoint `joinUnit` |
| スナップショット、ブロック、変更セットの読み取り | Service `readUnitData` |
| 内容の編集の送信 | Service `submitChangeset` |
| Unit の作成 | Service `createUnit` |
| Unit の削除 | Service `deleteUnits` |
| Unit の復元 | Service `recoverUnits` |

エンドポイント`joinUnit`は、セッションがリアルタイムルームに入ることができるかどうかだけを制御します。 スナップショットと欠落したチェンジセットは、HTTP上で直接読み込むことができます。そのため、JOINチェックは`readUnitData`を置き換えることができません。 同様に、読み取り専用クライアントUIは製品ヒントであり、`submitChangeset`ポリシーをサーバーに置き換えません。

## 読み取り、JOIN、編集を保護する

```ts
import { CollabError } from "@univerjs-pro/collaboration-service";

endpoint.use("joinUnit", async (context, next) => {
  const allowed = await acl.canRead(context.session.userID, context.unitID);
  if (!allowed) {
    throw new CollabError("PERMISSION_DENIED", "Cannot join this Unit");
  }
  await next();
});

service.use("readUnitData", async (context, next) => {
  const allowed = await acl.canRead(context.userID, context.request.unitID);
  if (!allowed) {
    throw new CollabError("PERMISSION_DENIED", "Unit is not accessible");
  }
  await next();
});

service.use("submitChangeset", async (context, next) => {
  const unitID = context.request.changeset.unitID;
  const allowed = await acl.canEdit(context.userID, unitID);
  if (!allowed) {
    throw new CollabError("PERMISSION_DENIED", "Unit is read-only");
  }
  await next();
});
```

このポリシーでは、すべての changeset に編集権限が必要です。閲覧者にコメントを許可する場合は、[サーバーの実装例](https://github.com/dream-num/univer-collaboration-examples/blob/main/examples/permissions/server/main.ts)のように `isCommentOnlyChangeset()` でコメントのみの変更を識別し、コメント権限を確認します。

## Unit のライフサイクルを保護する

コラボレーションプロトコルは、既に存在するユニットを開きます。 「ドキュメントを作成する」は通常、`createUnitFromData()`または`createUnitFromSnapshot()`を呼び出す前に、製品レコードとACLを記述するアプリケーションAPIです。 ライフサイクルには、サービスミドルウェア保護が必要です。

```ts
service.use("createUnit", async (context, next) => {
  if (!(await acl.canCreate(context.userID, context.request.snapshot.type))) {
    throw new CollabError("PERMISSION_DENIED", "Unit creation denied");
  }
  await next();
});

service.use("deleteUnits", async (context, next) => {
  for (const unitID of context.request.unitIDs) {
    if (!(await acl.canDelete(context.userID, unitID))) {
      throw new CollabError("PERMISSION_DENIED", `Cannot delete ${unitID}`);
    }
  }
  await next();
});
```

`recoverUnits`を別々に保護します。一度削除権限を持っていたユーザーは、必ずしも回復権限を保持しません。

## customData で検索結果を再利用する

同じサービスコール内のミドルウェアは、重複クエリを避けるために`customData`を使うことができます。

```ts
service.use("submitChangeset", async (context, next) => {
  const unitID = context.request.changeset.unitID;
  context.customData.role ??= await acl.getRole(context.userID, unitID);

  if (context.customData.role === "viewer") {
    throw new CollabError("PERMISSION_DENIED", "Unit is read-only");
  }
  await next();
});
```

`customData`は、現在のコールまたはセッションにのみ属し、自動的に主張されていません。 役割、ACL、テナント関係は、アプリケーションストレージに残ります。

## 拡張モジュールには個別のポリシーが必要

歴史、スレッドコメント、Worktree、ファイル、および取引所はそれぞれ独自のサービスミドルウェアを持っています。

- 履歴リストとチェンジセットの読み込みは、呼び出し主がユニットを読み込むことができることを確認する必要があります。
- コメントリストは、コメントポリシーを追加、返信、編集、削除する際の読み取りアクセスをチェックする必要があります。
- Worktreeは、可視性、草案の編集、ステータス変更、およびマージのための別のチェックを必要とします。
- Worktreeはトランクに統合し、トランクサービスミドルウェアを経由します。
- ファイル `upload` は、`signUrl`と `download` check read access で、対象ユニットへの編集アクセスを確認する必要があります。
- 交換`import`と`export`は、クォータチェックの適切な場所であり、ソースユニットへのアクセスをチェックします。 インポートユニットを作成し、エクスポートされたユニットを読んだりしても、コアサービスミドルウェアを通過します。

コアコラボレーションサービスにインストールされているルールは、これらのモジュールを自動的に保護しません。各拡張用に構築された別の ACL データモデルではなく、同じアプリケーションポリシーサービスを再使用する必要があります。

## クライアントの現在のユーザーを設定する

`UserManagerService.setCurrentUser()`は、現在のUniverインスタンスのユーザーID、名前、アバターを設定し、フロントエンドコンポーネントはそこからこれらの値を読みます。コメントパネルの「Concern me」フィルタは、このユーザーIDを使用して、現在のユーザーを含むコメントを表示します。

Univerインスタンスが作成され、ドキュメントがロードされる前に呼び出します。

```ts
import { UserManagerService } from "@univerjs/core";

// currentUser is your application profile; id/name/avatar are example field names.
univer
  .__getInjector()
  .get(UserManagerService)
  .setCurrentUser({
    userID: currentUser.id,
    name: currentUser.name,
    avatar: currentUser.avatar ?? "",
  });
```

アプリケーションの安定したユーザー ID を `userID` にマップし、サーバー上で認証された `context.userID` と同一に保ちます。 コラボレーション中に共有されたメンバー名とアバターは、[プレゼンス](/server/collaboration/presence) で説明されているように、サーバーの `connect` ミドルウェアで設定されます。

[許可例](/server/collaboration/examples#permissions)は、完全な実行可能なバージョンです。
