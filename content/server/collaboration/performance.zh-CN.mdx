测试覆盖单文档多人编辑和多文档同时编辑两种场景。文档预热后，测试记录持续编辑期间的提交确认延迟、吞吐量、提交达成率，以及协同服务进程的 CPU 和内存占用。

## 测试环境

协同服务与数据库分别部署在独立的服务器上。结果表中的节点规格指图中的协同节点。

### 协同服务配置

4 核和 8 核节点均将 `runtime.maxLoadedUnits` 从默认值 1,200 调至 4,000，允许单节点在内存中同时保留最多 4,000 份文档。其余 SDK 运行时参数沿用默认值，工作线程数由 SDK 自动确定。快照也采用默认策略：距上次成功快照累计 50 个版本，或单次变更集达到 5 MiB 时触发。4 核和 8 核节点的协同服务进程内存上限分别为 14 GiB 和 29 GiB。

以下是压测服务的核心代码节选。适配器使用已初始化的 PostgreSQL 连接池和 OSS 客户端，传输层挂载到 Node.js HTTP 服务。

```ts
const dbAdapter = await PostgresS3DatabaseAdapter.create({
  pool,
  s3: { client, bucket, prefix },
});
const service = new UniverCollabService({
  dbAdapter,
  runtime: { maxLoadedUnits: 4000 },
});
const endpoint = new UniverCollabEndpoint(service);
const transport = createNodeTransport();
transport.register(endpoint);
transport.attach(server);
```

## 测试方法

### 模拟客户端

结果表中的“编辑人数”按独立会话计数。每个会话加入一份文档，通过 HTTP 提交单元格修改，并通过 WebSocket 接收服务端确认。测试脚本直接调用协同接口。HTTP 请求和 WebSocket 确认等待均采用 10 秒超时。

### 预热与正式采样

每轮先从指定快照创建文档，待所有会话加入后开始预热。首次编辑会触发服务端加载文档。单文档场景预先提交 1 次编辑。多文档场景中各文档预热时提交不同次数的编辑，从不同版本开始正式编辑，保存快照的时刻也随之错开。

所有文档完成预热后开始正式采样。结果表中的提交统计、延迟分位数、CPU 和内存均取自正式采样期间。

### 编辑负载

单文档场景使用 `blank`，逐步增加编辑人数。多文档场景分别使用上述三种快照，在每种快照下逐步增加活跃文档数。两种场景中，每次提交都只包含一条 `sheet.mutation.set-range-values`，向一个单元格写入一个数值。

| 测试条件 | 单文档多人编辑 | 多文档同时编辑 |
| --- | --- | --- |
| 每份文档编辑人数 | 按测试组调整，见结果表 | 固定为 2 人，适用于全部多文档测试 |
| 每次编辑的操作 | 错峰修改各自的单元格 | 错峰修改各自的单元格 |
| 每人编辑频率 | 每 6 秒 1 次 | 每 2 秒 1 次 |
| 每轮采样时长 | 300 秒 | 300 秒 |

## 指标定义

| 指标 | 定义 |
| --- | --- |
| 提交确认延迟 | 从客户端发出一次编辑，到该客户端收到服务端确认所经过的时间。P50、P95、P99 分别表示 50%、95%、99% 的成功提交在相应时间内收到确认。Max 表示成功提交中最长的确认延迟。 |
| 吞吐量 | 正式采样期间成功提交的次数除以采样时长，单位为次/秒。 |
| 提交达成率 | 成功提交数占计划提交数的百分比。计划提交数包含成功、失败及未发出的提交。 |
| CPU 均值 / 峰值（%） | 协同服务进程在正式采样期间的平均 CPU 占用和最高采样值。每个 CPU 核心满载计为 100%，多核合计可超过 100%。 |
| 内存峰值（MiB） | 正式采样期间协同服务进程常驻内存（RSS）的最大采样值。 |

### 并发规模的判定标准

每轮同时满足以下条件才算达标：

- 提交确认延迟 **P99 < 1,000 ms**。
- 提交达成率 **> 90%**。
- 协同服务进程持续运行，直到所有测试文档通过一致性核对。
- 正式采样期间快照处理跟得上持续写入，待处理快照任务没有持续增长。持续增长时记为“快照持续积压”。

只测一轮的档位取该轮结果；测了多轮的档位，每轮都须达标。

## 测试结果的适用范围

为评估服务端处理并发编辑的能力，测试使用 Node.js 脚本模拟编辑会话，直接调用协同接口提交单元格修改。提交确认延迟仅衡量脚本从发出请求到收到服务端确认所用的时间，不包含用户在浏览器中操作和等待表格渲染的时间。

本报告的数据仅供性能评估和单协同节点容量规划参考。实际性能取决于部署配置、网络条件、文档大小以及编辑操作的类型和频率。

“档位”指一组测试条件下的一个负载值，即编辑人数或活跃文档数。“最高达标档位”指在本次测试条件下满足判定标准的最大已测档位。部分达标档位的平均 CPU 占用已接近节点上限。**最高达标档位仅供容量规划参考，不宜直接作为生产环境的长期运行负载。** 实际部署时，应为并发高峰和资源占用波动预留安全余量，并在目标环境中用典型业务负载验证可长期稳定承载的规模。

#### 节点池选型建议

采用[多节点部署](/server/deployment)时，网关可按文档大小将编辑请求分别路由到中小型文档池和大型文档池。以下为各池的单节点选型参考，测试负载为每份文档 2 人、每人每 2 秒编辑一次。

- **中小型文档池建议优先评估 4 核 8 GiB。** 按 4 核 16 GiB 的实测结果估算，在 8 GiB 规格的内存预算内，空白文档可参考 2,300 份，每份约 10,000 个单元格的文档可参考 1,800 份。
- **大型文档池建议评估 8 核 16 GiB 或 8 核 32 GiB。** 每份约 100,000 个单元格时，8 核 32 GiB 的最高达标档位为 700 份，内存峰值也在 8 核 16 GiB 的预算内。这一场景的限制因素是快照处理：750 份时提交确认延迟仍然达标，但出现快照持续积压。
