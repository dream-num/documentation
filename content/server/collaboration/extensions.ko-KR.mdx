History, Thread Comment, File, Worktree는 필요에 따라 활성화하는 독립적인 협업 확장 모듈입니다. Transport, 신원 시스템, 물리 DB를 재사용할 수 있지만 Service, Middleware, Event, Database Adapter, 수명 주기 경계는 각각 유지합니다.

서버 측 Office 변환은 File과 Collaboration Service를 조합합니다. Office 파일과 협업 Unit 사이를 변환하며 자체 Service, Endpoint, Middleware를 갖습니다.

| 확장 모듈 | 핵심 협업과의 관계 |
| --- | --- |
| History | 핵심 Events를 관찰하여 파생 기록 인덱스 구성 |
| Thread Comment | 핵심 Unit Room 재사용. 댓글 앵커는 핵심 콘텐츠에 속함 |
| File | Unit이 참조하는 이미지, 첨부 파일, 교환 파일을 저장. Unit 데이터에는 파일 ID만 기록 |
| Office Exchange | 핵심 Service로 Unit을 생성·읽고 File로 파일을 읽고 씀 |
| Worktree | 핵심 Unit과 OT 기능을 재사용하고 초안을 트렁크에 병합 |

History, Thread Comment, File, Worktree는 각자의 Middleware, Events, Database Adapter를 구성합니다.

## 버전 기록

History는 Unit 생성과 확정된 변경 집합을 사용자에게 표시할 기록 항목으로 묶습니다. 이는 파생 인덱스이며 Unit 콘텐츠의 기준은 핵심 Collaboration Service에 확정된 변경 집합입니다.

```ts
const historyService = new UniverHistoryService({
  collabService,
  dbAdapter: historyDatabase,
  userProvider,
});

transport.register(new UniverHistoryEndpoint(historyService));
```

History Service를 생성하면 핵심 Service의 `unitCreated`, `changesetCommitted` Events를 구독하고 인덱스를 갱신합니다. `dispose()`는 이 구독을 해제합니다. 기본 정책은 변경 집합마다 기록을 만들지 않고 시간 구간과 특수 mutation에 따라 묶습니다.

History는 `getHistoryList`, `listHistoryCreators`, `getHistoryChangesets` 읽기 Middleware를 제공합니다. 인덱싱은 Service 내부에서 수행됩니다. `userProvider`는 이름·아바타 같은 표시 데이터만 보완하며 인증이나 권한 부여는 하지 않습니다. Event Listener 실패는 이미 확정된 핵심 변경 집합을 롤백하지 않으므로 History는 항상 재구축 가능한 파생 데이터로 취급해야 합니다.

## 스레드 댓글

Comment Service는 Sheets와 Docs의 댓글 본문, 답글, 편집, 삭제, 해결 상태를 관리합니다.

```ts
const commentService = new UniverCommentService({
  database: commentDatabase,
  userProvider,
});

transport.register(
  new UniverCommentEndpoint({
    service: commentService,
    roomHost: collabEndpoint,
  }),
);
```

댓글 본문은 Comment Adapter에 속합니다. Sheet나 Doc 콘텐츠를 따라 이동하는 앵커는 핵심 스냅샷과 변경 집합에 남습니다. Comment Endpoint는 주 Collaboration Endpoint의 Unit Room을 통해 `comment_update`를 발행할 수 있지만 실시간 메시지가 댓글 상태의 기준은 아닙니다. 클라이언트는 댓글 목록을 다시 읽어 복구할 수 있습니다.

Comment Service는 추가, 목록, 답글, 해결/다시 열기, 편집, 삭제 Middleware와 `commentCommitted` Event를 제공합니다. 핵심 Service의 읽기·편집 정책을 상속하지 않습니다.

## 파일 스토리지

File은 Univer 클라이언트가 업로드하는 바이너리 파일을 저장합니다. Unit에 삽입한 이미지와 첨부 파일, 그리고 가져오기와 내보내기의 원본 파일과 결과 파일입니다. Unit 데이터에는 파일 ID만 기록하고 클라이언트가 로드 시 ID를 다운로드 URL로 변환하므로 snapshot과 changeset이 가볍게 유지됩니다.

```ts
const fileService = new UniverFileService({
  database: fileDatabase,
  blobStore,
});

transport.register(new UniverFileEndpoint(fileService));
```

메타데이터와 콘텐츠는 독립적인 두 계약입니다. `IFileDatabaseAdapter`가 파일 레코드를, `IFileBlobStore`가 콘텐츠를 저장합니다. 교환용 임시 파일은 업로드한 사용자만 접근할 수 있고 Service가 주기적으로 정리합니다. Unit의 이미지와 첨부 파일은 `upload`, `signUrl`, `download` Middleware에서 Unit 권한으로 제어합니다.

## 서버 측 Office 변환

Exchange Service는 Office 파일을 협업 Unit으로 가져오고 Unit을 파일로 내보냅니다. 변환은 `@univerjs-pro/exchange-node`에 의존하고, Unit 생성과 읽기는 Collaboration Service를, 원본 파일과 결과 파일 저장은 File Service를 통해 처리합니다.

```ts
const exchangeService = new UniverExchangeService({ collabService, fileService });

transport.register(new UniverExchangeEndpoint(exchangeService));
```

가져오기와 내보내기는 task입니다. 클라이언트가 task를 만들고 결과를 폴링합니다. 가져오기는 Core Service의 `createUnit` Middleware를, 내보내기는 `readUnitData` Middleware를 거칩니다. Exchange 자체의 `import`, `export` Middleware는 속도 제한, 할당량, 감사에 사용합니다.

| Unit | 가져오기 | 내보내기 |
| --- | --- | --- |
| Sheet | xls, xlsx, csv, tsv | xlsx, csv, tsv |
| Doc | doc, docx | docx |
| Slide | ppt, pptx | pptx |
| Base | xls, xlsx, csv, tsv | xlsx, csv |
| PDF | pdf | pdf |

task는 Service 인스턴스 안에 보관되므로 가져오기와 내보내기 노드는 하나만 배포하고 Exchange의 세 라우트를 모두 그 노드로 보냅니다.

## Worktree 초안과 병합

Worktree는 하나 이상의 Unit에 격리된 초안, 동결, 병합 평가, Unit별 병합을 추가합니다.

```text
create → draft → ready → merging → merged
           ↑       │
           └ reopen┘

draft / ready → discarded
```

```ts
const worktreeService = new UniverCollabWorktreeService({
  trunk: {
    service: collabService,
    dbAdapter: coreDatabase,
  },
  dbAdapter: worktreeDatabase,
});
```

Worktree는 `(worktreeID, unitID)`별 독립 초안 변경 집합을 저장하며 핵심 Service의 Unit, OT, 제출 엔진을 재사용합니다. `draft` 상태만 추가 편집을 허용합니다. `markReady()`는 현재 초안 리비전을 동결하고 `mergeWorktree()`는 Unit을 하나씩 트렁크에 병합합니다.

Worktree Service에는 독립적인 수명 주기, 읽기, 초안 submit/apply/commit Middleware와 생성, 상태 변경, 병합 결과, 초안 변경 집합 커밋 Events가 있습니다. 최종 트렁크 쓰기는 여전히 핵심 Service 자체 Middleware를 거칩니다.

여러 Unit의 병합은 Unit 사이에서 원자적이지 않습니다. 애플리케이션은 각 Unit의 병합 결과를 표시해야 합니다.

## 독립 확장 지점

확장을 활성화할 때 각 경계를 별도로 검토하세요.

| 경계 | 핵심 | History | Comment | File | Worktree |
| --- | --- | --- | --- | --- | --- |
| Service | 독립 | 독립 | 독립 | 독립 | 독립 |
| Middleware | 공유 안 함 | 핵심 상속 안 함 | 핵심 상속 안 함 | 핵심 상속 안 함 | 핵심 상속 안 함 |
| Event | 핵심 수명 주기 | 핵심 Events 관찰 | `commentCommitted` | — | Worktree 수명 주기/커밋 |
| Database Adapter | 핵심 Adapter | History Adapter | Comment Adapter | File Adapter와 Blob Store | Worktree Adapter |

같은 데이터베이스를 사용해도 Adapter는 독립 계약을 가진 별도 객체입니다. Service와 Adapter도 각각 해제해야 합니다.

Office Exchange는 Core와 File의 저장소를 재사용합니다. 자체 `import`, `export` Middleware를 실행한 뒤에도 가져오기와 내보내기는 Core와 File의 Middleware를 거칩니다.

## Web SDK 기록 UI 연결 [#web-history]

History Endpoint를 협업 엔드포인트와 함께 연결하세요. Web SDK의 `historyServerUrl`은 `/{unitId}/list`, `/{unitId}/creators`, `/{unitId}/cs`의 공통 접두 경로이며 기본값은 `/universer-api/history`입니다. 다른 경로를 사용하면 호스트 History 플러그인과 제품 History UI 플러그인에 같은 URL을 설정하세요.

복원은 별도의 기록 복원 REST API가 아니라 협업 mutation으로 제출됩니다. 협업 로딩, 제출, 권한 설정을 유지해야 합니다. `createUnitComparisonEngine()`은 완전한 두 스냅샷을 읽기 전용으로 비교하므로 실행 중인 기록 서비스가 필요하지 않으며 버전을 저장하거나 복원하지 않습니다.
