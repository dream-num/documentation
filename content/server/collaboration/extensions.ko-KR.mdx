역사, 스레드 코멘트, 파일 및 Worktree는 코어를 변경하지 않고 협업을 확장하는 옵션 협업 확장 모듈입니다. 각 모듈은 자체 서비스, Middleware, 이벤트, 데이터베이스 어댑터 및 수명주기 경계를 제공합니다. 따라서 애플리케이션은 제품 요구 사항을 충족하는 모듈 만 사용할 수 있습니다. 모듈은 여전히 운송, 정체성 시스템 및 동일한 물리적 데이터베이스를 공유 할 수 있습니다.

Server-side Office Exchange는 파일 및 협업 서비스에 구축합니다. 그것은 Office 파일과 협업 장치 사이에 변환되며 자체 서비스, 엔드포인트 및 Middleware를 제공합니다.

| 확장 모듈 | 핵심 협업과의 관계 |
| --- | --- |
| History | 핵심 Events를 관찰하여 파생 기록 인덱스 구성 |
| Thread Comment | 핵심 Unit Room 재사용. 댓글 앵커는 핵심 콘텐츠에 속함 |
| File | Unit이 참조하는 이미지, 첨부 파일, 교환 파일을 저장. Unit 데이터에는 파일 ID만 기록 |
| Office Exchange | 핵심 Service로 Unit을 생성·읽고 File로 파일을 읽고 씀 |
| Worktree | 핵심 Unit과 OT 기능을 재사용하고 초안을 트렁크에 병합 |

History, Thread Comment, File 및 Worktree는 각각의 미들웨어, 이벤트 및 데이터베이스 어댑터를 구성합니다.

## 버전 기록

역사는 단위 생성을 돌리고 사용자가 볼 수있는 역사 항목으로 변경합니다. 인덱스는 파생됩니다 : 핵심 협업 서비스에서 확인 된 변경 세트는 단위 내용의 저자 소스를 유지합니다.

```ts
const historyService = new UniverHistoryService({
  collabService,
  dbAdapter: historyDatabase,
  userProvider,
});

transport.register(new UniverHistoryEndpoint(historyService));
```

구성 요소는 코어 서비스 `unitCreated` 및 `changesetCommitted` 이벤트에 가입하고 인덱스 전류를 유지하고 `dispose()`는 그 구독을 제거합니다. 기본적으로, 역사 그룹은 시간 창에 의해 변경되며 모든 변경 사항에 대한 항목이 아닌 특수 mutations로 변경됩니다.

역사는 `getHistoryList`, `listHistoryCreators` 및 `getHistoryChangesets`를 위한 미들웨어를 읽었습니다. 색인을 붙이는 것은 서비스 안쪽에 일어났습니다. `userProvider`는 이름과 아바타와 같은 전시 자료만 공급하고, 입증 또는 허가를 실행하지 않습니다. 사건 인 Listener 실패는 이미 확인한 핵심 변위, 그래서 역사는 항상 재건될 수 있는 파생한 자료로 대우되어야 합니다.

## 스레드 댓글

댓글 서비스 관리 코멘트 기관, replies, 편집, 삭제, 및 두 장과 문서 모두에 대한 해결 상태:

```ts
const commentService = new UniverCommentService({
  database: commentDatabase,
  userProvider,
});

transport.register(
  new UniverCommentEndpoint({
    service: commentService,
    roomHost: collabEndpoint,
  }),
);
```

코멘트 바디는 코멘트 어댑터에 속하지만, 시트 또는 Doc 컨텐츠로 이동하는 앵커는 핵심 스냅 샷 및 변경 세트의 일부 남아 있습니다. 코멘트 엔드 포인트는 `comment_update`를 메인 협업 엔드 포인트의 단위 룸으로 게시 할 수 있지만 실시간 메시지는 저자의 의견 상태가 아닙니다. 메시지를 놓는 클라이언트는 다시 코멘트를 나열하여 복구 할 수 있습니다.

Comment Service는 추가, 목록, 회신, 해결 또는 재개, 편집 및 삭제를 위한 Middleware를 제공하고, `commentCommitted` 이벤트를 출판합니다. Comment Service는 Core Service의 읽기 또는 편집 정책을 상속하지 않습니다.

## 파일 스토리지

파일 저장 Univer 클라이언트 업로드: 이미지 및 첨부 파일 단위로 삽입, 그리고 수입 및 수출의 소스 및 결과 파일. 단위 데이터 레코드 만 파일 ID, 클라이언트는 단위를로드 할 때 다운로드 URL에 ID를 해결. 스냅 샷 및 변경 집합 따라서 작은 체재.

```ts
const fileService = new UniverFileService({
  database: fileDatabase,
  blobStore,
});

transport.register(new UniverFileEndpoint(fileService));
```

Metadata 및 콘텐츠는 두 개의 독립적 인 계약입니다. `IFileDatabaseAdapter` 상점 파일 레코드 및 `IFileBlobStore` 저장 콘텐츠. 임시 교환 파일은 업로드 한 사용자에게만 액세스 할 수 있으며, 서비스는 일정에 삭제합니다. 단위 내부 이미지 및 첨부 파일은 `upload`, `signUrl` 및 `download` Middleware를 통해 단위 권한에 따라 달라질 수 있습니다.

## 서버 측 Office 변환

Exchange Service는 협업 단위 및 수출 단위로 사무실 파일을 가져옵니다. 그것은 변환을 위해 `@univerjs-pro/exchange-node`를 사용하고 협업 서비스를 통해 Units를 생성하고 읽습니다. File Service를 통해 소스 및 결과 파일을 저장하십시오.

```ts
const exchangeService = new UniverExchangeService({ collabService, fileService });

transport.register(new UniverExchangeEndpoint(exchangeService));
```

수입 및 수출은 작업입니다. 클라이언트는 작업을 만들고 그 결과에 대한 설문 조사를 생성합니다. 수입은 핵심 서비스의 `createUnit` Middleware를 통해 진행되며 `readUnitData`를 통해 수출됩니다. `import` 및 `export` Exchange 핸들 속도 제한, quotas 및 감사의 미들웨어.

| Unit | 가져오기 | 내보내기 |
| --- | --- | --- |
| Sheet | xls, xlsx, csv, tsv | xlsx, csv, tsv |
| Doc | doc, docx | docx |
| Slide | ppt, pptx | pptx |
| Base | xls, xlsx, csv, tsv | xlsx, csv |
| PDF | pdf | pdf |

작업은 서비스 인스턴스에서 살고, 그래서 응용 프로그램은 단일 수입 및 수출 노드를 배치하고 노드에 모든 3 개의 교환 경로.

## Worktree 초안과 병합

Worktree는 하나 이상의 Unit에 격리된 초안, 동결, 병합 평가, Unit별 병합을 추가합니다.

```text
create → draft → ready → merging → merged
           ↑       │
           └ reopen┘

draft / ready → discarded
```

```ts
const worktreeService = new UniverCollabWorktreeService({
  trunk: {
    service: collabService,
    dbAdapter: coreDatabase,
  },
  dbAdapter: worktreeDatabase,
});
```

Worktree는 `(worktreeID, unitID)`에 의해 자신의 초안 변경 집합을 저장하고 핵심 서비스의 단위, OT 및 제출 엔진을 재사용합니다. `draft` 국가 만 더 편집을받습니다. `markReady()`은 현재 초안 개정을 동결하고 `mergeWorktree()`가 한 번에 단위를 병합합니다.

Worktree 서비스는 자체 수명주기, 자체 읽기 Middleware, 초안 제출 / 승인 / 할당 Middleware, 생성, 상태 변경, 합병 결과 및 초안 변경을위한 이벤트가 있습니다. 최종 쓰기는 여전히 핵심 서비스의 Middleware를 통해 이동.

여러 Unit의 병합은 Unit 사이에서 원자적이지 않습니다. 애플리케이션은 각 Unit의 병합 결과를 표시해야 합니다.

## 독립 확장 지점

응용 프로그램이 확장 모듈을 활성화 할 때, 각 경계는 별도의 평가를 요구합니다.

| 경계 | 핵심 | History | Comment | File | Worktree |
| --- | --- | --- | --- | --- | --- |
| Service | 독립 | 독립 | 독립 | 독립 | 독립 |
| Middleware | 공유 안 함 | 핵심 상속 안 함 | 핵심 상속 안 함 | 핵심 상속 안 함 | 핵심 상속 안 함 |
| Event | 핵심 수명 주기 | 핵심 Events 관찰 | `commentCommitted` | — | Worktree 수명 주기/커밋 |
| Database Adapter | 핵심 Adapter | History Adapter | Comment Adapter | File Adapter와 Blob Store | Worktree Adapter |

사무실 교환은 핵심과 파일의 저장을 재사용합니다. `import` 및 `export` Exchange 런닝의 중간웨어, 수입 및 수출이 핵심 및 파일 미들웨어를 통해 여전히 패스합니다.

이 어댑터는 데이터베이스를 공유 할 수 있으며 여전히 별도의 계약으로 분리 된 객체를 유지 할 수 있습니다. 서비스 및 어댑터는 독립적으로 처분해야합니다.

## Web SDK 기록 UI 연결 [#web-history]

Web SDK, `historyServerUrl`는 `/{unitId}/list`의 공통 접두사이며 `/{unitId}/creators` 및 `/{unitId}/cs`와 `/universer-api/history`를 기본으로 구성해야 합니다. 다른 접두사가 사용되면 호스트 기록 플러그인 및 제품 역사 UI 플러그인은 동일한 URL로 구성되어야 합니다.

버전 복원은 협업 뮤테이션 경로를 통해 진행됩니다. 복원을위한 독립 역사 REST 엔드 포인트가 없습니다. 협업 로딩, 제출 및 승인은 구성되어야합니다. `createUnitComparisonEngine()`을 통해 2 개의 재료화된 스냅 샷을 비교하면 데이터 만 읽는 별도의 작업입니다. 그것은 실행 역사 서비스를 필요로하지 않으며 persists 또는 복원 버전이 없습니다.
