description: Understand how History, Thread Comment, Worktree, File, and server-side Office Exchange extend core collaboration.

History, Thread Comment, File, and Worktree are independent collaboration extension modules that can be enabled as needed. They can reuse the Transport, identity system, and physical database, but each keeps its own Service, Middleware, Event, Database Adapter, and lifecycle boundaries.

Server-side Office Exchange combines File with Collaboration Service: it converts between Office files and collaborative Units, with its own Service, Endpoint, and Middleware.

| Extension module | Relationship with Core Collaboration                                                                  |
| ---------------- | ----------------------------------------------------------------------------------------------------- |
| History          | Observes Core Events to build a derived history index                                                 |
| Thread Comment   | Reuses the Core Unit Room; comment anchors belong to Core content                                     |
| File             | Stores the images, attachments, and exchange files a Unit references; Unit data records only file IDs |
| Office Exchange  | Creates or reads Units through Core Service and reads and writes files through File                   |
| Worktree         | Reuses Core Unit and OT capabilities and merges drafts into the trunk                                 |

History, Thread Comment, File, and Worktree configure their own Middleware, Events, and Database Adapters.

## Version history

History groups Unit creation and confirmed changesets into user-facing history entries. It is a derived index: confirmed changesets in Core Collaboration Service remain the authoritative source for Unit content.

```ts
const historyService = new UniverHistoryService({
  collabService,
  dbAdapter: historyDatabase,
  userProvider,
});

transport.register(new UniverHistoryEndpoint(historyService));
```

The constructor subscribes to the Core Service `unitCreated` and `changesetCommitted` Events and updates the index. `dispose()` removes those subscriptions. The default policy groups changes by time window and special mutations rather than creating a history entry for every changeset.

History exposes read Middleware for `getHistoryList`, `listHistoryCreators`, and `getHistoryChangesets`. Indexing runs inside the service. `userProvider` only enriches display data such as names and avatars; it does not authenticate or authorize users. An Event Listener failure does not roll back an already confirmed Core changeset, so History should always be treated as rebuildable derived data.

## Thread Comment

Comment Service manages comment bodies, replies, edits, deletion, and solved state for Sheets and Docs:

```ts
const commentService = new UniverCommentService({
  database: commentDatabase,
  userProvider,
});

transport.register(
  new UniverCommentEndpoint({
    service: commentService,
    roomHost: collabEndpoint,
  }),
);
```

Comment bodies belong to the Comment Adapter. Anchors that move with Sheet or Doc content remain part of Core snapshots and changesets. The Comment Endpoint can publish `comment_update` through the main Collaboration Endpoint's Unit Room, but the realtime message is not the authoritative comment state; a Client can recover by listing comments again.

Comment Service provides Middleware for add, list, reply, solve/reopen, edit, and delete operations, plus a `commentCommitted` Event. It does not inherit the Core Service's read or edit policy.

## File storage

File stores the binary files that Univer clients upload: images and attachments inserted into a Unit, plus the source and result files of import and export. Unit data records only the file ID; the client resolves the ID to a download URL when loading, so snapshots and changesets stay small.

```ts
const fileService = new UniverFileService({
  database: fileDatabase,
  blobStore,
});

transport.register(new UniverFileEndpoint(fileService));
```

Metadata and content are two independent contracts: `IFileDatabaseAdapter` stores file records and `IFileBlobStore` stores content. Temporary exchange files are accessible only to their uploader and are cleaned up by the Service on a schedule; Unit images and attachments are controlled by Unit permissions through the `upload`, `signUrl`, and `download` Middleware.

## Server-side Office Exchange

Exchange Service imports Office files as collaborative Units and exports Units as files. It relies on `@univerjs-pro/exchange-node` for conversion, creates and reads Units through Collaboration Service, and stores source and result files through File Service:

```ts
const exchangeService = new UniverExchangeService({ collabService, fileService });

transport.register(new UniverExchangeEndpoint(exchangeService));
```

Import and export are tasks: the client creates a task and polls for the result. Import passes through the Core Service `createUnit` Middleware and export through `readUnitData`; Exchange's own `import` and `export` Middleware cover rate limits, quotas, and audit.

| Unit  | Import              | Export         |
| ----- | ------------------- | -------------- |
| Sheet | xls, xlsx, csv, tsv | xlsx, csv, tsv |
| Doc   | doc, docx           | docx           |
| Slide | ppt, pptx           | pptx           |
| Base  | xls, xlsx, csv, tsv | xlsx, csv      |
| PDF   | pdf                 | pdf            |

Tasks live in the Service instance, so deploy one import and export node and route all three Exchange routes to it.

## Worktree drafts and merge

Worktree adds isolated drafts, freezing, merge evaluation, and per-Unit merge for one or more Units:

```text
create → draft → ready → merging → merged
           ↑       │
           └ reopen┘

draft / ready → discarded
```

```ts
const worktreeService = new UniverCollabWorktreeService({
  trunk: {
    service: collabService,
    dbAdapter: coreDatabase,
  },
  dbAdapter: worktreeDatabase,
});
```

Worktree stores independent draft changesets by `(worktreeID, unitID)` while reusing the Core Service's Unit, OT, and submission engines. Only the `draft` state accepts further edits. `markReady()` freezes the current draft revision, and `mergeWorktree()` merges Units into the trunk one at a time.

Worktree Service owns independent lifecycle, read, draft submit/apply/commit Middleware, plus Events for creation, status changes, merge results, and draft changeset commits. A final write to the trunk still passes through the Core Service's own Middleware.

A multi-Unit merge is not atomic across Units. The application should display the merge result for each Unit.

## Independent extension points

When enabling an extension module, evaluate each boundary separately:

| Boundary         | Core           | History               | Comment               | File                        | Worktree                  |
| ---------------- | -------------- | --------------------- | --------------------- | --------------------------- | ------------------------- |
| Service          | Independent    | Independent           | Independent           | Independent                 | Independent               |
| Middleware       | Not shared     | Does not inherit Core | Does not inherit Core | Does not inherit Core       | Does not inherit Core     |
| Event            | Core lifecycle | Observes Core Events  | `commentCommitted`    | —                           | Worktree lifecycle/commit |
| Database Adapter | Core Adapter   | History Adapter       | Comment Adapter       | File Adapter and Blob Store | Worktree Adapter          |

Office Exchange reuses the storage of Core and File: after its own `import` and `export` Middleware run, import and export still pass through the Core and File Middleware.

These Adapters can use the same database while remaining separate objects with separate contracts. Services and Adapters should also be disposed independently.

## Connect the Web SDK history viewer [#web-history]

Mount the History Endpoint alongside the collaboration endpoints. The Web SDK `historyServerUrl` is the prefix for `/{unitId}/list`, `/{unitId}/creators`, and `/{unitId}/cs`; its default is `/universer-api/history`. If you expose a different prefix, configure the host History plugin and product History UI plugin with the same URL.

Restoring a version goes through the collaboration mutation path, not a standalone history REST restore endpoint. Keep collaboration loading, submission, and authorization configured. Read-only comparison of two materialized snapshots through `createUnitComparisonEngine()` is separate: it does not require a running history service and does not persist or restore versions.
