여러 사용자가 한 문서를 편집하는 경우와 여러 문서를 동시에 편집하는 경우를 시험했습니다. 문서 워밍업 후 편집을 지속하면서 확인 응답 지연 시간, 처리량, 계획 대비 제출 달성률, 협업 프로세스의 CPU 및 메모리 사용량을 측정했습니다.

## 테스트 환경

협업 서비스와 데이터베이스는 별도 서버에서 실행했습니다. 결과 표의 사양은 그림에 표시된 협업 노드의 사양입니다.

PostgreSQL은 문서 레코드, 변경 집합, 스냅샷 레코드와 블록 참조를 저장합니다. OSS는 스냅샷의 셀 데이터 블록을 저장합니다.

모든 결과는 단일 협업 노드에서 측정했습니다. 동시 편집 문서 수가 노드 용량을 넘으면 노드를 추가해 문서별로 편집 부하를 분산할 수 있습니다. 노드는 데이터베이스를 공유하며 발행/구독을 통해 룸, 접속 상태, 편집 내용 전파를 동기화합니다. [여러 협업 노드](/server/deployment#여러-협업-노드)를 참고하세요.

| 항목 | 구성 |
| --- | --- |
| Univer 협업 SDK 버전 | 1.5.2 |
| 운영체제 및 런타임 | Ubuntu 26.04.1 LTS, Node.js 24.14.0 |
| 스토리지 | PostgreSQL 18.6 및 Alibaba Cloud OSS |
| 데이터베이스 어댑터 | [PostgreSQL + S3 Adapter](/server/collaboration/database-adapters#postgresql-s3-adapter) |
| 협업 노드 | Alibaba Cloud ECS `ecs.g9i.xlarge`(4 vCPU, 16 GiB) 및 `ecs.g9i.2xlarge`(8 vCPU, 32 GiB), Intel Xeon 6982P-C, 40 GiB ESSD |
| 데이터베이스 서버 | Alibaba Cloud ECS `ecs.c9i.large`, 2 vCPU, 4 GiB, Intel Xeon 6982P-C, 60 GiB ESSD |
| 부하 생성기 | Alibaba Cloud ECS `ecs.u2a-c1m2.xlarge`, 4 vCPU, 8 GiB, AMD EPYC |
| 네트워크 | Alibaba Cloud 선전 리전. 클라이언트, 협업 노드, 데이터베이스가 리전 내 사설망으로 통신하며 OSS는 내부 엔드포인트를 사용합니다. |

### 협업 서비스 설정

두 노드 모두 `runtime.maxLoadedUnits`를 기본값 1,200에서 4,000으로 높여 문서를 최대 4,000개까지 메모리에 유지했습니다. 다른 런타임 설정은 기본값이며 워커 스레드 수는 SDK가 결정합니다. 기본 스냅샷 정책에 따라 마지막 스냅샷 성공 후 50개 리비전이 쌓이거나 단일 변경 집합이 5 MiB에 도달하면 스냅샷이 생성됩니다.

테스트 서비스의 주요 코드입니다. 어댑터는 초기화된 PostgreSQL 연결 풀과 OSS 클라이언트를 사용하며 전송 계층은 Node.js HTTP 서버에 연결됩니다.

```ts
const dbAdapter = await PostgresS3DatabaseAdapter.create({
  pool,
  s3: { client, bucket, prefix },
});
const service = new UniverCollabService({
  dbAdapter,
  runtime: { maxLoadedUnits: 4000 },
});
const endpoint = new UniverCollabEndpoint(service);
const transport = createNodeTransport();
transport.register(endpoint);
transport.attach(server);
```

## 테스트 스냅샷

각 문서는 스냅샷으로 초기화합니다. 아래 셀 수는 워밍업 전에 데이터나 수식이 들어 있는 셀의 수입니다.

| 스냅샷 | 채워진 셀 수 | 내용 |
| --- | ---: | --- |
| `blank` | 0 | 빈 워크시트 |
| `10k-cells` | 약 10,000 | 숫자, 텍스트, 수식 |
| `100k-cells` | 약 100,000 | 숫자, 텍스트, 수식 |

데이터가 있는 두 시트는 모두 26열입니다. 14열은 숫자, 9열은 텍스트, 3열은 같은 행의 데이터를 참조하는 수식입니다.

## 테스트 방법

### 모의 클라이언트

편집자 수는 독립 세션 수입니다. 각 세션은 한 문서에 접속하여 HTTP로 셀 변경을 제출하고 WebSocket으로 확인 응답을 받습니다. 스크립트가 협업 API를 직접 호출하며 HTTP 요청과 확인 응답 대기에는 각각 10초의 제한 시간이 적용됩니다.

### 워밍업 및 측정

매회 지정한 스냅샷으로 문서를 만든 뒤 모든 세션이 접속하면 워밍업을 시작합니다. 첫 편집 시 서버가 문서를 로드합니다. 단일 문서는 미리 한 번 편집합니다. 여러 문서는 순서대로 1회부터 49회까지 편집하고 50번째 문서부터 다시 1회로 시작합니다. 문서마다 시작 리비전이 달라져 스냅샷 저장 시점이 분산됩니다.

모든 문서의 워밍업이 끝나면 측정을 시작합니다. 최초 제출 지연은 워밍업 중 별도로 기록합니다. 표에 표시된 제출 통계, 지연 백분위수, CPU 및 메모리 값은 측정 구간의 값입니다.

### 편집 부하

단일 문서에서는 `blank`의 편집자 수를 늘렸습니다. 여러 문서에서는 세 스냅샷 각각에 대해 활성 문서 수를 늘렸습니다. 두 시나리오 모두 한 번의 제출에 `sheet.mutation.set-range-values` 연산 하나만 포함해 셀 하나에 숫자를 기록합니다.

| 조건 | 단일 문서 | 여러 문서 |
| --- | --- | --- |
| 문서당 편집자 수 | 시험별로 다름(결과 표 참조) | 모든 시험에서 2명 |
| 편집 작업 | 각자 자신의 셀에 시차를 두고 기록 | 각자 자신의 셀에 시차를 두고 기록 |
| 편집자당 빈도 | 6초에 1회 | 2초에 1회 |
| 회당 측정 시간 | 300초 | 300초 |

## 지표 정의

| 지표 | 정의 |
| --- | --- |
| 확인 응답 지연 | 클라이언트가 편집을 제출한 시점부터 서버의 확인 응답을 받을 때까지의 시간입니다. P50, P95, P99는 각각 성공한 제출의 50%, 95%, 99%가 확인된 시간이며 Max는 성공한 제출 중 가장 긴 시간입니다. |
| 처리량 | 측정 구간의 성공한 제출 수를 측정 시간으로 나눈 초당 제출 수입니다. |
| 제출 달성률 | 계획한 제출 수 중 성공한 비율입니다. 계획한 수에는 실패하거나 전송하지 못한 제출도 포함됩니다. |
| CPU 평균 / 최대 (%) | 측정 구간에서 협업 프로세스가 사용한 CPU의 평균과 최대 관측값입니다. 한 코어를 완전히 사용하면 100%이므로 합계는 100%를 넘을 수 있습니다. |
| 최대 메모리 (MiB) | 측정 구간에서 협업 프로세스의 상주 메모리(RSS)가 기록한 최댓값입니다. |

### 합격 기준

제출 확인 지연 **P99 < 1,000 ms**, 제출 달성률 **> 90%**를 충족하고 모든 테스트 문서의 일관성 검사가 끝날 때까지 협업 프로세스가 동작해야 합격입니다. 지연과 달성률은 반올림 전 값으로 판단합니다.

각 부하 단계는 보고서에 실린 측정 횟수를 기준으로 평가합니다. 한 번만 측정했으면 그 결과를 사용하고 여러 번 측정했으면 매회 합격해야 합니다. 측정이 중단되거나 지표가 누락된 경우 누락 사유를 표시합니다.

## 결과의 적용 범위

서버의 동시 편집 처리 능력을 측정하기 위해 Node.js 스크립트가 편집 세션을 모의하고 API에 직접 셀 수정을 제출합니다. 확인 응답 지연은 전송부터 확인까지의 시간이며 브라우저 조작과 시트 렌더링 시간은 제외합니다.

결과는 성능 평가와 단일 노드 용량 계획의 참고 자료입니다. 실제 성능은 배포 구성, 네트워크, 문서 크기, 편집의 종류와 빈도에 따라 달라집니다.

최대 합격 부하는 테스트한 단계 중 기준을 충족한 가장 높은 부하입니다. 일부 합격 단계에서는 평균 CPU 사용량이 노드 한계에 가까웠습니다. **최대 합격 부하는 용량 계획의 참고값이며 운영 환경의 지속 부하 목표로 그대로 사용하기 어렵습니다.** 동시 편집 집중과 자원 사용량 변화에 대비해 여유를 두고 대상 환경에서 대표적인 부하로 장기 처리 용량을 검증하세요.

#### 노드 풀 사양 선택

[다중 노드 배포](/server/deployment)에서 게이트웨이는 문서 크기에 따라 서로 다른 풀로 편집 요청을 보낼 수 있습니다. 다음은 문서마다 2명이 각각 2초에 한 번 편집하는 경우의 노드당 사양입니다.
