Univer Collaboration SDK 不定義使用者、角色，也不提供 ACL 模型。應用在 Transport Middleware 中建立可信身分，再透過 Endpoint 與 Service Middleware 保護即時 Session 和權威協同資料。

本頁將 [Middleware 與 Event](/server/collaboration/middleware-and-events) 應用到一個具體場景：接入身分與權限。

## 驗證編輯與唯讀權限 [#verify-permissions]

執行 `pnpm example:permissions`，開啟 `http://127.0.0.1:3010`，依序切換帳號。

1. 用 Bob 修改一個儲存格。
2. 切換到 Casey，確認能看到剛才的修改，但不能編輯儲存格。
3. 切換到 Dana，確認無法開啟這份文件。

## 身分模型

| 識別碼 | 提供方 | 意義與生命週期 |
| --- | --- | --- |
| `userID` | 應用 | 穩定的業務身分，也是已確認變更集的作者 |
| `memberID` | Endpoint | 一個 WebSocket Session 的線上成員 ID；重新連線後會改變 |
| `sid + reqId` | 用戶端 | 變更集提交識別碼，在重試期間保持不變 |

瀏覽器提交的使用者資料、`memberID` 和 revision 都不能代替應用認證。應用應將自身穩定的使用者主鍵對映到 `context.userID`。

## 在 Transport Middleware 中建立身分

每個 Collaboration HTTP request 到達時，Transport 都會執行一次 Middleware。應用可以讀取 Cookie、Session 或 Bearer Token，並將認證結果附加到 Context：

```ts
transport.use(async (context, next) => {
  const user = await auth.requireUser(context.incomingMessage);

  context.userID = user.id;
  context.customData.user = user;
  context.customData.tenantID = user.tenantID;
  context.customData.traceID = readTraceID(context.incomingMessage);

  await next();
});
```

認證失敗時直接結束 HTTP response，不再呼叫 `next()`：

```ts
transport.use(async (context, next) => {
  const user = await auth.findUser(context.incomingMessage);
  if (!user) {
    context.response.statusCode = 401;
    context.response.end("Authentication required");
    return;
  }

  context.userID = user.id;
  await next();
});
```

SDK 不規定 Cookie 名稱、Token 格式、使用者表結構或登入流程。

## 身分如何進入 WebSocket Session

WebSocket 路徑不信任客戶端 payload 中的使用者欄位。Endpoint 透過一次性 Session Ticket 將已認證的 HTTP Context 帶入即時 Session：

```text
Session Ticket HTTP 請求
  → Transport Middleware 驗證身分
  → Endpoint 儲存 { userID, customData }
  → 傳回不透明的一次性票證
  → WebSocket 開啟時消耗票證
  → 建立 Session { userID, memberID, customData }
```

Ticket 字串本身既不包含 `userID`，也不包含 `customData`。`memberID` 只標識當前連線，不能單獨作為身分憑據。多節點部署共用 Ticket 儲存時，儲存的 `customData` 會被序列化，因此必須保證它可以 JSON 序列化。

## 在正確的邊界授權

| 需要保護的行為 | Middleware |
| --- | --- |
| 協同 HTTP 入口 | Transport `use()` |
| WebSocket 連線 | Endpoint `connect` |
| 加入 Unit Room | Endpoint `joinUnit` |
| 讀取快照、區塊或變更集 | Service `readUnitData` |
| 提交內容編輯 | Service `submitChangeset` |
| 建立 Unit | Service `createUnit` |
| 刪除 Unit | Service `deleteUnits` |
| 還原 Unit | Service `recoverUnits` |

Endpoint 的 `joinUnit` 只決定 Session 能否進入即時 Room。Snapshot 和 missing changeset 可以直接透過 HTTP 讀取，因此 JOIN 檢查無法替代 `readUnitData`。同理，客戶端只讀 UI 只是產品層面的提示，不能替代伺服器端的 `submitChangeset` 策略。

## 保護讀取、JOIN 與編輯

```ts
import { CollabError } from "@univerjs-pro/collaboration-service";

endpoint.use("joinUnit", async (context, next) => {
  const allowed = await acl.canRead(context.session.userID, context.unitID);
  if (!allowed) {
    throw new CollabError("PERMISSION_DENIED", "Cannot join this Unit");
  }
  await next();
});

service.use("readUnitData", async (context, next) => {
  const allowed = await acl.canRead(context.userID, context.request.unitID);
  if (!allowed) {
    throw new CollabError("PERMISSION_DENIED", "Unit is not accessible");
  }
  await next();
});

service.use("submitChangeset", async (context, next) => {
  const unitID = context.request.changeset.unitID;
  const allowed = await acl.canEdit(context.userID, unitID);
  if (!allowed) {
    throw new CollabError("PERMISSION_DENIED", "Unit is read-only");
  }
  await next();
});
```

上述策略對所有 changeset 都要求編輯權限。如果檢視者也可以留言，可參考[範例的伺服器實作](https://github.com/dream-num/univer-collaboration-examples/blob/main/examples/permissions/server/main.ts)，用 `isCommentOnlyChangeset()` 識別僅含留言操作的變更集，再檢查留言權限。

### 工作表變更檢查

`submitChangeset` 策略只對每個變更集授權一次。開啟變更套用攔截後，伺服器還會逐條校驗工作表變更，包括凍結、網格線、列與欄的顯示狀態、工作表插入與複製，以及保護規則變更。其中任一項超出呼叫方的權限點位時，整個變更集都會被拒絕。可透過 `UniverCollaborationServerPlugin` 的 `enableMutationApplyInterceptor` 選項，或環境變數 `ENABLE_MUTATION_APPLY_INTERCEPTOR=true` 開啟攔截。

## 保護 Unit 生命週期

協同協議開啟的都是已經存在的 Unit。“新建文件”通常由應用自己的 API 完成：先寫入產品記錄和 ACL，再呼叫 `createUnitFromData()` 或 `createUnitFromSnapshot()`。生命週期同樣需要透過 Service Middleware 保護：

```ts
service.use("createUnit", async (context, next) => {
  if (!(await acl.canCreate(context.userID, context.request.snapshot.type))) {
    throw new CollabError("PERMISSION_DENIED", "Unit creation denied");
  }
  await next();
});

service.use("deleteUnits", async (context, next) => {
  for (const unitID of context.request.unitIDs) {
    if (!(await acl.canDelete(context.userID, unitID))) {
      throw new CollabError("PERMISSION_DENIED", `Cannot delete ${unitID}`);
    }
  }
  await next();
});
```

`recoverUnits` 需要單獨保護。使用者曾經擁有刪除權限，並不代表始終擁有恢復權限。

## 透過 customData 重用查詢結果

同一次 Service 呼叫中的 Middleware 可以透過 `customData` 複用查詢結果，避免重複查詢：

```ts
service.use("submitChangeset", async (context, next) => {
  const unitID = context.request.changeset.unitID;
  context.customData.role ??= await acl.getRole(context.userID, unitID);

  if (context.customData.role === "viewer") {
    throw new CollabError("PERMISSION_DENIED", "Unit is read-only");
  }
  await next();
});
```

`customData` 只屬於當前呼叫或當前 Session，不會自動持久化。角色、ACL 和租戶關係仍應儲存在應用自己的儲存中。

## 擴充模組需要獨立策略

History、Thread Comment、Worktree、File 和 Exchange 各自擁有獨立的 Service Middleware：

- History list 和 changeset read 應檢查呼叫方能否讀取該 Unit。
- Comment list 檢查讀取權限，add、reply、edit、delete 使用評論策略。
- Worktree 需要分別檢查可見性、draft 編輯、狀態變化和 merge。
- Worktree 合入 trunk 時仍然經過 trunk Service 的 Middleware。
- File 的 `upload` 檢查目標 Unit 的編輯權限，`signUrl` 和 `download` 檢查讀取權限。
- Exchange 的 `import` 和 `export` 是執行配額檢查和來源 Unit 訪問檢查的位置；匯入時建立 Unit、匯出時讀取 Unit 仍然經過 Core Service 的 Middleware。

安裝在核心 Collaboration Service 上的規則不會自動保護這些模組。應複用應用同一套 policy service，不必為每個擴充套件模組另外建立 ACL 資料模型。

## 在用戶端設定目前使用者

`UserManagerService.setCurrentUser()` 為當前 Univer 例項設定使用者 ID、名稱和頭像，前端元件從這裡讀取這些值。例如，評論面板的“與我有關”篩選項使用該使用者 ID 顯示與當前使用者相關的評論。

在建立 Univer 例項之後、載入文件之前呼叫該方法：

```ts
import { UserManagerService } from "@univerjs/core";

// currentUser is your application profile; id/name/avatar are example field names.
univer
  .__getInjector()
  .get(UserManagerService)
  .setCurrentUser({
    userID: currentUser.id,
    name: currentUser.name,
    avatar: currentUser.avatar ?? "",
  });
```

將應用的穩定使用者 ID 對映到 `userID`，並與伺服器端認證得到的 `context.userID` 保持一致。協同過程中共享的成員名稱與頭像在伺服器端 `connect` Middleware 中設定，詳見 [Presence](/server/collaboration/presence)。

完整可執行的版本見 [Permissions 範例](/server/collaboration/examples#permissions)。
