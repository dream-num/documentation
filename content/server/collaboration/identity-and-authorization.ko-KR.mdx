Univer Collaboration SDK는 사용자, 역할, 또는 ACL 모델을 정의하지 않습니다. 응용 프로그램은 전송 Middleware에서 신뢰할 수있는 ID를 설정하고 Endpoint 및 Service Middleware와 실시간 세션 및 권한 협업 데이터를 보호합니다.

이 페이지는 [Middleware 및 이벤트](/server/collaboration/middleware-and-events)를 하나의 콘크리트 작업에 적용합니다: 미들웨어를 통해 정체성과 권한성을 통합합니다.

## 편집 및 읽기 권한 검증 [#verify-permissions]

이전 예제를 중지하고 실행 `pnpm example:permissions`. 오픈 `http://127.0.0.1:3010` 두 개의 별도의 브라우저 컨텍스트: 로그인 **Alice · 편집자** 하나와 같이 **밥 · 뷰어** 다른 경우. 편집기는 문서를 수정할 수 있으며, 뷰어는 동기화 된 결과를 볼 수 있지만 수정할 수 없습니다. [서버/main.ts](https://github.com/dream-num/univer-collaboration-examples/blob/main/examples/permissions/server/main.ts) 코드를 따르기 위해: ID 해상도에 `transport.use()`, 읽는 체크에서 `readUnitData`, 객실 체크인 `joinUnit`, 그리고 체크를 편집 `submitChangeset`. 데모 쿠키 및 사용자 목록을 자신의 인증 및 문서 ACL로 대체하십시오. **Frontend readonly state 혼자 이다 충분 한.**

이 페이지는 **Casey · 액세스 없음** 계정을 제공합니다. 계정으로 로그인하면 문서 로딩을 차단하고 스냅샷 요청은 HTTP 403을 반환합니다.

## 신원 모델

| 식별자 | 제공 주체 | 평균 및 수명 |
| --- | --- | --- |
| `userID` | 애플리케이션 | 안정적인 업무 신원이며 확정된 변경 집합의 작성자 |
| `memberID` | Endpoint | WebSocket Session 하나의 온라인 멤버 ID. 재연결하면 변경됨 |
| `sid + reqId` | 클라이언트 | 재시도해도 유지되는 변경 집합 제출 식별자 |

브라우저, `memberID` 및 개정에 의해 제출된 사용자 프로필 필드는 애플리케이션 인증을 대체할 수 없습니다. 응용 프로그램은 `context.userID`에 안정적인 사용자 키를 맵니다.

## Transport Middleware에서 신원 확립

전송은 모든 협업 HTTP 요청에 대한 Middleware를 실행합니다. 응용 프로그램은 쿠키, 세션 또는 Bearer 토큰을 읽고 Context에 정통한 결과를 첨부 할 수 있습니다.

```ts
transport.use(async (context, next) => {
  const user = await auth.requireUser(context.incomingMessage);

  context.userID = user.id;
  context.customData.user = user;
  context.customData.tenantID = user.tenantID;
  context.customData.traceID = readTraceID(context.incomingMessage);

  await next();
});
```

인증이 실패하면 `next()`를 호출하지 않고 HTTP 응답을 종료합니다.

```ts
transport.use(async (context, next) => {
  const user = await auth.findUser(context.incomingMessage);
  if (!user) {
    context.response.statusCode = 401;
    context.response.end("Authentication required");
    return;
  }

  context.userID = user.id;
  await next();
});
```

SDK는 Cookie 이름, 토큰 형식, 사용자 테이블, 로그인 흐름을 지정하지 않습니다.

## WebSocket Session에 신원이 전달되는 방식

WebSocket 경로는 클라이언트 페이로드에서 사용자 필드를 신뢰하지 않습니다. 엔드포인트는 한 번 세션 티켓의 의미로 실시간 세션에 정통 HTTP 컨텍스트를 수행합니다.

```text
Session Ticket HTTP 요청
  → Transport Middleware에서 인증
  → Endpoint가 { userID, customData } 저장
  → 불투명한 일회용 티켓 반환
  → WebSocket 연결 시 티켓 소비
  → Session { userID, memberID, customData } 생성
```

티켓 문자열에는 `userID` 또는 `customData`가 포함되어 있지 않습니다. `memberID`는 현재 연결만 식별하며 독립적 인 ID 자격 증명이 아닙니다. 공유 티켓 저장소가있는 멀티 노드 배포에서 저장 된 `customData`은 일관되게 유지되므로 JSON-serializable을 유지해야합니다.

## 올바른 경계에서 권한 부여

| 보호할 동작 | Middleware |
| --- | --- |
| 협업 HTTP 진입 | Transport `use()` |
| WebSocket 연결 | Endpoint `connect` |
| Unit Room 참여 | Endpoint `joinUnit` |
| 스냅샷, 블록, 변경 집합 읽기 | Service `readUnitData` |
| 콘텐츠 편집 제출 | Service `submitChangeset` |
| Unit 생성 | Service `createUnit` |
| Unit 삭제 | Service `deleteUnits` |
| Unit 복구 | Service `recoverUnits` |

Endpoint `joinUnit`는 세션이 실시간 룸에 들어갈 수 있는지 만 제어합니다. Snapshots 및 누락 된 변경 세트는 HTTP를 통해 직접 읽을 수 있으므로, JOIN 체크는 `readUnitData`를 대체 할 수 없습니다. 마찬가지로, 읽기 전용 클라이언트 UI는 제품 힌트이며 서버의 `submitChangeset` 정책을 대체하지 않습니다.

## 읽기, JOIN, 편집 보호

```ts
import { CollabError } from "@univerjs-pro/collaboration-service";

endpoint.use("joinUnit", async (context, next) => {
  const allowed = await acl.canRead(context.session.userID, context.unitID);
  if (!allowed) {
    throw new CollabError("PERMISSION_DENIED", "Cannot join this Unit");
  }
  await next();
});

service.use("readUnitData", async (context, next) => {
  const allowed = await acl.canRead(context.userID, context.request.unitID);
  if (!allowed) {
    throw new CollabError("PERMISSION_DENIED", "Unit is not accessible");
  }
  await next();
});

service.use("submitChangeset", async (context, next) => {
  const unitID = context.request.changeset.unitID;
  const allowed = await acl.canEdit(context.userID, unitID);
  if (!allowed) {
    throw new CollabError("PERMISSION_DENIED", "Unit is read-only");
  }
  await next();
});
```

실제 응용 프로그램은 일반적으로 모든 세 가지 규칙을 설치 : HTTP 및 JOIN에 대한 정책을 읽고, 제출에 대한 정책을 편집합니다.

## Unit 수명 주기 보호

공동 프로토콜은 이미 존재하는 단위를 엽니 다. "Create document"는 일반적으로 `createUnitFromData()` 또는 `createUnitFromSnapshot()`를 호출하기 전에 제품 레코드와 ACL를 작성하는 응용 API입니다. 수명주기는 또한 서비스 미들웨어 보호를 요구합니다.

```ts
service.use("createUnit", async (context, next) => {
  if (!(await acl.canCreate(context.userID, context.request.snapshot.type))) {
    throw new CollabError("PERMISSION_DENIED", "Unit creation denied");
  }
  await next();
});

service.use("deleteUnits", async (context, next) => {
  for (const unitID of context.request.unitIDs) {
    if (!(await acl.canDelete(context.userID, unitID))) {
      throw new CollabError("PERMISSION_DENIED", `Cannot delete ${unitID}`);
    }
  }
  await next();
});
```

`recoverUnits`를 별도로 보호하십시오. 한 번 삭제 권한을받은 사용자는 반드시 복구 권한을 유지하지 않습니다.

## customData로 조회 결과 재사용

동일한 서비스 전화 내의 Middleware는 중복 쿼리를 피하기 위해 `customData`를 사용할 수 있습니다.

```ts
service.use("submitChangeset", async (context, next) => {
  const unitID = context.request.changeset.unitID;
  context.customData.role ??= await acl.getRole(context.userID, unitID);

  if (context.customData.role === "viewer") {
    throw new CollabError("PERMISSION_DENIED", "Unit is read-only");
  }
  await next();
});
```

`customData`는 현재 통화 또는 세션에만 속하며 자동으로 인식되지 않습니다. 역할, ACL 및 열악한 관계는 애플리케이션 저장소에 남아 있습니다.

## 확장 모듈에는 별도 정책이 필요합니다

History, Thread Comment, Worktree, File, Exchange는 각각 자신의 서비스 Middleware가 있습니다.

- 역사 목록 및 변경 사항은 콜러가 단위를 읽을 수 있다는 것을 확인해야합니다.
- 댓글 목록은 읽는 접근을 검사해야 합니다, 추가, 대답, 편집 및 삭제는 덧글 정책을 적용합니다.
- Worktree는 가시성, 초안 편집, 상태 변경 및 합병을 위한 별도의 검사를 요구합니다.
- Worktree는 트렁크 서비스 Middleware를 통해 여전히 전환됩니다.
- `upload`는 `signUrl` 및 `download` 체크 읽기 액세스가 진행되는 동안 대상 단위에 대한 액세스를 편집해야합니다.
- 교환 `import` 및 `export`는 할당량 검사를 위한 적당한 장소이고 근원 단위에 접근에 체크를 위해; 수입한 단위를 창조하고 수출한 단위를 아직도 핵심 서비스 Middleware를 통해서 읽으십시오.

핵심 협업 서비스에 설치된 규칙은 이 모듈을 자동으로 보호하지 않습니다. 동일한 응용 정책 서비스는 각 확장을 위해 내장 된 별도의 ACL 데이터 모델보다 오히려 재사용되어야합니다.

## 클라이언트에서 현재 사용자 설정

`UserManagerService.setCurrentUser()`는 현재 Univer 인스턴스의 사용자 ID, 이름 및 avatar를 설정하고, frontend 구성 요소는 이러한 값을 다음과 같이 읽습니다. 예를 들어, 이 사용자 ID를 사용하여 현재 사용자의 의견을 표시하십시오.

Univer 인스턴스가 생성되고 문서가 로드되기 전에 호출하십시오.

```ts
import { UserManagerService } from "@univerjs/core";

// currentUser is your application profile; id/name/avatar are example field names.
univer
  .__getInjector()
  .get(UserManagerService)
  .setCurrentUser({
    userID: currentUser.id,
    name: currentUser.name,
    avatar: currentUser.avatar ?? "",
  });
```

`userID`에 응용 프로그램의 안정적인 사용자 ID를지도하고 서버에서 정통 `context.userID`와 동일하게 유지하십시오. 공동 작업 중에 회원 이름과 아바타는 [- 연혁](/server/collaboration/presence)에서 설명 된 서버의 `connect` Middleware에서 설정됩니다.

[Permissions 예제](/server/collaboration/examples#permissions)는 완전한 runnable 버전입니다.
