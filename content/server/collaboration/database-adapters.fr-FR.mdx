title: Adaptateurs de base de données
description: Comprenez le contrat de persistance collaborative et choisissez entre Memory, SQLite, PostgreSQL et un Database Adapter personnalisé.
---

Un adaptateur de base de données persiste les données de collaboration de base que le Service de collaboration gère. Le Service possède la sémantique de l'unité, de l'OT et de la révision, et l'adaptateur transforme ces sémantiques en opérations de stockage atomiques qui sont sûres à reessayer. Pour connecter une base de données qui n'est pas couverte par les adaptateurs intégrés, implémenter `IDatabaseAdapter` et satisfaire son contrat comportemental complet.

Les adaptateurs de base de données sont open source sous Apache-2.0. Le code source est disponible dans [univer-collaboration-sdk-community](https://github.com/dream-num/univer-collaboration-sdk-community), et les paquets utilisent les mêmes noms et versions que tous les autres paquets.

## Vérifier la persistance [#verify-persistence]

Arrêtez le démarrage rapide et lancez `pnpm example:database-adapter` à partir de la racine du dépôt. Ouvrez `http://127.0.0.1:3010/?unit=persistent-sheet`, modifiez une cellule et validez le changement dans un deuxième navigateur. Puis arrêtez le serveur, exécutez à nouveau la même commande et rouvrez la même URL. La valeur doit être toujours présente.

Le [serveur de l’exemple](https://github.com/dream-num/univer-collaboration-examples/blob/main/examples/database-adapter/server/main.ts) enregistre les données dans `examples/database-adapter/.data/collaboration.sqlite`.

## Données stockées par l’Adapter

Pour chaque document collaboratif (Unit), l’Adapter stocke trois types de données.

- **L’enregistrement de l’Unit** contient l’identifiant du document, son type, son créateur, sa date de création et sa révision courante (`headRevision`). L’Adapter met à jour la révision dans la même opération que l’écriture du changeset. L’application peut gérer dans `UnitRecord.metadata` ses propres champs, par exemple le nom du document (`name`), l’identifiant de la dernière personne à l’avoir modifié (`lastEditorID`) et la date de cette modification (`lastModifiedAt`).
- **Les instantanés** conservent le contenu du document à une révision donnée. Pour lire une révision, le Service peut charger l’instantané le plus récent dont la révision ne dépasse pas celle demandée, puis rejouer les modifications jusqu’à cette dernière. Pour un classeur, l’Adapter stocke également les blocs de données référencés par l’instantané.
- **Les changesets** regroupent les opérations d’une soumission. L’Adapter les stocke dans l’ordre des révisions et conserve les identifiants de soumission `sid` et `reqId`. Le Service peut ainsi reconnaître une nouvelle tentative du client et éviter d’appliquer deux fois la même modification.[^submission-idempotency] L’application peut enregistrer dans `ChangesetRecord.metadata` l’origine de la modification (`source`) ou l’identifiant d’une opération métier associée (`operationId`).

Pour définir ces champs à la création ou à la soumission, consultez la section [Métadonnées persistantes](/server/collaboration/middleware-and-events#persistent-metadata).

Une suppression logique conserve ces données. L’édition peut reprendre après restauration. Après une suppression définitive, les données du document sont inaccessibles et son identifiant ne peut plus être utilisé.

L’application gère les utilisateurs, les rôles et les droits d’accès. History, Thread Comment et Worktree disposent chacun de leur propre interface Adapter.

## Règles de lecture et d’écriture de l’Adapter

Toute implémentation de `IDatabaseAdapter` doit respecter les règles suivantes.

| Opération | Règle |
| --- | --- |
| Créer une Unit | Enregistrer de façon atomique l’Unit, métadonnées comprises, l’instantané initial et les blocs Sheet qu’il référence afin que l’ensemble soit lisible simultanément. |
| Valider un changeset | Ne valider que si la révision courante correspond à la révision attendue (CAS)[^revision-cas]. En une écriture atomique, enregistrer le changeset avec ses métadonnées, remplacer intégralement les métadonnées de l’Unit et incrémenter la révision de un. En cas d’écart, renvoyer la révision courante sans rien écrire. |
| Lire les changesets | Renvoyer les changesets de la plage demandée dans l’ordre croissant des révisions, sans lacune. Conserver les valeurs d’origine de `sid` et `reqId` pour que le Service puisse reconnaître un doublon pour la même Unit. |
| Enregistrer un instantané | Dès que l’instantané est lisible, tous les blocs Sheet qu’il référence doivent l’être aussi. |
| Supprimer ou restaurer des Units | Appliquer l’opération au lot entier. Si un élément échoue, conserver l’état initial de tout le lot. |

## Memory Adapter

[`@univerjs-pro/collaboration-database-memory`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-memory) fonctionne à l'intérieur du processus Node.js. Il est adapté pour:

- aux tests unitaires et d’intégration
- aux environnements de développement temporaires
- contrôle rapide de l'assemblage personnalisé Middleware ou Client

```ts
import { MemoryDatabaseAdapter } from "@univerjs-pro/collaboration-database-memory";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";

const database = new MemoryDatabaseAdapter();
const service = new UniverCollabService({ dbAdapter: database });
```

L'adaptateur mémoire suit le même contrat de révision, CAS et idempotency que les implémentations persistantes. Ses données n'existent que dans le processus Node.js actuel et sont perdues lorsque ce processus s'en va.

## SQLite Adapter

[`@univerjs-pro/collaboration-database-sqlite`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-sqlite) stocke les données dans un fichier SQLite. Il convient au développement, aux essais, aux applications locales et à une utilisation à petite échelle.

```ts
import { mkdir } from "node:fs/promises";

import { SQLiteDatabaseAdapter } from "@univerjs-pro/collaboration-database-sqlite";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";

await mkdir("./data", { recursive: true });

const database = new SQLiteDatabaseAdapter({
  filename: "./data/collaboration.sqlite",
  busyTimeoutMs: 5_000,
});
const service = new UniverCollabService({ dbAdapter: database });
```

Il initialise le schéma lorsque la base de données est vide et ne vérifie le schéma que lorsqu'il existe déjà. L'emplacement du fichier, la méthode de sauvegarde et tout autre paramètre SQLite sont déterminés par l'application.

## PostgreSQL Adapter

[`@univerjs-pro/collaboration-database-postgres`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-postgres) stocke toutes les données de collaboration Core dans PostgreSQL, y compris les blocs de cellules référencés par les snapshots de feuilles. Plusieurs nœuds de collaboration peuvent partager la même base.

```ts
import { PostgresDatabaseAdapter } from "@univerjs-pro/collaboration-database-postgres";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";
import { Pool } from "pg";

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
const database = await PostgresDatabaseAdapter.create({ pool });
const service = new UniverCollabService({ dbAdapter: database });
```

L'application possède le pool et le ferme après avoir éliminé le Service. `create()` initialise le schéma `collaboration` dans une base de données vide et ne vérifie qu'un schéma existant.

Si vous disposez d’un stockage objet compatible S3, nous recommandons l’[adaptateur PostgreSQL + S3](#postgresql-s3-adapter) pour réduire la taille de la base et de ses sauvegardes.

## PostgreSQL + S3 Adapter [#postgresql-s3-adapter]

[`@univerjs-pro/collaboration-database-postgres-s3`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-postgres-s3) stocke les blocs de cellules dans un bucket compatible S3. Les Units, les changesets, les enregistrements de snapshot et les références aux blocs restent dans PostgreSQL.

Les données des cellules représentent l’essentiel du snapshot d’un grand classeur. Placer ces blocs dans S3 réduit la taille de la base PostgreSQL et de ses sauvegardes. La capacité de stockage des blocs peut évoluer indépendamment de la base à mesure que les classeurs grossissent.

Définissez `DATABASE_URL` sur la chaîne de connexion PostgreSQL, `S3_REGION` sur la région du bucket et `S3_BUCKET` sur le nom d’un bucket existant.

```ts
import { S3Client } from "@aws-sdk/client-s3";
import { PostgresS3DatabaseAdapter } from "@univerjs-pro/collaboration-database-postgres-s3";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";
import { Pool } from "pg";

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
const client = new S3Client({ region: process.env.S3_REGION });
const database = await PostgresS3DatabaseAdapter.create({
  pool,
  s3: { client, bucket: process.env.S3_BUCKET! },
});
const service = new UniverCollabService({ dbAdapter: database });
```

## Database Adapters personnalisés

Un adaptateur personnalisé est généralement approprié dans les cas suivants:

- l’application utilise déjà MySQL ou une autre base métier
- Les demandes de collaboration doivent utiliser des mécanismes de base de données que possède l'application
- les exigences d’exploitation ou de conformité dépassent le périmètre des Adapters intégrés

Implémentez `IDatabaseAdapter` et injectez-le dans le Service comme un Adapter intégré :

```ts
const database = new ApplicationCollaborationDatabase({ pool });
const service = new UniverCollabService({ dbAdapter: database });
```

Le Service ne dépend pas d'une base de données spécifique, mais il ne peut pas ajouter de transactions, de CAS ou de déduplication à une implémentation personnalisée. L'Adaptateur doit mettre en œuvre le contrat complet en utilisant les capacités de sa base de données. Les implémentations intégrées dans le [dépôt communautaire](https://github.com/dream-num/univer-collaboration-sdk-community) appliquent le même contrat à différentes bases de données et servent de références.

## Stocker les données métier

**Utilisez `metadata` pour obtenir des informations jointes à un document ou à un ensemble de modifications.** L'application peut définir ces champs lorsqu'elle crée un document ou soumet un jeu de modifications, et les Adaptateurs intégrés les sauvegardent avec les données de collaboration. Voir [Middleware et événements](/server/collaboration/middleware-and-events#persistent-metadata).

**Utilisez Middleware ou Events pour écrire pour séparer les tables d'affaires.** Pour vérifier une tentative d'opération, écrivez à une table d'audit dans Middleware. Pour mettre à jour une table commerciale après un commit réussi, écoutez pour `changesetCommitted`. Par défaut, ces écritures s'exécutent en dehors de la transaction de collaboration. Un conflit de révision peut provoquer une nouvelle exécution de commit-stade Middle Software, de sorte qu'une réessayer ne doit pas créer un enregistrement dupliqué. Les événements sont livrés dans le processus sur une base de meilleur effort. Utilisez-les pour les données que l'application peut reremplir ou reconstruire.

**Utilisez un adaptateur de base de données personnalisé lorsque l'application a besoin de sa propre base de données et de son propre schéma, ou lorsque les données d'affaires et de collaboration doivent être écrites dans une seule transaction.** Lorsque vous appelez le Service, l'application peut passer le contexte comme un ID d'opération d'entreprise dans `customData`. L'adaptateur peut alors lire les champs dont il a besoin de `ctx.customData` et décider quelles tables mettre à jour. Par exemple, `commitChangeset()` peut utiliser l'ID d'opération pour mettre à jour l'enregistrement d'entreprise correspondant dans la même transaction qui enregistre les changements.

`customData` Adaptateurs intégrés ne persistent pas automatiquement ses champs, et ils ne les utilisent pas pour écrire aux tables d'affaires.

## Stockage des modules d’extension

Les modules d'extension tels que History, Thread Comment, Worktree et File définissent chacun une interface d'adaptateur de base de données indépendante. Leurs adaptateurs peuvent partager une base de données ou utiliser un stockage séparé. Une seule implémentation personnalisée peut également fournir plusieurs interfaces d'adaptateur et être injecté dans les Services correspondants.

Comme ces interfaces Adapter sont indépendantes, le SDK ne fournit pas de transactions entre modules par défaut. Même lorsque plusieurs modules partagent une base de données, l'application possède la stratégie de cohérence entre modules.

## Choisir un Adapter

| Adapter         | Usage adapté                                                                     | Contrainte principale                                                                                                          |
| --------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Memory          | Tests, exemples, développement temporaire                                        | Les données sont perdues lorsque le processus se termine                                                                       |
| SQLite          | Développement, tests, applications locales, petite échelle                       | Base monofichier dont l’application gère les réglages                                                                          |
| PostgreSQL + S3 | Applications PostgreSQL avec stockage objet, notamment pour les grands classeurs | L’application gère la base et le bucket. Sans stockage compatible S3, utilisez l’[adaptateur PostgreSQL](#postgresql-adapter). |
| Personnalisé    | Bases existantes ou intégration métier spécifique                                | L’application doit implémenter et vérifier le contrat complet                                                                  |

L’application possède chaque Adapter injecté. Libérez le Service avant l’Adapter :

```ts
await service.dispose();
await database.dispose();
```

Consultez l’[exemple Database Adapter](/server/collaboration/examples#database-adapter) exécutable pour comparer les implémentations.

[^submission-idempotency]: L’idempotence permet de réessayer une soumission sans appliquer deux fois ses modifications. Conservez le même identifiant : un contenu identique avec un nouvel identifiant constitue une nouvelle soumission.

[^revision-cas]: Le CAS ne modifie une valeur que si elle correspond encore à la valeur attendue. La vérification de la révision et l’écriture suivante doivent être atomiques pour empêcher deux soumissions concurrentes de valider la même révision.
