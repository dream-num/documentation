Un Database Adapter persiste les données collaboratives centrales utilisées par Collaboration Service. Les développeurs peuvent implémenter `IDatabaseAdapter` pour connecter toute base capable de satisfaire son contrat comportemental complet. Le Service gère la sémantique des Units, de l’OT et des révisions ; l’Adapter la traduit en opérations de persistance atomiques et sûres à réessayer.

Les Database Adapters sont open source sous Apache-2.0 ; le code se trouve dans [univer-collaboration-sdk-community](https://github.com/dream-num/univer-collaboration-sdk-community), avec les mêmes noms de paquet et versions que les autres paquets.

## Vérifier la persistance [#verify-persistence]

Arrêtez Quick Start puis lancez `pnpm example:database-adapter` depuis la racine. Ouvrez `http://127.0.0.1:3010/?unit=persistent-sheet`, modifiez une cellule et vérifiez-la dans un second navigateur. Arrêtez, relancez la même commande et rouvrez la même URL : la valeur doit rester. Le fichier est `examples/database-adapter/.data/collaboration.sqlite` ; ne le supprimez pas entre les lancements. Le serveur lit le Unit existant et appelle `createUnitFromData()` seulement pour `UNIT_NOT_FOUND`. Voir [server/main.ts](https://github.com/dream-num/univer-collaboration-examples/blob/main/examples/database-adapter/server/main.ts).

## Données stockées par l’Adapter

Pour chaque document collaboratif (Unit), l’Adapter stocke trois types de données.

- **L’enregistrement de l’Unit** contient l’identifiant du document, son type, son créateur, sa date de création et sa révision courante (`headRevision`). L’Adapter met à jour la révision dans la même opération que l’écriture du changeset. L’application peut gérer dans `UnitRecord.metadata` ses propres champs, par exemple le nom du document (`name`), l’identifiant de la dernière personne à l’avoir modifié (`lastEditorID`) et la date de cette modification (`lastModifiedAt`).
- **Les instantanés** conservent le contenu du document à une révision donnée. Pour lire une révision, le Service peut charger l’instantané le plus récent dont la révision ne dépasse pas celle demandée, puis rejouer les modifications jusqu’à cette dernière. Pour un classeur, l’Adapter stocke également les blocs de données référencés par l’instantané.
- **Les changesets** regroupent les opérations d’une soumission. L’Adapter les stocke dans l’ordre des révisions et conserve les identifiants de soumission `sid` et `reqId`. Le Service peut ainsi reconnaître une nouvelle tentative du client et éviter d’appliquer deux fois la même modification.[^submission-idempotency] L’application peut enregistrer dans `ChangesetRecord.metadata` l’origine de la modification (`source`) ou l’identifiant d’une opération métier associée (`operationId`).

Pour définir ces champs à la création ou à la soumission, consultez la section [Métadonnées persistantes](/server/collaboration/middleware-and-events#persistent-metadata).

Une suppression logique conserve ces données. L’édition peut reprendre après restauration. Après une suppression définitive, les données du document sont inaccessibles et son identifiant ne peut plus être utilisé.

L’application gère les utilisateurs, les rôles et les droits d’accès. History, Thread Comment et Worktree disposent chacun de leur propre interface Adapter.

## Règles de lecture et d’écriture de l’Adapter

Toute implémentation de `IDatabaseAdapter` doit respecter les règles suivantes.

| Opération | Règle |
| --- | --- |
| Créer une Unit | Enregistrer de façon atomique l’Unit, métadonnées comprises, l’instantané initial et les blocs Sheet qu’il référence afin que l’ensemble soit lisible simultanément. |
| Valider un changeset | Ne valider que si la révision courante correspond à la révision attendue (CAS)[^revision-cas]. En une écriture atomique, enregistrer le changeset avec ses métadonnées, remplacer intégralement les métadonnées de l’Unit et incrémenter la révision de un. En cas d’écart, renvoyer la révision courante sans rien écrire. |
| Lire les changesets | Renvoyer les changesets de la plage demandée dans l’ordre croissant des révisions, sans lacune. Conserver les valeurs d’origine de `sid` et `reqId` pour que le Service puisse reconnaître un doublon pour la même Unit. |
| Enregistrer un instantané | Dès que l’instantané est lisible, tous les blocs Sheet qu’il référence doivent l’être aussi. |
| Supprimer ou restaurer des Units | Appliquer l’opération au lot entier. Si un élément échoue, conserver l’état initial de tout le lot. |

## Memory Adapter

[`@univerjs-pro/collaboration-database-memory`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-memory) est une implémentation en mémoire du processus adaptée :

- aux tests unitaires et d’intégration ;
- aux environnements de développement temporaires ;
- à la validation rapide de Middleware personnalisés ou de l’assemblage client.

```ts
import { MemoryDatabaseAdapter } from "@univerjs-pro/collaboration-database-memory";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";

const database = new MemoryDatabaseAdapter();
const service = new UniverCollabService({ dbAdapter: database });
```

Memory Adapter respecte les mêmes contrats de révision, de CAS et d’idempotence que les implémentations persistantes, mais toutes les données résident dans le processus Node.js courant et disparaissent à son arrêt.

## SQLite Adapter

[`@univerjs-pro/collaboration-database-sqlite`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-sqlite) est une implémentation SQLite persistante pour le développement, les tests, les applications locales et les usages à petite échelle.

```ts
import { mkdir } from "node:fs/promises";

import { SQLiteDatabaseAdapter } from "@univerjs-pro/collaboration-database-sqlite";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";

await mkdir("./data", { recursive: true });

const database = new SQLiteDatabaseAdapter({
  filename: "./data/collaboration.sqlite",
  busyTimeoutMs: 5_000,
});
const service = new UniverCollabService({ dbAdapter: database });
```

Il initialise le schéma dans une base vide et ne fait que vérifier une base existante. L’emplacement du fichier, les sauvegardes et les autres réglages SQLite relèvent de l’application.

## PostgreSQL Adapter

[`@univerjs-pro/collaboration-database-postgres`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-postgres) est une implémentation persistante basée sur node-postgres que plusieurs nœuds de collaboration peuvent partager.

```ts
import { PostgresDatabaseAdapter } from "@univerjs-pro/collaboration-database-postgres";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";
import { Pool } from "pg";

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
const database = await PostgresDatabaseAdapter.create({ pool });
const service = new UniverCollabService({ dbAdapter: database });
```

L’application possède le pool et le ferme après avoir libéré le Service. `create()` initialise le schéma `collaboration` dans une base vide et ne fait que vérifier un schéma existant.

## Database Adapters personnalisés

Un Adapter personnalisé convient généralement si :

- l’application utilise déjà MySQL ou une autre base métier ;
- les soumissions collaboratives doivent s’intégrer à des mécanismes de base propres à l’application ;
- les exigences d’exploitation ou de conformité dépassent le périmètre des Adapters intégrés.

Implémentez `IDatabaseAdapter` et injectez-le dans le Service comme un Adapter intégré :

```ts
const database = new ApplicationCollaborationDatabase({ pool });
const service = new UniverCollabService({ dbAdapter: database });
```

Le Service ne dépend pas d’une base particulière, mais ne peut pas ajouter transactions, CAS ou déduplication à votre implémentation. L’Adapter doit réaliser le contrat complet avec les capacités de sa base. Les implémentations intégrées du [dépôt communautaire](https://github.com/dream-num/univer-collaboration-sdk-community) montrent le même contrat sur différentes bases et servent de référence.

## Stocker les données métier

**Utilisez `metadata` pour les informations rattachées à un document ou à un changeset.** L’application peut définir ces champs à la création du document ou à la soumission du changeset. L’Adapter intégré les enregistre avec les données collaboratives. Voir [Métadonnées persistantes](/server/collaboration/middleware-and-events#persistent-metadata).

**Utilisez les Middleware ou les Events pour écrire dans des tables métier distinctes.** Pour consigner une tentative d’opération, écrivez dans une table d’audit depuis un Middleware. Pour mettre à jour une table après la réussite du commit, écoutez `changesetCommitted`. Par défaut, ces écritures ont lieu en dehors de la transaction collaborative. Un conflit de révision peut relancer le Middleware de commit. Prévoyez le cas d’une nouvelle tentative pour éviter les doublons. Les Events sont locaux au processus et leur livraison n’est pas garantie. Ils conviennent aux données que l’application peut compléter ou reconstruire ultérieurement.

**Utilisez un Adapter personnalisé si l’application a besoin de sa propre base et de son propre schéma, ou si les données métier et collaboratives doivent être écrites dans la même transaction.** Lors d’un appel au Service, l’application peut transmettre dans `customData` un identifiant d’opération métier, par exemple. La méthode de l’Adapter peut lire les champs nécessaires dans `ctx.customData` et choisir les tables à mettre à jour. Ainsi, `commitChangeset()` peut utiliser cet identifiant pour mettre à jour l’enregistrement métier dans la transaction qui enregistre le changeset.

La portée de `customData` est limitée à l’appel en cours. Les Adapters intégrés ne persistent pas automatiquement ses champs et ne les utilisent pas pour écrire dans les tables métier.

## Stockage des modules d’extension

History, Thread Comment, Worktree et File définissent des interfaces Database Adapter indépendantes. Leurs Adapters peuvent partager une base ou utiliser des stockages distincts. Une seule implémentation personnalisée peut aussi fournir plusieurs interfaces Adapter et être injectée dans les Services correspondants.

Ces interfaces étant indépendantes, le SDK ne fournit pas par défaut de transactions intermodules. Même avec une base partagée, la stratégie de cohérence intermodules appartient à l’application.

## Choisir un Adapter

| Adapter | Usage adapté | Contrainte principale |
| --- | --- | --- |
| Memory | Tests, exemples, développement temporaire | Données perdues à l’arrêt du processus |
| SQLite | Développement, tests, applications locales, petite échelle | Base monofichier dont l’application gère les réglages |
| PostgreSQL | Déploiements multi-nœuds et bases PostgreSQL existantes | L’application gère le pool et l’exploitation de la base |
| Personnalisé | Bases existantes ou intégration métier spécifique | L’application doit implémenter et vérifier le contrat complet |

L’application possède chaque Adapter injecté. Libérez le Service avant l’Adapter :

```ts
await service.dispose();
await database.dispose();
```

Consultez l’[exemple Database Adapter](/server/collaboration/examples#database-adapter) exécutable pour comparer les implémentations.

[^submission-idempotency]: L’idempotence permet de réessayer une soumission sans appliquer deux fois ses modifications. Conservez le même identifiant : un contenu identique avec un nouvel identifiant constitue une nouvelle soumission.

[^revision-cas]: Le CAS ne modifie une valeur que si elle correspond encore à la valeur attendue. La vérification de la révision et l’écriture suivante doivent être atomiques pour empêcher deux soumissions concurrentes de valider la même révision.
