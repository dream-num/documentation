Промежуточное ПО и События являются точками расширения общего назначения Collaboration SDK. Идентификацию и авторизацию интегрируют через Middleware. Промежуточные программы проверяют или ограничивают операцию до ее запуска; События записывают изменения или запускают последующую работу после подтверждения изменения состояния. Оба поддерживают журналирование, отслеживание запросов, метрики и обновления производного состояния.

## Два момента расширения

| | Middleware | Event |
| --- | --- | --- |
| Выполнение | Во время операции | После подтверждения изменения состояния |
| Участие в операции или её отклонение | Да | Нет |
| Дополнение Context вызова | Да | Прочитывает контекст и результат, который несет Событие |
| Ошибка обработчика | Может завершить текущую операцию ошибкой | Изолирована от уже определённого доменного результата |
| Типичные задачи | Идентификация, авторизация, проверка, логи, замер времени | Производные индексы, кеши, метрики, уведомления внутри процесса |

Используйте промежуточное ПО, когда вы должны решить, может ли операция продолжаться. Используйте Событие, когда вам нужно только наблюдать, что изменение состояния уже произошло.

## Модель выполнения Middleware

Промежуточное ПО для того же действия формирует асинхронную цепочку в порядке регистрации. `await next()` входит в следующее Промежуточном ПО, а операция SDK выполняется в самой внутренней точке:

```ts
service.use("submitChangeset", async (context, next) => {
  const startedAt = performance.now();
  context.customData.startedAt = startedAt;

  try {
    await next();
  } finally {
    metrics.observe("collaboration.submit.duration", performance.now() - startedAt);
  }
});
```

Промежуточное ПО может считывать запрос, относящийся к действию, обмениваться данными вызова через `customData`, проверять системы ввода или запроса перед `next()` и записывать продолжительность или результаты после возвращения `next()`. Бросок `CollabError` отклоняет ожидаемую операцию совместной работы.

Транспортное HTTP-промежуточное ПО может прекратить ответ HTTP без вызова `next()`. Сервисное и Endpoint-промежуточное ПО должно отклоняться с явной ошибкой, а не молча пропускать `next()` .

## Middleware Transport

`transport.use()` регистрирует Middleware для обычных HTTP-запросов; они выполняются в порядке регистрации. Вызовите `await next()`, чтобы продолжить обработку, или завершите ответ напрямую. `transport.useUpgrade()` обрабатывает рукопожатия WebSocket.

В следующем примере записывается продолжительность HTTP, аутентифицируется запрос и устанавливается доверенный `userID`, а затем регистрируется конечная точка совместной работы:

```ts
transport.use(async (context, next) => {
  const start = performance.now();
  context.response.once("finish", () => {
    recordHttpDuration({
      method: context.incomingMessage.method,
      route: context.route?.path ?? "unmatched",
      status: context.response.statusCode,
      durationMs: performance.now() - start,
    });
  });
  await next();
});

transport.use(async (context, next) => {
  const user = await authenticate(context.incomingMessage);
  if (!user) {
    context.response.statusCode = 401;
    context.response.end("Authentication required");
    return;
  }
  context.userID = user.userId;
  await next();
});

transport.register(collaborationEndpoint);
```

Приложение поставляет `recordHttpDuration` и `authenticate`. Конечная точка использует `userID`, установленный более ранним Middleware. Наблюдатель продолжительности работает до аутентификации, поэтому также регистрируются отклоненные запросы.

`context.route?.path` - это полный шаблон маршрута, доступный после того, как выполнение достигает конечной точки. Используйте событие `finish` для измерения, когда ответ завершается. Отказы перед маршрутизацией и неизвестные пути записываются как `unmatched`.

## Middleware Endpoint

Endpoint Middleware охватывает операции сеанса и присутствия в режиме реального времени:

| Action | Момент | Типичные задачи |
| --- | --- | --- |
| `connect` | После погашения билета и создания Session, до HELLO | Политика подключения, имя и аватар участника |
| `joinUnit` | До входа Session в Room Unit | Допуск в Room и видимость Unit |
| `receivePresence` | После получения Presence от вошедшей Session, до рассылки | Проверка и фильтрация Presence |
| `sendPresence` | До отправки Presence каждому участнику | Фильтрация по получателю |

```ts
endpoint.use("receivePresence", async (context, next) => {
  if (JSON.stringify(context.payload).length > 8_000) {
    throw new CollabError("INVALID_REQUEST", "Presence payload is too large");
  }
  await next();
});
```

`session.userID` и `session.customData` от конечной точки исходят из HTTP-запроса, который выдал билет на сеанс. Конечная точка создает `memberID` для текущей сессии WebSocket, и этот идентификатор изменяется после повторного подключения.

## Middleware Service

Service Middleware охватывает жизненный цикл авторитетных данных о совместной работе:

| Action | Граница | Типичные задачи |
| --- | --- | --- |
| `readUnitData` | До чтения снимков, блоков или изменений | Политика чтения, проверки арендатора, аудит |
| `createUnit` | До атомарного создания Unit | Проверка типов, политика создания, бизнес-правила |
| `deleteUnits` | До записи пакета удаления | Политика удаления и проверки каждой Unit |
| `recoverUnits` | До записи пакета восстановления | Политика восстановления и аудит |
| `submitChangeset` | После получения отправки, до проверки на дубликаты и OT | Проверить права на редактирование или ограничить размер отправки |
| `applyChangeset` | После OT, до применения changeset к документу | Проверить преобразованные операции, например затрагивают ли они защищённый диапазон |
| `commitChangeset` | После применения changeset к промежуточному состоянию, до записи через Adapter | Задать метаданные, которые нужно сохранить с этой отправкой |

```ts
service.use("createUnit", async (context, next) => {
  await creationPolicy.assertAllowed({
    userID: context.userID,
    unitID: context.request.snapshot.unitID,
    type: context.request.snapshot.type,
  });
  context.customData.creationPolicyChecked = true;
  await next();
});
```

`submitChangeset` запускается один раз для каждого логического представления. Разрешение на пересмотр может привести к тому, что `applyChangeset` и `commitChangeset` снова будут работать с новым `attempt`. Промежуточное ПО на этих этапах должно быть безопасным для повторного использования и не должно отправлять необратимые внешние сообщения или выполнять одноразовые зарядки напрямую.

## Область customData

`customData` несет контекст в пределах одного вызова. Абонент может поставлять данные, а Middleware может добавлять к нему для последующего Middleware, Адаптера базы данных и связанных с ним событий. Типичные виды использования включают в себя:

- Передать идентификатор арендатора, идентификатор трассировки или логгер запроса.
- Повторно использовать результат проверки прав в рамках вызова.
- Записать время начала операции или метку аудита.

Встроенные адаптеры баз данных не сохраняются `customData`. Для сохранения полей вместе с документом или набором изменений см. [Постоянные метаданные](#persistent-metadata) .

## Сохранение метаданных [#persistent-metadata]

В `metadata` хранятся данные, которые определяет приложение. `UnitRecord.metadata` сохраняется вместе с документом, а `ChangesetRecord.metadata` — с каждой отдельной отправкой.

При создании документа передайте `metadata` в `createUnitFromData()` или `createUnitFromSnapshot()` либо задайте `context.unit.metadata` в Middleware для `createUnit`. Значение по умолчанию — `{}`.

При отправке набора изменений оба объекта метаданных могут быть обновлены в промежуточном программном обеспечении `commitChangeset`. `context.unit.metadata` начинается с текущих метаданных документа, а `context.changeset.metadata` - как `{}`, их типы, `UnitMetadata` и `ChangesetMetadata` являются псевдонимами `Record<string, unknown>` . Значения поля должны быть JSON-сериализируемыми.

Обновить метаданные перед вызовом `await next()`. В следующем примере записывается последний редактор документа и источник представления.

```ts
service.use("commitChangeset", async (context, next) => {
  context.unit.metadata.lastEditorID = context.userID;
  context.changeset.metadata.source = "application";
  await next();
});
```

Service передаёт адаптеру оба объекта целиком для сохранения вместе с набором изменений.

- **Конфликт ревизий.** При повторной попытке Service снова запускает Middleware для `commitChangeset` с актуальными метаданными Unit и пустыми метаданными набора изменений.
- **Повторная отправка.** Если эта отправка ранее завершилась успешно, Service возвращает метаданные исходного changeset.

Чтобы прочитать метаданные документа, вызовите `getUnit()` у адаптера и обратитесь к полю `metadata` возвращённой записи. Для текущей отправки прочитайте `changeset.metadata` в результате успешного вызова `submitChangeset()`. Для предыдущих отправок вызовите `getChangesets()`. Каждый элемент возвращённого массива `changesets` содержит `metadata`.

С помощью встроенного адаптера SQLite или PostgreSQL метаданные документов и изменений также могут быть запрошены непосредственно с помощью SQL. Используйте имена таблиц и столбцов, определенные схемой этого адаптера.

## Модель выполнения Events

Services регистрируют локальные для процесса обработчики через `on()`, возвращающий освобождаемую подписку:

```ts
const subscription = service.on("changesetCommitted", async (event) => {
  metrics.increment("collaboration.changeset.committed", {
    unitType: String(event.changeset.type),
  });
  localCache.delete(event.changeset.unitID);
});

subscription.dispose();
```

Слушатели для одного и того же События выполняются последовательно в порядке регистрации, и SDK ждет каждого. Ошибки слушателя регистрируются и изолируются от уже определенного результата домена. Неудавшийся слушатель `changesetCommitted`, например, не откатывает назад набор изменений, который Адаптер уже сохранил.

Мероприятия подходят для работы в процессе, восстанавливаемой или некритической последующей работы. Они не являются границей транзакций, совместно используемой в базе данных, и не гарантируют доставку во внешнюю систему.

## Events основного Service

| Event | Подтверждённый факт | Типичное применение |
| --- | --- | --- |
| `unitCreated` | Unit и начальные данные созданы | Локальный кеш каталога или производный индекс |
| `changesetCommitted` | Adapter сохранил changeset и обновил ревизию | Рассылка, метрики, производные индексы |
| `unitsDeleted` | Adapter подтвердил пакет удаления | Очистка связанного состояния процесса |
| `unitsRecovered` | Adapter подтвердил пакет восстановления | Восстановление производного состояния процесса |

В обработчике `unitCreated` метаданные документа доступны в `event.record.metadata`, а в обработчике `changesetCommitted` метаданные отправки — в `event.changeset.metadata`.

Конечная точка слушает `changesetCommitted` в той же Службе и транслирует подтвержденный набор изменений клиентам, которые присоединились к Единице в текущем процессе. Когда конфигурируется адаптер паба/суба, трансляция также достигает каждого узла. Конечная точку также подвергает `memberLeftUnit` для явного отпуска, отключения и удаления конечной точки.

## Независимые точки расширения модулей

History, Thread Comment и Worktree не наследуют Middleware и Events основного Collaboration Service:

- History предоставляет Middleware чтения для `getHistoryList`, `listHistoryCreators` и `getHistoryChangesets`;
- Comment — добавления, ответа, правки, удаления, решения и списка, а также `commentCommitted`;
- Worktree — жизненного цикла и read/submit/commit черновиков, а также Events создания, статуса, слияния и коммита черновика.

Правила установки отдельно для каждого включенного модуля.Промежуточное программное обеспечение для регистрации, арендатора или авторизации в базовой службе не охватывает эти модули автоматически.

Продолжите с [Идентификацией и авторизацией](/server/collaboration/identity-and-authorization): там показано сопоставление существующих пользователей и ACL этим общим границам.
