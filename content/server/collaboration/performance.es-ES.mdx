Probamos dos escenarios: varios usuarios editando un mismo documento y la edición simultánea de varios documentos. Tras el calentamiento, medimos la latencia de confirmación, el rendimiento, el porcentaje de envíos previstos que se completaron y el uso de CPU y memoria del proceso de colaboración.

## Entorno de pruebas

El servicio de colaboración y la base de datos se ejecutaron en servidores distintos. Las especificaciones de los resultados corresponden al nodo de colaboración del diagrama.

PostgreSQL guarda los registros de documentos e instantáneas, los conjuntos de cambios y las referencias a bloques. OSS almacena los bloques de datos de celdas de las instantáneas.

Todos los resultados corresponden a un solo nodo de colaboración. Si los documentos activos superan su capacidad, se pueden distribuir entre varios nodos. Estos comparten la base de datos y sincronizan las salas, la presencia y la difusión de cambios mediante publicación y suscripción. ### Configuración del servicio de colaboración

En ambos nodos elevamos `runtime.maxLoadedUnits` de 1.200 a 4.000 para mantener hasta 4.000 documentos en memoria. Los demás parámetros conservaron sus valores predeterminados, incluida la selección automática del número de hilos. Se genera una instantánea tras 50 revisiones desde la última instantánea correcta o cuando un conjunto de cambios alcanza los 5 MiB.

El servicio de prueba usa un grupo de conexiones PostgreSQL y un cliente OSS ya inicializados. El transporte se conecta al servidor HTTP de Node.js.

```ts
const dbAdapter = await PostgresS3DatabaseAdapter.create({
  pool,
  s3: { client, bucket, prefix },
});
const service = new UniverCollabService({
  dbAdapter,
  runtime: { maxLoadedUnits: 4000 },
});
const endpoint = new UniverCollabEndpoint(service);
const transport = createNodeTransport();
transport.register(endpoint);
transport.attach(server);
```

## Instantáneas de prueba

Cada documento se inicializa a partir de una instantánea. El recuento incluye las celdas con datos o fórmulas antes del calentamiento.

| Instantánea | Celdas con contenido | Contenido |
| --- | ---: | --- |
| `blank` | 0 | Hoja vacía |
| `10k-cells` | Unas 10.000 | Números, texto y fórmulas |
| `100k-cells` | Unas 100.000 | Números, texto y fórmulas |

Ambas hojas con datos contienen 26 columnas: 14 numéricas, nueve de texto y tres con fórmulas que hacen referencia a celdas de la misma fila.

## Método

### Clientes simulados

Cada editor representa una sesión independiente que se une a un documento, envía cambios por HTTP y recibe confirmaciones por WebSocket. Los scripts llaman directamente a la API de colaboración. Tanto la petición HTTP como la espera de confirmación tienen un tiempo de espera de 10 segundos.

### Calentamiento y muestreo

Cada ejecución crea documentos a partir de la instantánea elegida. El calentamiento empieza cuando se han unido todas las sesiones. La primera edición carga el documento en el servidor. Para un solo documento se envía una edición previa. Con varios documentos se envían entre 1 y 49 ediciones por documento en orden y se vuelve a 1 en el documento 50. Así se escalonan las revisiones iniciales y las escrituras de instantáneas.

El muestreo comienza cuando todos los documentos se han calentado. La latencia del primer envío se registra por separado durante el calentamiento. Los envíos, percentiles de latencia y valores de CPU y memoria de las tablas proceden del muestreo.

### Carga de edición

En la prueba de un documento aumentamos el número de editores de `blank`. Para cada una de las tres instantáneas aumentamos después el número de documentos activos. Cada envío contiene una operación `sheet.mutation.set-range-values` que escribe un número en una celda.

| Condición | Un documento | Varios documentos |
| --- | --- | --- |
| Editores por documento | Varía según la prueba (véanse los resultados) | Dos en todas las pruebas |
| Operación | Cada editor modifica su celda en momentos escalonados | Cada editor modifica su celda en momentos escalonados |
| Frecuencia por editor | Una vez cada 6 segundos | Una vez cada 2 segundos |
| Muestreo por ejecución | 300 segundos | 300 segundos |

## Métricas

| Métrica | Definición |
| --- | --- |
| Latencia de confirmación | Tiempo desde que el cliente envía una edición hasta que recibe la confirmación del servidor. P50, P95 y P99 son los tiempos en que se confirma el 50 %, 95 % y 99 % de los envíos correctos. Max es la mayor latencia de estos envíos. |
| Rendimiento | Envíos correctos divididos por la duración del muestreo, en envíos por segundo. |
| Tasa de cumplimiento | Porcentaje de envíos previstos que se completan correctamente. El total previsto incluye los fallidos y los que no llegaron a enviarse. |
| CPU media / máxima (%) | Uso medio y máximo observado del proceso de colaboración. Un núcleo saturado cuenta como 100 %, por lo que la suma puede superar el 100 %. |
| Memoria máxima (MiB) | Mayor valor muestreado de memoria residente (RSS) del proceso de colaboración. |

### Criterios de aceptación

Una ejecución cumple los criterios si la latencia de confirmación es **P99 < 1.000 ms**, la tasa de cumplimiento es **> 90 %** y el proceso sigue activo hasta que todos los documentos superan la comprobación de coherencia. Se evalúan los valores sin redondear.

Si se hizo una sola ejecución para un nivel de carga, se usa ese resultado. Si hubo varias, todas deben cumplir los criterios. Las muestras interrumpidas y las métricas ausentes se indican como datos faltantes junto con el motivo.

## Alcance de los resultados

Los scripts de Node.js simulan sesiones y envían cambios directamente a la API para medir el procesamiento concurrente del servidor. La latencia abarca desde el envío hasta la confirmación. Excluye la interacción en el navegador y el renderizado de la hoja.

Los resultados sirven para evaluar el rendimiento y dimensionar un nodo. Influyen la configuración, la red, el tamaño de los documentos y el tipo y la frecuencia de las ediciones.

La carga máxima aceptada es el mayor nivel probado que cumplió los criterios. En algunos niveles, el uso medio de CPU se acercó al límite del nodo. **Estos valores orientan el dimensionamiento y no deben adoptarse directamente como carga sostenida de producción.** Reserve margen para picos y fluctuaciones y valide la carga sostenida con documentos representativos en el entorno de destino.

#### Dimensionamiento de grupos de nodos

En un [despliegue con varios nodos](/server/deployment), la puerta de enlace puede enrutar las ediciones a grupos distintos según el tamaño del documento. Las estimaciones por nodo suponen dos editores por documento, cada uno con una edición cada dos segundos.

- **Para documentos pequeños y medianos, evalúe primero 4 núcleos con 8 GiB.** En el nodo de 4 núcleos con 16 GiB, las mayores cargas aceptadas dentro del presupuesto reducido fueron 2.100 hojas vacías o 1.800 hojas de unas 10.000 celdas con contenido.
- **Para documentos grandes, evalúe 8 núcleos con 16 o 32 GiB.** Con unas 100.000 celdas por documento, el nodo de 8 núcleos con 32 GiB superó la prueba con 750 documentos. El nivel más alto dentro del presupuesto de la configuración de 16 GiB fue de 600.
