title: Middleware와 Events

---

Middleware와 Events는 Collaboration SDK의 범용 확장 지점입니다. 신원 확인과 권한 부여는 Middleware로 통합합니다. 작업 전 검증·제한에는 Middleware를, 상태 확정 후 변경 기록·후속 작업에는 Events를 사용합니다. 둘 다 로깅, 요청 추적, 지표, 파생 상태 업데이트를 지원할 수 있습니다.

## 두 가지 확장 시점

| | Middleware | Event |
| --- | --- | --- |
| 실행 시점 | 작업 중 | 상태 변경 확정 후 |
| 작업 참여 또는 거부 | 가능 | 불가 |
| 호출 Context 보강 | 가능 | Event가 전달하는 Context와 결과 읽기 |
| 리스너 실패 | 현재 작업 실패 가능 | 이미 결정된 도메인 결과와 격리 |
| 일반 용도 | 신원 확인, 권한 부여, 검증, 로깅, 시간 측정 | 파생 인덱스, 캐시, 지표, 프로세스 내부 알림 |

작업의 계속 진행 여부를 결정하려면 Middleware를, 상태 변경이 이미 일어났음을 관찰하려면 Event를 사용합니다.

## Middleware 실행 모델

같은 Action의 Middleware는 등록 순서대로 비동기 체인을 형성합니다. `await next()`가 다음 Middleware로 진입하며 SDK 작업은 가장 안쪽에서 실행됩니다.

```ts
service.use("submitChangeset", async (context, next) => {
  const startedAt = performance.now();
  context.customData.startedAt = startedAt;

  try {
    await next();
  } finally {
    metrics.observe("collaboration.submit.duration", performance.now() - startedAt);
  }
});
```

Middleware는 다음을 할 수 있습니다.

- Action별 요청 읽기
- `customData`로 호출 내부 데이터 공유
- `next()` 전에 입력 검사 또는 애플리케이션 시스템 조회
- `next()` 반환 후 소요 시간이나 결과 기록
- `CollabError`를 던져 예상된 협업 작업 거부

Transport HTTP Middleware는 `next()` 호출 없이 HTTP 응답을 종료할 수 있습니다. Service와 Endpoint Middleware는 조용히 `next()`를 생략하지 말고 명시적인 오류로 거부해야 합니다.

## Transport Middleware

`transport.use()`는 일반 HTTP Middleware를 등록하며 등록 순서대로 실행합니다. `await next()`를 호출해 다음 처리를 진행하거나 응답을 직접 종료할 수 있습니다. `transport.useUpgrade()`는 WebSocket 핸드셰이크를 처리합니다.

다음 예제는 HTTP 소요 시간을 기록하고, 인증 후 신뢰할 수 있는 `userID`를 설정한 다음 Collaboration Endpoint를 등록합니다.

```ts
transport.use(async (context, next) => {
  const start = performance.now();
  context.response.once("finish", () => {
    recordHttpDuration({
      method: context.incomingMessage.method,
      route: context.route?.path ?? "unmatched",
      status: context.response.statusCode,
      durationMs: performance.now() - start,
    });
  });
  await next();
});

transport.use(async (context, next) => {
  const user = await authenticate(context.incomingMessage);
  if (!user) {
    context.response.statusCode = 401;
    context.response.end("Authentication required");
    return;
  }
  context.userID = user.userId;
  await next();
});

transport.register(collaborationEndpoint);
```

`recordHttpDuration`과 `authenticate`는 애플리케이션에서 제공합니다. Endpoint는 앞선 Middleware가 설정한 `userID`를 사용합니다. 관측 Middleware를 인증보다 먼저 등록하므로 인증 거부도 기록됩니다.

`context.route?.path`는 일치한 전체 경로 템플릿이며 처리가 Endpoint에 도달하면 사용할 수 있습니다. response의 `finish` 이벤트로 응답 완료까지의 시간을 측정합니다. 경로 매칭 전의 거부와 알 수 없는 경로는 `unmatched`로 기록됩니다.

## Endpoint Middleware

Endpoint Middleware는 실시간 Session과 Presence 작업에 참여합니다.

| Action | 실행 시점 | 일반 용도 |
| --- | --- | --- |
| `connect` | 티켓 소비·Session 생성 후, HELLO 전 | 연결 정책, 멤버 표시 이름·아바타 |
| `joinUnit` | Session의 Unit Room 참여 전 | Room 입장과 Unit 가시성 |
| `receivePresence` | 참여한 Session에서 Presence 수신 후, 브로드캐스트 전 | 검증과 Presence 필터링 |
| `sendPresence` | 각 Room 멤버에게 Presence 전송 전 | 수신자별 Presence 필터링 |

```ts
endpoint.use("receivePresence", async (context, next) => {
  if (JSON.stringify(context.payload).length > 8_000) {
    throw new CollabError("INVALID_REQUEST", "Presence payload is too large");
  }
  await next();
});
```

Endpoint의 `session.userID`, `session.customData`는 Session Ticket을 발급한 HTTP 요청에서 옵니다. Endpoint가 현재 WebSocket Session에 부여한 `memberID`는 재연결 시 변경됩니다.

## Service Middleware

Service Middleware는 서버 기준 협업 데이터의 수명 주기에 참여합니다.

| Action | 경계 | 일반 용도 |
| --- | --- | --- |
| `readUnitData` | 스냅샷·블록·변경 집합 읽기 전 | 읽기 정책, 테넌트 검사, 감사 |
| `createUnit` | 원자적 Unit 생성 전 | 유형 검사, 생성 정책, 업무 규칙 |
| `deleteUnits` | 삭제 배치 쓰기 전 | 삭제 정책과 Unit별 검사 |
| `recoverUnits` | 복구 배치 쓰기 전 | 복구 정책과 감사 |
| `submitChangeset` | 제출을 받은 후, 중복 제거와 OT 전 | 편집 권한 확인 또는 제출 크기 제한 |
| `applyChangeset` | OT 후, 문서에 변경 집합을 적용하기 전 | 변환된 작업이 보호 범위에 영향을 주는지 검사하는 등 작업 내용 검증 |
| `commitChangeset` | 변경 집합을 후보 상태에 적용한 후, Adapter가 저장하기 전 | 이번 제출과 함께 저장할 메타데이터 설정 |

```ts
service.use("createUnit", async (context, next) => {
  await creationPolicy.assertAllowed({
    userID: context.userID,
    unitID: context.request.snapshot.unitID,
    type: context.request.snapshot.type,
  });
  context.customData.creationPolicyChecked = true;
  await next();
});
```

`submitChangeset`는 논리 제출마다 한 번 실행됩니다. 리비전 경합으로 `applyChangeset`, `commitChangeset`가 새 `attempt`로 다시 실행될 수 있습니다. 이 단계의 Middleware는 재시도에 안전해야 하며 되돌릴 수 없는 외부 메시지 전송이나 일회성 과금을 직접 수행하면 안 됩니다.

## customData 범위

`customData`는 한 호출 안에서 컨텍스트를 공유하는 데 사용합니다. 호출자가 데이터를 전달하고 Middleware가 처리 중에 추가하면, 이후의 Middleware와 Database Adapter, 관련 Event에서 읽을 수 있습니다.

- 테넌트 ID, 추적 ID 또는 요청에 사용할 로거를 전달합니다.
- 같은 호출에서 권한 조회 결과를 재사용합니다.
- 측정 시작 시각이나 감사용 레이블을 기록합니다.

SDK 내장 데이터베이스 Adapter는 `customData`를 영구 저장하지 않습니다. 문서나 변경 집합과 함께 저장할 필드는 [메타데이터 저장](#persistent-metadata)을 참고하세요.

## 메타데이터 저장 [#persistent-metadata]

`metadata`는 애플리케이션에서 정의한 데이터를 저장합니다. `UnitRecord.metadata`는 문서와 함께, `ChangesetRecord.metadata`는 개별 제출과 함께 저장됩니다.

문서를 생성할 때 `createUnitFromData()` 또는 `createUnitFromSnapshot()`의 입력에 `metadata`를 전달하거나 `createUnit` Middleware에서 `context.unit.metadata`를 설정합니다. 기본값은 `{}`입니다.

변경 집합을 제출할 때 `commitChangeset` Middleware에서 두 메타데이터 객체를 갱신할 수 있습니다. `context.unit.metadata`는 문서의 현재 메타데이터로, `context.changeset.metadata`는 `{}`로 시작합니다. 타입은 각각 `UnitMetadata`와 `ChangesetMetadata`이며 둘 다 `Record<string, unknown>`의 별칭입니다. 필드 값은 JSON으로 직렬화할 수 있어야 합니다.

`await next()`를 호출하기 전에 값을 설정합니다. 다음 예제는 문서의 마지막 편집자를 갱신하고 이번 제출의 출처를 기록합니다.

```ts
service.use("commitChangeset", async (context, next) => {
  context.unit.metadata.lastEditorID = context.userID;
  context.changeset.metadata.source = "application";
  await next();
});
```

Service는 두 객체 전체를 Adapter에 전달하여 이번 제출과 함께 저장합니다.

- **리비전 충돌**: Service는 최신 Unit 메타데이터와 비어 있는 변경 집합 메타데이터로 `commitChangeset` Middleware를 다시 실행합니다.
- **중복 제출**: 이미 성공한 제출을 재시도하면 Service는 원래 변경 집합의 메타데이터를 반환합니다.

문서 메타데이터는 Adapter의 `getUnit()`이 반환한 레코드의 `metadata`에서 읽습니다. 이번 제출의 메타데이터는 `submitChangeset()`의 성공 결과에 있는 `changeset.metadata`에서 읽을 수 있습니다. 이전 제출을 조회할 때는 `getChangesets()`가 반환하는 `changesets` 배열의 각 항목에 `metadata`가 포함됩니다.

내장 SQLite 또는 PostgreSQL Adapter를 사용한다면 SQL로 문서나 변경 집합의 메타데이터를 직접 조회할 수도 있습니다. 테이블 이름과 열 이름은 사용하는 Adapter의 데이터베이스 스키마를 따릅니다.

## Event 실행 모델

Service는 `on()`으로 프로세스 내부 리스너를 등록하고 해제 가능한 구독을 받습니다.

```ts
const subscription = service.on("changesetCommitted", async (event) => {
  metrics.increment("collaboration.changeset.committed", {
    unitType: String(event.changeset.type),
  });
  localCache.delete(event.changeset.unitID);
});

subscription.dispose();
```

같은 Event의 리스너는 등록 순서대로 실행되며 완료를 기다립니다. 리스너 오류는 기록되고 이미 결정된 도메인 결과에서 격리됩니다. 예를 들어 `changesetCommitted` 리스너 실패는 Adapter가 저장한 변경 집합을 롤백하지 않습니다.

따라서 Events는 프로세스 내부, 복구 가능 또는 비핵심 후속 작업에 적합합니다. DB 커밋과 공유하는 트랜잭션 경계가 아니며 외부 시스템 전달을 보장하지 않습니다.

## 핵심 Service Events

| Event | 확정된 사실 | 일반 용도 |
| --- | --- | --- |
| `unitCreated` | Unit과 초기 데이터 생성 완료 | 로컬 목록 캐시·파생 인덱스 |
| `changesetCommitted` | Adapter가 변경 집합을 저장하고 리비전을 갱신함 | 브로드캐스트, 지표, 파생 인덱스 |
| `unitsDeleted` | Adapter가 삭제 배치 확정 | 프로세스 내부 관련 상태 정리 |
| `unitsRecovered` | Adapter가 복구 배치 확정 | 프로세스 내부 파생 상태 복구 |

`unitCreated` 리스너에서는 `event.record.metadata`로 문서 메타데이터를 읽습니다. `changesetCommitted` 리스너에서는 `event.changeset.metadata`로 이번 제출의 메타데이터를 읽습니다.

Endpoint는 같은 Service의 `changesetCommitted`를 듣고 현재 프로세스에서 Unit에 참여한 클라이언트로 변경 집합을 브로드캐스트합니다. pub/sub 어댑터를 구성하면 다른 노드에도 전달합니다. 명시적 나가기, 연결 해제, Endpoint 해제에는 `memberLeftUnit`도 제공합니다.

## 확장 모듈의 독립 확장 지점

History, Thread Comment, Worktree는 핵심 Collaboration Service의 Middleware나 Events를 상속하지 않습니다.

- History는 `getHistoryList`, `listHistoryCreators`, `getHistoryChangesets` 읽기 Middleware를 제공합니다.
- Comment는 추가, 답글, 편집, 삭제, 해결, 목록 Middleware와 `commentCommitted`를 제공합니다.
- Worktree는 수명 주기와 초안 read/submit/commit Middleware, 생성·상태·병합·초안 커밋 Events를 제공합니다.

활성화한 모듈마다 규칙을 설치하세요. 핵심 Service의 로깅·테넌트·권한 Middleware가 자동 적용되지는 않습니다.

기존 사용자와 ACL을 이러한 경계에 매핑하는 사례는 [신원 확인과 권한 부여](/server/collaboration/identity-and-authorization)를 참고하세요.
