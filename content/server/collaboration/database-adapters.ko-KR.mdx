Database Adapter는 Collaboration Service가 사용하는 핵심 협업 데이터를 영속화합니다. 개발자는 `IDatabaseAdapter`를 구현하여 전체 동작 계약을 충족하는 데이터베이스를 연결할 수 있습니다. Service는 Unit, OT, 리비전의 의미를 관리하고 Adapter는 이를 원자적이며 안전하게 재시도할 수 있는 저장 작업으로 구현합니다.

Database Adapter는 Apache-2.0 오픈 소스입니다. 소스는 [univer-collaboration-sdk-community](https://github.com/dream-num/univer-collaboration-sdk-community)에 있으며 패키지 이름과 버전은 다른 패키지와 같습니다.

## 재시작 후 데이터 유지 확인 [#verify-persistence]

Quick Start를 중지하고 루트에서 `pnpm example:database-adapter`를 실행하세요. `http://127.0.0.1:3010/?unit=persistent-sheet`에서 셀을 바꾸고 다른 브라우저에서 확인합니다. 중지 후 같은 명령과 URL로 다시 열어 값이 남아 있는지 확인하세요. 파일은 `examples/database-adapter/.data/collaboration.sqlite`이며 재시작 시 삭제하지 마세요. 서버는 기존 Unit을 읽고 `UNIT_NOT_FOUND`일 때만 `createUnitFromData()`를 호출합니다. [server/main.ts](https://github.com/dream-num/univer-collaboration-examples/blob/main/examples/database-adapter/server/main.ts)를 참고하세요.

## Adapter가 저장하는 데이터

Adapter는 각 협업 문서(Unit)에 대해 세 종류의 데이터를 저장합니다.

- **Unit 레코드**에는 문서 ID, 유형, 작성자, 생성 시각, 현재 리비전(`headRevision`)이 들어갑니다. Adapter는 변경 집합을 저장할 때 리비전도 함께 갱신합니다. 애플리케이션은 `UnitRecord.metadata`에 문서 이름(`name`), 마지막 편집자 ID(`lastEditorID`), 마지막 수정 시각(`lastModifiedAt`) 같은 필드를 직접 관리할 수 있습니다.
- **스냅샷**은 특정 리비전의 문서 내용을 담습니다. Service는 요청한 리비전 이하의 가장 최근 스냅샷을 읽고, 그 이후부터 요청한 리비전까지의 변경을 순서대로 적용할 수 있습니다. 스프레드시트의 경우 스냅샷이 참조하는 데이터 블록도 저장합니다.
- **변경 집합**은 한 번에 제출한 작업을 묶은 것입니다. Adapter는 변경 집합을 리비전 순서대로 저장하고 제출 식별자 `sid`와 `reqId`를 보존합니다. Service는 이 값으로 클라이언트의 재시도를 식별해 같은 작업이 두 번 적용되는 것을 방지합니다.[^submission-idempotency] 애플리케이션은 `ChangesetRecord.metadata`에 편집 출처(`source`)나 관련 업무 작업 ID(`operationId`) 등을 저장할 수 있습니다.

생성 및 제출 시 메타데이터를 설정하는 방법은 [메타데이터 저장](/server/collaboration/middleware-and-events#persistent-metadata)을 참고하세요.

소프트 삭제는 데이터를 보존하므로 복구 후 편집을 재개할 수 있습니다. 영구 삭제 후에는 문서 데이터에 접근하거나 원래 문서 ID를 재사용할 수 없습니다.

사용자, 역할, 접근 권한은 애플리케이션이 관리합니다. History, Thread Comment, Worktree는 각각 별도의 Adapter 인터페이스를 사용합니다.

## Adapter 읽기 및 쓰기 요구 사항

`IDatabaseAdapter`를 구현할 때는 작업별로 다음 요구 사항을 충족해야 합니다.

| 작업 | 요구 사항 |
| --- | --- |
| Unit 생성 | Unit 레코드(메타데이터 포함), 초기 스냅샷, 스냅샷이 참조하는 Sheet 블록을 원자적으로 저장해 동시에 읽을 수 있도록 합니다. |
| 변경 집합 커밋 | 현재 리비전이 예상 리비전과 일치할 때만 커밋합니다(CAS)[^revision-cas]. 한 번의 원자적 쓰기로 변경 집합과 해당 메타데이터를 저장하고, Unit 메타데이터 전체를 교체하고, 리비전을 1 증가시킵니다. 리비전이 일치하지 않으면 쓰기 없이 현재 리비전을 반환합니다. |
| 변경 집합 읽기 | 요청 범위에 있는 변경 집합을 빠짐없이 리비전 오름차순으로 반환합니다. Service가 같은 Unit에 대한 중복 제출을 식별할 수 있도록 원래의 `sid`와 `reqId`를 보존합니다. |
| 스냅샷 저장 | 스냅샷을 읽을 수 있는 시점에 참조된 Sheet 블록도 모두 읽을 수 있어야 합니다. |
| 삭제 또는 복구 | 배치의 모든 Unit에 작업을 적용합니다. 하나라도 실패하면 배치 전체가 이전 상태를 유지해야 합니다. |

## Memory Adapter

[`@univerjs-pro/collaboration-database-memory`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-memory)는 프로세스 내부 구현으로 다음에 적합합니다.

- 단위 및 통합 테스트
- 임시 개발 환경
- 사용자 정의 Middleware나 클라이언트 구성의 빠른 검증

```ts
import { MemoryDatabaseAdapter } from "@univerjs-pro/collaboration-database-memory";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";

const database = new MemoryDatabaseAdapter();
const service = new UniverCollabService({ dbAdapter: database });
```

Memory Adapter는 영속 구현과 동일한 리비전, CAS, 멱등성 계약을 따릅니다. 다만 모든 데이터는 현재 Node.js 프로세스에 있으므로 프로세스가 종료되면 사라집니다.

## SQLite Adapter

[`@univerjs-pro/collaboration-database-sqlite`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-sqlite)는 개발, 테스트, 로컬 애플리케이션, 소규모 사용을 위한 영속 SQLite 구현입니다.

```ts
import { mkdir } from "node:fs/promises";

import { SQLiteDatabaseAdapter } from "@univerjs-pro/collaboration-database-sqlite";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";

await mkdir("./data", { recursive: true });

const database = new SQLiteDatabaseAdapter({
  filename: "./data/collaboration.sqlite",
  busyTimeoutMs: 5_000,
});
const service = new UniverCollabService({ dbAdapter: database });
```

빈 DB에는 스키마를 초기화하고 기존 DB는 검증만 합니다. 파일 위치, 백업, 기타 SQLite 설정은 애플리케이션이 결정합니다.

## PostgreSQL Adapter

[`@univerjs-pro/collaboration-database-postgres`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-postgres)는 node-postgres 기반 영속 구현으로, 여러 협업 노드가 공유할 수 있습니다.

```ts
import { PostgresDatabaseAdapter } from "@univerjs-pro/collaboration-database-postgres";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";
import { Pool } from "pg";

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
const database = await PostgresDatabaseAdapter.create({ pool });
const service = new UniverCollabService({ dbAdapter: database });
```

연결 풀은 애플리케이션이 소유하며 Service를 해제한 뒤 닫습니다. `create()`는 빈 DB에 `collaboration` 스키마를 초기화하고 기존 스키마는 검증만 합니다.

## 사용자 정의 Database Adapter

보통 다음 경우에 적합합니다.

- 이미 MySQL 등 업무 DB를 사용함
- 협업 제출을 애플리케이션 고유 DB 메커니즘과 통합해야 함
- 운영 또는 규정 준수 요구가 내장 Adapter의 범위를 넘음

`IDatabaseAdapter`를 구현하고 내장 Adapter와 같은 방식으로 Service에 주입합니다.

```ts
const database = new ApplicationCollaborationDatabase({ pool });
const service = new UniverCollabService({ dbAdapter: database });
```

Service는 특정 DB에 의존하지 않지만 사용자 정의 구현에 트랜잭션, CAS, 중복 제거를 보완해 주지도 못합니다. Adapter가 DB 기능을 사용해 전체 계약을 구현해야 합니다. [커뮤니티 저장소](https://github.com/dream-num/univer-collaboration-sdk-community)의 내장 구현은 같은 계약을 서로 다른 DB에 구현한 예이며 참고용으로 쓸 수 있습니다.

## 업무 데이터 저장 방법

**문서나 변경 집합에 속한 정보는 `metadata`에 저장할 수 있습니다.** 애플리케이션에서 문서를 생성하거나 변경 집합을 제출할 때 값을 설정하면 내장 Adapter가 협업 데이터와 함께 저장합니다. [메타데이터 저장](/server/collaboration/middleware-and-events#persistent-metadata)을 참고하세요.

**별도 업무 테이블에는 Middleware나 Event를 통해 기록할 수 있습니다.** 작업 시도를 감사 테이블에 남기려면 Middleware에서 기록합니다. 커밋 성공 후 테이블을 갱신하려면 `changesetCommitted`를 구독합니다. 기본적으로 이러한 쓰기는 협업 트랜잭션 밖에서 실행됩니다. 리비전 충돌로 커밋 단계의 Middleware가 다시 실행될 수 있으므로 중복 레코드가 생기지 않게 해야 합니다. Event는 프로세스 내부에서만 전달되며 전달이 보장되지는 않습니다. 나중에 보충하거나 재구성할 수 있는 데이터에 적합합니다.

**자체 데이터베이스와 스키마를 사용하거나 업무 데이터와 협업 데이터를 같은 트랜잭션에서 기록하려면 사용자 정의 Adapter를 구현할 수 있습니다.** Service 호출 시 애플리케이션이 업무 작업 ID 같은 정보를 `customData`로 전달하면 Adapter 메서드에서 `ctx.customData`를 읽어 갱신할 테이블을 결정할 수 있습니다. 예를 들어 `commitChangeset()`은 변경 집합을 저장하는 트랜잭션 안에서 작업 ID에 해당하는 업무 레코드를 갱신할 수 있습니다.

`customData`의 범위는 현재 호출입니다. 내장 Adapter는 이 필드들을 자동으로 저장하거나 업무 테이블에 기록하지 않습니다.

## 확장 모듈 저장소

History, Thread Comment, Worktree, File 등은 독립적인 Database Adapter 인터페이스를 정의합니다. 어댑터는 하나의 DB를 공유하거나 별도 저장소를 사용할 수 있습니다. 하나의 사용자 정의 구현이 여러 Adapter 인터페이스를 제공하고 각 Service에 주입될 수도 있습니다.

인터페이스가 독립적이므로 SDK는 기본적으로 모듈 간 트랜잭션을 제공하지 않습니다. 같은 DB를 공유해도 모듈 간 일관성 전략은 애플리케이션이 담당합니다.

## Adapter 선택

| Adapter | 적합한 용도 | 주요 제약 |
| --- | --- | --- |
| Memory | 테스트, 예제, 임시 개발 | 프로세스 종료 시 데이터 소멸 |
| SQLite | 개발, 테스트, 로컬 앱, 소규모 사용 | 단일 파일 DB이며 설정은 애플리케이션이 관리 |
| PostgreSQL | 다중 노드 배포와 기존 PostgreSQL DB | 연결 풀과 DB 운영은 애플리케이션이 관리 |
| 사용자 정의 | 기존 DB 또는 자체 업무 데이터 통합 | 전체 계약을 직접 구현하고 검증해야 함 |

주입한 Adapter는 모두 애플리케이션이 소유합니다. Service를 먼저 해제한 뒤 Adapter를 해제하세요.

```ts
await service.dispose();
await database.dispose();
```

실행하며 비교할 수 있는 [데이터베이스 어댑터 예제](/server/collaboration/examples#database-adapter)를 참고하세요.

[^submission-idempotency]: 멱등성은 같은 제출을 재시도해도 편집이 두 번 적용되지 않도록 합니다. 재시도 시 제출 식별자를 유지해야 하며, 같은 내용이라도 새 식별자를 쓰면 새 제출로 처리됩니다.

[^revision-cas]: CAS는 현재 값이 예상 값과 일치할 때만 갱신합니다. 현재 리비전 확인과 다음 상태 기록을 원자적으로 수행하여 동시 제출이 같은 리비전을 차지하지 않도록 해야 합니다.
