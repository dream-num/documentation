데이터베이스 어댑터는 협업 서비스 관리 핵심 협업 데이터를 주장합니다. 이 서비스는 단위, OT 및 개정 semantics를 소유하고 있으며, 어댑터는 재발급에 안전한 원자 저장 작업으로 그 하수인을 전환합니다. 내장 어댑터에 의해 덮지 않는 데이터베이스를 연결하려면 `IDatabaseAdapter`를 구현하고 완전한 행동 계약을 만족시킵니다.

데이터베이스 어댑터는 Apache-2.0의 오픈 소스입니다. 소스 코드는 [univer-collaboration-sdk 커뮤니티](https://github.com/dream-num/univer-collaboration-sdk-community)에서 사용할 수 있으며 패키지는 동일한 이름과 버전을 다른 패키지로 사용합니다.

## 재시작 후 데이터 유지 확인 [#verify-persistence]

빠른 시작을 중지하고 저장소 루트에서 `pnpm example:database-adapter`를 실행합니다. `http://127.0.0.1:3010/?unit=persistent-sheet`을 열고, 세포를 변경하고, 두 번째 브라우저에서 변경을 확인합니다. 그런 다음 서버를 중지하고 같은 명령을 다시 실행하고 동일한 URL을 다시 열 수 있습니다. 값은 여전히 존재해야합니다.

데이터는 `examples/database-adapter/.data/collaboration.sqlite`에 저장되므로 실행 중에 파일을 삭제하지 마십시오. 서버가 기존 단위를 읽고 `createUnitFromData()`를 `UNIT_NOT_FOUND`을 수신할 때 ZXQXZ 만 호출하면 저장 된 데이터를 덮지 못합니다. 이 구현은 [서버/main.ts](https://github.com/dream-num/univer-collaboration-examples/blob/main/examples/database-adapter/server/main.ts)입니다.

## Adapter가 저장하는 데이터

Adapter는 각 협업 문서(Unit)에 대해 세 종류의 데이터를 저장합니다.

- **Unit 레코드**에는 문서 ID, 유형, 작성자, 생성 시각, 현재 리비전(`headRevision`)이 들어갑니다. Adapter는 변경 집합을 저장할 때 리비전도 함께 갱신합니다. 애플리케이션은 `UnitRecord.metadata`에 문서 이름(`name`), 마지막 편집자 ID(`lastEditorID`), 마지막 수정 시각(`lastModifiedAt`) 같은 필드를 직접 관리할 수 있습니다.
- **스냅샷**은 특정 리비전의 문서 내용을 담습니다. Service는 요청한 리비전 이하의 가장 최근 스냅샷을 읽고, 그 이후부터 요청한 리비전까지의 변경을 순서대로 적용할 수 있습니다. 스프레드시트의 경우 스냅샷이 참조하는 데이터 블록도 저장합니다.
- **변경 집합**은 한 번에 제출한 작업을 묶은 것입니다. Adapter는 변경 집합을 리비전 순서대로 저장하고 제출 식별자 `sid`와 `reqId`를 보존합니다. Service는 이 값으로 클라이언트의 재시도를 식별해 같은 작업이 두 번 적용되는 것을 방지합니다.[^submission-idempotency] 애플리케이션은 `ChangesetRecord.metadata`에 편집 출처(`source`)나 관련 업무 작업 ID(`operationId`) 등을 저장할 수 있습니다.

생성 및 제출 시 메타데이터를 설정하는 방법은 [메타데이터 저장](/server/collaboration/middleware-and-events#persistent-metadata)을 참고하세요.

소프트 삭제는 데이터를 보존하므로 복구 후 편집을 재개할 수 있습니다. 영구 삭제 후에는 문서 데이터에 접근하거나 원래 문서 ID를 재사용할 수 없습니다.

사용자, 역할, 접근 권한은 애플리케이션이 관리합니다. History, Thread Comment, Worktree는 각각 별도의 Adapter 인터페이스를 사용합니다.

## Adapter 읽기 및 쓰기 요구 사항

`IDatabaseAdapter`를 구현할 때는 작업별로 다음 요구 사항을 충족해야 합니다.

| 작업 | 요구 사항 |
| --- | --- |
| Unit 생성 | Unit 레코드(메타데이터 포함), 초기 스냅샷, 스냅샷이 참조하는 Sheet 블록을 원자적으로 저장해 동시에 읽을 수 있도록 합니다. |
| 변경 집합 커밋 | 현재 리비전이 예상 리비전과 일치할 때만 커밋합니다(CAS)[^revision-cas]. 한 번의 원자적 쓰기로 변경 집합과 해당 메타데이터를 저장하고, Unit 메타데이터 전체를 교체하고, 리비전을 1 증가시킵니다. 리비전이 일치하지 않으면 쓰기 없이 현재 리비전을 반환합니다. |
| 변경 집합 읽기 | 요청 범위에 있는 변경 집합을 빠짐없이 리비전 오름차순으로 반환합니다. Service가 같은 Unit에 대한 중복 제출을 식별할 수 있도록 원래의 `sid`와 `reqId`를 보존합니다. |
| 스냅샷 저장 | 스냅샷을 읽을 수 있는 시점에 참조된 Sheet 블록도 모두 읽을 수 있어야 합니다. |
| 삭제 또는 복구 | 배치의 모든 Unit에 작업을 적용합니다. 하나라도 실패하면 배치 전체가 이전 상태를 유지해야 합니다. |

## Memory Adapter

[`@univerjs-pro/collaboration-database-memory`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-memory)는 Node.js 과정 안쪽에 달립니다. 그것은 다음을 위해 적당합니다:

- 단위 및 통합 테스트
- 임시 개발 환경
- 사용자 정의 Middleware 또는 클라이언트 어셈블리의 빠른 체크

```ts
import { MemoryDatabaseAdapter } from "@univerjs-pro/collaboration-database-memory";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";

const database = new MemoryDatabaseAdapter();
const service = new UniverCollabService({ dbAdapter: database });
```

메모리 어댑터는 지속적 구현으로 동일한 개정, CAS 및 idempotency 계약을 따릅니다. 이 데이터는 현재 Node.js 프로세스에서만 존재하며 그 프로세스가 종료 될 때 손실됩니다.

## SQLite Adapter

[`@univerjs-pro/collaboration-database-sqlite`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-sqlite)는 SQLite 파일에 있는 자료를 저장합니다. 그것은 발달, 테스트, 국부적으로 신청 및 소규모 사용을 위해 적당합니다.

```ts
import { mkdir } from "node:fs/promises";

import { SQLiteDatabaseAdapter } from "@univerjs-pro/collaboration-database-sqlite";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";

await mkdir("./data", { recursive: true });

const database = new SQLiteDatabaseAdapter({
  filename: "./data/collaboration.sqlite",
  busyTimeoutMs: 5_000,
});
const service = new UniverCollabService({ dbAdapter: database });
```

데이터베이스가 비어있을 때 스키마를 초기화하고 이미 존재하는 경우 스키마를 검증합니다. 파일 위치, 백업 방법 및 기타 SQLite 설정은 응용 프로그램에 의해 결정됩니다.

## PostgreSQL Adapter

[`@univerjs-pro/collaboration-database-postgres`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-postgres)는 노드 포스트에 내장되어 있으며 PostgreSQL에서 데이터를 저장합니다. 여러 협업 노드는 단일 데이터베이스를 공유할 수 있습니다.

```ts
import { PostgresDatabaseAdapter } from "@univerjs-pro/collaboration-database-postgres";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";
import { Pool } from "pg";

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
const database = await PostgresDatabaseAdapter.create({ pool });
const service = new UniverCollabService({ dbAdapter: database });
```

이 응용 프로그램은 풀을 소유하고 서비스 처분 후 닫습니다. `create()`는 빈 데이터베이스의 `collaboration` 스키마를 초기화하고 기존 스키마를 검증합니다.

## 사용자 정의 Database Adapter

사용자 정의 어댑터는 일반적으로 다음과 같은 경우에 적합합니다.

- 이미 MySQL 등 업무 DB를 사용함
- 협력 제출은 데이터베이스 메커니즘을 사용하여 응용 프로그램이 소유합니다.
- 운영 또는 규정 준수 요구가 내장 Adapter의 범위를 넘음

`IDatabaseAdapter`를 구현하고 내장 Adapter와 같은 방식으로 Service에 주입합니다.

```ts
const database = new ApplicationCollaborationDatabase({ pool });
const service = new UniverCollabService({ dbAdapter: database });
```

이 서비스는 특정 데이터베이스에 의존하지 않지만 거래, CAS, 또는 사용자 정의 구현에 deduplication을 추가 할 수 없습니다. 어댑터는 데이터베이스가 제공하는 기능을 사용하여 완전한 계약을 실행해야합니다. [커뮤니티 저장소](https://github.com/dream-num/univer-collaboration-sdk-community)의 내장 구현은 다른 데이터베이스와 동일한 계약을 적용하고 참조로 봉사합니다.

## 업무 데이터 저장 방법

**문서 또는 변경 사항에 첨부된 정보를 위해 `metadata`를 사용하십시오.** 이 응용 프로그램은 문서 작성 또는 변경 사항을 제출할 때이 필드를 설정할 수 있으며 내장 어댑터는 협업 데이터와 함께 저장합니다. [Middleware 및 이벤트](/server/collaboration/middleware-and-events#persistent-metadata)를 참조하십시오.

**Middleware 또는 이벤트를 사용하여 별도의 비즈니스 테이블에 쓰기.**는 시도한 가동을 감사하기 위하여, Middleware에 있는 감사 테이블에 쓰기. 성공적인 투입 후에 사업 테이블을 새롭게 하기 위하여는, `changesetCommitted`를 들어갑니다. 기본적으로, 이 쓰기는 협력 거래 밖에 뛰기. 개정 분쟁은 다시 실행하기 위하여 커밋 단계 Middleware를 일으키는 원인이 될 수 있습니다, 그래서 재량은 중복 기록을 창조하지 않아야 합니다. 사건은 제일 노력 기초에 과정에 배달됩니다. 신청은 자료에 대 한 그(것)들을 뒤집거나 재건할 수 있습니다.

**애플리케이션이 자신의 데이터베이스와 스키마를 필요로 할 때 사용자 정의 데이터베이스 어댑터를 사용하거나 비즈니스 및 협업 데이터가 하나의 거래에서 작성되어야 할 때.** 서비스를 호출 할 때 응용 프로그램은 `customData`의 비즈니스 운영 ID와 같은 컨텍스트를 통과 할 수 있습니다. 어댑터는 `ctx.customData`에서 필요한 필드를 읽고 업데이트 할 테이블을 결정할 수 있습니다. 예를 들어 `commitChangeset()`는 변경 사항을 저장하는 동일한 거래에서 해당 비즈니스 레코드를 업데이트하는 작동 ID를 사용할 수 있습니다.

`customData`는 현재 호출에 범위를 갖습니다. 내장 어댑터는 필드를 자동으로 인식하지 않으며 비즈니스 테이블에 쓰기 위해 사용하지 않습니다.

## 확장 모듈 저장소

역사와 같은 확장 모듈, 스레드 코멘트, Worktree, 그리고 각각 독립적 인 데이터베이스 어댑터 인터페이스를 정의합니다. 그들의 어댑터는 하나의 데이터베이스를 공유하거나 별도의 저장을 사용할 수 있습니다. 단일 사용자 정의 구현은 여러 어댑터 인터페이스를 제공 할 수 있으며 해당 서비스로 주입됩니다.

이 어댑터 인터페이스는 독립적이므로 SDK는 기본으로 크로스 모듈 트랜잭션을 제공하지 않습니다. 여러 모듈이 데이터베이스를 공유할 때 애플리케이션은 크로스 모듈 일관성 전략을 소유합니다.

## Adapter 선택

| Adapter | 적합한 용도 | 주요 제약 |
| --- | --- | --- |
| Memory | 테스트, 예제, 임시 개발 | Data는 프로세스 종료시 손실됩니다. |
| SQLite | 개발, 테스트, 로컬 앱, 소규모 사용 | 단일 파일 DB이며 설정은 애플리케이션이 관리 |
| PostgreSQL | 다중 노드 배포와 기존 PostgreSQL DB | 연결 풀과 DB 운영은 애플리케이션이 관리 |
| 사용자 정의 | 기존 DB 또는 자체 업무 데이터 통합 | 전체 계약을 직접 구현하고 검증해야 함 |

주입한 Adapter는 모두 애플리케이션이 소유합니다. Service를 먼저 해제한 뒤 Adapter를 해제하세요.

```ts
await service.dispose();
await database.dispose();
```

실행하며 비교할 수 있는 [데이터베이스 어댑터 예제](/server/collaboration/examples#database-adapter)를 참고하세요.

[^submission-idempotency]: 멱등성은 같은 제출을 재시도해도 편집이 두 번 적용되지 않도록 합니다. 재시도 시 제출 식별자를 유지해야 하며, 같은 내용이라도 새 식별자를 쓰면 새 제출로 처리됩니다.

[^revision-cas]: CAS는 현재 값이 예상 값과 일치할 때만 갱신합니다. 현재 리비전 확인과 다음 상태 기록을 원자적으로 수행하여 동시 제출이 같은 리비전을 차지하지 않도록 해야 합니다.
