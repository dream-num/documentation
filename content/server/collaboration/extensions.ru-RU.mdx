History, Thread Comment, File и Worktree являются дополнительными модулями расширения совместной работы, которые расширяют совместную работу без изменения ядра. Каждый модуль предоставляет свои собственные Service, Middleware, Event, Database Adapter и границу жизненного цикла, поэтому приложение позволяет использовать только те модули, которые требуются продукту. Модули все еще могут совместно использовать транспорт, систему идентификации и одну и ту же физическую базу данных.

Office Exchange на стороне сервера основан на файлообменном сервисе. Он преобразует файлы Office в совместные блоки и предоставляет собственный сервис, конечную точку и промежуточное программное обеспечение.

| Расширение | Связь с ядром совместной работы |
| --- | --- |
| History | Наблюдает Events ядра и строит производный индекс истории |
| Thread Comment | Использует Room Unit ядра; привязки комментариев относятся к основному содержимому |
| File | Хранит изображения, вложения и файлы обмена, на которые ссылается Unit; в данных Unit записаны только ID файлов |
| Office Exchange | Создаёт или читает Units через Service ядра, а файлы читает и записывает через File |
| Worktree | Использует Unit и OT ядра и сливает черновики в основную ветку |

История, Thread Comment, File и Worktree настраивают свои собственные адаптеры Middleware, Events и Database.

## История версий

История превращает создание Unit и подтвержденные изменения в записи истории, которые видит пользователь.Показатель получается: подтвержденные изменения остаются авторитетным источником контента Unit.

```ts
const historyService = new UniverHistoryService({
  collabService,
  dbAdapter: historyDatabase,
  userProvider,
});

transport.register(new UniverHistoryEndpoint(historyService));
```

Конструктор подписывается на Core Service `unitCreated` и `changesetCommitted` Events и сохраняет текущий индекс, а `dispose()` удаляет эти подписки.По умолчанию группы Истории меняются по временному окну и по специальным мутациям, а не записывают запись для каждого набора изменений.

История раскрывает прочитанное Промежуточное ПО для `getHistoryList`, `listHistoryCreators` и `getHistoryChangesets`. Индексирование происходит внутри сервиса. `userProvider` поставляет только отображаемые данные, такие как имена и аватары, и он не выполняет ни аутентификацию, ни авторизацию. Неисправность Прослушивателя событий не откатывает уже подтвержденную основную замену, поэтому историю следует рассматривать как производные данные, которые всегда можно восстановить.

## Ветки комментариев

Служба комментариев управляет телами комментариев, ответами, редактированием, удалением и состоянием для Sheets и Docs:

```ts
const commentService = new UniverCommentService({
  database: commentDatabase,
  userProvider,
});

transport.register(
  new UniverCommentEndpoint({
    service: commentService,
    roomHost: collabEndpoint,
  }),
);
```

Тела комментариев принадлежат Адаптеру комментариев, в то время как якоря, которые перемещаются с контентом Sheet или Doc, остаются частью основных снимков и изменений. Конечная точка комментариев может публиковать `comment_update` через единичную комнату основной конечной точки сотрудничества, но это сообщение в реальном времени не является авторитетным состоянием комментария. Клиент, который пропускает сообщение, может восстановиться, перечислив комментарии снова.

Служба комментариев предоставляет Промежуточное ПО для добавления, перечисления, ответа, решения или повторного открытия, редактирования и удаления, а также публикует Событие `commentCommitted`.

## Хранение файлов

Файл хранит двоичные файлы, которые загружают клиенты Univer: изображения и вложения, вставленные в блок, а также файлы источника и результата импорта и экспорта. Данные блока записывают только идентификатор файла, и клиент разрешает этот идентификатор для URL-адреса загрузки, когда он загружает блок. Снимки и вложения поэтому остаются небольшими.

```ts
const fileService = new UniverFileService({
  database: fileDatabase,
  blobStore,
});

transport.register(new UniverFileEndpoint(fileService));
```

Метаданные и контент представляют собой два независимых контракта: `IFileDatabaseAdapter` хранит записи файлов и `IFileBlobStore` сохраняет контент. Временные файлы обмена доступны только пользователю, который их загрузил, а Сервис удаляет их по расписанию. Изображения и вложения внутри Единицы подлежат разрешениям Единицы через `upload`, `signUrl` и `download` Middleware.

## Серверное преобразование Office

Служба обмена импортирует офисные файлы как совместные единицы и экспортирует единицы как файлы. Она использует `@univerjs-pro/exchange-node` для преобразования, создает и считывает единицы через службу совместной работы и хранит исходные и конечные файлы через службу файлов:

```ts
const exchangeService = new UniverExchangeService({ collabService, fileService });

transport.register(new UniverExchangeEndpoint(exchangeService));
```

Импорт и экспорт - это задачи. Клиент создает задачу, а затем проводит опросы для получения результата. Импорт проходит через `createUnit` Middleware of the Core Service, а экспорт проходит через `readUnitData`. Промежуточное ПО `import` и `export` Exchange обрабатывает лимиты ставок, квоты и аудит.

| Unit | Импорт | Экспорт |
| --- | --- | --- |
| Sheet | xls, xlsx, csv, tsv | xlsx, csv, tsv |
| Doc | doc, docx | docx |
| Slide | ppt, pptx | pptx |
| Base | xls, xlsx, csv, tsv | xlsx, csv |
| PDF | pdf | pdf |

Задачи находятся в экземпляре Сервиса, поэтому приложение развертывает один импортный и экспортный узел и направляет все три маршрута Exchange к этому узлу.

## Черновики Worktree и слияние

Worktree добавляет изолированные черновики, заморозку, оценку слияния и слияние по Unit для одной или нескольких Units:

```text
create → draft → ready → merging → merged
           ↑       │
           └ reopen┘

draft / ready → discarded
```

```ts
const worktreeService = new UniverCollabWorktreeService({
  trunk: {
    service: collabService,
    dbAdapter: coreDatabase,
  },
  dbAdapter: worktreeDatabase,
});
```

Worktree хранит свои собственные черновые наборы изменений `(worktreeID, unitID)` и повторно использует движки Unit, OT и отправки Core Service. Только состояние `draft` принимает дальнейшие правки. `markReady()` замораживает текущую версию проекта, а `mergeWorktree()` объединяет блоки в багажник по одному за раз.

Worktree Service имеет собственный жизненный цикл, собственное прочтение Middleware, проект представления/приложения/совершения Middleware, а также События для создания, изменения статуса, слияния результатов, и проект changeet фиксирует.Окончательное письмо в багажник все еще проходит через Middleware Core Service.

Слияние нескольких Units не атомарно между Units. Приложение должно показывать результат для каждой Unit.

## Независимые точки расширения

Когда приложение включает модуль расширения, каждая граница требует отдельной оценки:

| Граница | Ядро | History | Comment | File | Worktree |
| --- | --- | --- | --- | --- | --- |
| Service | Независим | Независим | Независим | Независим | Независим |
| Middleware | Не общий | Не наследует ядро | Не наследует ядро | Не наследует ядро | Не наследует ядро |
| Event | Жизненный цикл ядра | Наблюдает Events ядра | `commentCommitted` | — | Жизненный цикл/коммит Worktree |
| Database Adapter | Adapter ядра | History Adapter | Comment Adapter | File Adapter и Blob Store | Worktree Adapter |

Office Exchange повторно использует хранилище Core and File.После запуска `import` и `export` Middleware Exchange импорт и экспорт по-прежнему проходят через Core и File Middleware.

Эти Адаптеры могут совместно использовать базу данных и по-прежнему оставаться отдельными объектами с отдельными контрактами.

## Подключение интерфейса истории Web SDK [#web-history]

В Web SDK, `historyServerUrl` является общим префиксом для `/{unitId}/list`, `/{unitId}/creators` и `/{unitId}/cs`, и он по умолчанию `/universer-api/history`. Когда используется другой префикс, плагин истории хоста и плагин пользовательского интерфейса истории продукта должны быть настроены с одним и тем же URL.

Восстановление версии проходит через мутационный путь совместной работы; для восстановления не существует автономной конечной точки REST истории. Загрузка совместной работы, отправка и авторизация должны оставаться настроенными. Сравнение двух материализованных снимков через `createUnitComparisonEngine()` - это отдельная операция, которая считывает только данные. Она не требует запущенной службы истории, и она не сохраняется и не восстанавливает версии.
