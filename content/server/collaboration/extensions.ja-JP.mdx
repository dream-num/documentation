---
title: 共同編集の拡張モジュール
description: History、Thread Comment、Worktree、サーバー側の Office 変換による共同編集の拡張を理解します。
---

History、Thread Comment、Worktree は必要に応じて有効化できる独立した拡張モジュールです。Transport、ID システム、物理 DB を再利用できますが、Service、Middleware、Event、Database Adapter、ライフサイクルの境界は個別に持ちます。

サーバー側の Office 変換は、ファイル変換と Collaboration Service API を組み合わせるアプリケーションの処理です。主 Service の機能スイッチではありません。

| 拡張モジュール | 基本の共同編集との関係 |
| --- | --- |
| History | 基本 Events を監視して派生履歴インデックスを構築 |
| Thread Comment | 基本の Unit Room を再利用。コメントのアンカーは基本コンテンツに属する |
| Worktree | 基本の Unit と OT を再利用し、下書きをトランクにマージ |
| Office Exchange | 基本 Service のスナップショット API で Unit を作成・読み取り |

History、Thread Comment、Worktree はそれぞれ Middleware、Events、Database Adapter を設定します。

## バージョン履歴

History は Unit 作成と確定した変更セットを、ユーザー向けの履歴項目にまとめます。これは派生インデックスであり、Unit 内容の正本は基本 Collaboration Service の確定済み変更セットです。

```ts
const historyService = new UniverHistoryService({
  collabService,
  dbAdapter: historyDatabase,
  userProvider,
});

const attachment = historyService.attach(collabService);
transport.register(new UniverHistoryEndpoint(historyService));
```

`attach()` は基本 Service の `unitCreated` と `changesetCommitted` Events を監視してインデックスを更新します。既定のポリシーは変更セットごとに履歴を作らず、時間枠と特別な mutation によってまとめます。

History は独立した読み取り・索引作成 Middleware を持ちます。`userProvider` は名前やアバターなどの表示情報を補完するだけで、認証や認可はしません。Event Listener が失敗しても確定済みの基本変更セットはロールバックされないため、History は常に再構築可能な派生データとして扱います。

## スレッドコメント

Comment Service は Sheets と Docs のコメント本文、返信、編集、削除、解決状態を管理します。

```ts
const commentService = new UniverCommentService({
  database: commentDatabase,
  userProvider,
});

transport.register(
  new UniverCommentEndpoint({
    service: commentService,
    roomHost: collabEndpoint,
  }),
);
```

コメント本文は Comment Adapter に属します。Sheet や Doc の内容に追従するアンカーは基本のスナップショットと変更セットに残ります。Comment Endpoint は主 Collaboration Endpoint の Unit Room で `comment_update` を配信できますが、リアルタイムメッセージがコメント状態の正本ではありません。クライアントはコメント一覧を再取得して復帰できます。

Comment Service は追加、一覧、返信、解決／再開、編集、削除の Middleware と `commentCommitted` Event を提供します。基本 Service の読み取り・編集ポリシーは継承しません。

## Worktree の下書きとマージ

Worktree は 1 つ以上の Unit に隔離した下書き、凍結、マージ評価、Unit ごとのマージを追加します。

```text
create → draft → ready → merging → merged
           ↑       │
           └ reopen┘

draft / ready → discarded
```

```ts
const worktreeService = new UniverCollabWorktreeService({
  trunk: {
    service: collabService,
    dbAdapter: coreDatabase,
  },
  dbAdapter: worktreeDatabase,
});
```

Worktree は `(worktreeID, unitID)` ごとに独立した下書き変更セットを保存し、基本 Service の Unit、OT、送信エンジンを再利用します。追加編集を受け付けるのは `draft` 状態だけです。`markReady()` が現在の下書きリビジョンを凍結し、`mergeWorktree()` が Unit を 1 つずつトランクにマージします。

Worktree Service は独立したライフサイクル、読み取り、下書きの submit/apply/commit Middleware と、作成、状態変更、マージ結果、下書き変更セットのコミットに対応する Events を持ちます。トランクへの最終書き込みは基本 Service 自身の Middleware を通ります。

複数 Unit のマージは Unit 間でアトミックではありません。アプリケーションは各 Unit のマージ結果を表示してください。

## サーバー側の Office 変換

サーバー側 Exchange は `@univerjs-pro/exchange-node` と Collaboration Service API を組み合わせ、ファイルと共同編集状態を変換します。

```text
Office ファイル
  → exchange-node でインポート
  → Snapshot + Sheet Blocks
  → createUnitFromSnapshot()

確定した Unit リビジョン
  → getUnitLoadDataWithBlocks()
  → UnitSnapshotMaterializer
  → exchange-node でエクスポート
  → Office ファイル
```

公式サンプルは XLS、XLSX、CSV、TSV を新しい共同編集 Sheet として取り込み、現在の確定リビジョンを XLSX、CSV、TSV に出力します。

ファイル保存、タスク状態、アクセス制御、サイズ制限、業務 API はアプリケーションが担当します。Exchange に独立した共同編集 Database Adapter はなく、基本 Service を通じて正本の Unit を読み取り・作成します。

## 独立した拡張ポイント

拡張を有効にするときは各境界を個別に検討します。

| 境界 | 基本 | History | Comment | Worktree |
| --- | --- | --- | --- | --- |
| Service | 独立 | 独立 | 独立 | 独立 |
| Middleware | 共有しない | 基本から継承しない | 基本から継承しない | 基本から継承しない |
| Event | 基本ライフサイクル | 基本 Events を監視 | `commentCommitted` | Worktree のライフサイクル／コミット |
| Database Adapter | 基本 Adapter | History Adapter | Comment Adapter | Worktree Adapter |

同じ SQLite ファイルを使っても、これらの Adapter は別の契約を持つ別オブジェクトです。Service と Adapter も個別に破棄します。

## Web SDK の履歴 UI への接続 [#web-history]

History Endpoint を共同編集のエンドポイントとともに公開します。Web SDK の `historyServerUrl` は `/{unitId}/list`、`/{unitId}/creators`、`/{unitId}/cs` の共通プレフィックスで、既定値は `/universer-api/history` です。別のパスを使う場合は、ホストの History プラグインと製品の History UI プラグインに同じ URL を設定します。

復元は共同編集の mutation として送信され、独立した履歴復元 REST API は使いません。共同編集の読み込み、送信、認可の設定を維持してください。`createUnitComparisonEngine()` による完全なスナップショット同士の読み取り専用比較には履歴サービスは不要です。バージョンの保存や復元は行いません。

## ライブシェアの統合 [#live-share]

ライブシェアは同じ Sheet にいる参加者へ発表者の表示を同期し、共同編集の Session と Unit ルームを再利用します。リモートカーソルだけを表示し、自分の表示位置を動かさない Presence とは異なります。

**バージョンの制約：**`@univerjs-pro/collaboration-endpoint@1.0.0-rc.0` は `INGEST` のカーソル Presence のみを処理し、`liveshare.*` には対応していません。登録するだけで使える Live Share サービスはありません。バックエンドに下記のプロトコルを実装するか、明示的に対応したバージョンを使います。`UniverLiveSharePlugin` の登録だけでは利用できません。

先に[ブラウザー統合](/server/collaboration/browser-integration)と[認証・権限](/server/collaboration/identity-and-authorization)を設定します。フロントエンドでは共同編集とライセンスの設定後、共有 Sheet を開く前に `UniverLiveSharePlugin` を登録します。[Web SDK ガイド](/guides/sheets/features/live-share)を参照してください。

| クライアントイベント | バックエンドの責務 |
| --- | --- |
| `liveshare.request_host` | 認証済み Session と参加済み Unit で発表権限を確認し、発表者を決定して `liveshare.new_host` を配信します。 |
| `liveshare.operation` | 現在の発表者の操作だけを受け入れ、信頼できる発表者の member ID を付けて Unit 内へ配信し、operation ID ごとの最新値をキャッシュします。 |
| `liveshare.fetch_operations` | 権限のある新規参加者や再接続したメンバーへ、現在の発表者とキャッシュした操作を返します。 |
| `liveshare.terminate` | 送信者の終了権限を確認し、発表状態を消去して参加者へ通知します。 |

接続の識別には Session の `memberID` を使い、クライアントが送るユーザー ID を信用しないでください。文書アクセスと発表権限、operation ID と引数を検証し、発表者の退出時に状態を消去または移譲します。表示状態は一時的な情報であり、文書の changeset として永続化しません。

独立した二つのブラウザーセッションで同じ Sheet を開き、発表開始、シート切り替え、スクロールとズーム、追従の停止と再開、参加者の再接続、発表者の退出を確認します。権限のないメンバーが発表者になったり操作を送信できないことも確認します。**セルの編集が同期できても、ライブシェアが動く証明にはなりません。**
