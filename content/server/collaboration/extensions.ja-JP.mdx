title: 共同編集の拡張モジュール
description: History、Thread Comment、Worktree、File、サーバー側の Office 変換による共同編集の拡張を理解します。

歴史、スレッドコメント、ファイル、およびWorktreeは、コアを変更することなくコラボレーションを拡張するオプションのコラボレーション拡張モジュールです。各モジュールは、独自のサービス、ミドルウェア、イベント、データベースアダプタ、およびライフサイクル境界を提供しているため、アプリケーションは製品が必要とするモジュールのみを有効にします。モジュールは、輸送、アイデンティティシステム、および同じ物理データベースを共有できます。

Server-side Office Exchange は、ファイルとコラボレーションサービスで構築されています。Office ファイルとコラボレーションユニット間で変換し、独自のサービス、エンドポイント、ミドルウェアを提供します。

| 拡張モジュール | 基本の共同編集との関係 |
| --- | --- |
| History | 基本 Events を監視して派生履歴インデックスを構築 |
| Thread Comment | 基本の Unit Room を再利用。コメントのアンカーは基本コンテンツに属する |

| Office Exchange | 基本 Service で Unit を作成・読み取りし、File でファイルを読み書き |
| Worktree | 基本の Unit と OT を再利用し、下書きをトランクにマージ |

歴史、スレッドコメント、ファイル、およびWorktreeは、それぞれ独自のミドルウェア、イベント、およびデータベースアダプタを設定します。

## バージョン履歴

履歴は、ユニットの作成と、ユーザーが見る履歴エントリへの変更を確認しました。 インデックスが由来します。コアコラボレーションサービスの確認された変更は、ユニットコンテンツの権威的なソースのままです。

```ts
const historyService = new UniverHistoryService({
  collabService,
  dbAdapter: historyDatabase,
  userProvider,
});

transport.register(new UniverHistoryEndpoint(historyService));
```

コンストラクタは、コアサービス`unitCreated`と`changesetCommitted`イベントを購読し、インデックスの現在の状態を維持し、`dispose()`はそれらのサブスクリプションを削除します。デフォルトでは、履歴グループはタイムウィンドウによって変更され、すべてのチェンジセットのエントリを書くのではなく、特別なミューテーションによって変更されます。

`getHistoryList`、`listHistoryCreators`および`getHistoryChangesets`のミドルウェアを読みました。 インデックス作成は、サービス内で行われます。 `userProvider`は、名前やアバターなどの表示データのみを供給し、認証や認可を行わないことを示しています。 イベントリスナーの故障は、既に確認済みのコアチェンジセットをロールバックしないので、履歴は、常に再構築できる誘導データとして扱われるべきです。

## スレッドコメント

コメントサービスは、シートとドキュメントの両方のコメントボディ、返信、編集、削除、および解決された状態を管理します。

```ts
const commentService = new UniverCommentService({
  database: commentDatabase,
  userProvider,
});

transport.register(
  new UniverCommentEndpoint({
    service: commentService,
    roomHost: collabEndpoint,
  }),
);
```

コメントボディはコメントアダプタに属していますが、シートまたはドキュメントコンテンツで移動するアンカーはコアスナップショットとチェンジセットの一部のままです。コメントエンドポイントは、メインコラボレーションエンドポイントのユニットルームを介して`comment_update`を公開することができますが、そのリアルタイムメッセージは権威的なコメント状態ではありません。メッセージが見逃すクライアントは、コメントを再びリストすることによって回復することができます。

コメントサービスは、ミドルウェアに`commentCommitted`イベントを追加、リスト、応答、解決、再オープン、編集、削除、および公開します。 コメントサービスは、コアサービスの読み取りまたは編集ポリシーを継承しません。

## ファイルストレージ

ファイルは、Univerクライアントがアップロードするバイナリファイルを格納します: ユニットに差し込まれた画像と添付ファイル、およびインポートとエクスポートのソースと結果ファイル。 ユニットデータは、ファイルIDのみを記録し、クライアントは、ユニットをロードしたときにIDがダウンロードURLに解決します。 スナップショットと変更セットは小さくとどまります。

```ts
const fileService = new UniverFileService({
  database: fileDatabase,
  blobStore,
});

transport.register(new UniverFileEndpoint(fileService));
```

メタデータとコンテンツは、`IFileDatabaseAdapter`のストアファイルレコードと`IFileBlobStore`ストアのコンテンツの2つの独立した契約です。 一時的な交換ファイルは、アップロードしたユーザーのみにアクセスでき、サービスがスケジュールでそれらを削除します。 ユニット内の画像と添付ファイルは、`upload`、`signUrl`および`download`ミドルウェアを介してユニットの許可を受けています。

## サーバー側の Office 変換

Exchange Service は、Office ファイルを共同ユニットとしてインポートし、ユニットをファイルとしてエクスポートします。`@univerjs-pro/exchange-node` は、コンバージョン用に使用し、コラボレーションサービスを通じてユニットを作成および読み込み、ファイルサービスを通じてソースと結果ファイルを保存します。

```ts
const exchangeService = new UniverExchangeService({ collabService, fileService });

transport.register(new UniverExchangeEndpoint(exchangeService));
```

インポートとエクスポートはタスクです。クライアントはタスクを作成し、結果の投票を行います。インポートは、コアサービスの`createUnit`ミドルウェアを通過し、エクスポートは`readUnitData`を通過します。 `import`と交換ハンドルレートの`export`中間物、クォーター、および監査。

| Unit | インポート | エクスポート |
| --- | --- | --- |
| Sheet | xls, xlsx, csv, tsv | xlsx, csv, tsv |
| Doc | doc, docx | docx |
| Slide | ppt, pptx | pptx |
| Base | xls, xlsx, csv, tsv | xlsx, csv |
| PDF | pdf | pdf |

タスクはServiceインスタンスに住んでいるため、アプリケーションは単一のインポートとエクスポートノードをデプロイし、すべての3つのExchangeルートをそのノードにルーティングします。

## Worktree の下書きとマージ

Worktree は 1 つ以上の Unit に隔離した下書き、凍結、マージ評価、Unit ごとのマージを追加します。

```text
create → draft → ready → merging → merged
           ↑       │
           └ reopen┘

draft / ready → discarded
```

```ts
const worktreeService = new UniverCollabWorktreeService({
  trunk: {
    service: collabService,
    dbAdapter: coreDatabase,
  },
  dbAdapter: worktreeDatabase,
});
```

Worktreeは、`(worktreeID, unitID)`によって独自の草案変更を保存し、コアサービスのユニット、OT、および提出エンジンを再利用します。 `draft`状態のみが、さらなる編集を受け入れます。 `markReady()`では、現在の草案の修正を凍結し、`mergeWorktree()`がユニットをトランクに統合します。

Worktreeサービスは、独自のライフサイクル、独自の読み取りミドルウェア、ドラフト/アプリ/コミットミドルウェア、作成、ステータス変更、結果のマージ、およびチェンジセットのコミットのためのイベントがあります。 トランクへの最終書き込みは、コアサービスのミドルウェアを通過します。

複数 Unit のマージは Unit 間でアトミックではありません。アプリケーションは各 Unit のマージ結果を表示してください。

## 独立した拡張ポイント

アプリケーションが拡張モジュールを有効にすると、各境界は別々の評価を必要とします。

| 境界 | 基本 | History | Comment | File | Worktree |
| --- | --- | --- | --- | --- | --- |
| Service | 独立 | 独立 | 独立 | 独立 | 独立 |
| Middleware | 共有しない | 基本から継承しない | 基本から継承しない | 基本から継承しない | 基本から継承しない |
| Event | 基本ライフサイクル | 基本 Events を監視 | `commentCommitted` | — | Worktree のライフサイクル／コミット |
| Database Adapter | 基本 Adapter | History Adapter | Comment Adapter | File Adapter と Blob Store | Worktree Adapter |

オフィス交換は、コアとファイルのストレージを再利用します。 `import`と交換ランの`export`ミドルウェアの後、インポートとエクスポートはコアとファイルミドルウェアを通過します。

これらのアダプタは、データベースを共有し、別の契約でオブジェクトを分離し続けることができます。サービスやアダプタも独立して処分する必要があります。

## Web SDK の履歴 UI への接続 [#web-history]

コラボレーションエンドポイントと一緒に履歴エンドポイントをマウントします。 Web SDK, `historyServerUrl` 一般的な接頭辞は、 `/{unitId}/list`, `/{unitId}/creators`, と `/{unitId}/cs`デフォルトでは、 `/universer-api/history`. 異なるプレフィックスが使用される場合、ホスト履歴プラグインと製品履歴 UI プラグインは同じ URL で構成する必要があります。

バージョンを復元すると、コラボレーションのミューテーションパスを経由します。 復元のためのスタンドアローンの履歴RESTエンドポイントはありません。 コラボレーションのロード、投稿、および承認が構成されなければなりません。 `createUnitComparisonEngine()`を介して2つの材料化されたスナップショットを比較することは、データを読む唯一の別の操作です。 実行中の履歴サービスを必要としません、そしてそれは主張もバージョンを復元しません。
