Collaboration Service 的核心協同資料由 Database Adapter 負責持久化。Service 負責 Unit、OT 與 revision 語義，Adapter 將這些語義轉換為原子且可安全重試的儲存操作。如需接入內建 Adapter 之外的資料庫，應實現 `IDatabaseAdapter`，並滿足其完整的行為約束。

Database Adapter 以 Apache-2.0 開源，原始碼位於 [univer-collaboration-sdk-community](https://github.com/dream-num/univer-collaboration-sdk-community)。其包名與版本和其他 package 保持一致。

## 驗證重啟後資料保留 [#verify-persistence]

停止 Quick Start，然後從倉庫根目錄執行 `pnpm example:database-adapter`。開啟 `http://127.0.0.1:3010/?unit=persistent-sheet`，修改一個單元格，再在另一個瀏覽器中確認修改結果。停止服務，重新執行同一條命令並開啟同一個 URL，該值應當仍然存在。

資料儲存在 `examples/database-adapter/.data/collaboration.sqlite`。範例服務每次啟動都會呼叫 `createUnitFromData()`。如果 Unit 已存在，傳回結果的狀態為 `already-exists`，先前的修改會保留。 [server/main.ts](https://github.com/dream-num/univer-collaboration-examples/blob/main/examples/database-adapter/server/main.ts)

## Adapter 儲存的資料

Adapter 為每份協作文件（Unit）儲存三類資料：

- **文件資訊**記錄文件 ID、型別、建立者、建立時間和當前版本號（`headRevision`）。Adapter 儲存變更集（changeset）時會同時更新版本號。應用可以在 `UnitRecord.metadata` 中儲存文件級的自定義資訊，例如文件名稱（`name`）、最近編輯者（`lastEditorID`）和最近修改時間（`lastModifiedAt`），這些欄位由應用維護。
- **快照**保存文件在特定版本的內容。讀取指定版本時，Service 可載入不晚於目標版本的最新快照，再依序重播到目標版本為止的修改。對於試算表，Adapter 也會儲存快照參照的資料區塊。
- **變更集**包含一次提交中的操作。Adapter 依版本順序儲存變更集，並保留 `sid` 和 `reqId`，讓 Service 能辨識用戶端重試的提交，避免重複套用修改。[^submission-idempotency] 應用程式可以在 `ChangesetRecord.metadata` 中保存這次編輯的來源（`source`）或相關業務操作的 ID（`operationId`）。

建立和提交時設定 metadata 的方法，見 [Middleware 與 Event](/server/collaboration/middleware-and-events#persistent-metadata)。

軟刪除會保留這些資料，還原後可繼續編輯。永久刪除後，文件資料無法再存取，原文件 ID 也不能重複使用。

使用者、角色和存取權限由應用程式管理。History、Thread Comment 和 Worktree 各自使用獨立的 Adapter 介面。

## Adapter 的讀寫要求

自訂 `IDatabaseAdapter` 時，各項操作須符合以下要求。

| 操作 | 實作要求 |
| --- | --- |
| 建立文件 | 以原子操作儲存 Unit 記錄（含 metadata）、初始快照及其參照的 Sheet 區塊，讓這些資料同時可讀。 |
| 提交變更集 | 只有目前版本號與預期值相符時才能提交（CAS）[^revision-cas]。在同一次原子寫入中保存變更集及其 metadata、完整取代 Unit metadata，並將版本號加 1。版本不符時，傳回目前版本號，不寫入資料。 |
| 讀取變更集 | 依版本號遞增順序傳回指定範圍內的變更集，版本號必須連續。保留每個變更集原有的 `sid` 和 `reqId`，供 Service 辨識同一 Unit 內的重複提交。 |
| 儲存快照 | 快照可讀時，它參照的所有 Sheet 區塊也必須可讀。 |
| 刪除與還原 | 刪除或還原須對整批 Unit 生效。任一項失敗時，整批維持原狀。 |

## Memory Adapter

[`@univerjs-pro/collaboration-database-memory`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-memory) 在程序內執行，適用於以下場景：

- 單元測試與整合測試
- 臨時開發環境
- 快速驗證自訂 Middleware 或用戶端組裝

```ts
import { MemoryDatabaseAdapter } from "@univerjs-pro/collaboration-database-memory";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";

const database = new MemoryDatabaseAdapter();
const service = new UniverCollabService({ dbAdapter: database });
```

Memory Adapter 與持久化實現遵守相同的 revision、CAS 與冪等合同，但其資料僅存在於當前 Node.js 程序中，程序退出後即丟失。

## SQLite Adapter

[`@univerjs-pro/collaboration-database-sqlite`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-sqlite) 將資料儲存到 SQLite 檔案中，適用於開發、測試、本地應用與小規模使用。

```ts
import { mkdir } from "node:fs/promises";

import { SQLiteDatabaseAdapter } from "@univerjs-pro/collaboration-database-sqlite";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";

await mkdir("./data", { recursive: true });

const database = new SQLiteDatabaseAdapter({
  filename: "./data/collaboration.sqlite",
  busyTimeoutMs: 5_000,
});
const service = new UniverCollabService({ dbAdapter: database });
```

資料庫為空時，它會初始化 schema；schema 已存在時，只做校驗。資料庫檔案的位置、備份方式以及其他 SQLite 設定均由應用決定。

## PostgreSQL Adapter

[`@univerjs-pro/collaboration-database-postgres`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-postgres) 將所有核心協同資料保存在 PostgreSQL 中，包括 Sheet 快照參照的儲存格資料區塊。多個協同節點可以共用同一個資料庫。

```ts
import { PostgresDatabaseAdapter } from "@univerjs-pro/collaboration-database-postgres";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";
import { Pool } from "pg";

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
const database = await PostgresDatabaseAdapter.create({ pool });
const service = new UniverCollabService({ dbAdapter: database });
```

連線池由應用持有，並在釋放 Service 之後關閉。`create()` 會在空資料庫中初始化 `collaboration` schema，schema 已存在時只做校驗。

若有 S3 相容的物件儲存服務，建議使用 [PostgreSQL + S3 Adapter](#postgresql-s3-adapter)，以減少資料庫及其備份的大小。

## PostgreSQL + S3 Adapter [#postgresql-s3-adapter]

[`@univerjs-pro/collaboration-database-postgres-s3`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-postgres-s3) 將 Sheet 的儲存格資料區塊存入 S3 相容儲存桶，Unit、changeset、快照記錄和區塊參照仍保存在 PostgreSQL 中。

大型活頁簿的快照主要由儲存格資料構成。將這些資料區塊放在 S3，可以減少 PostgreSQL 資料庫及其備份的大小。活頁簿成長時，區塊的儲存容量也可以獨立擴充。

將 `DATABASE_URL`、`S3_REGION` 和 `S3_BUCKET` 分別設為資料庫連線位址、儲存桶所在區域和既有儲存桶名稱。

```ts
import { S3Client } from "@aws-sdk/client-s3";
import { PostgresS3DatabaseAdapter } from "@univerjs-pro/collaboration-database-postgres-s3";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";
import { Pool } from "pg";

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
const client = new S3Client({ region: process.env.S3_REGION });
const database = await PostgresS3DatabaseAdapter.create({
  pool,
  s3: { client, bucket: process.env.S3_BUCKET! },
});
const service = new UniverCollabService({ dbAdapter: database });
```

## 自訂 Database Adapter

通常在以下情況下需要自定義 Adapter：

- 應用已在使用 MySQL 或其他業務資料庫
- 協同提交必須使用應用自有的資料庫機制
- 運維或合規要求超出內建 Adapter 的覆蓋範圍

實現 `IDatabaseAdapter`，然後像內建 Adapter 一樣將其注入 Service：

```ts
const database = new ApplicationCollaborationDatabase({ pool });
const service = new UniverCollabService({ dbAdapter: database });
```

Service 不依賴具體資料庫，但也無法為自定義實現補充 transaction、CAS 或 deduplication。Adapter 必須利用自身資料庫提供的能力實現完整合同。[社群倉庫](https://github.com/dream-num/univer-collaboration-sdk-community)中的內建實現在不同資料庫上實現了同一份合同，可以作為參考。

## 如何儲存業務資料

**附在文件或 changeset 上的資訊，使用 `metadata` 儲存。** 應用可以在建立文件或提交 changeset 時設定這些欄位，內建 Adapter 會將它們隨協同資料一起儲存。具體用法見 [Middleware 與 Event](/server/collaboration/middleware-and-events#persistent-metadata)。

**獨立的業務資料表可透過 Middleware 或 Event 寫入**。要記錄一次操作嘗試，可在 Middleware 中寫入稽核表。若要在提交成功後更新業務表，可監聽 `changesetCommitted`。這些寫入預設在協作交易之外執行。版本衝突可能導致提交階段的 Middleware 重跑，寫入時應避免重複記錄。Event 只在程序內盡力投遞，適合可稍後補寫或重建的資料。

**使用應用自己的資料庫和表結構，或在同一事務中寫入業務資料和協同資料時，可以自定義 Database Adapter。** 呼叫 Service 時，應用可以將業務操作 ID 等上下文放入 `customData`。Adapter 在對應方法中讀取 `ctx.customData` 中所需的欄位，再決定寫入哪些表。例如，`commitChangeset()` 可以在儲存 changeset 的同一事務中，用業務操作 ID 更新對應的業務記錄。

`customData` 僅在本次呼叫內有效。內建 Adapter 不會自動儲存其中的欄位，也不會據此寫入業務表。

## 擴充模組的儲存

History、Thread Comment、Worktree 與 File 等擴充套件模組各自定義獨立的 Database Adapter 介面。這些 Adapter 可以共用一個資料庫，也可以使用獨立的儲存。一個自定義實現還可以同時提供多個 Adapter 介面，並分別注入對應的 Service。

由於這些 Adapter 介面彼此獨立，SDK 預設不提供跨模組事務。即使多個模組共用一個資料庫，跨模組的一致性策略仍由應用負責。

## 選擇 Adapter

| Adapter         | 適用情境                                                 | 主要限制                                                                                     |
| --------------- | -------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Memory          | 測試、範例、臨時開發                                     | 程序結束後資料消失                                                                           |
| SQLite          | 開發、測試、本地應用與小規模使用                         | 單檔案資料庫，設定由應用管理                                                                 |
| PostgreSQL + S3 | 使用 PostgreSQL 和物件儲存的應用程式，尤其適合大型活頁簿 | 需管理資料庫和儲存桶。沒有 S3 相容儲存時，可選用 [PostgreSQL Adapter](#postgresql-adapter)。 |
| 自訂            | 已有資料庫或自定義業務資料整合                           | 應用需要實現並驗證完整合同                                                                   |

應用擁有所有注入的 Adapter。釋放時先釋放 Service，再釋放 Adapter：

```ts
await service.dispose();
await database.dispose();
```

可執行的對照範例見 [Database Adapter 範例](/server/collaboration/examples#database-adapter)。

[^revision-cas]: *CAS（比較並交換）* 僅在當前值仍等於預期值時更新資料。這裡必須原子地檢查當前修訂號並寫入下一狀態，避免兩個並行提交同時佔用同一修訂號。

[^submission-idempotency]: 冪等性允許重試同一次提交，而不會將編輯套用兩次。重試時應保留原提交識別碼；即使內容相同，使用新識別碼仍會被視為新的提交。
