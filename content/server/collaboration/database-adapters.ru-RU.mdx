Адаптер базы данных сохраняет основные данные совместной работы, которыми управляет Служба совместной работы. Сервис владеет семантикой Unit, OT и ревизии, а Адаптер превращает эти семантики в операции хранения атомов, которые безопасны для повторного использования. Для подключения базы данных, которая не покрыта встроенными Адаптерами, реализуйте `IDatabaseAdapter` и удовлетворяйте его полному поведенческому контракту.

Адаптеры баз данных с открытым исходным кодом Apache-2.0. Исходный код доступен в [сообщество единомышленников-совместителей](https://github.com/dream-num/univer-collaboration-sdk-community), а пакеты используют те же имена и версии, что и любой другой пакет.

## Проверка сохранения после перезапуска [#verify-persistence]

Остановите Quick Start и запустите `pnpm example:database-adapter` из корня репозитория. Откройте `http://127.0.0.1:3010/?unit=persistent-sheet`, измените ячейку и подтвердите изменение во втором браузере. Затем остановите сервер, снова запустите ту же команду и снова откройте тот же URL. Значение все равно должно присутствовать.

Данные хранятся в `examples/database-adapter/.data/collaboration.sqlite`, поэтому не удаляйте этот файл между запусками. При запуске сервер считывает существующий блок и звонит `createUnitFromData()` только тогда, когда он получает `UNIT_NOT_FOUND`, поэтому он никогда не перезаписывает сохраненные данные. Реализация находится в [Сервер/main.ts](https://github.com/dream-num/univer-collaboration-examples/blob/main/examples/database-adapter/server/main.ts).

## Что хранит Adapter

Для каждого совместно редактируемого документа (Unit) Adapter хранит три вида данных.

- **Запись Unit** содержит идентификатор документа, тип, автора, время создания и текущую ревизию (`headRevision`). При сохранении changeset адаптер обновляет ревизию в рамках той же операции. В `UnitRecord.metadata` приложение может хранить и обновлять собственные поля, например название документа (`name`), идентификатор последнего редактора (`lastEditorID`) и время последней правки (`lastModifiedAt`).
- **Снимок** содержит данные документа на определённой ревизии. Для чтения заданной ревизии Service может загрузить последний снимок с номером не выше запрошенного и применить последующие изменения вплоть до нужной ревизии. Для электронных таблиц Adapter также хранит блоки данных, на которые ссылается снимок.
- **Набор изменений (changeset)** объединяет операции одной отправки. Adapter сохраняет наборы изменений в порядке ревизий вместе с идентификаторами отправки `sid` и `reqId`. По ним Service распознаёт повторную отправку клиента и не применяет одну правку дважды.[^submission-idempotency] В `ChangesetRecord.metadata` приложение может записать источник правки (`source`) или идентификатор связанной бизнес-операции (`operationId`).

О том, как задать метаданные при создании документа и отправке изменений, см. раздел [Сохранение метаданных](/server/collaboration/middleware-and-events#persistent-metadata).

При мягком удалении данные сохраняются. После восстановления редактирование можно продолжить. При окончательном удалении данные документа становятся недоступны, а его идентификатор нельзя использовать повторно.

Пользователями, ролями и правами доступа управляет приложение. У History, Thread Comment и Worktree отдельные интерфейсы адаптеров.

## Требования к чтению и записи

При реализации `IDatabaseAdapter` соблюдайте следующие требования.

| Операция | Требование |
| --- | --- |
| Создание Unit | Атомарно сохраните запись Unit с метаданными, начальный снимок и блоки Sheet, на которые он ссылается. Все эти данные должны стать доступны для чтения одновременно. |
| Фиксация changeset | Запись допустима только при совпадении текущей и ожидаемой ревизий (CAS)[^revision-cas]. За одну атомарную операцию сохраните changeset с его метаданными, полностью замените метаданные Unit и увеличьте номер ревизии на единицу. При несовпадении верните текущую ревизию без записи данных. |
| Чтение наборов изменений | Верните наборы из запрошенного диапазона в порядке возрастания ревизий, без пропусков. Сохраняйте исходные `sid` и `reqId`, чтобы Service мог распознать повторную отправку для той же Unit. |
| Сохранение снимка | К моменту, когда снимок станет доступен для чтения, должны читаться и все блоки Sheet, на которые он ссылается. |
| Удаление и восстановление | Применяйте операцию ко всем Unit в пакете. Если хотя бы для одной она завершилась ошибкой, весь пакет должен остаться в исходном состоянии. |

## Memory Adapter

[`@univerjs-pro/collaboration-database-memory`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-memory) работает внутри процесса Node.js. Он подходит для:

- модульных и интеграционных тестов
- временных сред разработки
- быстрые проверки пользовательского Middleware или сборки клиента

```ts
import { MemoryDatabaseAdapter } from "@univerjs-pro/collaboration-database-memory";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";

const database = new MemoryDatabaseAdapter();
const service = new UniverCollabService({ dbAdapter: database });
```

Адаптер памяти следует тому же самому пересмотру, CAS и контракту идемпотентности, что и постоянные реализации.Его данные существуют только в текущем процессе Node.js и теряются при выходе этого процесса.

## SQLite Adapter

[`@univerjs-pro/collaboration-database-sqlite`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-sqlite) хранит данные в файле SQLite. Он подходит для разработки, тестирования, локальных приложений и мелкомасштабного использования.

```ts
import { mkdir } from "node:fs/promises";

import { SQLiteDatabaseAdapter } from "@univerjs-pro/collaboration-database-sqlite";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";

await mkdir("./data", { recursive: true });

const database = new SQLiteDatabaseAdapter({
  filename: "./data/collaboration.sqlite",
  busyTimeoutMs: 5_000,
});
const service = new UniverCollabService({ dbAdapter: database });
```

Он инициализирует схему, когда база данных пуста и проверяет схему только тогда, когда она уже существует. Местоположение файла, метод резервного копирования и любые другие настройки SQLite определяются приложением.

## PostgreSQL Adapter

[`@univerjs-pro/collaboration-database-postgres`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-postgres) построен на узле-постгре и хранит свои данные в PostgreSQL. Несколько узлов совместной работы могут совместно использовать одну базу данных.

```ts
import { PostgresDatabaseAdapter } from "@univerjs-pro/collaboration-database-postgres";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";
import { Pool } from "pg";

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
const database = await PostgresDatabaseAdapter.create({ pool });
const service = new UniverCollabService({ dbAdapter: database });
```

Приложение владеет пулом и закрывает его после удаления Сервиса. `create()` инициализирует схему `collaboration` в пустой базе данных и только проверяет существующую схему.

## Собственные Database Adapters

Настраиваемый адаптер обычно подходит в следующих случаях:

- приложение уже использует MySQL или другую бизнес-базу
- В совместных заявках должны использоваться механизмы баз данных, которыми владеет приложение.
- эксплуатационные или нормативные требования выходят за рамки встроенных Adapters

Реализуйте `IDatabaseAdapter` и внедрите его в Service так же, как встроенный Adapter:

```ts
const database = new ApplicationCollaborationDatabase({ pool });
const service = new UniverCollabService({ dbAdapter: database });
```

Сервис не зависит от конкретной базы данных, но не может добавлять транзакции, CAS или дедупликацию в пользовательскую реализацию. Адаптер должен реализовать полный контракт с использованием возможностей, которые предоставляет его база данных. Встроенные реализации в [Репозиторий сообщества](https://github.com/dream-num/univer-collaboration-sdk-community) применяют один и тот же контракт к разным базам данных и служат ссылками.

## Как хранить бизнес-данные

**Используйте `metadata` для информации, прикрепленной к документу или внесенной в него записке.** Приложение может устанавливать эти поля при создании документа или отправке в него изменений, а встроенные Адаптеры сохраняют их вместе с данными о сотрудничестве. См. [Промежуточное ПО и события](/server/collaboration/middleware-and-events#persistent-metadata).

**Используйте Middleware или Events для написания отдельных бизнес-таблиц.** Для аудита предпринятой операции напишите в таблицу аудита в Middleware. Чтобы обновить бизнес-таблицу после успешного совершения сделки, прослушивайте `changesetCommitted`. По умолчанию эти записи выполняются вне транзакции совместной работы. Конфликт пересмотра может привести к повторному запуску промежуточного программного обеспечения на стадии выполнения, поэтому повторная проверка не должна создавать дубликатную запись. События доставляются в процессе на основе наилучших усилий. Используйте их для данных, которые приложение может заполнить или восстановить.

**Используйте пользовательский адаптер базы данных, когда приложение нуждается в собственной базе данных и схеме, или когда данные о бизнесе и сотрудничестве должны быть записаны в одной транзакции.** При вызове Сервиса приложение может передавать контекст, такой как идентификатор бизнес-операции в `customData`. Затем Адаптер может считывать нужные ему поля из `ctx.customData` и решать, какие таблицы обновлять. Например, `commitChangeset()` может использовать идентификатор операции для обновления соответствующей бизнес-записи в той же транзакции, которая сохраняет набор изменений.

`customData` Встроенные адаптеры не сохраняют свои поля автоматически, и они не используют их для записи в бизнес-таблицы.

## Хранение расширений

Модули расширения, такие как History, Thread Comment, Worktree и File, каждый определяют независимый интерфейс адаптера базы данных. Их адаптеры могут совместно использовать одну базу данных или использовать отдельное хранилище. Одна пользовательская реализация также может обеспечить несколько интерфейсов адаптера и быть введена в соответствующие службы.

Поскольку эти интерфейсы адаптера независимы, SDK по умолчанию не обеспечивает трансакции кросс-модулей.Даже когда несколько модулей совместно используют базу данных, приложению принадлежит стратегия согласованности кросс-моделей.

## Выбор Adapter

| Adapter | Подходящие задачи | Основное ограничение |
| --- | --- | --- |
| Memory | Тесты, примеры, временная разработка | Данные теряются при выходе из процесса |
| SQLite | Разработка, тесты, локальные приложения, небольшой масштаб | Однофайловая база с настройками под контролем приложения |
| PostgreSQL | Развёртывание на нескольких узлах и существующие базы PostgreSQL | Пул и эксплуатация базы под контролем приложения |
| Собственный | Существующие базы или особая интеграция бизнес-данных | Приложение реализует и проверяет полный контракт |

Приложение владеет всеми внедрёнными Adapters. Освободите Service раньше Adapter:

```ts
await service.dispose();
await database.dispose();
```

Сравнить работающие реализации можно в [примере Database Adapter](/server/collaboration/examples#database-adapter).

[^submission-idempotency]: Идемпотентность позволяет повторить отправку без повторного применения изменений. Сохраняйте идентификатор отправки: те же данные с новым идентификатором считаются новой отправкой.

[^revision-cas]: CAS обновляет значение, только если оно совпадает с ожидаемым. Проверка текущей ревизии и запись следующего состояния должны быть атомарными, чтобы два параллельных запроса не подтвердили одну ревизию.
