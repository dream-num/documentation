Middleware y Eventos son los puntos de extensión para fines generales de la Collaboration SDK. La identidad y la autorización se integran a través de Middleware. Middleware valida o restringe una operación antes de que se ejecute; Eventos registra cambios o activa el trabajo de seguimiento después de que se confirme un cambio de estado.

## Dos momentos de extensión

| | Middleware | Event |
| --- | --- | --- |
| Ejecución | Durante una operación | Tras confirmar un cambio de estado |
| Participar o rechazar la operación | Sí | No |
| Ampliar el Context | Sí | Lea el Contexto y el resultado llevado por el Evento |
| Fallo del receptor | Puede fallar la operación actual | Aislado del resultado de dominio ya determinado |
| Usos habituales | Identidad, autorización, validación, registro, medición de tiempo | Índices derivados, cachés, métricas, notificaciones internas |

Use Middleware cuando usted debe decidir si una operación puede continuar. Utilice un evento cuando usted necesita sólo para observar que un cambio de estado ya ha ocurrido.

## Modelo de ejecución de Middleware

Middleware para la misma Acción forma una cadena asincrónica en orden de registro. `await next()` entra en el próximo Middleware, y la operación SDK se ejecuta en el punto más interior:

```ts
service.use("submitChangeset", async (context, next) => {
  const startedAt = performance.now();
  context.customData.startedAt = startedAt;

  try {
    await next();
  } finally {
    metrics.observe("collaboration.submit.duration", performance.now() - startedAt);
  }
});
```

Un Middleware puede leer la solicitud de acción específica, compartir datos de llamada local a través de `customData`, inspeccionar los sistemas de aplicación de entrada o consulta antes de `next()` y registrar la duración o los resultados después de que `next()` regrese. Lanzar un `CollabError` rechaza una operación de colaboración esperada.

Transporte HTTP Middleware puede terminar la respuesta HTTP sin llamar a `next()`. Servicio y Endpoint Middleware debe rechazar con un error explícito en lugar de saltar silenciosamente `next()` .

## Middleware de Transport

`transport.use()` registra Middleware HTTP ordinario, que se ejecuta en orden de registro. Llama a `await next()` para continuar el procesamiento o finaliza la respuesta directamente. `transport.useUpgrade()` gestiona los protocolos de enlace WebSocket.

El siguiente ejemplo registra la duración de HTTP, autentica la solicitud y establece un `userID` de confianza, luego registra el Punto Final de Colaboración:

```ts
transport.use(async (context, next) => {
  const start = performance.now();
  context.response.once("finish", () => {
    recordHttpDuration({
      method: context.incomingMessage.method,
      route: context.route?.path ?? "unmatched",
      status: context.response.statusCode,
      durationMs: performance.now() - start,
    });
  });
  await next();
});

transport.use(async (context, next) => {
  const user = await authenticate(context.incomingMessage);
  if (!user) {
    context.response.statusCode = 401;
    context.response.end("Authentication required");
    return;
  }
  context.userID = user.userId;
  await next();
});

transport.register(collaborationEndpoint);
```

La aplicación suministra `recordHttpDuration` y `authenticate`. El Endpoint utiliza el `userID` establecido por el Middleware anterior. El observador de duración corre antes de la autenticación, por lo que las solicitudes rechazadas también se registran.

`context.route?.path` es la plantilla de ruta completa, disponible una vez que la ejecución llegue al punto final. Utilice la respuesta `finish` evento para medir cuando la respuesta se complete. Reyecciones antes de la enrutamiento y caminos desconocidos se registran como `unmatched`.

## Middleware de Endpoint

Endpoint Middleware cubre las operaciones de sesión y presencia en tiempo real:

| Action | Momento | Usos habituales |
| --- | --- | --- |
| `connect` | Tras consumir el ticket y crear Session, antes de HELLO | Política de conexión, nombre y avatar del miembro |
| `joinUnit` | Antes de entrar en una Room Unit | Admisión y visibilidad de la Unit |
| `receivePresence` | Tras recibir Presence de una Session unida, antes de difundir | Validación y filtrado de Presence |
| `sendPresence` | Antes de enviar Presence a cada miembro | Filtrado por destinatario |

```ts
endpoint.use("receivePresence", async (context, next) => {
  if (JSON.stringify(context.payload).length > 8_000) {
    throw new CollabError("INVALID_REQUEST", "Presence payload is too large");
  }
  await next();
});
```

El `session.userID` y `session.customData` de Endpoint provienen de la solicitud HTTP que emitió el boleto de sesión. El Endpoint crea `memberID` para la actual sesión WebSocket, y este identificador cambia después de la reconexión.

## Middleware de Service

Service Middleware cubre el ciclo de vida de los datos de colaboración autorizados:

| Action | Límite | Usos habituales |
| --- | --- | --- |
| `readUnitData` | Antes de leer instantáneas, bloques o cambios | Lectura, comprobación de inquilino, auditoría |
| `createUnit` | Antes de crear una Unit atómicamente | Tipos, política de creación, reglas de negocio |
| `deleteUnits` | Antes de escribir el lote de eliminación | Política de eliminación y comprobaciones por Unit |
| `recoverUnits` | Antes de escribir el lote de recuperación | Política de recuperación y auditoría |
| `submitChangeset` | Al recibir el envío, antes de la deduplicación y de la OT | Comprobar los permisos de edición o limitar el tamaño del envío |
| `applyChangeset` | Después de la OT, antes de aplicar el changeset al documento | Validar las operaciones transformadas, por ejemplo, comprobar si afectan a un rango protegido |
| `commitChangeset` | Después de aplicar el changeset al estado candidato y antes de que el Adapter lo guarde | Definir los metadatos que se guardarán con el envío |

```ts
service.use("createUnit", async (context, next) => {
  await creationPolicy.assertAllowed({
    userID: context.userID,
    unitID: context.request.snapshot.unitID,
    type: context.request.snapshot.type,
  });
  context.customData.creationPolicyChecked = true;
  await next();
});
```

`submitChangeset` se ejecuta una vez por cada sumisión lógica. La contención de revisión puede causar `applyChangeset` y `commitChangeset` a ejecutar de nuevo con un nuevo `attempt`. El software medio en esas etapas debe ser seguro de reingreso y no debe enviar mensajes externos irreversibles o realizar cargos de una sola vez directamente.

## Alcance de customData

`customData` lleva el contexto dentro de una sola llamada. El callador puede suministrar datos, y Middleware puede agregar a él para más tarde Middleware, el Adaptador de bases de datos y eventos relacionados a leer.

- Pasar un ID de inquilino, un ID de traza o el logger de la petición.
- Reutilizar los resultados de una consulta de permisos durante la llamada.
- Registrar la hora de inicio de una medición o una etiqueta de auditoría.

Los adaptadores integrados de base de datos no persisten `customData`. Para guardar campos junto con un documento o un cambio, consulte [Metadatos persistentes](#persistent-metadata) .

## Metadatos persistentes [#persistent-metadata]

`metadata` almacena datos definidos por la aplicación. `UnitRecord.metadata` se guarda con el documento y `ChangesetRecord.metadata` con cada envío.

Al crear un documento puedes pasar `metadata` a `createUnitFromData()` o a `createUnitFromSnapshot()`, o bien establecer `context.unit.metadata` en el Middleware `createUnit`. El valor predeterminado es `{}`.

Al enviar un cambio, ambos objetos de metadatos se pueden actualizar en el middleware `commitChangeset`. `context.unit.metadata` comienza con los metadatos actuales del documento, y `context.changeset.metadata` comienza como `{}`. Sus tipos, `UnitMetadata` y `ChangesetMetadata`, son alias de `Record<string, unknown>`. Los valores de campo deben ser JSON-serializable.

Actualizar metadatos antes de llamar a `await next()`. El siguiente ejemplo registra el último editor del documento y la fuente de la presentación.

```ts
service.use("commitChangeset", async (context, next) => {
  context.unit.metadata.lastEditorID = context.userID;
  context.changeset.metadata.source = "application";
  await next();
});
```

El Service pasa los dos objetos completos al Adapter para que los guarde con el envío.

- **Conflicto de revisión.** Al reintentar, el Service vuelve a ejecutar el Middleware `commitChangeset` con los últimos metadatos de la Unit y los metadatos del changeset vacíos.
- **Envío duplicado.** Si el mismo envío ya se completó correctamente, el Service devuelve los metadatos del changeset original.

Para leer los metadatos del documento, llama a `getUnit()` en el Adapter y lee `metadata` en el registro devuelto. Para el envío actual, lee `changeset.metadata` en el resultado de `submitChangeset()` si el envío se ha completado correctamente. Al consultar envíos anteriores con `getChangesets()`, cada elemento del array `changesets` devuelto contiene `metadata`.

Con el adaptador SQLite incorporado o PostgreSQL, los metadatos de documento y de cambios también pueden ser consultados directamente con SQL. Utilice los nombres de tabla y columna definidos por el esquema de Adaptador.

## Modelo de ejecución de Events

Los Services registran receptores locales al proceso con `on()`, que devuelve una suscripción liberable:

```ts
const subscription = service.on("changesetCommitted", async (event) => {
  metrics.increment("collaboration.changeset.committed", {
    unitType: String(event.changeset.type),
  });
  localCache.delete(event.changeset.unitID);
});

subscription.dispose();
```

Los oyentes del mismo Evento se ejecutan secuencialmente en orden de registro, y el SDK espera a cada uno. Los errores del oyente se registran y se aíslan del resultado de dominio ya determinado. Un oyente `changesetCommitted` fallido, por ejemplo, no retrocede un cambio que el Adaptador ya ha almacenado.

Los eventos son apropiados para trabajos de seguimiento en proceso, recuperables o no críticos. No son un límite de transacción compartido con el compromiso de la base de datos, y no garantizan la entrega a un sistema externo.

## Events del Service principal

| Event | Hecho confirmado | Uso habitual |
| --- | --- | --- |
| `unitCreated` | Unit y datos iniciales creados | Caché de catálogo local o índice derivado |
| `changesetCommitted` | El Adapter ha guardado el changeset y actualizado la revisión | Difusión, métricas, índices derivados |
| `unitsDeleted` | Adapter confirmó el lote de eliminación | Limpiar estado relacionado del proceso |
| `unitsRecovered` | Adapter confirmó el lote de recuperación | Restaurar estado derivado del proceso |

En un listener de `unitCreated` puedes leer los metadatos del documento en `event.record.metadata`. En un listener de `changesetCommitted` encontrarás los metadatos del envío en `event.changeset.metadata`.

El Endpoint escucha a `changesetCommitted` en el mismo Servicio y transmite los cambios confirmados a los clientes que se unieron a la Unidad en el proceso actual. Cuando se configura un adaptador de pub/sub, la emisión también llega a cada nodo. El Endpoint también expone `memberLeftUnit` para licencia explícita, desconexión y eliminación de Endpoint.

## Las extensiones tienen puntos independientes

History, Thread Comment y Worktree no heredan Middleware ni Events del Collaboration Service principal:

- History proporciona Middleware de lectura para `getHistoryList`, `listHistoryCreators` y `getHistoryChangesets`;
- Comment proporciona añadir, responder, editar, eliminar, resolver y listar, más `commentCommitted`;
- Worktree proporciona ciclo de vida y lectura/envío/commit de borradores, más Events de creación, estado, fusión y commit de borrador.

Instalar reglas por separado para cada módulo habilitado. Logging, tenant, o autorización Middleware en el Servicio básico no cubre estos módulos automáticamente.

Continúa con [Identidad y autorización](/server/collaboration/identity-and-authorization) para asociar usuarios y ACL existentes con estos límites generales.
