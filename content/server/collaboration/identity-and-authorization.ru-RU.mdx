Univer Collaboration SDK не определяет пользователей, роли или модель ACL. Приложение устанавливает доверенную личность в Transport Middleware, а затем защищает сеансы в реальном времени и авторитетные данные о сотрудничестве с Endpoint и Service Middleware.

На этой странице [Промежуточное ПО и события](/server/collaboration/middleware-and-events) применяется к одной конкретной задаче: интеграции идентификации и авторизации через Middleware.

## Проверка прав [#verify-permissions]

Запустите `pnpm example:permissions`, откройте `http://127.0.0.1:3010` и по очереди войдите под тремя учётными записями.

1. Войдите как Bob и измените ячейку.
2. Переключитесь на Casey. Убедитесь, что изменение видно, а ячейка доступна только для чтения.
3. Переключитесь на Dana. Убедитесь, что документ не открывается.

## Модель идентификации

| Идентификатор | Источник | Значение и жизнь |
| --- | --- | --- |
| `userID` | Приложение | Стабильная бизнес-идентичность и автор подтверждённых наборов изменений |
| `memberID` | Endpoint | ID участника в сети для одной Session WebSocket; меняется после переподключения |
| `sid + reqId` | Клиент | Идентификатор отправки набора изменений, сохраняющийся при повторах |

Поля профилей пользователей, представленные браузером `memberID`, и изменения не могут заменить аутентификацию приложения. Приложение отображает свой стабильный пользовательский ключ на `context.userID`.

## Установление идентичности в Middleware Transport

Транспорт запускает Middleware для каждого HTTP-запроса Сотрудничества. Приложение может прочитать файл cookie, сеанс или маркер Bearer и прикрепить аутентифицированный результат к контексту:

```ts
transport.use(async (context, next) => {
  const user = await auth.requireUser(context.incomingMessage);

  context.userID = user.id;
  context.customData.user = user;
  context.customData.tenantID = user.tenantID;
  context.customData.traceID = readTraceID(context.incomingMessage);

  await next();
});
```

Если аутентификация не удалась, отключите HTTP-ответ без вызова `next()`:

```ts
transport.use(async (context, next) => {
  const user = await auth.findUser(context.incomingMessage);
  if (!user) {
    context.response.statusCode = 401;
    context.response.end("Authentication required");
    return;
  }

  context.userID = user.id;
  await next();
});
```

SDK не предписывает имена Cookie, форматы токенов, таблицы пользователей и процессы входа.

## Передача идентичности в Session WebSocket

Путь WebSocket не доверяет полям пользователей в полезных нагрузках клиентов. Конечная точка переносит аутентифицированный HTTP-контекст в сеанс в режиме реального времени с помощью одноразового билета на сеанс:

```text
HTTP-запрос Session Ticket
  → аутентификация в Middleware Transport
  → Endpoint сохраняет { userID, customData }
  → возвращает непрозрачный одноразовый билет
  → открытие WebSocket погашает билет
  → создаётся Session { userID, memberID, customData }
```

Последовательность билетов не содержит ни `userID`, ни `customData`. `memberID` идентифицирует только текущее соединение, и это не является независимым удостоверением личности. В многоузловом развертывании с общим магазином билетов сохраненный `customData` сериализован, поэтому он должен оставаться JSON-сериализируемым.

## Авторизация на правильной границе

| Защищаемое действие | Middleware |
| --- | --- |
| HTTP-вход совместной работы | Transport `use()` |
| Соединение WebSocket | Endpoint `connect` |
| Вход в Room Unit | Endpoint `joinUnit` |
| Чтение снимков, блоков и наборов изменений | Service `readUnitData` |
| Отправка правок содержимого | Service `submitChangeset` |
| Создание Unit | Service `createUnit` |
| Удаление Units | Service `deleteUnits` |
| Восстановление Units | Service `recoverUnits` |

Конечная точка `joinUnit` контролирует только то, может ли Сеанс войти в комнату в реальном времени. Снимки и отсутствующие изменения могут быть прочитаны непосредственно по HTTP, поэтому проверка JOIN не может заменить `readUnitData`. Аналогично, пользовательский интерфейс клиента только для чтения является подсказкой продукта и не заменяет политику `submitChangeset` на сервере.

## Защита чтения, JOIN и редактирования

```ts
import { CollabError } from "@univerjs-pro/collaboration-service";

endpoint.use("joinUnit", async (context, next) => {
  const allowed = await acl.canRead(context.session.userID, context.unitID);
  if (!allowed) {
    throw new CollabError("PERMISSION_DENIED", "Cannot join this Unit");
  }
  await next();
});

service.use("readUnitData", async (context, next) => {
  const allowed = await acl.canRead(context.userID, context.request.unitID);
  if (!allowed) {
    throw new CollabError("PERMISSION_DENIED", "Unit is not accessible");
  }
  await next();
});

service.use("submitChangeset", async (context, next) => {
  const unitID = context.request.changeset.unitID;
  const allowed = await acl.canEdit(context.userID, unitID);
  if (!allowed) {
    throw new CollabError("PERMISSION_DENIED", "Unit is read-only");
  }
  await next();
});
```

Эта политика требует права на редактирование для каждого набора изменений. Если читателям разрешено комментировать, используйте `isCommentOnlyChangeset()`, как в [примере на сервере](https://github.com/dream-num/univer-collaboration-examples/blob/main/examples/permissions/server/main.ts), чтобы отдельно проверить права на отправку привязок комментариев.

### Проверки мутаций листа

Политика `submitChangeset` авторизует каждый набор изменений один раз. При включённом перехвате применения мутаций сервер также проверяет отдельные мутации листа, включая закрепление, линии сетки, видимость строк и столбцов, вставку и копирование листа, а также изменения защиты, и отклоняет весь набор изменений, если одна из них выходит за пределы точек разрешения вызывающей стороны. Включите перехват с помощью параметра `enableMutationApplyInterceptor` плагина `UniverCollaborationServerPlugin` или через переменную среды `ENABLE_MUTATION_APPLY_INTERCEPTOR=true`.

## Защита жизненного цикла Unit

Протокол совместной работы открывает Единицы, которые уже существуют. «Создание документа» обычно представляет собой API приложения, который записывает запись продукта и ACL, прежде чем он вызовет `createUnitFromData()` или `createUnitFromSnapshot()`. Жизненный цикл также требует защиты Service Middleware:

```ts
service.use("createUnit", async (context, next) => {
  if (!(await acl.canCreate(context.userID, context.request.snapshot.type))) {
    throw new CollabError("PERMISSION_DENIED", "Unit creation denied");
  }
  await next();
});

service.use("deleteUnits", async (context, next) => {
  for (const unitID of context.request.unitIDs) {
    if (!(await acl.canDelete(context.userID, unitID))) {
      throw new CollabError("PERMISSION_DENIED", `Cannot delete ${unitID}`);
    }
  }
  await next();
});
```

Защищать `recoverUnits` отдельно. Пользователь, который когда-то имел разрешение на удаление, не обязательно сохраняет разрешение на восстановление.

## Повторное использование результатов через customData

Промежуточное ПО в рамках одного и того же вызова службы может использовать `customData`, чтобы избежать дублирования запросов:

```ts
service.use("submitChangeset", async (context, next) => {
  const unitID = context.request.changeset.unitID;
  context.customData.role ??= await acl.getRole(context.userID, unitID);

  if (context.customData.role === "viewer") {
    throw new CollabError("PERMISSION_DENIED", "Unit is read-only");
  }
  await next();
});
```

`customData` относится только к текущему вызову или сеансу и не сохраняется автоматически. Роли, ACL и отношения арендатора остаются в хранилище приложений.

## Отдельные политики для расширений

История, Thread Comment, Worktree, File и Exchange имеют свои собственные сервисные программы:

- Список истории и списки изменений должны проверять, что абонент может прочитать блок.
- Список комментариев должен проверять доступ к чтению, а также добавлять, отвечать, редактировать и удалять политику комментариев.
- Worktree требует отдельной проверки видимости, редактирования проектов, изменения статуса и слияния.
- Слияние Worktree в багажник по-прежнему проходит через багажник Service Middleware.
- Файл `upload` должен проверять доступ к целевому блоку редактирования, в то время как `signUrl` и `download` проверяют доступ к чтению.
- Биржа `import` и `export` являются подходящим местом для проверки квот и для проверки доступа к исходному блоку; создание импортного блока и чтение экспортируемого блока по-прежнему проходят через программное обеспечение Core Service Middleware.

Правила, установленные на базовой службе совместной работы, не защищают автоматически эти модули.Одна и та же служба политики приложений должна использоваться повторно, а не отдельной моделью данных ACL, построенной для каждого расширения.

## Настройка текущего пользователя в клиенте

`UserManagerService.setCurrentUser()` устанавливает идентификатор пользователя, имя и аватар для текущего экземпляра Univer, и фронтенд-компоненты считывают эти значения оттуда.Фильтр панели комментариев «Заботьтесь обо мне», например, использует этот идентификатор пользователя для отображения комментариев, в которых участвует текущий пользователь.

Назовите его после создания экземпляра Univer и до загрузки документа:

```ts
import { UserManagerService } from "@univerjs/core";

// currentUser is your application profile; id/name/avatar are example field names.
univer
  .__getInjector()
  .get(UserManagerService)
  .setCurrentUser({
    userID: currentUser.id,
    name: currentUser.name,
    avatar: currentUser.avatar ?? "",
  });
```

Сопоставьте стабильный идентификатор пользователя приложения с `userID` и сохраните его идентичным аутентифицированному `context.userID` на сервере.Имена участников и аватары, используемые во время совместной работы, установлены в промежуточном программном обеспечении `connect` сервера, как описано в [Присутствие](/server/collaboration/presence).
