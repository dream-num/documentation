title: Adaptadores de base de datos

Un Database Adapter persiste los datos colaborativos principales que utiliza Collaboration Service. Puedes implementar `IDatabaseAdapter` para conectar cualquier base de datos que satisfaga su contrato de comportamiento completo. Service gestiona la semántica de Unit, OT y revisiones; Adapter la convierte en operaciones de persistencia atómicas y seguras ante reintentos.

Los Database Adapters son de código abierto bajo Apache-2.0; el código está en [univer-collaboration-sdk-community](https://github.com/dream-num/univer-collaboration-sdk-community), con los mismos nombres de paquete y versiones que el resto de paquetes.

## Verificar la persistencia [#verify-persistence]

Detén Quick Start y ejecuta `pnpm example:database-adapter` desde la raíz. Abre `http://127.0.0.1:3010/?unit=persistent-sheet`, modifica una celda y compruébala en otro navegador. Detén el servidor, repite el comando y abre la misma URL: el valor debe permanecer. El archivo es `examples/database-adapter/.data/collaboration.sqlite`; no lo borres entre ejecuciones. El servidor lee el Unit existente y llama a `createUnitFromData()` solo ante `UNIT_NOT_FOUND`. Consulta [server/main.ts](https://github.com/dream-num/univer-collaboration-examples/blob/main/examples/database-adapter/server/main.ts).

## Qué almacena un Adapter

El Adapter almacena tres tipos de datos por cada documento colaborativo (Unit).

- **El registro de la Unit** contiene el ID del documento, su tipo, el autor, la fecha de creación y la revisión actual (`headRevision`). Al guardar un changeset, el Adapter actualiza la revisión en la misma operación. La aplicación puede gestionar campos propios en `UnitRecord.metadata`, como el nombre del documento (`name`), el ID de quien lo editó por última vez (`lastEditorID`) o la fecha de esa edición (`lastModifiedAt`).
- **Las instantáneas** guardan el contenido del documento en una revisión concreta. Para leer una revisión, el Service puede cargar la instantánea más reciente cuya revisión sea menor o igual que la solicitada y aplicar los cambios posteriores hasta llegar a ella. En las hojas de cálculo, el Adapter también almacena los bloques de datos a los que hace referencia la instantánea.
- **Los changesets** agrupan las operaciones de cada envío. El Adapter los guarda por orden de revisión y conserva los identificadores `sid` y `reqId`. Así, el Service reconoce los reintentos del cliente y evita aplicar dos veces el mismo cambio.[^submission-idempotency] La aplicación puede guardar en `ChangesetRecord.metadata` datos como el origen de la edición (`source`) o el ID de una operación de negocio asociada (`operationId`).

Para definir estos campos al crear un documento o enviar un changeset, consulta [Metadatos persistentes](/server/collaboration/middleware-and-events#persistent-metadata).

La eliminación lógica conserva los datos y permite volver a editar el documento tras su recuperación. Una vez eliminado de forma permanente, ya no se puede acceder a sus datos ni reutilizar su ID.

La aplicación gestiona los usuarios, roles y permisos de acceso. History, Thread Comment y Worktree tienen interfaces de Adapter independientes.

## Requisitos de lectura y escritura del Adapter

Al implementar `IDatabaseAdapter`, respeta los siguientes requisitos para cada operación.

| Operación | Requisito |
| --- | --- |
| Crear una Unit | Guarda de forma atómica el registro de la Unit con sus metadatos, la instantánea inicial y los bloques Sheet que esta referencia. Todos deben estar disponibles para su lectura al mismo tiempo. |
| Guardar un changeset | Guarda los datos solo si la revisión actual coincide con la esperada (CAS)[^revision-cas]. En una sola escritura atómica, guarda el changeset con sus metadatos, sustituye por completo los metadatos de la Unit e incrementa la revisión en uno. Si no coincide, devuelve la revisión actual sin escribir datos. |
| Leer changesets | Devuelve los changesets del intervalo solicitado en orden ascendente de revisión, sin saltos. Conserva los valores originales de `sid` y `reqId` para que el Service reconozca envíos duplicados de una misma Unit. |
| Guardar una instantánea | Cuando la instantánea se pueda leer, también deben poder leerse todos los bloques Sheet que referencia. |
| Eliminar o recuperar Units | Aplica la operación al lote completo. Si falla un elemento, todo el lote debe conservar su estado anterior. |

## Memory Adapter

[`@univerjs-pro/collaboration-database-memory`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-memory) es una implementación dentro del proceso apropiada para:

- pruebas unitarias y de integración;
- entornos temporales de desarrollo;
- validación rápida de Middleware personalizados o del montaje del cliente.

```ts
import { MemoryDatabaseAdapter } from "@univerjs-pro/collaboration-database-memory";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";

const database = new MemoryDatabaseAdapter();
const service = new UniverCollabService({ dbAdapter: database });
```

Memory Adapter sigue el mismo contrato de revisión, CAS e idempotencia que las implementaciones persistentes, pero los datos viven en el proceso Node.js actual y se pierden cuando termina.

## SQLite Adapter

[`@univerjs-pro/collaboration-database-sqlite`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-sqlite) es una implementación persistente SQLite para desarrollo, pruebas, aplicaciones locales y uso a pequeña escala.

```ts
import { mkdir } from "node:fs/promises";

import { SQLiteDatabaseAdapter } from "@univerjs-pro/collaboration-database-sqlite";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";

await mkdir("./data", { recursive: true });

const database = new SQLiteDatabaseAdapter({
  filename: "./data/collaboration.sqlite",
  busyTimeoutMs: 5_000,
});
const service = new UniverCollabService({ dbAdapter: database });
```

Inicializa el esquema en una base vacía y solo verifica una existente. La ubicación del archivo, las copias de seguridad y otros ajustes SQLite los decide la aplicación.

## PostgreSQL Adapter

[`@univerjs-pro/collaboration-database-postgres`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-postgres) es una implementación persistente basada en node-postgres que varios nodos de colaboración pueden compartir.

```ts
import { PostgresDatabaseAdapter } from "@univerjs-pro/collaboration-database-postgres";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";
import { Pool } from "pg";

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
const database = await PostgresDatabaseAdapter.create({ pool });
const service = new UniverCollabService({ dbAdapter: database });
```

La aplicación es dueña del pool y lo cierra después de liberar el Service. `create()` inicializa el esquema `collaboration` en una base vacía y solo verifica uno existente.

## Database Adapters personalizados

Un Adapter personalizado suele ser adecuado cuando:

- la aplicación ya utiliza MySQL u otra base de negocio;
- los envíos colaborativos deben integrarse con mecanismos de base específicos de la aplicación;
- las necesidades operativas o de cumplimiento exceden el alcance de los Adapters integrados.

Implementa `IDatabaseAdapter` e inyéctalo en Service igual que un Adapter integrado:

```ts
const database = new ApplicationCollaborationDatabase({ pool });
const service = new UniverCollabService({ dbAdapter: database });
```

Service no depende de una base concreta, pero tampoco puede añadir transacciones, CAS o deduplicación a una implementación personalizada. Adapter debe implementar el contrato completo con las capacidades de su base de datos. Las implementaciones integradas del [repositorio de la comunidad](https://github.com/dream-num/univer-collaboration-sdk-community) muestran el mismo contrato en distintas bases de datos y sirven de referencia.

## Cómo almacenar datos de negocio

**Usa `metadata` para los datos asociados a un documento o a un changeset.** La aplicación puede definir los campos al crear el documento o al enviar el changeset. El Adapter integrado los guarda junto con los datos de colaboración. Consulta [Metadatos persistentes](/server/collaboration/middleware-and-events#persistent-metadata).

**Usa Middleware o Events para escribir en tablas de negocio independientes.** Para registrar un intento de operación, escribe en una tabla de auditoría desde un Middleware. Para actualizar una tabla solo después de que se guarden los cambios, escucha `changesetCommitted`. Por defecto, estas escrituras se realizan fuera de la transacción de colaboración. Un conflicto de revisión puede provocar que el Middleware de commit vuelva a ejecutarse. Evita que un reintento genere registros duplicados. Los Events se entregan dentro del proceso sin garantía de entrega, por lo que son adecuados para datos que la aplicación pueda completar o reconstruir más adelante.

**Usa un Adapter personalizado si necesitas una base de datos y un esquema propios o si los datos de negocio y de colaboración deben guardarse en la misma transacción.** Al llamar al Service, la aplicación puede incluir en `customData` el ID de una operación de negocio. El método del Adapter puede leer los campos que necesita de `ctx.customData` y decidir qué tablas actualizar. Por ejemplo, `commitChangeset()` puede usar ese ID para actualizar el registro de negocio en la misma transacción que guarda el changeset.

El alcance de `customData` se limita a la llamada actual. Los Adapters integrados no guardan sus campos automáticamente ni los utilizan para escribir en tablas de negocio.

## Almacenamiento de extensiones

History, Thread Comment, Worktree y File definen interfaces Database Adapter independientes. Sus Adapters pueden compartir una base o usar almacenamiento separado. Una implementación personalizada también puede proporcionar varias interfaces Adapter e inyectarse en los Services correspondientes.

Como son interfaces independientes, el SDK no proporciona transacciones entre módulos por defecto. Aunque compartan base de datos, la aplicación define la estrategia de consistencia entre módulos.

## Elegir un Adapter

| Adapter | Uso más adecuado | Restricción principal |
| --- | --- | --- |
| Memory | Pruebas, ejemplos, desarrollo temporal | Los datos desaparecen al terminar el proceso |
| SQLite | Desarrollo, pruebas, aplicaciones locales, pequeña escala | Base de un archivo con ajustes a cargo de la aplicación |
| PostgreSQL | Despliegues en varios nodos y bases PostgreSQL existentes | La aplicación gestiona el pool y la operación de la base |
| Personalizado | Bases existentes o integración de datos de negocio | La aplicación debe implementar y verificar el contrato completo |

La aplicación es propietaria de cada Adapter inyectado. Libera Service antes de Adapter:

```ts
await service.dispose();
await database.dispose();
```

Consulta el [ejemplo de Database Adapter](/server/collaboration/examples#database-adapter), ejecutable y con implementaciones para comparar.

[^submission-idempotency]: La idempotencia permite reintentar un envío sin aplicar sus cambios dos veces. Conserve el identificador original; el mismo contenido con otro identificador constituye un nuevo envío.

[^revision-cas]: CAS actualiza un valor solo si aún coincide con el esperado. La comprobación de la revisión y la escritura siguiente deben ser atómicas para impedir que dos envíos concurrentes confirmen la misma revisión.
