title: Adaptadores de base de datos
description: Comprende el contrato de persistencia colaborativa y elige entre Memory, SQLite, PostgreSQL y Database Adapters personalizados.
---

Un adaptador de base de datos persiste los datos básicos de colaboración que gestiona el Servicio de Colaboración. El Servicio posee la Unidad, OT y la semántica de revisión, y el Adaptador convierte esas semánticas en operaciones de almacenamiento atómico que son seguras de reingresar. Conectar una base de datos que no está cubierta por los adaptadores incorporados, implementar `IDatabaseAdapter` y satisfacer su contrato de comportamiento completo.

Los adaptadores de bases de datos son de código abierto bajo Apache-2.0. El código fuente está disponible en [univer-collaboration-sdk-community](https://github.com/dream-num/univer-collaboration-sdk-community), y los paquetes utilizan los mismos nombres y versiones que cualquier otro paquete.

## Verificar la persistencia [#verify-persistence]

Parar Inicio Rápido y ejecutar `pnpm example:database-adapter` desde la raíz del repositorio. Abrir `http://127.0.0.1:3010/?unit=persistent-sheet`, cambiar una celda, y confirmar el cambio en un segundo navegador. Después de detener el servidor, ejecutar el mismo comando de nuevo, y volver a abrir la misma URL. El valor todavía debe estar presente.

El [servidor del ejemplo](https://github.com/dream-num/univer-collaboration-examples/blob/main/examples/database-adapter/server/main.ts) guarda los datos en `examples/database-adapter/.data/collaboration.sqlite`.

## Qué almacena un Adapter

El Adapter almacena tres tipos de datos por cada documento colaborativo (Unit).

- **El registro de la Unit** contiene el ID del documento, su tipo, el autor, la fecha de creación y la revisión actual (`headRevision`). Al guardar un changeset, el Adapter actualiza la revisión en la misma operación. La aplicación puede gestionar campos propios en `UnitRecord.metadata`, como el nombre del documento (`name`), el ID de quien lo editó por última vez (`lastEditorID`) o la fecha de esa edición (`lastModifiedAt`).
- **Las instantáneas** guardan el contenido del documento en una revisión concreta. Para leer una revisión, el Service puede cargar la instantánea más reciente cuya revisión sea menor o igual que la solicitada y aplicar los cambios posteriores hasta llegar a ella. En las hojas de cálculo, el Adapter también almacena los bloques de datos a los que hace referencia la instantánea.
- **Los changesets** agrupan las operaciones de cada envío. El Adapter los guarda por orden de revisión y conserva los identificadores `sid` y `reqId`. Así, el Service reconoce los reintentos del cliente y evita aplicar dos veces el mismo cambio.[^submission-idempotency] La aplicación puede guardar en `ChangesetRecord.metadata` datos como el origen de la edición (`source`) o el ID de una operación de negocio asociada (`operationId`).

Para definir estos campos al crear un documento o enviar un changeset, consulta [Metadatos persistentes](/server/collaboration/middleware-and-events#persistent-metadata).

La eliminación lógica conserva los datos y permite volver a editar el documento tras su recuperación. Una vez eliminado de forma permanente, ya no se puede acceder a sus datos ni reutilizar su ID.

La aplicación gestiona los usuarios, roles y permisos de acceso. History, Thread Comment y Worktree tienen interfaces de Adapter independientes.

## Requisitos de lectura y escritura del Adapter

Al implementar `IDatabaseAdapter`, respeta los siguientes requisitos para cada operación.

| Operación | Requisito |
| --- | --- |
| Crear una Unit | Guarda de forma atómica el registro de la Unit con sus metadatos, la instantánea inicial y los bloques Sheet que esta referencia. Todos deben estar disponibles para su lectura al mismo tiempo. |
| Guardar un changeset | Guarda los datos solo si la revisión actual coincide con la esperada (CAS)[^revision-cas]. En una sola escritura atómica, guarda el changeset con sus metadatos, sustituye por completo los metadatos de la Unit e incrementa la revisión en uno. Si no coincide, devuelve la revisión actual sin escribir datos. |
| Leer changesets | Devuelve los changesets del intervalo solicitado en orden ascendente de revisión, sin saltos. Conserva los valores originales de `sid` y `reqId` para que el Service reconozca envíos duplicados de una misma Unit. |
| Guardar una instantánea | Cuando la instantánea se pueda leer, también deben poder leerse todos los bloques Sheet que referencia. |
| Eliminar o recuperar Units | Aplica la operación al lote completo. Si falla un elemento, todo el lote debe conservar su estado anterior. |

## Memory Adapter

[`@univerjs-pro/collaboration-database-memory`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-memory) se ejecuta dentro del proceso Node.js. Es adecuado para:

- pruebas unitarias y de integración
- entornos temporales de desarrollo
- cheques rápidos de montaje personalizado de Middleware o cliente

```ts
import { MemoryDatabaseAdapter } from "@univerjs-pro/collaboration-database-memory";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";

const database = new MemoryDatabaseAdapter();
const service = new UniverCollabService({ dbAdapter: database });
```

El adaptador de memoria sigue el mismo contrato de revisión, CAS, e idempotencia como las implementaciones persistentes. Sus datos sólo existen en el actual proceso Node.js y se pierde cuando ese proceso sale.

## SQLite Adapter

[`@univerjs-pro/collaboration-database-sqlite`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-sqlite) almacena datos en un archivo SQLite. Es adecuado para el desarrollo, pruebas, aplicaciones locales y uso a pequeña escala.

```ts
import { mkdir } from "node:fs/promises";

import { SQLiteDatabaseAdapter } from "@univerjs-pro/collaboration-database-sqlite";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";

await mkdir("./data", { recursive: true });

const database = new SQLiteDatabaseAdapter({
  filename: "./data/collaboration.sqlite",
  busyTimeoutMs: 5_000,
});
const service = new UniverCollabService({ dbAdapter: database });
```

Inicia el esquema cuando la base de datos está vacía y sólo verifica el esquema cuando ya existe. La ubicación del archivo, el método de copia de seguridad, y cualquier otra configuración de SQLite se deciden por la aplicación.

## PostgreSQL Adapter

[`@univerjs-pro/collaboration-database-postgres`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-postgres) guarda todos los datos de colaboración de Core en PostgreSQL, incluidos los bloques de celdas a los que hacen referencia las instantáneas de las hojas. Varios nodos de colaboración pueden compartir una base de datos.

```ts
import { PostgresDatabaseAdapter } from "@univerjs-pro/collaboration-database-postgres";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";
import { Pool } from "pg";

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
const database = await PostgresDatabaseAdapter.create({ pool });
const service = new UniverCollabService({ dbAdapter: database });
```

La aplicación es dueña de la piscina y la cierra después de deshacerse del Servicio. `create()` inicializa el esquema `collaboration` en una base de datos vacía y sólo verifica un esquema existente.

Si dispones de almacenamiento de objetos compatible con S3, recomendamos el [adaptador PostgreSQL + S3](#postgresql-s3-adapter) para reducir el tamaño de la base de datos y de sus copias de seguridad.

## PostgreSQL + S3 Adapter [#postgresql-s3-adapter]

[`@univerjs-pro/collaboration-database-postgres-s3`](https://github.com/dream-num/univer-collaboration-sdk-community/tree/main/packages/collaboration-database-postgres-s3) guarda los bloques de celdas en un bucket compatible con S3. Las Units, los changesets, los registros de instantáneas y las referencias a los bloques permanecen en PostgreSQL.

Los datos de las celdas ocupan la mayor parte de la instantánea de un libro grande. Guardar estos bloques en S3 reduce el tamaño de la base PostgreSQL y de sus copias de seguridad. A medida que crecen los libros, la capacidad de almacenamiento de los bloques puede ampliarse de forma independiente.

Configura `DATABASE_URL` con la cadena de conexión a la base de datos, `S3_REGION` con la región del bucket y `S3_BUCKET` con el nombre de un bucket existente.

```ts
import { S3Client } from "@aws-sdk/client-s3";
import { PostgresS3DatabaseAdapter } from "@univerjs-pro/collaboration-database-postgres-s3";
import { UniverCollabService } from "@univerjs-pro/collaboration-service";
import { Pool } from "pg";

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
const client = new S3Client({ region: process.env.S3_REGION });
const database = await PostgresS3DatabaseAdapter.create({
  pool,
  s3: { client, bucket: process.env.S3_BUCKET! },
});
const service = new UniverCollabService({ dbAdapter: database });
```

## Database Adapters personalizados

Un adaptador personalizado suele ser adecuado en los siguientes casos:

- la aplicación ya utiliza MySQL u otra base de negocio
- las presentaciones de colaboración deben utilizar mecanismos de base de datos que la aplicación posee
- las necesidades operativas o de cumplimiento exceden el alcance de los Adapters integrados

Implementa `IDatabaseAdapter` e inyéctalo en Service igual que un Adapter integrado:

```ts
const database = new ApplicationCollaborationDatabase({ pool });
const service = new UniverCollabService({ dbAdapter: database });
```

El Servicio no depende de una base de datos específica, pero no puede agregar transacciones, CAS o deduplicación a una implementación personalizada. El Adaptador debe implementar el contrato completo utilizando las capacidades que su base de datos proporciona. Las implementaciones incorporadas en el [repositorio comunitario](https://github.com/dream-num/univer-collaboration-sdk-community) aplican el mismo contrato a diferentes bases de datos y sirven como referencias.

## Cómo almacenar datos de negocio

**Utilice `metadata` para obtener información adjunta a un documento o un cambio.** La aplicación puede establecer estos campos cuando crea un documento o presenta un cambio, y los Adaptadores incorporados los guardan junto con los datos de colaboración. Véase [Medios y Eventos](/server/collaboration/middleware-and-events#persistent-metadata).

**Utilice Middleware o Eventos para escribir para tablas de negocios separadas.** Para auditar un intento de operación, escriba a una tabla de auditoría en Middleware. Para actualizar una tabla de negocios después de un compromiso exitoso, escuche para `changesetCommitted`. Por defecto, estos escritos se ejecutan fuera de la transacción de colaboración. Un conflicto de revisión puede hacer que el middleware de inicio se ejecute de nuevo, por lo que una reingresa no debe crear un registro duplicado.

**Utilice un adaptador de base de datos personalizado cuando la aplicación necesita su propia base de datos y esquemas, o cuando los datos de negocios y colaboración deben ser escritos en una sola transacción.** Al llamar al Servicio, la aplicación puede pasar contexto como un ID de operación de negocios en `customData`. El Adaptador puede leer los campos que necesita de `ctx.customData` y decidir qué tablas actualizar. Por ejemplo, `commitChangeset()` puede utilizar el ID de operación para actualizar el registro de negocio correspondiente en la misma transacción que guarda los cambios.

`customData` es acertado a la llamada actual. Adaptadores incorporados no persisten sus campos automáticamente, y no los utilizan para escribir a tablas de negocios.

## Almacenamiento de extensiones

Módulos de extensión como Historia, Comentario de los hilos, Worktree y File definen cada una una una interfaz independiente de Adaptador de bases de datos. Sus adaptadores pueden compartir una base de datos o utilizar almacenamiento separado. Una única implementación personalizada también puede proporcionar varias interfaces de Adaptador y ser inyectado en los servicios correspondientes.

Debido a que estas interfaces de Adaptador son independientes, el SDK no proporciona transacciones multimodulo por defecto. Incluso cuando varios módulos comparten una base de datos, la aplicación es dueña de la estrategia de consistencia multimodulo.

## Elegir un Adapter

| Adapter         | Uso más adecuado                                                                           | Restricción principal                                                                                                                          |
| --------------- | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Memory          | Pruebas, ejemplos, desarrollo temporal                                                     | Los datos se pierden cuando el proceso sale                                                                                                    |
| SQLite          | Desarrollo, pruebas, aplicaciones locales, pequeña escala                                  | Base de un archivo con ajustes a cargo de la aplicación                                                                                        |
| PostgreSQL + S3 | Aplicaciones con PostgreSQL y almacenamiento de objetos, especialmente para libros grandes | La aplicación gestiona la base de datos y el bucket. Sin almacenamiento compatible con S3, usa el [adaptador PostgreSQL](#postgresql-adapter). |
| Personalizado   | Bases existentes o integración de datos de negocio                                         | La aplicación debe implementar y verificar el contrato completo                                                                                |

La aplicación es propietaria de cada Adapter inyectado. Libera Service antes de Adapter:

```ts
await service.dispose();
await database.dispose();
```

Consulta el [ejemplo de Database Adapter](/server/collaboration/examples#database-adapter), ejecutable y con implementaciones para comparar.

[^submission-idempotency]: La idempotencia permite reintentar un envío sin aplicar sus cambios dos veces. Conserve el identificador original; el mismo contenido con otro identificador constituye un nuevo envío.

[^revision-cas]: CAS actualiza un valor solo si aún coincide con el esperado. La comprobación de la revisión y la escritura siguiente deben ser atómicas para impedir que dos envíos concurrentes confirmen la misma revisión.
