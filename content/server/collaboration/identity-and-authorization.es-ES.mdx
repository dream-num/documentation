El Univer Collaboration SDK no define usuarios, roles o un modelo ACL. Una aplicación establece la identidad de confianza en el Transport Middleware y luego protege las sesiones en tiempo real y los datos de colaboración autorizados con Endpoint y Service Middleware.

Esta página aplica [Medios y Eventos](/server/collaboration/middleware-and-events) a una tarea concreta: integración de la identidad y la autorización a través de Middleware.

## Verificar los permisos [#verify-permissions]

Ejecuta `pnpm example:permissions`, abre `http://127.0.0.1:3010` y prueba las tres cuentas por turnos.

1. Con la cuenta de Bob, modifica una celda.
2. Cambia a Casey. Comprueba que el cambio es visible y que la celda es de solo lectura.
3. Cambia a Dana. Comprueba que no puedes abrir el documento.

## Modelo de identidad

| Identificador | Proveedor | Significado y vida |
| --- | --- | --- |
| `userID` | Aplicación | Identidad de negocio estable y autor de los conjuntos de cambios confirmados |
| `memberID` | Endpoint | ID del miembro conectado para una Session WebSocket; cambia al reconectar |
| `sid + reqId` | Cliente | Identidad de envío del conjunto de cambios que se mantiene durante los reintentos |

Campos de perfil de usuario enviados por el navegador, `memberID`, y las revisiones no pueden sustituir la autenticación de aplicaciones. Una aplicación mapea su clave de usuario estable para `context.userID`.

## Establecer identidad en el Middleware de Transport

El Transporte funciona con Middleware para cada solicitud de colaboración HTTP. Una aplicación puede leer una cookie, una sesión, o una ficha de Bearer y adjuntar el resultado autenticado a Contexto:

```ts
transport.use(async (context, next) => {
  const user = await auth.requireUser(context.incomingMessage);

  context.userID = user.id;
  context.customData.user = user;
  context.customData.tenantID = user.tenantID;
  context.customData.traceID = readTraceID(context.incomingMessage);

  await next();
});
```

Cuando la autenticación falla, termine la respuesta HTTP sin llamar a `next()`:

```ts
transport.use(async (context, next) => {
  const user = await auth.findUser(context.incomingMessage);
  if (!user) {
    context.response.statusCode = 401;
    context.response.end("Authentication required");
    return;
  }

  context.userID = user.id;
  await next();
});
```

El SDK no impone nombres de Cookie, formatos de token, tablas de usuarios ni flujos de inicio de sesión.

## Cómo llega la identidad a una Session WebSocket

La ruta WebSocket no confía en los campos de usuario en las cargas de pago de los clientes. El Endpoint lleva un HTTP autenticado Contexto en una sesión en tiempo real por medio de un boleto de sesión de una sola vez:

```text
Solicitud HTTP de Session Ticket
  → autenticación en Middleware de Transport
  → Endpoint almacena { userID, customData }
  → devuelve un ticket opaco de un solo uso
  → la apertura de WebSocket consume el ticket
  → crea Session { userID, memberID, customData }
```

La cadena de tickets no contiene `userID` ni `customData`. `memberID` identifica solamente la conexión actual, y no es una credencial de identidad independiente. En un despliegue de varios nodos con una tienda de tickets compartida, el `customData` almacenado es serializado, por lo que debe permanecer JSON-serializable.

## Autorizar en el límite adecuado

| Comportamiento que se protege | Middleware |
| --- | --- |
| Entrada HTTP de colaboración | Transport `use()` |
| Conexión WebSocket | Endpoint `connect` |
| Entrada en una Room de Unit | Endpoint `joinUnit` |
| Lectura de instantáneas, bloques o conjuntos de cambios | Service `readUnitData` |
| Envío de ediciones de contenido | Service `submitChangeset` |
| Creación de una Unit | Service `createUnit` |
| Eliminación de Units | Service `deleteUnits` |
| Recuperación de Units | Service `recoverUnits` |

Endpoint `joinUnit` solo controla si una sesión puede entrar en una habitación en tiempo real. Las instantáneas y los cambios que faltan se pueden leer directamente sobre HTTP, por lo que un cheque Únete no puede reemplazar `readUnitData`. Asimismo, un cliente de sólo lectura UI es una pista de producto y no reemplaza la política `submitChangeset` en el servidor.

## Proteger lectura, JOIN y edición

```ts
import { CollabError } from "@univerjs-pro/collaboration-service";

endpoint.use("joinUnit", async (context, next) => {
  const allowed = await acl.canRead(context.session.userID, context.unitID);
  if (!allowed) {
    throw new CollabError("PERMISSION_DENIED", "Cannot join this Unit");
  }
  await next();
});

service.use("readUnitData", async (context, next) => {
  const allowed = await acl.canRead(context.userID, context.request.unitID);
  if (!allowed) {
    throw new CollabError("PERMISSION_DENIED", "Unit is not accessible");
  }
  await next();
});

service.use("submitChangeset", async (context, next) => {
  const unitID = context.request.changeset.unitID;
  const allowed = await acl.canEdit(context.userID, unitID);
  if (!allowed) {
    throw new CollabError("PERMISSION_DENIED", "Unit is read-only");
  }
  await next();
});
```

Esta política exige permiso de edición para cada changeset. Si los lectores pueden comentar, usa `isCommentOnlyChangeset()` como en el [ejemplo de servidor](https://github.com/dream-num/univer-collaboration-examples/blob/main/examples/permissions/server/main.ts) para autorizar por separado las anclas de los comentarios.

## Proteger el ciclo de vida de las Units

El protocolo de colaboración abre Unidades que ya existen. “Crear documento” es normalmente una API de aplicación que escribe un registro de producto y un ACL antes de llamar `createUnitFromData()` o `createUnitFromSnapshot()`. El ciclo de vida también requiere protección de Service Middleware:

```ts
service.use("createUnit", async (context, next) => {
  if (!(await acl.canCreate(context.userID, context.request.snapshot.type))) {
    throw new CollabError("PERMISSION_DENIED", "Unit creation denied");
  }
  await next();
});

service.use("deleteUnits", async (context, next) => {
  for (const unitID of context.request.unitIDs) {
    if (!(await acl.canDelete(context.userID, unitID))) {
      throw new CollabError("PERMISSION_DENIED", `Cannot delete ${unitID}`);
    }
  }
  await next();
});
```

Proteger `recoverUnits` por separado. Un usuario que una vez tuvo permiso de eliminación no necesariamente conserva el permiso de recuperación.

## Reutilizar consultas mediante customData

Middleware dentro de la misma llamada de servicio puede utilizar `customData` para evitar consultas duplicadas:

```ts
service.use("submitChangeset", async (context, next) => {
  const unitID = context.request.changeset.unitID;
  context.customData.role ??= await acl.getRole(context.userID, unitID);

  if (context.customData.role === "viewer") {
    throw new CollabError("PERMISSION_DENIED", "Unit is read-only");
  }
  await next();
});
```

`customData` pertenece sólo a la llamada actual o sesión y no se persiste automáticamente. Las funciones, ACLs y las relaciones de inquilino permanecen en el almacenamiento de aplicaciones.

## Las extensiones necesitan políticas independientes

Historia, Comentario de los hilos, Worktree, Archivo y Intercambio cada uno tiene su propio Servicio de Medios:

- La lista de historia y las lecturas de los cambios deben comprobar que la persona que llama puede leer la Unidad.
- La lista de comentarios debe comprobar el acceso leído, al tiempo que añadir, responder, editar y eliminar la política de comentario.
- Worktree requiere cheques separados para la visibilidad, borrado de ediciones, cambios de estado, y fusión.
- Un Worktree se fusiona en el maletero todavía pasa por el maletero Service Middleware.
- El archivo `upload` debe comprobar el acceso de edición a la unidad de destino, mientras que `signUrl` y `download` controlan el acceso de lectura.
- Exchange `import` y `export` son el lugar adecuado para las comprobaciones de cupos y para los cheques de acceso a la unidad fuente; la creación de la unidad importada y la lectura de la unidad exportada siguen pasando por el equipo básico de servicio.

Las reglas instaladas en el Servicio de Colaboración central no protegen automáticamente estos módulos. El mismo servicio de políticas de aplicación debe ser reutilizado en lugar de un modelo de datos ACL separado construido para cada extensión.

## Definir el usuario actual en el cliente

`UserManagerService.setCurrentUser()` establece el ID de usuario, nombre y avatar para la instancia Univer actual, y los componentes de frontend leen estos valores desde allí. El filtro “Concern me” del panel de comentarios, por ejemplo, utiliza este ID de usuario para mostrar los comentarios que involucran al usuario actual.

Llámalo después de la instancia Univer se crea y antes de que el documento se cargue:

```ts
import { UserManagerService } from "@univerjs/core";

// currentUser is your application profile; id/name/avatar are example field names.
univer
  .__getInjector()
  .get(UserManagerService)
  .setCurrentUser({
    userID: currentUser.id,
    name: currentUser.name,
    avatar: currentUser.avatar ?? "",
  });
```

Mapea el ID de usuario estable de la aplicación a `userID` y manténgalo idéntico al `context.userID` autenticado en el servidor. Los nombres de los miembros y avatares compartidos durante la colaboración se establecen en el `connect` Middleware del servidor, como se describe en [Presencia](/server/collaboration/presence).

El [Ejemplo de permisos](/server/collaboration/examples#permissions) es la versión completa ejecutable.
