Univer builds products and features from plugins and exposes content operations through Facade APIs. An application chooses the content engine, the features, and the UI it needs, or packages its own business logic as a plugin and provides typed methods for the application and Agent tools to call.

## Compose the content capabilities you need [#composition]

A Preset is a preassembled collection of plugins intended for a quick start. In Plugin mode, the host selects products, features, and configuration explicitly. Both modes use the same plugin mechanism.

| Layer | Responsibility | Typical components |
| --- | --- | --- |
| Products and content models | Manage Units, content structures, and fundamental operations. | Product plugins for Sheet, Doc, Slide, Relational Table, Canvases, and PDF. |
| Feature plugins | Add domain capabilities. | Formulas, filtering, charts, comments, and more. |
| UI and rendering plugins | Provide presentation and interaction entry points. | Canvas rendering, menus, toolbars, shortcuts, and components. |
| Facade extensions | Expose public APIs for installed capabilities. | Workbook, range, document, and object operations, plus semantic events. |

Separating product logic from UI allows suitable content capabilities to run in Node.js, in Workers, or in the browser. A Headless host registers only the content plugins it needs, while menus, DOM, and interaction APIs still require their UI environment.

## Dependencies, lifecycle, and resource ownership [#coordination]

A plugin declares its direct dependencies with `@DependentOn(...)`, and the runtime resolves them and determines the construction order. When a dependency plugin is missing, the runtime registers it with the default configuration. When a dependency requires custom configuration, register and configure it first. This mechanism does not install packages, and it does not import styles, locales, Facade entries, or Workers.

Inside a plugin, dependency injection (DI) connects services, controllers, and models through public service identifiers. Platform implementations can be replaced at supported configuration or injection boundaries, so business logic does not need to construct and manage every dependency itself.

| Lifecycle hook | Appropriate work |
| --- | --- |
| `onStarting()` | Register dependencies, commands, and controllers; do not read Units or DOM that do not exist yet. |
| `onReady()` | Initialize logic that depends on the model once the corresponding content is ready. |
| `onRendered()` | Initialize extensions that need the renderer, Canvas, or DOM. |
| `onSteady()` | Defer work that initial rendering does not require. |

The owner manages command registrations, event subscriptions, shortcuts, and render modules. When a registration returns a disposable, call `disposeWithMe()` so that it is released together with the plugin or controller. `mergeMenu()` currently returns `void` and is therefore not a disposable.

## Different entry points, one content-change mechanism [#commands]

A toolbar, a shortcut, and a business API can invoke the same business command. An Agent host can reuse that entry point after the required capabilities are installed. The command system separates business intent, persisted changes, and transient interaction.

| Type | Responsibility | Example |
| --- | --- | --- |
| `COMMAND` | Validate targets and orchestrate business steps, Mutations, or Operations. | Write a sales report or delete a row. |
| `MUTATION` | Change the content model through explicit, serializable parameters so that the change can be replayed and handled by collaboration. | Update cell content or insert a row. |
| `OPERATION` | Change transient interaction state. | Update a selection, scroll position, or panel. |

For example, `FRange.setValues()` invokes `SetRangeValuesCommand`, which produces a `SetRangeValuesMutation` and prepares the undo data. All content changes follow the same execution path, so different entry points reuse the existing validation, interceptors, and change handling. Undo, collaboration, and history in the diagram still depend on their respective mechanisms; registering a Mutation alone does not provide them.

## Expose plugin capabilities as Facade APIs [#facade]

Facade provides public interfaces oriented to content objects and hides the internal service lookups and command parameter assembly. An extension can compose existing Facade methods or invoke the plugin's own business command.

The following extension adds `generateSalesReport()` to `FUniver`; the business command it invokes is implemented in the next section. The file has three parts: the runtime method, the runtime registration, and the TypeScript types.

### sales-report.facade.ts

```typescript
import { FUniver } from '@univerjs/core/facade';
import type { ISalesReportParams } from './sales-report.plugin';
import { GenerateSalesReportCommand } from './sales-report.plugin';

export interface IFUniverSalesReport {
  generateSalesReport(params: ISalesReportParams): Promise<boolean>;
}

export class FUniverSalesReport extends FUniver implements IFUniverSalesReport {
  override generateSalesReport(params: ISalesReportParams): Promise<boolean> {
    return this._commandService.executeCommand(GenerateSalesReportCommand.id, params);
  }
}

FUniver.extend(FUniverSalesReport);

declare module '@univerjs/core/facade' {
  interface FUniver extends IFUniverSalesReport {}
}
```

`FUniver.extend()` installs the method at runtime, and module augmentation only supplies types. Consumers must execute the extension file through a side-effect import; exporting the class or registering a plugin does not execute a separate Facade entry. A published package can expose a dedicated `/facade` subpath and preserve that registration side effect through `package.json#sideEffects`.

This pattern applies only to Facade classes that explicitly support `extend()`. The fact that a Facade class is exported does not mean it can serve as a mixin target. Method names should state their business meaning clearly and should not collide with existing methods or other extensions.

## Example: one sales report for applications and Agents [#example]

This minimal business plugin writes English sales data, summary formulas, and header styles into `A1:D5` of the specified Sheet and replaces that range. The workbook ID and worksheet ID are passed explicitly by the caller rather than taken from the current selection or focus.

The command first checks the target and the range dimensions, then invokes the existing `SetRangeValuesCommand` so that its content-change and undo/redo logic is reused. The plugin registers the command in `onStarting()` and owns its disposable. The data is fixed and serves only as an illustration; an application should replace it with validated business input.

Example output. The presentation colors, number formatting, and row and column dimensions were adjusted for readability.

### sales-report.plugin.ts

```typescript
import type { ICellData, ICommand, Workbook } from '@univerjs/core';
import {
  CommandType, DependentOn, ICommandService, Inject, Injector,
  IUniverInstanceService, Plugin, UniverInstanceType,
} from '@univerjs/core';
import { SetRangeValuesCommand, UniverSheetsPlugin } from '@univerjs/sheets';

export interface ISalesReportParams {
  unitId: string;
  subUnitId: string;
}

export const GenerateSalesReportCommand: ICommand<ISalesReportParams> = {
  id: 'sales-report.command.generate',
  type: CommandType.COMMAND,
  handler: (accessor, params) => {
    if (!params) return false;
    const sheet = accessor.get(IUniverInstanceService)
      .getUnit<Workbook>(params.unitId, UniverInstanceType.UNIVER_SHEET)
      ?.getSheetBySheetId(params.subUnitId);
    if (!sheet || sheet.getRowCount() < 5 || sheet.getColumnCount() < 4) return false;

    const value: ICellData[][] = [
      ['Region', 'Q1', 'Q2', 'H1 Total'].map((v) => ({
        v, t: 1, s: { bg: { rgb: '#17324D' }, cl: { rgb: '#FFFFFF' }, bl: 1 },
      })),
      [{ v: 'East', t: 1 }, { v: 128000, t: 2 }, { v: 142000, t: 2 }, { f: '=SUM(B2:C2)' }],
      [{ v: 'West', t: 1 }, { v: 96000, t: 2 }, { v: 118000, t: 2 }, { f: '=SUM(B3:C3)' }],
      [{ v: 'North', t: 1 }, { v: 110000, t: 2 }, { v: 125000, t: 2 }, { f: '=SUM(B4:C4)' }],
      [{ v: 'Total', t: 1 }, { f: '=SUM(B2:B4)' }, { f: '=SUM(C2:C4)' }, { f: '=SUM(D2:D4)' }],
    ];

    return accessor.get(ICommandService).executeCommand(SetRangeValuesCommand.id, {
      ...params,
      range: { startRow: 0, endRow: 4, startColumn: 0, endColumn: 3 },
      value,
    });
  },
};

@DependentOn(UniverSheetsPlugin)
export class SalesReportPlugin extends Plugin {
  static override pluginName = 'SALES_REPORT_PLUGIN';
  static override type = UniverInstanceType.UNIVER_SHEET;

  constructor(
    _config: undefined,
    @Inject(Injector) protected override readonly _injector: Injector,
    @ICommandService private readonly _commands: ICommandService,
  ) { super(); }

  override onStarting(): void {
    this.disposeWithMe(this._commands.registerCommand(GenerateSalesReportCommand));
  }
}
```

Configure the products and formula capabilities with the [Sheet installation guide](/guides/sheets/getting-started/installation), then register the business plugin, import its Facade extension, and call it. In this example, `univer` is an instance with that configuration already complete. For the Node.js configuration, see [headless Univer](/guides/sheets/getting-started/node).

```typescript
import { FUniver } from '@univerjs/core/facade';
import '@univerjs/sheets/facade';
import '@univerjs/engine-formula/facade';
import { SalesReportPlugin } from './sales-report.plugin';
import './sales-report.facade';

univer.registerPlugin(SalesReportPlugin);
const univerAPI = FUniver.newAPI(univer);
const workbook = univerAPI.createWorkbook({ name: 'Quarterly Sales' });
const worksheet = workbook.getActiveSheet();
const target = { unitId: workbook.getId(), subUnitId: worksheet.getSheetId() };

const generated = await univerAPI.generateSalesReport(target);
if (!generated) throw new Error('Sales report could not be generated');
await univerAPI.getFormula().onCalculationResultApplied();
console.log(worksheet.getRange('D5').getValue()); // 719000
```

A successful command result indicates that the content write has completed. Wait for the calculation results to be applied before reading formula values. In this example, `D5` is **719000**.

An application button can call `generateSalesReport(target)` from its click handler. An Agent tool handler can call the same method after its Headless host installs the same plugin and Facade extension. The business action and the target remain the same; the UI supplies the entry point and feedback. Installing a custom plugin does not automatically expose the method as an Agent tool. Tool registration and Unit authorization remain the responsibility of the application.

## Implementation boundaries and further reading [#boundaries]

- This example reuses `SetRangeValuesCommand`. A new Mutation requires inverse operations and the corresponding collaboration integration. A new persisted resource also requires serialization, so do not write directly to the underlying model.
- Execution, calculation, and submission are separate steps, and multiple Facade calls do not form an automatic atomic transaction. This example performs a single range write; a collaborative host still submits and confirms changes under the Runtime contract.
- Compose plugins according to the environment in which they run. Install content plugins and UI plugins separately, keep Univer release-train packages on the same version, and use locale resources for UI copy. Agent entry points still require authorization and parameter validation owned by the application.
