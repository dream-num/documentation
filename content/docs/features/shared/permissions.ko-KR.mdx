Univer는 2개의 층으로 허가를 분리합니다: **전체 콘텐츠 단위의 작업**와 **객체에 대한 권한이 내부에**. Web SDK은 상호 작용과 명령 실행을 통제하기 위하여 이 권한을 이용합니다. Server SDK 는 읽기, 공동 제출 및 연장 서비스를 위한 허가 경계를 정의합니다.

## Unit 수준 권한 [#unit-permissions]

[제품정보](/guides/sheets/getting-started/quickstart#unit)는 워크북, 문서, 프레젠테이션, 관계 테이블, 보드, 또는 PDF와 같은 하나의 완전한 내용 인스턴스입니다. 아래 단위 권한은 시트, 문서, 슬라이드, 관계 테이블 및 캔버스에 적용됩니다. PDF는 자체 섹션에서 별도로 설명됩니다.

| 권한 | 제어 대상 | 사용 예 |
| --- | --- | --- |
| 편집(Edit) | 콘텐츠 및 구조 변경. | Viewers read; 편집기 작성 및 리어 스코어 콘텐츠. |
| 복사(Copy) | 편집자 내부의 내용을 복사합니다. | 복사 방지를 위해 읽기 및 의견 허용. |
| 댓글(Comment) | 코멘트를 시작하고 댓글이 설치될 때 답을 replies. | 리뷰 작성자 댓글 동안 내용이 읽기 전용 남아 있습니다. |
| 인쇄(Print) | 제품의 인쇄 기능 사용. | 인쇄를 막는 동안 온라인 독서를 허용하십시오. |
| 내보내기(Export) | 지원되는 파일 형식으로 콘텐츠 내보내기. | 다른 사람에게 파일을 전달하거나 아카이브합니다. |

편집 및 의견은 서로 독립적입니다. 편집, 삭제 및 관리 의견도 응용 프로그램의 저자 및 소유자 정책을 따르십시오.

인쇄 및 수출은 또한 단위 수준 허가입니다. 장, 문서, 활주 및 화포는 둘 다 노출합니다; 관계되는 테이블은 현재 수출을 만 노출합니다. 각 허가는 그것의 대응 특징 플러그인으로 작동합니다.

복사 내용, 파일을 duplicating, 수출, 다운로드는 4개의 분리된 가동입니다. 파일은 당신의 신청의 읽힌 허가에 달려 있을 수 있다는 것을.

예를 들어 Doc의 Unit 수준 권한을 각각 설정할 수 있습니다.

```ts
import { UnitAction } from '@univerjs/protocol'

const document = univerAPI.getActiveDocument()
if (!document) throw new Error('Open a document first')

const permission = document.getPermission()
await permission.setReadOnly()
await permission.setPoint(UnitAction.Copy, false)
await permission.setPoint(UnitAction.Comment, true)
await permission.setPoint(UnitAction.Print, false)
await permission.setPoint(UnitAction.Export, false)
```

제품 및 의견 플러그인을 먼저 등록하십시오. 플러그인 모드는 `@univerjs/docs/facade`가 필요합니다. 제품 액세서리는 아래에 나열되어 있습니다. 시트는 자체 권한 포인트를 사용합니다.

`UnitAction.Comment`를 사용하면 비방적인 변경 사항이 포함될 때 프로 협업 서버가 `UnitAction.Edit`을 확인합니다. 추가, 삭제, 해결, 업데이트, 또는 참고 업데이트. 혼합 변경 설정 및 문서 내용 변경, Docs 코멘트 장식 포함, 여전히 Collaboration SDK가 필요합니다. 응용 프로그램은 자체 의견 작성자 및 소유자 정책을 시행해야합니다. 사용자 정의 `submitChangeset` 서비스 Middleware, ClassXZXZXQXZXXZ를 사용하여 같은 허가를 검토하십시오.

## 제품별 세부 권한

### Sheets

제출 수준은 **workbook → 워크 시트 → 셀 범위**입니다. 작업 책 레벨은 전체 파일에 대한 편집, 복사 및 주석을 제어합니다. Worksheet 권한 포인트는 값, 스타일, 행 및 열 변경, 정렬, 필터링, 피벗 테이블 및 추가 개체를 제한합니다. 선택한 영역을 편집하거나 볼 수있는 범위 보호 제어, 허용되는 콜러레이터를 명명 할 수 있습니다.

예를 들어 예산 공식을 보호하고 비용을 수정할 수 있습니다. `getWorkbookPermission()`, `getWorksheetPermission()` 및 `getRangePermission()`를 사용하십시오. 보호 포인트를 설정하기 전에 워크 시트 또는 범위 보호 규칙을 작성하십시오. 액세스가 제한되면 응용 프로그램은 데이터가 반환됩니다.

[Sheets 권한과 보호](/guides/sheets/features/core/permission)

### Docs

문서 수준 아래, **섹션, 단락 및 콘텐츠 entities**는 보호할 수 있습니다. 항목에는 테이블, 그림, 사용자 정의 블록 및 안정적인 식별자와 범위가 포함되어 있습니다. 헤더 및 발터 단락은 세그먼트를 통해 해결됩니다.

예를 들어, 계약 조항을 보호하고 편집 할 필요가있는 단락을 남깁니다. 섹션과 단락은 `getPermission()`를 노출합니다. 엔티티티티의 경우 `document.getEntityPermission()`을 사용하십시오. 효과적인 결과는 문서, 적용 가능한 부모 및 객체의 규칙을 결합합니다.

[문서 권한](/reference/facade/document-permission) · [구역·단락·엔터티 권한](/reference/facade/document-object-permission)

### Slides

보호는 **프리젠 테이션, 개별 슬라이드, 페이지 요소 및 마스터 편집 항목 및 마스터 요소**에 적용할 수 있습니다. 상표가 붙은 템플렛 및 조정 도표는 선택된 원본 상자, 이미지, 또는 도표 목표가 편집할 수 있는 동안 잠글 수 있습니다.

`presentation.getPermission()`, `slide.getPermission()` 및 `slide.getElementPermission()`를 사용하십시오. 주된 관련 accessors는 프리젠 테이션 정면에 의해 제공됩니다.

[Slides 권한](/guides/slides/features/core/permissions) · [Presentation Facade](/reference/facade/presentation)

### Relational Table [#base]

권한은 **테이블, 필드, 기록, 조회, 대시보드**를 포함합니다. 누군가가 세포, 관계 테이블, 테이블, 필드를 편집하고, 제한은 함께 적용합니다. 구성과 대쉬보드를 별도로 보호할 수 있습니다.

예를 들어, 스키마와 금융 레코드를 보호하면서 사람들은 일상적인 작업을 계속 유지하도록 계속합니다. 테이블, 필드, 레코드 및 레이아웃은 `getPermission()`를 노출; 대시보드는 플러그인을 필요로합니다. 사용자 당 읽기 쉬운 필드와 레코드를 필터링하는 것은 응용 프로그램의 데이터 읽기 정책의 책임입니다.

[Relational Table 권한](/guides/bases/features/core/permissions) · [객체 권한 API](/reference/facade/base-object-permission)

### Canvases [#board]

캔버스 단위 내에서 **개별 요소**는 보호 할 수 있습니다 : 모양, 텍스트, 이미지, 커넥터. 아키텍처 배경 또는 워크 플로우 프레임 워크는 그들이 유지 노드 만 편집하면서 보호 할 수.

단위 및 `board.getElementPermission(elementId)`에 대한 `board.getPermission()`를 사용하여 개별 요소에 대한. 요소를 편집하면 캔버스 레벨과 요소 레벨 모두에서 권한이 필요합니다.

[Canvases 권한](/reference/facade/board-permission) · [요소 권한](/reference/facade/board-element-permission)

### PDF

PDF는 현재 현지 상호 작용을 위해 **보기/edit 모드**를 사용하고 있으며, 다른 5개의 제품 사용인 Unit 및 object permission APIs에서 다른 범위가 있습니다. 백엔드는 파일 읽기, 다운로드 및 수출을 승인합니다. PDF는 Core Collaboration가 지원하는 5개의 단위 유형 밖에 있습니다.

[PDF 통합과 콘텐츠 작업](/guides/pdfs/getting-started/facade)

## 권한 상속과 공동 작업자 정책

**물체는 단위 수준의 제한 또는 적용 가능한 부모 제한을 무시하지 않습니다.** 문서를 읽을 때 단락 편집 가능에는 아무 효력도 없습니다. 지원되는 목표를 위해, 효과적인 결과를 위한 `canEdit()`를 쿼리하십시오.

Docs, 슬라이드, 관계 테이블 및 캔버스에서, 아이 - 보스 권한 주로 제어 편집; 복사 및 코멘트는 단위 수준에서 구성 됩니다. 시트는 워크 시트 및 범위 권한 포인트를 추가, 그래서 과립은 제품별로 다릅니다.

Docs, 슬라이드, 관계 테이블 및 캔버스는 `setObjectPermissions()`를 제공하여 일괄 처리에 대한 공동 정책 설정 :

| 정책 | 객체를 편집할 수 있는 사용자 |
| --- | --- |
| `all` | 이미 Unit에서 편집 권한을 보유한 Collaborators. |
| `owner` | 개체의 소유자는 단위와 부모 제한을 제공 할 수 있습니다. |
| `members` | Unit collaborators만 선택하실 수 있습니다. |

이 정책은 Authz 통합, `objectPermissionTypes` 대상 유형 및 지속 대상 바인딩, 규칙 및 회원에 대 한 구성. SDK 수출 및 콘텐츠 ID를 안정적으로 유지 하는 객체 ID 도우미를 사용 합니다. `policy: null` 보호 및 복원 상속을 제거 합니다. 일괄 쓰기는 일부 개체에 대 한 성공 하 고 다른 사람에 대 한 실패, 그래서 확인 `failed` 및 `refreshError`. 시트는 작업 시트 및 범위 보호 API를 통해 그것의 정책을 적용 합니다.

## 프런트엔드와 백엔드의 인가

단일 신뢰할 수있는 정체성과 Unit/object 정책 시스템을 유지하여 frontend 행동과 백엔드 권한 모두 구동합니다.

| 계층 | 책임 |
| --- | --- |
| Web SDK | 현재 사용자의 허용된 행동, 업데이트 권한 포인트 및 편집 컨트롤을 읽고, 명령을 확인합니다. |
| 애플리케이션 Authz API | 신뢰할 수있는 정체성을 사용하여 쿼리 또는 변경 정책, 효과적인 단위 및 객체 권한을 반환하고 정책 관리를 승인합니다. |
| Transport | 쿠키, 세션, 또는 토큰 자격 증명을 인증하고 신뢰할 수있는 정체성을 설정합니다. 클라이언트가 보낸 사용자 필드는 승인 증거가 아닙니다. |
| Endpoint | WebSocket 연결 및 `joinUnit` 룸 회원을 승인합니다. |
| Service | `submitChangeset`에서 `readUnitData` 및 제출에 대한 읽음을 확인하고 영향을받는 내용에 대한 객체 정책을 평가합니다. 변경 사항이 적용됩니다. |

Server SDK 공급 Middleware 후크; 응용 프로그램은 ACL 및 객체 정책을 제공합니다. 응용 프로그램은 단일 레벨 편집 만 확인하는 경우 **frontend에 읽기 전용 설정 및 객체 보호는 자신에 의해 백엔드 권한이 시행하지 않습니다.**, 개체 체크는 단락, 요소, 필드 또는 기록 제한에 추가해야합니다.

기존 `collabService`에 애플리케이션의 `acl`을 연결하는 예입니다.

```ts
import { CollabError } from '@univerjs-pro/collaboration-service'

collabService.use('submitChangeset', async (context, next) => {
  const allowed = await acl.canEdit(
    context.userID,
    context.request.changeset.unitID,
  )
  if (!allowed) {
    throw new CollabError('PERMISSION_DENIED', 'Editing is not allowed')
  }
  await next()
})
```

이 예제는 Unit-level 편집 만 포함합니다. 읽기, JOIN, 정책 변경 및 확장 엔드 포인트는 보호뿐만 아니라 보호해야합니다. 미세 곡물 쓰기를 위해 `applyChangeset`와 같은 응용 프로그램 단계에서 영향을받는 개체를 검증하고, 복원 할 수있는 정책 안전을 유지합니다.

전체 통합을 위해 [ID 및 인증](/server/collaboration/identity-and-authorization)를 참조하십시오. Lifecycle 걸이는 [Middleware 및 이벤트](/server/collaboration/middleware-and-events)에서 설명됩니다.
