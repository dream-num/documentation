비주얼 검사는 이미지 및 레이아웃 증거로 콘텐츠 모델을 변환합니다. 에이전트는 데이터를 검증하고 공식을 먼저 검증하고 렌더링 된 텍스트, 모양 및 페이지를 검사합니다. 문제가 발견되면 Facade를 통해 콘텐츠를 수정하고 결과를 조사합니다.

## 세 종류의 증거 [#evidence]

| 증거 | 확인할 수 있는 내용 |
| --- | --- |
| 구조화된 재조회 | 원시값, 공식 및 그 결과, 단락 및 객체 속성. |
| PNG | 클립핑, 차트, 색상 및 전체 구성을 포함하여 실제로 볼 수있는 내용. |
| 레이아웃 진단 | 규칙, 객체 ID, 경계, 그리고 렌더링에서 파생 된 문제 위치, 이는 객체를 올바른 식별. |

## 콘텐츠 상태와 종속성 준비 [#state]

스크린 샷과 Layout Lint는 재료화 된 UnitData에서 작동한다. 그들은 원격 대상에 연결하지 않으며, 변경 설정을 해석하지 않습니다. 공동 콘텐츠를 위해 `pull()`를 호출하고, 공식 편집 후 완료 할 때까지 계산을 기다리고 `exportUnitData()`로 전화하십시오. Worktree에서는 검사를 위해 예정된 초안을 수출합니다. 응용 프로그램은 대상을 기록 할 수 있으며, 개정, 그 반대의 범위는 하나의 상태 보고서를 나타냅니다.

호스트 Snapshot은 모든 의존성을 포함하지 않습니다. `formulaReferenceUnits`를 통해 시트 및 관계 테이블 소스를 통과하고 `embeddedUnits`을 통해 어린이 콘텐츠를 전달하십시오. 호스트 전에 의존성을 부여하는 페이지 렌더링은 이미 소스와 함께 수식 및 블록로드를 형성합니다. UUID 이미지 자산은 `resolveUnitScreenshotImageAssets()` 및 해결사로 준비 할 수 있습니다. 해결은 최고의 노력이므로 누락 된 리소스는 검증을 필요로합니다.

## 안정된 화면 생성 [#rendering]

<Mermaid chart={"flowchart LR\nA[\"명확한 콘텐츠 상태<br/>UnitData + 종속성\"]\nB[\"Render Runtime<br/>브라우저·페이지 프로토콜\"]\nC[\"Render Page<br/>Univer 기본 레이아웃\"]\nD[\"준비 완료 확인<br/>계산·화면 안정\"]\nE[\"PNG / 레이아웃 사실<br/>Agent와 사람 검토\"]\nA --> B --> C --> D --> E"} />

`univer-render-runtime`는 응용 프로그램에 의해 구축 된 Render Page를 호스팅하고 Node.js에서 브라우저를 시작합니다. 제품 플러그인은 그 페이지에 내용을 복원하고 양쪽 모두 페이지 프로토콜 버전을 확인합니다. 런타임은 단일 직렬 큐를 통해 작업을 수행하므로 동일한 실행 시간은 검사 라운드를 통해 유지 될 수 있습니다. 작업이 완료되면 Runtime 호출 `close()`의 소유자.

읽음은 제품에 달려 있습니다. 공식 구동 모양은 결과가 종료 될 때까지 기다리며 필요한 경우, 픽셀이 프레임에 따라 변경되지 않도록 전환 애니메이션이 캡처되지 않습니다. 관계 테이블은 글꼴, 계산, 활성 테이블 또는보기 및 안정적인 DOM 및 캔버스 레이아웃을 기다립니다. 공식 결과는 종료가 여전히 오류가 될 수 있으므로 값과 그 상태는 검증이 필요합니다.

현재 구현은 직렬화된 호스트 UnitData, 공식 소스 및 임베디드 어린이를 렌더링 세션 키로 제공합니다. 변경된 내용은 단위 ID가 동일하게 유지될 때에도 새로운 키를 수신하므로 기존 이미지는 ID 일치 때문에 단독으로 재사용되지 않습니다.

## 제품별 범위 선택 [#scope]

| 제품 | 범위 및 출력 |
| --- | --- |
| Sheet | 지역 PNG를 얻기 위해 워크 시트 및 A1 범위를 선택하십시오. 중요한 결과를 명시적으로 선택하십시오. |
| Doc | 페이지를 선택, 또는 그들을 대문, 페이지 당 하나의 PNG를 얻을. |
| Slide | 1기반 페이지 번호 또는 페이지 ID를 선택하고, 선택적으로 연락처 시트를 추가하십시오. |
| Relational Table | 브라우저 DOM과 Canvas에서 Active table 또는 view를 포함한 workbench를 캡처합니다. |
| Canvases | 콘텐츠 경계 또는 지역 / elementIds selector; 두는 상호 전용입니다. 패딩 및 레이아웃 증거는 선택 사항입니다. |

`unit-screenshot`는 이미지 바이트, 차원, 페이지 또는 범위 정체성을 돌려주고, 파일 이름을 건의합니다; 신청은 그(것)들을 저장합니다. 가늠자 요인은 0.1-4를 받아들입니다. `maxPages`와 per-image `maxPixels`를 놓으십시오. 가늠자를 두배로 하고십시오 대략 4배 화소를, 그래서 지구에 있는 큰 내용을 검열합니다. PDF는 이 스크린 샷 입구 점 이상으로, 위에 5개의 제품을 커버합니다.

## 스크린샷과 Lint의 공통 입력 [#example]

예를 들어 캡처하고 동일한 슬라이드 데이터 및 공식 소스를 lints. `renderRuntime`는 기존 렌더링 실행 시간이며 `slideData`은 준비 스냅 샷입니다. Neither 기능은 파일을 작성합니다. 페이지 건설 및 리소스 정리의 경우 [AI SDK 시각 검사](/ai/visual-inspection)를 참조하십시오.

```ts
import { createUnitScreenshot } from '@univer-cli/unit-screenshot'
import { createUnitLayoutLint } from '@univer-cli/unit-layout-lint'

const source = {
  unitType: 'slide' as const,
  unitData: slideData,
  formulaReferenceUnits,
}
const screenshot = createUnitScreenshot({ runtime: renderRuntime })
const lint = createUnitLayoutLint({ runtime: renderRuntime })

const capture = await screenshot.capture({
  ...source,
  target: { kind: 'slide-pages', pages: [1], scale: 2 },
})
const report = await lint.lint({ ...source, pages: [1] })
```

## Slide: 글리프 잉크로 문제 찾기 [#slide-lint]

Layout Lint는 브라우저가 생성되는 레이아웃에서 작동합니다. 요소의 `declared` 상자는 모델의 기하학을 설명하면서 텍스트 `ink`가 실제로 커버하는 영역을 설명하고, 레이아웃, 정렬 및 회전과 페이지 좌표로 매핑 된 영역을 설명합니다. 페이지에 맞는 텍스트 상자는 그 글리프가 적합하다고 증명하지 않습니다.

| 현재 규칙 | 검사 근거 |
| --- | --- |
| `text-off-page` | 실제 텍스트 잉크는 페이지 가장자리 과거를 확장합니다. |
| `text-escapes-container` | 텍스트가 눈에 띄는 불투명한 컨테이너를 흘러 관통합니다. |
| `text-overlaps-text` | 2개의 실제적인 원본 잉크 지역 overlap 실질적으로. |

보고서에는 `coverage.pages` 및 `coverage.rules`가 포함되어 있습니다. 각 결과는 `pageId`, `id`의 `text.ink`와 관련 `overflow`를, `container` 또는 `other` 증거를 나릅니다. 안정적인 `fingerprint`는 수리 라운드 사이의 비교를 단순화합니다. 찾기는 현재 경고 및 읽기는 이러한 규칙을 따르지 않습니다. 이러한 규칙은 스크린 샷을 포함하지 않습니다.

## Canvases: 렌더링된 연결선 확인 [#board-analysis]

캔버스 스크린 샷은 브라우저, 문제 및 요약에 의해 해결 된 루트를 포함하는 `layoutAnalysis`를 반환합니다. 이것은 슬라이드를 처리하는 `unit-layout-lint`에서 분리됩니다. 자동 커넥터 경로는 모델에서 해결되지 않을 수 있으므로 `source: 'rendered'`의 증거를 통해 최종 노선을 검사합니다.

진단은 교차 요소 또는 간섭, 충돌 라벨을 식별 할 수 있으며 해당 `connectorIds`, `elementIds` 및 `focusBounds`를보고하는 커넥터를 식별 할 수 있습니다. 관련된 개체를 수정하고 지역 또는 원자 세트를 캡처하고 전체 캔버스를 다시 검토하십시오. 이 하나의 특정 Facade 편집과 시각적 인 우려를 준수합니다.

구조상 결과, 범위 및 페이지 정보, 이미지 및 진단을 함께 유지하십시오. 스크린 샷은 공식이 정확하지 않으며 lint는 시각적 판결을 대체하지 않습니다. 도구 모음, 초점 및 팝업을 포함하는 상호 작용은 여전히 웹 편집기에서 검증을 필요로하며, 크로스 단위의 의존성은로드되어야합니다.

[Worktree](/overview/features/shared/worktree) 이전에 이러한 검사를 실행하면, 검토자가 증거에 대한 내용 변경 사항을 일치 할 수 있도록 준비되었습니다. 관현악을 위해 [headless 및 서버 계산](/overview/features/shared/server-calculation) 실행 및 [에이전트 및 자동화](/overview/features/shared/agents)를 참조하십시오.
