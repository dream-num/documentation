Version history organizes confirmed collaborative changes into browsable versions. For each confirmed change, developers and users can see the author, the timestamp, and the action, open the document as it stood at that point, review the difference, and restore a version when they have permission. History remains available after the editing session ends and across page reloads.

## How version history works

A **mutation** is one replayable content change, such as setting a cell or inserting a paragraph. A **changeset** is one collaboration submission that carries an ordered group of mutations.

### 1. Record changes

Every edit from a user or an Agent produces mutations. Univer packs these mutations into a changeset and submits it for collaboration to confirm and persist.

<Mermaid chart={"flowchart LR\n    A[\"Edit content\"]\n    B[\"Mutation\"]\n    C[\"Changeset\"]\n    D[\"Confirm and persist<br/>Record revision\"]\n    A --> B\n    B --> C\n    C --> D\n"} />

After confirmation, a submission receives a **revision**, which identifies its position in the document's history. History indexes the confirmed changesets, groups them by time and operation, and builds the version timeline.

### 2. Reconstruct historical content

A **snapshot** is the complete content state at one revision. When a historical version is selected, Univer loads a baseline snapshot and the changesets that follow it up to the target revision, then replays their mutations in order. The result is a read-only view of the content as it stood at that revision.

<Mermaid chart={"flowchart LR\n    A[\"Select version<br/>revision N\"]\n    B[\"Load snapshot<br/>+ later changesets\"]\n    C[\"Replay mutations<br/>in order\"]\n    D[\"Historical content<br/>Read-only view\"]\n    A --> B\n    B --> C\n    C --> D\n"} />

For example: **snapshot at revision 10 + changesets for revisions 11–15 = content at revision 15.**

### 3. Restore the current document

Selecting **Restore this version** starts the following flow:

> Select a target version → Submit a restore mutation → Collaboration confirms → Update the current document at a new revision

The restore operation creates a new history record. Earlier versions remain available.

## Browse versions and changes

1. Open **Version history** from the editor and select a version.
2. Expand a version group to inspect the individual revisions. Select one revision to read its content and changes in a read-only viewer.
3. Select **Restore this version** when a rollback is required. The restore updates the shared document through collaboration, so every other participant receives the change.

A version group can combine the edits made within a time window. Expand the group to inspect the individual revisions. **One history entry does not necessarily correspond to one keystroke or one generated Snapshot.**

### Read the change colors

| Marker | Meaning | Example |
| --- | --- | --- |
| 🟦 **Blue: updated** | Existing content changed. | A value, a paragraph format, or an object property was updated. |
| 🟩 **Green: inserted** | Content added in this version. | A new row, paragraph, record, or board object. |
| 🟥 **Red: deleted** | Content removed in this version. | Removed text or objects keep a marker in the history view. |

Colors indicate the **type of change**. Replacing text can produce both an insertion and a deletion. Each product's viewer determines how much of the content is highlighted.

## Integrate with your application

Version history combines the History extension in Server SDK with the product history plugins in Web SDK.

- On the server, add History Service, Endpoint, and a persistent Database Adapter to Core Collaboration. The service subscribes to Unit creation and committed changesets, builds a history index, and exposes queries for versions and changesets.
- In the browser, register the common history capability and the product's History / History UI plugins, then connect the history endpoint. The viewer loads the selected revision and displays its changes. For custom content, register the matching viewer plugins.
- Your application supplies identity and authorization, and the server checks history-read and restore permissions. A historical version can contain data that the current document has already removed.

See [collaboration extensions](/server/collaboration/extensions) and assemble the service with the [History example](/server/collaboration/examples#history), then connect the UI with the product guides above.

History indexes are rebuildable derived data. **Confirmed changesets remain the authoritative content source.** Your application controls persistence and retention. The history panel does not replace backups.

## History, undo, comparison, and Worktree

| Capability | Purpose |
| --- | --- |
| Undo / redo | Revert or reapply an editing operation without a history service. |
| Version history | Trace confirmed versions across sessions, inspect changes, and restore shared content. |
| [Content comparison](/overview/features/shared/compare) | Compare two content states for a UI or an Agent. A read-only comparison does not restore content. |
| [Worktree](/overview/features/shared/worktree) | Isolate draft changes for review before merging them into shared content. |

Agent changes made through Facade APIs enter the same history pipeline once collaboration confirms them. Applications can combine history with content comparison for automated review and checks.
