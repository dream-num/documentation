Version history organizes confirmed collaborative changes into browsable versions. Developers and users can inspect authors, timestamps, and actions, open historical content, review changes, and restore a version when permitted. History remains available across editing sessions and page reloads.

**Product names:** [Relational Table](/overview/features/relational-table) is named `Base` in the SDK and APIs; [Canvases](/overview/features/canvas) is named `Board`.

## How version history works

- **Mutation**: A replayable content change, such as setting a cell or inserting a paragraph.
- **Changeset**: A collaboration submission containing an ordered group of mutations.

### 1. Record changes

**When edits are submitted.** User or Agent edits produce mutations, which are packaged into a changeset and submitted for collaboration confirmation and persistence.

<Mermaid chart={"flowchart LR\n    A[\"Edit content\"]\n    B[\"Mutation\"]\n    C[\"Changeset\"]\n    D[\"Confirm and persist<br/>Record revision\"]\n    A --> B\n    B --> C\n    C --> D\n"} />

A **revision** identifies a confirmed submission’s position in document history. History indexes confirmed changesets and groups them by time and operation to build the version timeline.

### 2. Reconstruct historical content

**When a historical version is selected.** A snapshot is the complete content state at a revision. The system loads a baseline snapshot and the subsequent changesets up to the target revision, then replays their mutations in order to produce a read-only historical view.

<Mermaid chart={"flowchart LR\n    A[\"Select version<br/>revision N\"]\n    B[\"Load snapshot<br/>+ later changesets\"]\n    C[\"Replay mutations<br/>in order\"]\n    D[\"Historical content<br/>Read-only view\"]\n    A --> B\n    B --> C\n    C --> D\n"} />

For example: **snapshot at revision 10 + changesets for revisions 11–15 = content at revision 15.**

### 3. Restore the current document

**When Restore this version is selected.**

> Select a target version → Submit a restore mutation → Collaboration confirms → Update the current document at a new revision

The restore operation creates a new history record, while earlier versions remain available.

## Browse versions and changes

1. Open **Version history** from the editor and select a version.
2. Expand a version group to inspect individual revisions. Select an entry to review its content and changes in a read-only viewer.
3. Select **Restore this version** when a rollback is needed. Restoration updates the current shared document through collaboration, so other participants receive the change.

A version group can combine edits within a time window. Expand it to inspect individual revisions. **A history entry is not necessarily one keystroke or one generated Snapshot.**

### Read the change colors

| Marker | Meaning | Example |
| --- | --- | --- |
| 🟦 **Blue: updated** | Existing content changed. | A value, paragraph format, or object property was updated. |
| 🟩 **Green: inserted** | Content added in this version. | A new row, paragraph, record, or board object. |
| 🟥 **Red: deleted** | Content removed in this version. | Removed text or objects retain a visual marker in the history view. |

Colors indicate **change types**. A text replacement may show both an insertion and a deletion. Each product viewer determines the highlighted scope.

## Integrate with your application

Version history combines the Server SDK History extension with Web SDK product history plugins:

- **Server**: add History Service, Endpoint, and a persistent Database Adapter to Core Collaboration. The service subscribes to Unit creation and committed changesets, builds a history index, and exposes version and changeset queries.
- **Browser**: register the common history capability and the product's History / History UI plugins, then connect the history endpoint. The viewer loads the selected revision and displays its changes. Register the appropriate viewer plugins for custom content.
- **Permissions**: your application supplies identity and authorization; the server checks history-read and restore permissions. Historical versions can contain data already removed from the current document.

See [collaboration extensions](/server/collaboration/extensions), assemble the service with the [History example](/server/collaboration/examples#history), then connect the UI using the product guides above.

History indexes are rebuildable derived data. **Confirmed changesets remain the authoritative content source.** Your application controls persistence and retention; the history panel does not replace backups.

## History, undo, comparison, and Worktree

| Capability | Purpose |
| --- | --- |
| Undo / redo | Revert or reapply editing operations without a history service. |
| Version history | Trace confirmed versions across sessions, inspect changes, and restore shared content. |
| [Content comparison](/overview/features/shared/compare) | Compare two content states for a UI or Agent. Read-only comparison does not restore content. |
| [Worktree](/overview/features/shared/worktree) | Isolate draft changes for review before merging them into shared content. |

Agent changes made through Facade APIs can enter the same history pipeline once collaboration confirms them. Applications can combine history with content comparison for automated review and checks.
