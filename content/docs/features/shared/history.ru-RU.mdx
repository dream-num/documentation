История версий организует подтвержденные совместные изменения в просматриваемые версии. Для каждого подтвержденного изменения разработчики и пользователи могут видеть автора, временную метку и действие, открывать документ в том виде, в котором он стоял в тот момент, просматривать разницу и восстанавливать версию, когда у них есть разрешение. История остается доступной после окончания сеанса редактирования и перезагрузки страниц.

## Как работает история версий

**мутация** - это одно повторно воспроизводимое изменение контента, такое как установка ячейки или вставка абзаца. **менять** является одним представлением о сотрудничестве, которое несет упорядоченную группу мутаций.

### 1. Запись изменений

Каждое редактирование от пользователя или агента производит мутации. Univer упаковывает эти мутации в набор изменений и отправляет его для совместной работы, чтобы подтвердить и сохранить.

<Mermaid chart={"flowchart LR\n    A[\"Редактирование\"]\n    B[\"Mutation\"]\n    C[\"Changeset\"]\n    D[\"Подтвердить и сохранить<br/>Записать revision\"]\n    A --> B\n    B --> C\n    C --> D\n"} />

После подтверждения в подачу поступает **пересмотр**, который идентифицирует свою позицию в истории документа.История индексирует подтверждённые вносимые в него изменения, группирует их по времени и операции и строит временную шкалу версии.

### 2. Воссоздание прошлого содержимого

**снимок** - это полное состояние контента при одной ревизии. Когда выбирается историческая версия, Univer загружает базовый снимок и наборы изменений, которые следуют за ним до целевой ревизии, а затем переигрывает их мутации в порядке. Результатом является только просмотр содержимого, как оно стояло при этой ревизии.

<Mermaid chart={"flowchart LR\n    A[\"Выбрать версию<br/>revision N\"]\n    B[\"Загрузить snapshot<br/>и последующие changesets\"]\n    C[\"Воспроизвести mutations<br/>по порядку\"]\n    D[\"Прошлое содержимое<br/>Только чтение\"]\n    A --> B\n    B --> C\n    C --> D\n"} />

Пример: **snapshot на revision 10 + changesets для ревизий 11–15 = содержимое на revision 15.**

### 3. Восстановление текущего документа

Выбор **Восстановите эту версию** начинается следующим образом:

> Выбрать версию → Отправить mutation восстановления → Подтверждение → Обновить текущий документ с новой revision

Операция восстановления создает новый исторический рекорд.Предыдущие версии остаются доступными.

## Просмотр версий и изменений

1. Откройте историю в редакторе и выберите версию.
2. Расширить группу версий, чтобы проверить индивидуальные изменения. Выберите один пересмотр, чтобы прочитать его содержание и изменения в просмотрщике только для чтения.
3. Выберите **Восстановите эту версию**, когда требуется откат. Восстановление обновляет общий документ посредством совместной работы, поэтому каждый другой участник получает изменение.

Группа версий может комбинировать изменения, сделанные в пределах временного окна. Расширить группу для проверки отдельных изменений. **Одна запись истории не обязательно соответствует одному нажатию клавиши или одному сгенерированному снимку.**

### Цвета изменений

| Метка | Значение |
| --- | --- |
| 🟦 **Синий: обновлено** | Существующий контент изменился. | Обновлено значение, формат абзаца или свойство объекта. |
| 🟩 **Зелёный: добавление** | Новая строка, абзац, запись или объект доски. |
| 🟥 **Красный: удалено** | Содержимое удалено в этой версии. | Снятый текст или объекты сохраняют маркер в виде истории. |

Цвета указывают на **Тип изменения**. Замена текста может производить как вставку, так и удаление. Каждый зритель продукта определяет, сколько контента выделено.

## Интеграция с приложением

История версий объединяет расширение History в Server SDK с плагинами истории продуктов в Web SDK.

- На сервере добавьте History Service, Endpoint и постоянный адаптер базы данных для Core Collaboration. Сервис подписывается на создание Unit и совершенные изменения, строит индекс истории и обнажает запросы на версии и изменения.
- В браузере регистрируют общую возможность истории и плагины пользовательского интерфейса History/ History продукта, затем подключают конечную точку истории. Зритель загружает выбранный пересмотр и отображает его изменения. Для пользовательского контента регистрируют соответствующие плагины просмотра.
- Ваше приложение предоставляет идентификатор и авторизацию, а сервер проверяет прочитанные истории и восстанавливает разрешения. Историческая версия может содержать данные, которые текущий документ уже удалил.

См. [Расширения сотрудничества](/server/collaboration/extensions) и соберите сервис с помощью [Пример истории](/server/collaboration/examples#history), а затем соедините пользовательский интерфейс с руководствами по продукту выше.

Индексы истории - это восстановленные производные данные. **Подтвержденные изменения остаются авторитетным источником контента.** Ваше приложение контролирует постоянство и удержание. Панель истории не заменяет резервные копии.

## Связь с другими функциями

| Способность | Цель |
| --- | --- |
| Ундо / Redo | Восстановить или повторно применить операцию редактирования без службы истории. |
| История версий | Следите за подтвержденными версиями во время сеансов, проверяйте изменения и восстанавливайте общий контент. |
| [Сравнение контента](/overview/features/shared/compare) | Сравните два состояния контента для пользовательского интерфейса или агента. Сравнение только для чтения не восстанавливает контент. |
| [Worktree](/overview/features/shared/worktree) | Изолируйте проекты изменений для обзора, прежде чем объединять их в общий контент. |

Изменения агентов, внесенные через API Facade, входят в один и тот же конвейер истории, как только их подтверждает сотрудничество.Приложения могут комбинировать историю с сравнением контента для автоматического обзора и проверок.
