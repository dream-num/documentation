La inspección visual convierte un modelo de contenido en imágenes y evidencias de diseño que pueden ser examinadas. Un agente verifica los datos y las fórmulas primero, luego examina el texto renderizado, las formas y las páginas. Cuando encuentra un problema, corrige el contenido a través de una Facade y examina el estado resultante de nuevo.

## Tres clases de evidencia [#evidence]

| Evidencia | Qué comprueba |
| --- | --- |
| Lectura estructurada | Valores brutos, fórmulas y sus resultados, y propiedades de párrafo y objeto. |
| PNG | El contenido que en realidad es visible, incluyendo recortado, gráficos, colores y composición general. |
| Diagnóstico de diseño | Reglas, identificaciones de objetos, límites y lugares de emisión derivados del renderizado, que identifican el objeto para corregir. |

## Preparar estado y dependencias [#state]

Captura de pantalla y Layout Lint operan en UnitData materializada. No se conectan a un objetivo remoto, y no interpretan los cambios. Para el contenido colaborativo, llame a `pull()`, espere a que el cálculo termine después de una edición de fórmula, y luego llame a `exportUnitData()`. En un Worktree exporte el borrador que está destinado a la inspección.

Un host Snapshot no incluye cada dependencia. Fuentes de la hoja de paso y la tabla relacional a través de `formulaReferenceUnits`, y pasar el contenido de los niños a través de`embeddedUnits`. La página Render materializa las dependencias antes del host, por lo que las fórmulas y bloques de carga con sus fuentes ya existentes. Los activos de la imagen UUID pueden ser preparados con `resolveUnitScreenshotImageAssets()` y una solución de la aplicación.

## Del contenido a una imagen estable [#rendering]

`univer-render-runtime` acoge una página Render construida por la aplicación y comienza un navegador de Node.js. plugins de productos restauran el contenido en esa página, y ambos lados revisan la versión del protocolo de página. Un Runtime ejecuta sus operaciones a través de una sola cola de serie, por lo que el mismo Runtime puede ser retenido en rondas de inspección. El propietario de la Runtime llama `close()` cuando el trabajo está completo.

La lectura depende del producto. Las formas impulsadas por la fórmula esperan hasta que los resultados se dejen pendientes y, cuando sea necesario, hasta que los píxeles permanezcan inalterados en marcos, de modo que no se capture una animación transitoria. La tabla de relaciones espera fuentes, cálculo, tabla activa o vista, y un diseño estable de DOM y Canvas. Un resultado de fórmula que ha dejado pendiente puede ser un error, por lo tanto su valor y su estado requieren verificación.

La implementación actual tiene el host serializado UnitData, las fuentes de fórmula y los niños incrustados en una clave de sesión de renderizado. El contenido modificado recibe una nueva clave incluso cuando el ID de unidad sigue siendo el mismo, por lo que una imagen vieja nunca se reutiliza solamente porque el ID coincide.

## Elegir el alcance por producto [#scope]

| Producto | Alcance y salida |
| --- | --- |
| Sheet | Seleccione una hoja de trabajo y una gama A1 para obtener una región PNG. Seleccione resultados importantes explícitamente. |
| Doc | Seleccione páginas, o enumerarlas, para obtener un PNG por página. |
| Slide | Seleccione los números de página o los IDs de página de 1 base, y agregue opcionalmente una hoja de contacto. |
| Relational Table | Captura el banco de trabajo a medida que se abre, incluyendo su mesa o vista activa, desde el navegador DOM y Canvas. |
| Canvases | Utilice los límites de contenido, o un selector de región / elementoIds; los dos son mutuamente excluyentes. Las pruebas de relleno y diseño son opcionales. |

`unit-screenshot` devuelve los bytes de imagen, las dimensiones, la página o la identidad de rango, y los nombres de archivos sugeridos; la aplicación los salva. El factor de escala acepta 0.1-4. Set `maxPages` y el per-imagen `maxPixels`. Duplicar la escala produce aproximadamente cuatro veces los píxeles, así que inspeccionar el contenido grande en regiones PDF está fuera de este punto de entrada de captura.

## Compartir datos para captura y lint [#example]

El ejemplo captura y recubre los mismos datos de diapositivas y fuentes de fórmula. `renderRuntime` es un render Runtime existente, y `slideData` son la instantánea preparada. Ninguna capacidad escribe archivos. Para la construcción de páginas y la limpieza de recursos, vea [Inspección visual de AI SDK](/ai/visual-inspection).

```ts
import { createUnitScreenshot } from '@univer-cli/unit-screenshot'
import { createUnitLayoutLint } from '@univer-cli/unit-layout-lint'

const source = {
  unitType: 'slide' as const,
  unitData: slideData,
  formulaReferenceUnits,
}
const screenshot = createUnitScreenshot({ runtime: renderRuntime })
const lint = createUnitLayoutLint({ runtime: renderRuntime })

const capture = await screenshot.capture({
  ...source,
  target: { kind: 'slide-pages', pages: [1], scale: 2 },
})
const report = await lint.lint({ ...source, pages: [1] })
```

## Slide: localizar problemas con tinta de glifos [#slide-lint]

Layout Lint trabaja de los hechos de diseño que el navegador produce. La caja `declared` de un elemento describe su geometría en el modelo, mientras que el texto `ink` describe el área que los glifos realmente cubren, mapeado en coordenadas de página con el diseño, alineación y rotación. Una caja de texto que se ajusta a la página no prueba que sus glifos encajan.

| Regla actual | Evidencia |
| --- | --- |
| `text-off-page` | La tinta de texto real se extiende más allá del borde de la página. |
| `text-escapes-container` | El texto desborda visiblemente un recipiente opaco que es más pequeño. |
| `text-overlaps-text` | Dos áreas de tinta de texto reales superponen sustancialmente. |

Un informe incluye `coverage.pages` y `coverage.rules`. Cada hallazgo lleva `pageId`, el elemento `id`, el `text.ink`, y las pruebas correspondientes `overflow`, `container`, o `other`. Un `fingerprint` estable simplifica la comparación entre rondas de reparación. Los hallazgos son actualmente advertencias y están destinados a ser leídos junto a las capturas de pantalla. Una lista vacía sólo significa que el alcance seleccionado no ha activado ninguna de estas reglas.

## Canvases: comprobar rutas renderizadas [#board-analysis]

Canvases screenshots también devuelve `layoutAnalysis`, que contiene las rutas resueltas por el navegador, los problemas y un resumen. Esto es separado de `unit-layout-lint` que sólo maneja Slide. Las rutas de conexión automáticas pueden ser sin resolver en el modelo, así que inspecciona las rutas finales a través de la evidencia con `source: 'rendered'`.

Los diagnósticos pueden identificar conectores que cruzan elementos o intersectan, cabezas de flecha colliding, y etiquetas conflictivas, e informar de los correspondientes `connectorIds`, `elementIds` y `focusBounds`. Corrige los objetos involucrados, captura una región o un conjunto de elementos, y luego revisa todo el lienzo de nuevo. Esto asocia una preocupación visual con una edición específica de Facade.

## Entregar las evidencias [#handoff]

Mantenga los resultados estructurados, el alcance y la información de la página, las imágenes y el diagnóstico juntos. Una captura de pantalla no establece que las fórmulas son correctas, y lint no reemplaza el juicio visual. Las interacciones que involucran la barra de herramientas, el enfoque y los popups todavía requieren verificación en el editor web, y las dependencias de unidad cruzada deben ser cargadas.

Ejecute estos cheques antes de que una [Worktree](/overview/features/shared/worktree) esté marcada Listo, para que el revisor pueda coincidir con los cambios de contenido a la evidencia.
