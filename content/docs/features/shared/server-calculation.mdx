Headless Univer is Univer’s content runtime without an interactive editor UI. It shares content models, commands, calculation, and Facade APIs with the browser editor. It can process content in Node.js or run UI-free tasks in a browser. Available capabilities depend on the registered product and feature plugins.

The JavaScript/TypeScript content runtime described here and `univer-rs` are separate execution implementations. The latter supports server-side calculation and file conversion and can be combined with Headless workflows around the same snapshots.

## What Headless can do [#headless-capabilities]

- **Read and change content and structure:** create or load Univer snapshots, use Facade APIs to read and edit cells, paragraphs, pages, graphical objects, or records, then save updated snapshots. This supports batch processing, data generation, content inspection, and agent automation.
- **Run registered business logic:** use formula calculation, sorting, filtering, validation, and pivot plugins; modify resources such as images, charts, shapes, and comments. Available operations depend on the product and feature plugins and their dependencies.
- **Connect to other services:** add the Node.js collaboration client to load collaborative Units, submit changes, and wait for synchronization; combine Server SDK conversion modules with the runtime to import and export Office files.

Headless itself does not provide menus, toolbars, dialogs, mouse or keyboard interaction, screenshots, or printing. It does not automatically provide persistence, authentication, a collaboration server, or file conversion. `save()` returns a Univer snapshot; it does not write to a database or export XLSX, DOCX, or PDF. Screenshots and visual layout checks require a separate [rendering runtime](/ai/visual-inspection); a headless browser still runs the rendering layer.

Add infrastructure as needed: `@univerjs/network` and `@univerjs/rpc-node` provide networking and Node.js computation processes; `@univerjs-pro/license` handles license integration. `@univerjs-pro/collaboration`, `@univerjs-pro/collaboration-client`, and `@univerjs-pro/collaboration-client-node` can form a Headless collaboration client, not a collaboration server. Processing local snapshots independently does not require a collaboration service.

### Packages outside a content-only runtime

- `@univerjs/ui`, `@univerjs/design`, and product or feature `*-ui` packages, such as `@univerjs/sheets-ui`, `@univerjs/docs-ui`, and `@univerjs-pro/slides-ui`, provide UI, rendering integration, or interaction. Do not add them to a pure Node.js content-processing configuration.
- `@univerjs/sheets-find-replace` and `@univerjs/sheets-crosshair-highlight` depend on `@univerjs/sheets-ui` despite lacking a `-ui` suffix. Their names do not make them Headless plugins.
- The default `@univerjs/preset-sheets-core` and `@univerjs/preset-docs-core` presets register UI plugins. They are not Node.js Headless presets; use plugin mode to select content-layer dependencies explicitly.

**Treat `@univerjs/engine-render` separately.** Current Node.js examples register it to supply shared dependencies such as render management. Registering the plugin does not create a Canvas or mount an editor. It can appear in a Headless composition, but drawing, font measurement, and screenshot APIs still need a suitable rendering environment. This does not make every API in the package usable in pure Node.js.

**Facade is an operation API, not an environment adapter.** Import the required content plugins’ `/facade` extensions and register the plugins that implement those capabilities. UI extensions such as `@univerjs/ui/facade` and `@univerjs/sheets-ui/facade`, including menus, scrolling, and visual selection interactions, still require UI. Check plugin dependencies and the actual call path rather than relying on a package name or the presence of Facade APIs.

See the [Sheets Headless guide](/guides/sheets/getting-started/node) and [Docs Headless guide](/guides/docs/getting-started/node) for runnable plugin compositions.

## Immediate frontend calculation, versioned server calculation [#calculate-on-the-server-display-quickly-in-the-browser]

Both the frontend and server have formula engines. The frontend responds to editing; the server calculates a captured content revision when generating a snapshot or processing a file.

- **While editing:** the browser calculates affected formulas locally, optionally in a Worker, and displays results immediately. Collaboration records and synchronizes content changes.
- **When generating a snapshot:** the server’s snapshot policy triggers the save workflow. The server captures the content revision for this operation, calculates with `univer-rs`, then saves that revision’s content and results together.
- **When reopening:** the frontend reuses valid results in the snapshot, applies later changes, and continues calculating, reducing repeated full calculation.

<Mermaid chart={"flowchart LR\n    F[\"Frontend editing<br/>Immediate calculation\"]\n    C[\"Content synchronization<br/>Confirmed changes\"]\n    R[\"Rust calculation<br/>Content revision N\"]\n    S[\"Save snapshot<br/>saveSnapshot\"]\n    F <--> C\n    C -->|\"When generating a snapshot\"| R\n    R --> S"} />

**Content changes synchronize continuously. Server calculation runs as part of snapshot generation, with results saved for that content revision.**

Configure initial calculation to match the saved results:

- `WHEN_EMPTY`: reuse stored formula values and calculate only missing results.
- `NO_CALCULATION`: skip initial formula calculation when the application supplies the results.
- `FORCED`: recalculate all formulas when stored results need refreshing.

These options control initial loading. Subsequent editing continues to calculate in the frontend; the server calculates on demand when generating a versioned snapshot or processing files. See [formula configuration](/guides/sheets/features/core/formula), [collaboration](/server/collaboration/overview), and [file conversion](/overview/features/shared/file-conversion).

## Array formulas and spill results

Within the supported functions and formats, Rust follows Excel’s array-formula and spill semantics. It returns calculated values together with the anchor and spill range, including dynamic arrays and declared ranges for legacy array formulas.

For example, `=SEQUENCE(3,2)` in an empty `A1` produces:

| A | B |
| --- | --- |
| 1 | 2 |
| 3 | 4 |
| 5 | 6 |

The formula remains in `A1`; results occupy `A1:B3`. When an array shrinks, old spill values are cleared. A blocked spill reports `#SPILL!`. The browser, agent, and export pipeline can reuse the calculated snapshot.

See [formula support](/guides/sheets/features/core/formula) and [Excel array behavior](https://support.microsoft.com/en-us/excel/dynamic-array-formulas-and-spilled-array-behavior) for the corresponding function and range rules.

## Connect the runtime to an agent

Keep your existing model, conversation, and tool orchestration. AI SDK tools expose Office content operations to that agent:

1. Inspect structure and read the target content.
2. Apply Facade changes and run the required calculations in the headless runtime.
3. Wait for calculation and commit confirmation, then read back the updated state.
4. Check values and structure; add screenshots or layout checks when visual verification is needed.

Use [content operations](/ai/content-operations) and [visual inspection](/ai/visual-inspection) together. For human review, place edits in a [Worktree](/ai/worktree) before comparison and merge. [Univer CLI](/overview/examples/cli) demonstrates how to assemble these capabilities into an agent-facing application.
