Headless Univer is the Univer content runtime without the interactive editor UI. It shares content models, commands, calculation, and Facade APIs with the browser editor. An application can run it in Node.js to process content there, or in a browser for tasks that do not need a UI. Its capabilities depend on the registered product and feature plugins.

The JavaScript/TypeScript runtime described on this page and `univer-rs` are separate implementations. `univer-rs` supports server-side calculation and file conversion, and it participates in Headless workflows over the same snapshots.

## What Headless can do [#headless-capabilities]

- Read and modify content and structure. Create or load a Univer snapshot, use Facade APIs to read and edit cells, paragraphs, pages, graphical objects, or records, then save the updated snapshot. These operations support batch processing, data generation, content inspection, and agent automation.
- Run registered business logic. Formula calculation, sorting, filtering, validation, and pivot plugins are available, and applications can modify resources such as images, charts, shapes, and comments. The available operations depend on the registered product and feature plugins and their dependencies.
- Connect to other services. Add the Node.js collaboration client to load collaborative Units, submit changes, and wait for synchronization. Combine Server SDK conversion modules with the runtime to import and export Office files.

Headless does not provide the editor UI: no menus, toolbars, dialogs, mouse or keyboard interaction, screenshots, or printing. Persistence, authentication, a collaboration server, and file conversion are not included either. `save()` returns a Univer snapshot; it does not write to a database or export XLSX, DOCX, or PDF. Screenshots and visual layout checks require a separate [rendering runtime](/ai/visual-inspection), because a headless browser still runs the rendering layer.

## Which packages belong to Headless [#headless-packages]

Select the content packages that the application needs, then register the required product plugins and dependencies. Pro features also require their licenses to be configured.

### Content models

These packages provide instances, content models, commands, and basic content operations.

- `@univerjs/core`
- `@univerjs/sheets`
- `@univerjs/docs`

### Formulas and number formats

These packages provide formula execution, Sheet formula integration, and number formatting. Select the open-source or the Pro engine according to the required features.

- `@univerjs/engine-formula`
- `@univerjs/sheets-formula`
- `@univerjs/sheets-numfmt`
- `@univerjs-pro/engine-formula`

### Sheet data and rules

Sheet data and rule operations run without the panels or visual interaction that normally accompany them. Data validation also requires `@univerjs/data-validation`.

- `@univerjs/sheets-filter`
- `@univerjs/sheets-sort`
- `@univerjs/sheets-conditional-formatting`
- `@univerjs/sheets-data-validation`
- `@univerjs/sheets-table`
- `@univerjs/sheets-hyper-link`
- `@univerjs/sheets-note`

### Images, links, and comments

These packages add models, resources, and commands for images, links, and comments. Display, uploads, and external data sources are connected separately as needed.

- `@univerjs/drawing`
- `@univerjs/sheets-drawing`

- `@univerjs/docs-hyper-link`

### Other product models

These packages provide models and commands for the other products. `pdfs-editor` configures the PDF editor lifecycle and collaboration integration; the word editor in a package name does not imply a UI. Available APIs vary by product.

- `@univerjs-pro/slides`
- `@univerjs-pro/bases`
- `@univerjs-pro/boards`
- `@univerjs-pro/pdfs`
- `@univerjs-pro/pdfs-editor`

### Networking, computation processes, and collaboration

Add infrastructure only when it is required. `@univerjs/network` and `@univerjs/rpc-node` provide networking and Node.js computation processes, and `@univerjs-pro/license` handles license integration. `@univerjs-pro/collaboration`, `@univerjs-pro/collaboration-client`, and `@univerjs-pro/collaboration-client-node` together form a Headless collaboration client, not a collaboration server. Working with local snapshots does not require a collaboration service.

### Packages outside a content-only runtime

- `@univerjs/ui`, `@univerjs/design`, and the `*-ui` packages for a product or feature, such as `@univerjs/sheets-ui`, `@univerjs/docs-ui`, and `@univerjs-pro/slides-ui`, provide UI, rendering integration, or interaction. Do not add them to a Node.js configuration that only processes content.
- `@univerjs/sheets-find-replace` and `@univerjs/sheets-crosshair-highlight` have no `-ui` suffix but still depend on `@univerjs/sheets-ui`, so a package name alone does not imply that they are Headless plugins.
- The default `@univerjs/preset-sheets-core` and `@univerjs/preset-docs-core` presets register UI plugins and are not Node.js Headless presets. In that case, use plugin mode to select content-layer dependencies explicitly.

**`@univerjs/engine-render` requires separate consideration.** The current Node.js examples register it to supply shared dependencies such as render management. Registering the plugin does not create a Canvas or mount an editor. It can appear in a Headless composition, but drawing, font measurement, and screenshot APIs still need a suitable rendering environment. Therefore, not every API in the package is usable in pure Node.js.

**Facade is an operation API, not an environment adapter.** For each content plugin in use, import its `/facade` extension, and register the plugins that implement the required capabilities. UI extensions such as `@univerjs/ui/facade` and `@univerjs/sheets-ui/facade` still require UI, and so do the menus, scrolling, and visual selection interactions they provide. Examine the plugin dependencies and the actual call path rather than relying on a package name or the presence of Facade APIs.

Runnable plugin compositions appear in the [Sheets Headless guide](/guides/sheets/getting-started/node) and the [Docs Headless guide](/guides/docs/getting-started/node).

## Immediate frontend calculation, versioned server calculation [#calculate-on-the-server-display-quickly-in-the-browser]

Formula engines run in both the frontend and the server. The frontend responds as the user edits, and the server calculates a captured content revision when it generates a snapshot or processes a file.

- During editing, the browser calculates the affected formulas locally, optionally in a Worker, and displays the results immediately. The collaboration service records these content changes and synchronizes them.
- When a snapshot is generated, the server's snapshot policy starts the save workflow. The server captures the content revision for that operation, calculates it with `univer-rs`, and saves the content and results of that revision together.
- When the document is reopened, the frontend reuses the valid results in the snapshot, applies the subsequent changes, and continues calculating, which avoids a full recalculation.

<Mermaid chart={"flowchart LR\n    F[\"Frontend editing<br/>Immediate calculation\"]\n    C[\"Content synchronization<br/>Confirmed changes\"]\n    R[\"Rust calculation<br/>Content revision N\"]\n    S[\"Save snapshot<br/>saveSnapshot\"]\n    F <--> C\n    C -->|\"When generating a snapshot\"| R\n    R --> S"} />

**Content changes synchronize continuously. Server calculation runs as part of snapshot generation, and the results are saved for that content revision.**

On first load, the application configures how the initial calculation uses the saved results:

- `WHEN_EMPTY`: reuse stored formula values and calculate only missing results.
- `NO_CALCULATION`: skip initial formula calculation when the application supplies the results.
- `FORCED`: recalculate all formulas when stored results need refreshing.

These options govern initial loading only. After loading, editing continues to calculate in the frontend, and the server calculates on demand when it generates a versioned snapshot or processes files. See [formula configuration](/guides/sheets/features/core/formula), [collaboration](/server/collaboration/overview), and [file conversion](/overview/features/shared/file-conversion).

## Array formulas and spill results

Within the supported functions and formats, Rust follows the array-formula and spill semantics of Excel. It returns the calculated values together with the anchor and spill range, and it handles both dynamic arrays and the declared ranges of legacy array formulas.

For example, `=SEQUENCE(3,2)` in an empty `A1` produces:

| A | B |
| --- | --- |
| 1 | 2 |
| 3 | 4 |
| 5 | 6 |

The formula remains in `A1`, and the results occupy `A1:B3`. When the array shrinks, the previous spill values are cleared. When a spill is blocked, the result is `#SPILL!`. The browser, an agent, and the export pipeline can all reuse the calculated snapshot.

The corresponding function and range rules are in [formula support](/guides/sheets/features/core/formula) and [Excel array behavior](https://support.microsoft.com/en-us/excel/dynamic-array-formulas-and-spilled-array-behavior).

## Connect the runtime to an agent

Keep the existing model, conversation, and tool orchestration. AI SDK tools expose Office content operations to that agent:

1. Inspect the structure and read the target content.
2. Apply the Facade changes and run the required calculations in the headless runtime.
3. Wait for the calculation and the commit to be confirmed, then read the updated state back.
4. Check the values and structure, and add screenshots or layout checks when visual verification is required.

Use [content operations](/ai/content-operations) and [visual inspection](/ai/visual-inspection) together. When a person needs to review the work, place the edits in a [Worktree](/ai/worktree) first, then compare and merge them. [Univer CLI](/overview/examples/cli) demonstrates how to assemble these capabilities into an application that an agent can drive.
