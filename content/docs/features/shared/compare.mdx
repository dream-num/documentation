Compare reports what changed between two versions. It accepts two fully reconstructed Unit snapshots and returns semantic differences in cells, paragraphs, pages, or records. It supports history review, verification of Agent output, and inspection of a Worktree.

## Differences by product

| Product | Example comparison objects |
| --- | --- |
| Sheet | Worksheets, cell values and formulas, rows, columns, styles, and registered resources such as charts. |
| Doc | Paragraphs, text, styles, tables, blocks, and drawings. |
| Slide | Pages, elements, geometry, styles, layouts, and themes. |
| Relational Table | Tables, fields, records, and views. |
| Canvases | Pages, elements, and associated resources. |

Every change is an addition, a deletion, or an update. Temporary UI state such as zoom level and selection is not a content change. What Compare covers depends on the product adapter, and PDF is not included.

## How Snapshot and changesets contribute to Compare

A Snapshot stores the complete content state at a specific revision. A mutation describes a single content change, and a changeset groups mutations into an ordered commit. History stores versions and rebuilds them on demand. Compare describes the differences between two versions that have already been rebuilt.

To compare a history entry or a Worktree, load the base Snapshot and apply the subsequent changesets in order until the content reaches the target revision. Perform this reconstruction for each side, then pass both complete states to the product adapter. When the corresponding changesets are available, Compare aligns structural changes such as inserted or deleted rows and columns more accurately. When only the two complete states are provided, Compare still produces a Snapshot comparison.

Results follow the content model of each product: cells and rows or columns for Sheet, paragraphs for Doc, elements for Slide and Canvases, and fields and records for Relational Table. A temporary selection or zoom level is not a content change. Compare is read-only. Restoring a version and merging a Worktree are separate operations.

## Working with Server SDK and AI SDK

**Server SDK** supplies the Snapshots, the changesets, and the revision numbers, and it reconstructs the content to compare. An application passes both states and the history it has to Compare, receives structured differences, and presents a review interface on the web. See [history](/overview/features/shared/history) and [collaboration service extensions](/server/collaboration/extensions).

**AI SDK** loads and edits content in a Worktree and commits the Agent's result. An application can use the structured differences for Agent checks and further processing, while a person reviews the same changes visually and decides whether to merge them. See the [Agent Worktree workflow](/ai/worktree) and [content operations](/ai/content-operations).

All five examples use the same Northstar launch plan. We created and submitted a complete baseline, edited it in a Worktree, and then opened Compare to inspect the changes.

## Query and display results

Register the history comparison plugins and Facade extensions of the product, then call `compareUnitData()`. For repeated filtering and pagination, create a session with `prepareUnitComparison()` and call `query()`.

Display a summary first, then drill into worksheets, pages, or tables. Request change lists or full before/after values as needed. Default detail results are bounded, so the first page is not necessarily the complete diff. Check the diagnostics and coverage status before presenting results.

See the [Unit Comparison API](/reference/facade/unit-comparison), [version history](/overview/features/shared/history), and [Worktree](/overview/features/shared/worktree).
