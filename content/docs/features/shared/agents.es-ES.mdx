AI SDK expone los modelos de contenido de Univer, Facades y la colaboración como capacidades composables TypeScript. Un agente existente puede leer contenido, modificarlo, verificar el resultado y entregarlo para su revisión. La aplicación elige el modelo, el protocolo de herramienta y el método de orquestación.

## Conectar capacidades al Agent [#capabilities]

Los paquetes de capacidades devuelven resultados estructurados que la aplicación puede pasar a sus propias herramientas, servicios o CLI. Los paquetes opcionales `-command` exponen las mismas capacidades que los comandos nativos Commander. Ambos formularios operan en el modelo de contenido y sistema de comando compartido con el editor Web.

| Capacidad | Responsabilidad |
| --- | --- |
| Inspection | Lee estructura, rangos, párrafos y detalles de objetos para estrechar la tarea. |
| API Reference | Consulta las declaraciones de Facade agrupadas, sobrecargas, tipos y ejemplos fuera de línea. |
| Content Execution | Binds `workbook`, `doc` , `presentation` y `base` o `board` a una unidad específica y prepara el código para la ejecución. |
| Collaboration Runtime | Carga contenido, captura mutaciones, reconcilia cambios remotos y compromete explícitamente los cambios. |

## Cómo restaura el Runtime el estado editable [#runtime]

Un Collaboration Runtime permanece ligado a una unidad única para toda su vida. Durante la carga abre el backend proporcionado por la aplicación, lee un UnitData o un punto de control Snapshot, y vuelve a reproducir los cambios en la parte superior de ese punto de control. Luego cierra la brecha de revisión continua a la cabeza remota y, cuando se instala el módulo de fórmula, espera los últimos resultados de cálculo.

`fetch()` recupera los cambios y los valida. `pull()` concilia los cambios remotos con el estado pendiente local y pendiente a través de OT, luego aplica el resultado. El Runtime expone `baseRevision`, `knownHeadRevision`, `pendingMutationCount`, y `awaitingChangeset` para que la aplicación pueda evaluar el progreso.

## Localizar contenido antes de ejecutar [#inspection]

Proporcione el modelo con una visión general primero, luego consulta un ID estable o un selector preciso en lugar de enviar un Snapshot completo. La inspección cubre rangos de hoja, párrafos Doc, páginas de diapositivas, esquemas de tabla relacional, y objetos de Canvases. Una vista general de tabla relacional incluye la configuración de campo pero no registra valores o proyecciones de vista; leerlos a través de Facades cuando sea necesario.

`prepareContentExecutionProgram()` resuelve la fachada raíz del ID de unidad, independientemente de la selección actual del navegador, y rechaza una redeclaración de una unión inyectada. En modo de lectura, el Runtime bloquea las acciones de negocio que persistirían antes de ejecutar; en modo de escritura captura las mutaciones de la unidad objetivo. La creación y eliminación de unidad son operaciones separadas del ciclo de vida y se encuentran fuera de esta entrada de ejecución de unidad.

Cuando una API no está familiarizada, `find()` lista candidatos y `show()` imprime la declaración exacta junto con los tipos relacionados. La referencia se distribuye con el SDK, por lo que no requiere un motor de contenido ni la documentación en línea. Ver [operaciones de](/ai/content-operations) y el [Resumen del paquete](/ai/packages).

## Ejecución y persistencia confirmada [#commit]

`execute({ mode: 'write' })` modifica la unidad en vivo y acumula mutaciones pendientes. **No significa que el servidor haya guardado los cambios.** `commit()` crea un cambio con una identidad adjunta; el ACK debe coincidir con esa identidad, la carga útil y la revisión antes de que el cambio cuente como se confirma.

| Estado | Acción de la aplicación |
| --- | --- |
| `confirmed` / `nothing-to-commit` | Los cambios son confirmados, o no hubo nada que presentar. |
| `pull-required` | La revisión remota ha avanzado. Llame a `pull()` para reconciliarse, luego llame a `commit()` de nuevo. |
| `retry` / `unknown` | Mantenga el estado pendiente en el mismo Runtime y reingrese `commit()`. No vuelva a ejecutar el programa de edición. |
| `conflict` | Detenga escrituras y decida recuperación o recarga. |

Cuando el resultado de una presentación es incierto, el Runtime retiene `sid + reqId`, por lo que el backend puede confirmar el mismo cambio idempotentemente en lugar de duplicar las ediciones. El backend debe implementar este contrato de idempotencia. Un programa que lanza puede dejar las mutaciones que ya ha hecho en el lugar, así que inspeccionar el estado pendiente y decidir cómo recuperar. `execute()` no es una transacción que rodar.

El ejemplo a continuación acepta un tiempo de ejecución ya cargado y devuelve tanto el resultado de la ejecución como el resultado de compromiso. El callador maneja los estados arriba y cierra el tiempo de ejecución cuando su período de propiedad termina.

```ts
import { prepareContentExecutionProgram } from '@univer-cli/content-execution'
import type { UniverCollaborationRuntime } from '@univer-cli/univer-collaboration-runtime'

async function updateSales(runtime: UniverCollaborationRuntime) {
  const pulled = await runtime.pull()
  if (pulled.status === 'conflict') return pulled

  const code = prepareContentExecutionProgram({
    unitId: runtime.unitId,
    unitType: 'sheet',
    code: `
      const sheet = workbook.getSheetByName('Data');
      if (!sheet) throw new Error('Worksheet Data not found');
      sheet.getRange('A2:B2').setValues([
        [{ v: 'East', t: 1 }, { v: 128000, t: 2 }]
      ]);
      return sheet.getRange('A2:B2').getRawValues();
    `,
  })
  const execution = await runtime.execute({ mode: 'write', code })
  const commit = await runtime.commit()
  return { execution, commit }
}
```

## Reutilizar Runtimes en tareas frecuentes [#reuse]

Las tareas frecuentes pueden alquilar un Worker Runtime exclusivamente bajo una llave de propiedad de la aplicación. La creación fría es un solo vuelo por llave, los arrendamientos son puestos en orden FIFO, y diferentes claves pueden utilizar diferentes Trabajadores. `release()` devuelve la instancia, TTL/LRU desahucio reclama recursos ociosos, y `invalidate()` retira una instancia que ya no es confiable.

Una clave debe distinguir el backend, la Unidad y el Worktree. La piscina no verifica si dos conjuntos de entradas de inicialización son semánticamente compatibles. Un daemon puede mantener la piscina a través de llamadas CLI cortas, pero un Runtime reutilizado todavía requiere sincronización y confirmación de compromiso. La aplicación debe equilibrar el costo de arranque contra la memoria residente y cuenta de Worker; ver [Reutilización del tiempo de ejecución y daemon](/ai/runtime-architecture) .

## De la automatización a la revisión humana [#handoff]

Las capacidades se pueden combinar para la presentación de informes, la limpieza de datos, el llenado de plantillas o la generación de contenidos. El flujo localiza el objetivo, escribe a través de Facades, espera cualquier cálculo sobre el cual el resultado depende, y lee valores de espalda, texto y propiedades de objeto. [inspección visual](/overview/features/shared/visual-inspection) cuando la tarea lo requiera.

Para los flujos de trabajo de aprobación, el Agente trabaja en un [Worktree](/overview/features/shared/worktree). Se edita y verifica en rondas, y una persona entonces revisa el contenido Listo y decide si fusionarse. Seguimiento de la ejecución y comprometer resultados por Unidad, porque varios Runtimes juntos no forman una transacción atómica de documentos cruzados.

La aplicación posee identidad, autorización, integración de modelos, y el ciclo de vida de tarea. Leer y escribir restricciones imponen el límite alrededor de las operaciones de negocios, mientras procesan el aislamiento y los permisos de archivo o red para no confiar JavaScript seguir siendo la responsabilidad de la aplicación. Véase [Empezamos](/overview/get-started) y el [Univer CLI ejemplo](/overview/examples/cli).
