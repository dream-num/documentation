L'inspection visuelle convertit un modèle de contenu en images et en preuves de mise en page qui peuvent être examinées. Un agent vérifie d'abord les données et les formules, puis examine le texte rendu, les formes et les pages. Lorsqu'il trouve un problème, il corrige le contenu à travers une Facade et examine à nouveau l'état résultant.

## Trois sortes de preuves [#evidence]

| Preuve | Ce qu’elle vérifie |
| --- | --- |
| Relecture structurée | Valeurs brutes, formules et leurs résultats, et propriétés des paragraphes et des objets. |
| PNG | Le contenu qui est réellement visible, y compris le clipping, les graphiques, les couleurs et la composition globale. |
| Diagnostic de mise en page | Les règles, les ID d'objet, les limites et les emplacements d'émission dérivés du rendu, qui identifient l'objet à corriger. |

## Préparer état et dépendances [#state]

Capture d'écran et Layout Lint fonctionnant sur matérialisés UnitData. Ils ne se connectent pas à une cible distante, et ils n'interprètent pas les changements. `pull()`, attendre que le calcul se termine après une modification de formule, puis appeler `exportUnitData()`. Dans un Worktree, exporter le projet qui est destiné à l'inspection. Une demande peut enregistrer l'objectif, la révision, et la portée à côté du rapport, de sorte qu'un examen se réfère à un état connu.

Un serveur Snapshot n'inclut pas toutes les dépendances. Sources de la feuille de passe et de la table relationnelle via `formulaReferenceUnits`, et le contenu de l'enfant passe par `embeddedUnits`. La page Render matérialise les dépendances avant l'hôte, de sorte que les formules et les blocs se chargent avec leurs sources déjà en place. Les actifs d'image UUID peuvent être préparés avec `resolveUnitScreenshotImageAssets()` et un résolveur de l'application.

## Produire une image stable [#rendering]

<Mermaid chart={"flowchart LR\nA[\"État explicite<br/>UnitData + dépendances\"]\nB[\"Render Runtime<br/>Navigateur et protocole\"]\nC[\"Render Page<br/>Rendu natif Univer\"]\nD[\"Vérifier la disponibilité<br/>Calcul et image stable\"]\nE[\"PNG / faits de mise en page<br/>Agent et revue humaine\"]\nA --> B --> C --> D --> E"} />

`univer-render-runtime` héberge une page Render construite par l'application et démarre un navigateur à partir de Node.js. Les plugins de produit restaurent le contenu de cette page, et les deux côtés vérifient la version du protocole de page. Un Runtime exécute ses opérations par une seule file d'attente série, de sorte que le même Runtime peut être conservé à travers les tours d'inspection. Le propriétaire de l'Runtime appelle `close()` lorsque le travail est terminé.

La disponibilité dépend du produit. Formula-drived Shapes attend que les résultats laissent en suspens et, si nécessaire, jusqu'à ce que les pixels restent inchangés entre les images, de sorte qu'une animation transitoire n'est pas capturée. Relational Table attend pour les polices, le calcul, la table ou la vue active, et une mise en page stable DOM et Canvas. Un résultat de formule qui a laissé en attente peut toujours être une erreur, de sorte que sa valeur et son statut nécessitent une vérification.

L'implémentation actuelle hache l'hôte sérialisé UnitData, les sources de la formule et les enfants intégrés dans une clé de session de rendu. Le contenu modifié reçoit une nouvelle clé même lorsque l'ID de l'unité reste le même, de sorte qu'une vieille image n'est jamais réutilisée uniquement parce que l'ID correspond.

## Choisir le périmètre par produit [#scope]

| Produit | Périmètre et sortie |
| --- | --- |
| Sheet | Sélectionnez une feuille de travail et une plage A1 pour obtenir une région PNG. Sélectionnez des résultats importants explicitement. |
| Doc | Sélectionnez des pages, ou énumérez-les, pour obtenir une PNG par page. |
| Slide | Sélectionnez les numéros de page ou les identifiants de page basés sur 1 et ajoutez une feuille de contact. |
| Relational Table | Capturez l'atelier tel qu'il s'ouvre, y compris sa table active ou sa vue, depuis le navigateur DOM et Canvas. |
| Canvases | Utilisez les limites de contenu, ou un sélecteur d'Ids région / élément; les deux sont mutuellement exclusifs. Les preuves de padding et de mise en page sont facultatives. |

`unit-screenshot` retourne les octets d'image, les dimensions, l'identité de la page ou de la plage, et les noms de fichiers suggérés; l'application les enregistre. Le facteur d'échelle accepte 0.1–4. Définissez `maxPages` et le `maxPixels` par image. Le doublement de l'échelle produit environ quatre fois les pixels, inspectez donc le grand contenu dans les régions. PDF est à l'extérieur de ce point d'entrée de capture d'écran qui couvre les cinq produits ci-dessus.

## Partager les données entre capture et lint [#example]

`renderRuntime` est un Runtime de rendu existant, et `slideData` l'instantané préparé. Aucune des capacités n'écrit de fichiers. Pour la construction de page et le nettoyage des ressources, voir [Contrôle visuel AI SDK](/ai/visual-inspection).

```ts
import { createUnitScreenshot } from '@univer-cli/unit-screenshot'
import { createUnitLayoutLint } from '@univer-cli/unit-layout-lint'

const source = {
  unitType: 'slide' as const,
  unitData: slideData,
  formulaReferenceUnits,
}
const screenshot = createUnitScreenshot({ runtime: renderRuntime })
const lint = createUnitLayoutLint({ runtime: renderRuntime })

const capture = await screenshot.capture({
  ...source,
  target: { kind: 'slide-pages', pages: [1], scale: 2 },
})
const report = await lint.lint({ ...source, pages: [1] })
```

## Slide : localiser grâce à l’encre des glyphes [#slide-lint]

Layout Lint fonctionne à partir des faits de mise en page que produit le navigateur. La boîte `declared` d'un élément décrit sa géométrie dans le modèle, tandis que le texte `ink` décrit la zone que les glyphes couvrent réellement, cartographiée en coordonnées de page avec la mise en page, l'alignement et la rotation.

| Règle actuelle | Preuve examinée |
| --- | --- |
| `text-off-page` | L'encre de texte s'étend au-delà du bord de la page. |
| `text-escapes-container` | Le texte déborde visiblement un contenant opaque assorti qui est plus petit. |
| `text-overlaps-text` | Deux zones d'encre de texte se chevauchent considérablement. |

Un rapport comprend `coverage.pages` et `coverage.rules`. Chaque constatation porte `pageId`, l'élément `id` , le `text.ink` ainsi que les `overflow` pertinents, `container` ou `other` preuves . Un `fingerprint` stable simplifie la comparaison entre les cycles de réparation . Les résultats sont actuellement des avertissements et sont destinés à être lus à côté des captures d'écran . Une liste vide signifie seulement que la portée sélectionnée n'a déclenché aucune de ces règles .

## Canvases : examiner les tracés rendus [#board-analysis]

Canvas screenshots retourne également `layoutAnalysis`, qui contient les routes résolues par le navigateur, les problèmes, et un résumé. Ceci est séparé de `unit-layout-lint` qui ne gère que Slide. Les chemins de connecteurs automatiques peuvent être non résolus dans le modèle, donc inspecter les routes finales à travers les preuves avec `source: 'rendered'`.

Les diagnostics peuvent identifier des connecteurs qui croisent des éléments ou se croisent, en collision avec des têtes de flèche et des étiquettes contradictoires, et signaler les `connectorIds`, `elementIds` et `focusBounds` correspondants. Corriger les objets en cause, capturer une région ou un ensemble d'éléments, puis relire la toile entière. Ceci associe une préoccupation visuelle à une modification spécifique de Facade.

## Joindre les preuves à la livraison [#handoff]

<Mermaid chart={"flowchart LR\nA[\"Modifier via Facade\"]\nB[\"Relire données et formules\"]\nC[\"Capture + diagnostic\"]\nD[\"Corriger par ID\"]\nE[\"Vérifier le nouvel état\"]\nF[\"Revue / livraison\"]\nA --> B --> C --> D --> E --> F\nD --> B"} />

Conservez les résultats structurés, les informations sur la portée et la page, les images et les diagnostics ensemble. Une capture d'écran n'établit pas que les formules sont correctes, et le lint ne remplace pas le jugement visuel. Les interactions qui impliquent la barre d'outils, la mise au point et les popups nécessitent toujours une vérification dans l'éditeur Web, et les dépendances croisées doivent être chargées.

Exécutez ces vérifications avant un [Worktree](/overview/features/shared/worktree) est marqué Ready, de sorte que l'évaluateur puisse assortir les changements de contenu aux preuves. Voir [sans tête et calcul du serveur](/overview/features/shared/server-calculation) pour exécution et [Agents et automatisation](/overview/features/shared/agents) pour orchestrer.
