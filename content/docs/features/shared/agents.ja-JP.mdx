AI SDK は、Univerのコンテンツモデル、ファサード、およびコラボレーションを合成可能な TypeScript機能として公開しています。既存のエージェントは、コンテンツを読み、内容を変更したり、結果を検証したり、レビューのためにそれを渡すことができます。このアプリケーションは、モデル、ツールプロトコル、およびオーケストレーションの方法を選択します。

## 既存の Agent に接続する [#capabilities]

機能パッケージは、アプリケーションが独自のツール、サービス、またはCLIに渡すことができる構造の結果を返します。オプションの`-command`パッケージは、ネイティブCommanderコマンドと同じ機能を公開します。どちらのフォームも、Webエディタで共有されたコンテンツモデルとコマンドシステムで動作します。

| 機能 | 役割 |
| --- | --- |
| Inspection | 構造、範囲、段落、オブジェクトの詳細を読み込み、タスクを狭くします。 |
| API Reference | バンドルされたファサード宣言、オーバーロード、タイプ、および例をオフラインで囲みます。 |
| Content Execution | `workbook`、`doc`, `presentation`, `base`. または `board`を特定のユニットに結合し、実行するためのコードを用意します。 |
| Collaboration Runtime | コンテンツをロードし、ミューテーションをキャプチャし、リモートの変更を解除し、変更を明示的にコミットします。 |

## Runtime が編集可能な状態を復元する仕組み [#runtime]

Collaboration Runtimeは、その寿命全体にわたって単一のユニットにバインドされています。 ローディング中に、アプリケーションによって提供されるバックエンドを開き、UnitDataまたはスナップショットチェックポイントを読み、そのチェックポイントの上部にあるチェンジセットを再生します。 その後、リモートヘッドに継続的なリビジョンギャップを閉じ、式モジュールがインストールされると、最新の計算結果が待っています。

<Mermaid chart={"sequenceDiagram\nparticipant A as アプリのツール\nparticipant R as Runtime\nparticipant U as 内容エンジン\nparticipant B as 共同編集 backend\nA->>R: load\nR->>B: checkpoint と変更を取得\nR->>U: Unit と revision を復元\nA->>R: pull：リモート変更を取得\nR->>B: fetchChangesets\nB-->>R: changesets\nR->>U: OT で調整して適用\nA->>R: execute：Facade で編集\nR->>U: Facade\nU-->>R: mutation を生成\nNote over R: pending を保持\nA->>R: commit：changeset を送信\nR->>B: changeset\nB-->>R: ACK：識別子と revision を確認"} />

`fetch()`は変更を取り、それらを検証します。 `pull()` は、ローカルの保留状態と待ち受けた状態を OT を通して再構成し、その後、結果を適用します。 実行時間は、アプリケーションが進行状況を評価することができるように `baseRevision`、`knownHeadRevision`, `pendingMutationCount`および `awaitingChangeset`を暴露します。

## 対象を特定して Facade を実行する [#inspection]

モデルを概要で最初に提供し、完全なスナップショットを送信する代わりに安定したIDまたは精密なセレクタをクエリします。 検査は、シートの範囲、ドキュメント段落、スライドページ、リレーショナルテーブルのスキーマの概要、およびキャンバスオブジェクトをカバーします。 リレーショナルテーブルの概要には、フィールド構成が含まれているが、値やビューの予測を記録しません。 必要に応じて、ファサードを通してそれらを読みます。

`prepareContentExecutionProgram()`は、現在のブラウザ選択の独立して、ユニットIDからルートファサードを解決し、注入されたバインディングの再宣言を拒否します。 読み取りモードでは、ランタイムブロックは、実行前に持続するビジネスアクションをブロックします。 書き込みモードでは、ターゲットユニットのミューテーションをキャプチャします。 ユニット作成と処分は、この単一ユニットの実行エントリの外側にある別のライフサイクル操作と嘘です。

API が不慣れな場合、`find()` は候補リストをリストし、`show()`は関連するタイプとの完全な宣言をプリントします。参照は SDK で配布されるので、コンテンツエンジンやオンラインドキュメントも必要です。[コンテンツの操作](/ai/content-operations)と[パッケージの概要](/ai/packages)を参照してください。

## 実行と送信確認を区別する [#commit]

`execute({ mode: 'write' })`は、ライブユニットを変更し、終端の変異を蓄積します。 **サーバが変更を保存したという意味ではありません。** `commit()` は、添付されたアイデンティティでチェンジセットを作成します。 ACK は、そのアイデンティティ、ペイロード、および変更が確認される前のリビジョンに一致しなければなりません。

| 送信状態 | アプリケーションの対応 |
| --- | --- |
| `confirmed` / `nothing-to-commit` | 変更が確認されるか、提出することができませんでした。 |
| `pull-required` | リモートリビジョンが進んでいます。 `pull()` を呼び出して、再び `commit()`を呼び出します。 |
| `retry` / `unknown` | `commit()`と同じランタイムと再試行で待ち続ける状態を保ちます。編集プログラムを再実行しないでください。 |
| `conflict` | 書き込みを止め、復旧や再読み込みを判断する。 |

投稿の結果が不確実であるとき、ランタイムは`sid + reqId`を保持します。そのため、バックエンドは編集を複製するのではなく、同じチェンジセットが点在していることを確認することができます。バックエンドは、この点火契約を実装しなければなりません。投げるプログラムは、すでに行われているミューテーションを残すことができるので、保留状態を調べて、回復する方法を決定します。 `execute()`は、ロールバックするトランザクションではありません。

以下の例では、すでに読み込まれたシートランタイムを受け付け、実行結果とコミット結果の両方を返します。 呼び出し主は、上記のステータスを処理し、所有権期間が終了したときにランタイムを閉じます。

```ts
import { prepareContentExecutionProgram } from '@univer-cli/content-execution'
import type { UniverCollaborationRuntime } from '@univer-cli/univer-collaboration-runtime'

async function updateSales(runtime: UniverCollaborationRuntime) {
  const pulled = await runtime.pull()
  if (pulled.status === 'conflict') return pulled

  const code = prepareContentExecutionProgram({
    unitId: runtime.unitId,
    unitType: 'sheet',
    code: `
      const sheet = workbook.getSheetByName('Data');
      if (!sheet) throw new Error('Worksheet Data not found');
      sheet.getRange('A2:B2').setValues([
        [{ v: 'East', t: 1 }, { v: 128000, t: 2 }]
      ]);
      return sheet.getRange('A2:B2').getRawValues();
    `,
  })
  const execution = await runtime.execute({ mode: 'write', code })
  const commit = await runtime.commit()
  return { execution, commit }
}
```

## 頻繁なタスクで Runtime を再利用する [#reuse]

頻繁なタスクは、アプリケーションが所有するキーでのみワーカーのランタイムをリースすることができます。コールドクリエイションは、キーごとに単一フライトであり、リースはFIFOの注文でキューに入れられ、異なるキーは異なるワーカーを使うことができます。 `release()`は、インスタンスを返し、TTL/LRU evictionはアイドルリソースを返し、「`invalidate()`」はもはや信頼できないインスタンスを退職しました。

キーは、バックエンド、ユニット、およびWorktreeを区別する必要があります。プールは、初期化入力の2セットが分離的に対応しているかどうかを検証しません。デーモンは、短いCL呼び出しにプールを保持することができますが、再使用されたランタイムは同期とコミット確認を必要とします。アプリケーションは、既存のメモリとワーカーカウントに対するスタートアップコストをバランス良くする必要があります。 [ランタイムリユースとデーモン](/ai/runtime-architecture)を参照してください。

## 自動化から人によるレビューへ [#handoff]

レポート、データのクリーンアップ、テンプレートのフィリング、またはコンテンツの生成のために機能が組み合わすことができます。フローは、Facades を通して、ターゲットを探し、結果が依存する任意の計算を待って、バック値、テキスト、オブジェクトプロパティを読みます。タスクがそれを必要とするときに [ビジュアル検査](/overview/features/shared/visual-inspection) を追加します。

承認ワークフローでは、Agent は [Worktree](/overview/features/shared/worktree) で動作します。 これは、ラウンドで編集し、検証し、その人は、Ready コンテンツをレビューし、マージするかどうかを決定します。 複数の Runtimes がクロスドキュメント原子トランザクションを形成しないため、実行とコミットの結果を 1 単位で追跡します。

アプリケーションは、アイデンティティ、認可、モデル統合、およびタスクのライフサイクルを所有しています。 読書および書き込み制限は、プロセス分離とファイルや、JavaScriptが信頼できないためのネットワーク権限がアプリケーションの責任を保ちながら、ビジネス操作の境界を強制します。 [はじめる](/overview/get-started)と[Univer CLIの例](/overview/examples/cli)を参照してください。

## Skills によるコンテンツ生成と編集 [#skills]

既存の Agent が Office コンテンツに直接機能するようにするには、ファイルの位置に合ったアプリケーションから始めます。

- [CLIスキル](/overview/examples/cli#skills): ローカルオフィスファイルの作成、編集、およびチェックを行い、ビューアを開き、レビューを行います。
- [ワークスペーススキル](/overview/examples/workspace#skills): 接続されたスペース内のファイルで作業し、OfficeコンテンツとWeb Appsを生成し、コラボレーションとレビューのために手を離します。
