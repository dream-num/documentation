**Office Lab** 将仓库式协作引入日常产品工作。它基于 **[Univer Office SDK](/overview)** 构建，运行于 Workspace 的 Repo 模式，需求文档、电子表格、交互原型、Issue 与 PR 共同位于同一个项目。团队所有成员都可以看到提出了哪些需求、发生了哪些变更，以及哪些内容已经可以使用。

以团队邀请流程为例：产品经理和研发共同推进这套流程。两人各自的 Agent 负责准备并检查材料，由人讨论流程应有的行为、审阅改动并决定交付内容。随着讨论推进，工作上下文始终保留在项目中。

## 一个项目，两种专业视角 [#case-study]

**Team Invitations** 案例始于一个简单且熟悉的问题：邀请一位同事、选择一个角色，并确认邀请是否成功。而重复邀请同一个待加入邮箱，则成为连接原型、验收标准、埋点与排期的改进点。

| 角色 | 自选 Agent | 负责的工作 |
| --- | --- | --- |
| Maya · 产品经理 | 例如 Codex | 定义体验、需求、验收标准与埋点方案，并审阅最终结果。 |
| Alex · 研发 | 例如 Claude Code | 检查需求与原型，提出 Issue，准备修改并验证行为。 |

| 项目资料 | 在协作中起到的作用 |
| --- | --- |
| Product brief · 文档 | 产品目标、邀请规则、验收标准与发布条件。 |
| Tracking plan · 文档 | 埋点的触发时机、属性与统计口径。 |
| Event catalog · 表格 | 事件、负责人与就绪状态的结构化清单。 |
| Delivery schedule · 表格 | 工作事项、负责人、日期、进度与预估。 |
| Invite Prototype / Team Access Console · Web App | 可直接测试的邀请表单。 |

## 浏览 Repo，把工作资料放在一起 [#repository]

在 Repo 模式下打开团队 Space。**Code** 汇集可编辑的文档与应用文件，你可以搜索、预览文件，并在返回项目时保持上下文。Issues、Pull requests、Pages 与 Settings 都位于各自相关资料的旁边。

Repo 模式是同一个 Workspace Space 的另一种视图，沿用该 Space 的内容与权限。项目首页还可以预览选定的 Web App，因此打开项目即可同时阅读和使用内容。

## 把发现的问题变成可执行的 Issue [#issues]

Alex 试用原型时发现，重复邀请路径不够清晰。**Prevent duplicate invitations** 这个 Issue 记录了期望的提示信息、被拦截邀请对应的事件，以及 QA 的后续检查。关联文件将需求文档、埋点方案、事件表与排期引入讨论。

描述、评论、负责人与标签共同说明下一步行动。Issue 属于团队 Space。Agent 可以通过 Workspace CLI 读取同一个任务及其关联资料，然后提出具体方案。反馈保留在 Issue 中，或写在对应的文档上。

![把发现的问题变成可执行的 Issue](/assets/examples/office-lab/cloud-issue.png)

## 通过 PR 提出一组可审阅的修改 [#pull-requests]

PR 将 Workspace Worktree 变为可供审阅的提案。创建任务草稿，加入需要修改的现有文档，完成修改后标记为 Ready。提案包含独立的标题、摘要、作者、状态与变更文件列表；草稿修订期间，共享内容仍然可读可用。

截图中的 PR 在事件表中添加了 `invite_duplicate_blocked`，并延长了排期中的 QA。摘要引用了 Issue #1。产品与研发可以分别维护草稿，向有权限的审阅者开放，并基于同一份源资料互相检查工作。

![通过 PR 提出一组可审阅的修改](/assets/examples/office-lab/cloud-pull-request.png)

## 用 Worktree 与 Compare 审阅内容 [#review]

先查看摘要，再打开 **Files changed**。**View** 以只读方式展示变更内容；**Compare** 将正式版本与提议的修订并排展示，并提供可逐项定位的变更列表。事件名称、触发条件、负责人与排期影响都可以在原生 Office 内容中检查。

[Worktree](/overview/features/shared/worktree) 隔离当前任务的改动，[内容比较](/overview/features/shared/compare) 通过内容模型、Snapshot 与 Changeset 展示差异。有权限的人员可以要求修订，也可以确认合入。截图中的 PR 涉及两个文件，仍处于 Ready 状态，尚未合入。

![用 Worktree 与 Compare 审阅内容](/assets/examples/office-lab/cloud-compare.png)

### 把交付影响也放进同一次审阅 [#delivery-plan]

同一个 PR 将 Usability and QA 从 11 月 9 日调整到 11 月 10 日，并将预估从 2 天提高到 3 天。将负责人、日期、状态与事件改动放在一起检查，验收决定才能覆盖上线所需的工作。

## 生成、发布和管理 Web App [#web-apps]

原型是一个可运行的 HTML View。在 **Pages** 中可以找到项目已发布的 Web App，可以访问页面、复制地址，或将页面设为首页预览。所选默认页面是当前浏览器的偏好设置。文件组织与访问权限仍由 Workspace 管理。

邀请原型后来发展为 **Team Access Console**，在同一个页面中提供成员与角色目录、状态筛选、搜索、邀请与取消、最近活动、验收标准与会话内事件计数。添加一个示例邮箱时，列表与待处理数量都会更新，重复邀请会被阻止。数据仅保存在内存中，不发送邮件，也不发起分析请求。产品经理可以测试这些行为，并将发现的问题转为 Issue。

原生 Office 内容的改动通过 Worktree 审阅与合入完成。HTML View 的发布有独立的保存与授权流程，因此本示例将原型与待审阅的文档 PR 分开发布。要将 Web App 接入 Office 实时数据，可参阅实验性的[双向绑定](/overview/features/shared/binding)。

## 让团队协作有清晰的边界 [#team-settings]

**Settings** 汇集项目名称、描述、可见性、成员管理与回收站。拥有者和管理员负责组织访问权限；编辑、审阅与合入均遵循当前用户的有效权限，项目链接同样遵循这些权限。

交付决定应当保持明确。产品经理检查体验与验收标准，研发检查实现与埋点，最后由有权限的人员合入 Office 改动、验证已发布的原型，并在工作完成后关闭 Issue。

## 体验 Office Lab [#quick-start]

1. 登录[云端 Workspace](https://space.univer.ai)，或打开[私有部署](/overview/examples/workspace#self-host)，并创建或打开一个**团队 Space**。
2. 打开 **Application settings → Page theme → Repository (experimental)**。此操作仅改变同一个 Space 的视图，偏好只保存在当前浏览器中。
3. 在 **Code** 中浏览文档，在 **Issues** 中跟进工作，在 **Pull requests** 中审阅改动，在 **Pages** 中打开已发布的 Web App。

![将团队 Space 切换到 Repository 模式，再浏览文档、Issue、PR 和 Web App](/assets/examples/office-lab/cloud-office-lab-tour.gif)

要使用自己的 Agent，请按照 [Workspace CLI 接入说明](/overview/examples/workspace#cli-start)完成配置。每个 Agent 使用其所属用户已授权的账号。下面的任务提供了一个可复现的流程。

## 基于同一套 SDK 与 Skills 继续构建 [#skills]

双方的 Agent 都可以使用同一套与版本匹配的 Workspace CLI Skills：`core` 用于发现与 Worktree 操作，`doc` 与 `sheet` 用于需求与计划，`html-view` 用于原型。每个 Agent 都可以读取对方有权访问的资料与 Issue 反馈；最终交付决定仍由人作出。

Web SDK 提供内容模型、编辑器与 Headless 操作，Server SDK 支持协同、版本与 Worktree，AI SDK 提供内容操作与检查。Workspace 在此基础上提供项目、身份、Issue、Repo 视图与发布流程。这套组合可用于构建产品实验室、研究空间或团队内部交付工作台。
