**Office Lab**은 **[Univer Office SDK](/docs/overview)**와 Workspace Repo 모드로 구성한 제품·개발 협업 사례입니다. 요구사항 문서, 스프레드시트, 동작하는 프로토타입, Issue와 PR을 같은 프로젝트에 모아 요청과 변경, 결과를 함께 살펴봅니다.

제품 관리자와 개발자는 각자 익숙한 Agent로 자료를 준비하고 확인합니다. 사람은 사용자 경험을 논의하고 변경을 검토하며 최종 전달을 결정합니다.

[하나의 프로젝트, 두 가지 관점](#case-study) · [발견을 실행 가능한 Issue로 만들기](#issues) · [Worktree와 Compare로 내용 검토하기](#review) · [Web App 생성·게시·관리](#web-apps) · [자신의 Agent로 체험하기](#quick-start)

이미지는 실제 로컬 Workspace를 Desktop 브라우저 패널에서 촬영한 가상의 영어 사례입니다. 두 Agent의 역할 분담은 따라 할 수 있는 협업 제안입니다.

## Repo에서 작업 자료 살펴보기 [#repository]

팀 Space를 Repo 모드로 열면 **Code**에서 편집 가능한 문서와 앱 파일을 찾고 미리 볼 수 있습니다. 자료 옆에 Issues, Pull requests, Pages, Settings가 있어 같은 맥락에서 협업합니다.

Repo는 기존 Space의 다른 보기이며 콘텐츠와 권한을 그대로 사용합니다. 선택한 Web App을 프로젝트 홈에 표시해 바로 체험할 수도 있습니다.

![Repo에서 작업 자료 살펴보기](/assets/examples/office-lab/repository.png)

## 발견을 실행 가능한 Issue로 만들기 [#issues]

Alex는 중복 초대 안내가 불명확함을 발견하고 **Prevent duplicate invitations**에 기대 메시지, 차단 이벤트와 QA 작업을 기록합니다. 요구사항, 측정 계획, 이벤트 표와 일정을 연결합니다.

설명, 댓글, 담당자와 레이블로 다음 행동을 명확히 합니다. Issue는 팀 Space 기능이며 Agent도 Workspace CLI로 같은 작업과 자료를 읽습니다. 피드백은 Issue나 관련 문서 댓글에 남깁니다.

![발견을 실행 가능한 Issue로 만들기](/assets/examples/office-lab/issue.png)

## PR로 변경 제안하기 [#pull-requests]

PR은 Workspace Worktree를 검토할 수 있는 제안으로 표시합니다. 작업 초안에 기존 문서를 추가하고 수정한 뒤 Ready로 표시합니다. 제목, 요약, 작성자, 상태와 변경 파일을 확인하며 공유 콘텐츠는 계속 사용할 수 있습니다.

화면의 PR은 이벤트 표에 `invite_duplicate_blocked`를 추가하고 QA 일정을 조정하며 요약에서 Issue #1을 참조합니다. 각 담당자는 별도 초안에서 작업하고 권한 있는 검토자에게 공개해 같은 자료를 기준으로 결과를 확인할 수 있습니다.

![PR로 변경 제안하기](/assets/examples/office-lab/pull-request.png)

## Worktree와 Compare로 내용 검토하기 [#review]

요약을 읽고 **Files changed**를 엽니다. **View**는 결과를 읽기 전용으로 보여 주며, **Compare**는 공식 버전과 제안 버전을 나란히 표시하고 변경 목록에서 해당 위치로 이동합니다.

[Worktree](/docs/features/shared/worktree)가 작업을 분리하고 [Compare](/docs/features/shared/compare)는 콘텐츠 모델, Snapshot과 Changeset을 사용합니다. 권한 있는 사람이 수정을 요청하거나 병합을 결정합니다. 화면의 두 파일 PR은 Ready 상태로 병합하지 않았습니다.

![Worktree와 Compare로 내용 검토하기](/assets/examples/office-lab/compare.png)

## Web App 생성·게시·관리 [#web-apps]

**Pages**에서 게시된 Web App을 찾고, 열고, 주소를 복사하거나 홈 미리보기를 선택합니다. 기본 페이지 선택은 현재 브라우저에만 적용되며 파일과 접근은 Workspace가 관리합니다.

초대 양식은 실제로 동작합니다. 새 예시 이메일은 대기 수를 늘리고 중복 이메일은 안내를 표시합니다. 메모리의 샘플 데이터만 사용하며 이메일을 보내지 않습니다. 제품 담당자가 직접 행동을 확인하고 Issue로 이어갈 수 있습니다.

Office 변경은 Worktree 검토와 병합을 거치며 HTML View는 별도의 저장·게시 승인 흐름을 사용합니다. 예시 프로토타입은 대기 중인 문서 PR과 별도로 게시되었습니다. 실제 Office 데이터 연결은 실험적 [Binding](/docs/features/shared/binding)을 참고하세요.

## 팀 협업의 경계 정하기 [#team-settings]

**Settings**는 이름, 설명, 공개 범위, 협업자와 휴지통을 제공합니다. 소유자와 관리자가 접근을 정리하고 편집, 검토, 병합에는 현재 사용자의 유효 권한이 적용됩니다.

제품 담당자는 경험과 승인 기준을, 개발자는 구현과 측정을 확인합니다. 권한 있는 사람이 Office 변경을 병합하고 게시된 원형을 확인한 뒤 완료된 Issue를 닫습니다.

## 자신의 Agent로 체험하기 [#quick-start]

[클라우드](https://space.univer.ai)나 [자체 배포](/docs/examples/workspace#self-host)에 [Workspace CLI](/docs/examples/workspace#cli-start)로 Agent를 연결합니다. 앱 설정에서 **Repository(실험적)**를 선택하고 팀 Space를 엽니다. 각 Agent는 해당 사용자가 승인한 계정으로 작업합니다. 아래는 직접 따라 할 수 있는 역할 분담입니다.

## 같은 SDK와 Skills로 확장하기 [#skills]

양쪽은 버전에 맞는 CLI Skills를 사용합니다. `core`는 탐색과 Worktree, `doc`·`sheet`는 요구사항과 계획, `html-view`는 원형을 다룹니다. Agent는 접근 가능한 상대 자료와 Issue 피드백을 읽고 사람은 최종 결정을 내립니다.

Web SDK는 콘텐츠 모델, 편집기와 Headless를, Server SDK는 협업·버전·Worktree를, AI SDK는 조작과 검증을 제공합니다. Workspace는 프로젝트, ID, Issue, Repo와 게시를 구성합니다. 이를 재사용해 제품 연구 공간이나 내부 업무 허브를 만들 수 있습니다.
