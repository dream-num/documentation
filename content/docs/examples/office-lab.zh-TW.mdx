**Office Lab** 將倉庫式協作引入日常產品工作。它基於 **[Univer Office SDK](/overview)** 建置，執行於 Workspace 的 Repo 模式，需求文件、電子表格、互動原型、Issue 與 PR 共同位於同一個專案。團隊所有成員都可以看到提出了哪些需求、發生了哪些變更，以及哪些內容已經可以使用。

以團隊邀請流程為例：產品經理和研發共同推進這套流程。兩人各自的 Agent 負責準備並檢查材料，由人討論流程應有的行為、審閱改動並決定交付內容。隨著討論推進，工作上下文始終保留在專案中。

## 一個專案，兩種專業視角 [#case-study]

**Team Invitations** 案例始於一個簡單且熟悉的問題：邀請一位同事、選擇一個角色，並確認邀請是否成功。而重複邀請同一個待加入郵箱，則成為連線原型、驗收標準、埋點與排期的改進點。

## 瀏覽 Repo，集中工作資料 [#repository]

在 Repo 模式下開啟團隊 Space。**Code** 彙集可編輯的文件與應用檔案，你可以搜尋、預覽檔案，並在返回專案時保持上下文。Issues、Pull requests、Pages 與 Settings 都位於各自相關資料的旁邊。

Repo 模式是同一個 Workspace Space 的另一種檢視，沿用該 Space 的內容與權限。專案首頁還可以預覽選定的 Web App，因此開啟專案即可同時閱讀和使用內容。

## 把發現變成可執行的 Issue [#issues]

Alex 試用原型時發現，重複邀請路徑不夠清晰。**Prevent duplicate invitations** 這個 Issue 記錄了期望的提示資訊、被攔截邀請對應的事件，以及 QA 的後續檢查。關聯檔案將需求文件、埋點方案、事件表與排期引入討論。

描述、評論、負責人與標籤共同說明下一步行動。Issue 屬於團隊 Space。Agent 可以透過 Workspace CLI 讀取同一個任務及其關聯資料，然後提出具體方案。反饋保留在 Issue 中，或寫在對應的文件上。

![把發現變成可執行的 Issue](/assets/examples/office-lab/cloud-issue.png)

## 透過 PR 提出可審閱的修改 [#pull-requests]

PR 將 Workspace Worktree 變為可供審閱的提案。建立任務草稿，加入需要修改的現有文件，完成修改後標記為 Ready。提案包含獨立的標題、摘要、作者、狀態與變更檔案列表；草稿修訂期間，共享內容仍然可讀可用。

截圖中的 PR 在事件表中新增了 `invite_duplicate_blocked`，並延長了排期中的 QA。摘要引用了 Issue #1。產品與研發可以分別維護草稿，向有權限的審閱者開放，並基於同一份源資料互相檢查工作。

![透過 PR 提出可審閱的修改](/assets/examples/office-lab/cloud-pull-request.png)

## 用 Worktree 與 Compare 審閱內容 [#review]

先檢視摘要，再開啟 **Files changed**。**View** 以只讀方式展示變更內容；**Compare** 將正式版本與提議的修訂並排展示，並提供可逐項定位的變更列表。事件名稱、觸發條件、負責人與排期影響都可以在原生 Office 內容中檢查。

[Worktree](/overview/features/shared/worktree) 隔離當前任務的改動，[內容比較](/overview/features/shared/compare) 透過內容模型、Snapshot 與 Changeset 展示差異。有權限的人員可以要求修訂，也可以確認合入。截圖中的 PR 涉及兩個檔案，仍處於 Ready 狀態，尚未合入。

![用 Worktree 與 Compare 審閱內容](/assets/examples/office-lab/cloud-compare.png)

### 把交付影響放進同一次審閱 [#delivery-plan]

同一個 PR 將 Usability and QA 從 11 月 9 日調整到 11 月 10 日，並將預估從 2 天提高到 3 天。將負責人、日期、狀態與事件改動放在一起檢查，驗收決定才能覆蓋上線所需的工作。

## 產生、發布與管理 Web App [#web-apps]

原型是一個可執行的 HTML View。在 **Pages** 中可以找到專案已釋出的 Web App，可以訪問頁面、複製地址，或將頁面設為首頁預覽。所選預設頁面是當前瀏覽器的偏好設定。檔案組織與訪問權限仍由 Workspace 管理。

邀請原型後來發展為 **Team Access Console**，在同一個頁面中提供成員與角色目錄、狀態篩選、搜尋、邀請與取消、最近活動、驗收標準與會話內事件計數。新增一個範例郵箱時，列表與待處理數量都會更新，重複邀請會被阻止。資料僅儲存在記憶體中，不傳送郵件，也不發起分析請求。產品經理可以測試這些行為，並將發現的問題轉為 Issue。

原生 Office 內容的改動透過 Worktree 審閱與合入完成。HTML View 的釋出有獨立的儲存與授權流程，因此本範例將原型與待審閱的文件 PR 分開發布。要將 Web App 接入 Office 即時資料，可參閱實驗性的[雙向繫結](/overview/features/shared/binding)。

## 為團隊建立清楚的協作邊界 [#team-settings]

**Settings** 彙集專案名稱、描述、可見性、成員管理與回收站。擁有者和管理員負責組織訪問權限；編輯、審閱與合入均遵循當前使用者的有效權限，專案連結同樣遵循這些權限。

交付決定應當保持明確。產品經理檢查體驗與驗收標準，研發檢查實現與埋點，最後由有權限的人員合入 Office 改動、驗證已釋出的原型，並在工作完成後關閉 Issue。

## 體驗 Office Lab [#quick-start]

1. 登入[雲端 Workspace](https://space.univer.ai)，或開啟[私有部署](/overview/examples/workspace#self-host)，並建立或開啟一個**團隊 Space**。
2. 開啟 **Application settings → Page theme → Repository (experimental)**。此操作僅改變同一個 Space 的檢視，偏好只儲存在當前瀏覽器中。
3. 在 **Code** 中瀏覽文件，在 **Issues** 中跟進工作，在 **Pull requests** 中審閱改動，在 **Pages** 中開啟已釋出的 Web App。

![將團隊 Space 切換至 Repository 模式，再瀏覽文件、Issue、PR 與 Web App](/assets/examples/office-lab/cloud-office-lab-tour.gif)

要使用自己的 Agent，請按照 [Workspace CLI 接入說明](/overview/examples/workspace#cli-start)完成配置。每個 Agent 使用其所屬使用者已授權的賬號。下面的任務提供了一個可復現的流程。

## 以同一套 SDK 與 Skills 繼續建構 [#skills]

雙方的 Agent 都可以使用同一套與版本匹配的 Workspace CLI Skills：`core` 用於發現與 Worktree 操作，`doc` 與 `sheet` 用於需求與計劃，`html-view` 用於原型。每個 Agent 都可以讀取對方有權訪問的資料與 Issue 反饋；最終交付決定仍由人作出。

Web SDK 提供內容模型、編輯器與 Headless 操作，Server SDK 支援協同、版本與 Worktree，AI SDK 提供內容操作與檢查。Workspace 在此基礎上提供專案、身分、Issue、Repo 檢視與釋出流程。這套組合可用於建置產品實驗室、研究空間或團隊內部交付工作臺。
