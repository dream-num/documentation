**Office Lab** applies the repository workflow to everyday product work. It is built on the **[Univer Office SDK](/overview)** and runs in Workspace’s Repo mode, where requirements, spreadsheets, interactive prototypes, Issues and pull requests share one project. Every team member can see what was requested, what changed, and what is ready to use.

Consider a product manager and an engineer developing a team invitation flow. Their agents prepare and inspect the material, and the people involved discuss how the flow should behave, review the changes, and decide what to deliver. The working context remains with the project as the conversation develops.

## Browse the repository and its working material [#repository]

Open a Team Space in Repo mode. **Code** collects the editable documents and application files. You can search, preview a file, and return to the project without losing your place. Issues, Pull requests, Pages, and Settings appear next to the material they concern.

Repo mode is another view of the same Workspace Space and uses the content and permissions of that Space. The repository homepage can also preview a selected Web App, so a project opens with content that the team can both read and use.

## Turn a finding into an actionable Issue [#issues]

Alex tries the prototype and finds the duplicate-invitation path unclear. **Prevent duplicate invitations** records the expected message, the blocked-invite event, and the QA follow-up. Linked files bring the product brief, tracking plan, event catalog, and schedule into the discussion.

Descriptions, comments, assignees, and labels make the next action clear. Issues belong to Team Spaces. An agent can use Workspace CLI to read the same task and its linked material, then return with a concrete proposal. Feedback stays in the Issue or on the document it concerns.

![Turn a finding into an actionable Issue](/assets/examples/office-lab/cloud-issue.png)

## Propose a change through a pull request [#pull-requests]

A PR turns a Workspace Worktree into a proposal that others can review. Create a task draft, add the existing documents it requires, make the changes, and mark the draft Ready. The proposal has its own title, summary, author, state, and changed-file list. Shared content remains available while the draft is revised.

The PR in the screenshot adds `invite_duplicate_blocked` to the event catalog and extends QA in the delivery schedule. Its summary references Issue #1. Product and engineering can work in separate drafts, open them to reviewers with permission, and check each other’s work against the same source material.

![Propose a change through a pull request](/assets/examples/office-lab/cloud-pull-request.png)

## Review the content with Worktree and Compare [#review]

Start with the summary, then open **Files changed**. **View** opens the changed content as a read-only review. **Compare** places the official version next to the proposed revision and provides a change list that you can navigate. You can inspect the event name, trigger, owner, and scheduling impact in their native Office context.

[Worktree](/overview/features/shared/worktree) isolates the changes of the task, and [Compare](/overview/features/shared/compare) exposes differences through the content model, snapshots, and changesets. A person can request a revision or confirm the merge when authorized. In the captured example, the two-file PR remains Ready and unmerged.

![Review the content with Worktree and Compare](/assets/examples/office-lab/cloud-compare.png)

### Review the delivery impact too [#delivery-plan]

The same PR moves Usability and QA from November 9 to November 10 and raises the estimate from two to three days. Check the owner, dates, and status next to the event change, so that the acceptance decision covers the work required to ship the change.

## Generate, publish and manage the Web App [#web-apps]

The prototype is a live HTML View. Open **Pages** to find the Web Apps published by the project, then visit one, copy its address, or set it as the homepage preview. The default page you select is a preference of the current browser. File organization and access remain with Workspace.

The invitation prototype becomes **Team Access Console**, which provides a member and role directory, status filters, search, invitation and cancellation, recent activity, acceptance criteria, and session event counters on a single page. Adding a sample email updates both the list and the pending count, and duplicate invitations are blocked. Data stays in memory, with no email or analytics requests. A product manager can test the behavior and turn a finding into an Issue.

Native Office changes go through Worktree review and merge. HTML View publication has its own save and authorization flow, so this example publishes the prototype separately from the pending document PR. To connect a Web App to live Office data, see [Binding](/overview/features/shared/binding), which is experimental.

## Give the team a clear collaboration boundary [#team-settings]

**Settings** collects the repository name, description, and visibility together with collaborator management and Trash. Owners and administrators organize access. Editing, reviewing, and merging follow the effective permissions of the current user, and a project link respects those permissions as well.

The release decision should remain explicit. The product manager checks the experience and the acceptance criteria, engineering checks the implementation and measurement, and an authorized person merges the Office changes, verifies the published prototype, and closes the Issue when the work is complete.

## Try Office Lab [#quick-start]

1. Sign in to the [cloud Workspace](https://space.univer.ai), or open your [private deployment](/overview/examples/workspace#self-host). Create or open a **Team Space**.
2. Open **Application settings → Page theme → Repository (experimental)**. This changes the view of the same Space, and the preference is saved only in this browser.
3. Browse documents in **Code**, follow work in **Issues**, review changes in **Pull requests**, and open published Web Apps in **Pages**.

![Switch a Team Space to Repository mode, then explore documents, an Issue, a PR and a Web App](/assets/examples/office-lab/cloud-office-lab-tour.gif)

To work with your own agent, follow the [Workspace CLI setup](/overview/examples/workspace#cli-start). Each agent uses the authorized account of its user. The tasks below provide a workflow that you can reproduce.

## Build on the same SDK and Skills [#skills]

Both agents can use the same version-matched Workspace CLI Skills: `core` for discovery and Worktrees, `doc` and `sheet` for requirements and plans, and `html-view` for the prototype. Each agent can read the material and Issue feedback that the other can access. People retain the final delivery decision.

Web SDK supplies the content models, editors, and Headless operations, Server SDK supports collaboration, versions, and Worktrees, and AI SDK provides content operations and inspection. Workspace adds the project, identity, Issues, repository views, and publishing workflow. That combination can support a product lab, a research workspace, or an internal delivery hub.
