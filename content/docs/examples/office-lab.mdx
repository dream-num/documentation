**Office Lab** brings the repository workflow to everyday product work. Built on **[Univer Office SDK](/docs/overview)** through Workspace’s Repo mode, it puts requirements, spreadsheets, interactive prototypes, Issues and pull requests into one shared project. A teammate can see what was requested, what changed, and what is ready to use.

Picture a product manager and an engineer shaping a team invitation flow. Their agents prepare and inspect the material; the people discuss behavior, review the changes and decide what to deliver. The working context stays with the project as the conversation moves forward.

## Browse the repository and its working material [#repository]

Open the Team Space in Repo mode. **Code** brings the editable documents and application files together; search, preview a file, or return to the project without losing its context. Issues, Pull requests, Pages and Settings are next to the material they concern.

Repo mode is another view of the same Workspace Space, using its content and permissions. The repository homepage can also preview a selected Web App, so the project opens with something the team can use as well as read.

![Browse the repository and its working material](/assets/examples/office-lab/repository.png)

## Turn a finding into an actionable Issue [#issues]

Alex tries the prototype and identifies an unclear duplicate-invitation path. **Prevent duplicate invitations** records the expected message, the blocked-invite event and the QA follow-up. Linked files bring the product brief, tracking plan, event catalog and schedule into the discussion.

Use descriptions, comments, assignees and labels to make the next action clear. Issues belong to Team Spaces. An agent can read the same task and its linked material through Workspace CLI, then return with a concrete proposal. Feedback stays in the Issue or on the relevant document.

![Turn a finding into an actionable Issue](/assets/examples/office-lab/issue.png)

## Propose a change through a pull request [#pull-requests]

A PR presents a Workspace Worktree as a reviewable proposal. Create a task draft, add the existing documents it needs, make the changes and mark it Ready. The proposal has its own title, summary, author, state and changed-file list; shared content remains available while the draft is refined.

The captured PR adds `invite_duplicate_blocked` to the event catalog and extends QA in the delivery schedule. Its summary references Issue #1. Product and engineering can work in separate drafts, make them visible to permitted reviewers and use the same source material to check each other’s work.

![Propose a change through a pull request](/assets/examples/office-lab/pull-request.png)

## Review the content with Worktree and Compare [#review]

Start with the summary, then open **Files changed**. **View** shows the editable-content result in a read-only review; **Compare** shows the official version alongside the proposed revision with a navigable change list. Inspect the event name, trigger, owner and scheduling impact in their native Office context.

[Worktree](/docs/features/shared/worktree) isolates the task’s changes; [Compare](/docs/features/shared/compare) exposes differences using the content model, snapshots and changesets. A person can request a revision or confirm the merge when authorized. In this captured example, the two-file PR remains Ready and unmerged.

![Review the content with Worktree and Compare](/assets/examples/office-lab/compare.png)

### Review the delivery impact too [#delivery-plan]

The same PR extends Usability and QA from November 9 to November 10 and increases its estimate from two to three days. Review the owner, dates and status alongside the event change, so the acceptance decision includes the work needed to ship it.

## Generate, publish and manage the Web App [#web-apps]

The prototype is a live HTML View. Open **Pages** to find the project’s published Web Apps, visit the page, copy its address or choose the homepage preview. The selected default page is a preference of the current browser. File organization and access stay with Workspace.

The invitation form below is an interactive example: a new sample email increases the pending count; a duplicate pending email shows a helpful message. It uses in-memory sample data and sends no email. A product manager can test behavior directly and turn the finding into an Issue.

Native Office changes go through Worktree review and merge. HTML View publication uses its own save and authorization flow; this example publishes the prototype separately from the pending document PR. To connect a Web App to live Office data, explore [Binding](/docs/features/shared/binding), which is experimental.

## Give the team a clear collaboration boundary [#team-settings]

**Settings** brings the repository name, description and visibility together with collaborator management and Trash. Owners and administrators organize access; file editing, review and merge actions follow the current user’s effective permissions. A project link respects those permissions.

Keep the release decision explicit: the product manager checks the experience and acceptance criteria; engineering checks implementation and measurement; an authorized person merges the Office changes, verifies the published prototype and closes the Issue when the work is complete.

## Try the workflow with your own agent [#quick-start]

Open the [cloud Workspace](https://space.univer.ai), or use your [private deployment](/docs/examples/workspace#self-host). Connect each agent with [Workspace CLI](/docs/examples/workspace#cli-start). In application settings, select **Repository (experimental)** and create or open a Team Space. Each agent uses its user’s authorized account; the roles below describe a workflow you can reproduce.

## Build on the same SDK and Skills [#skills]

Both agents can use the same version-matched Workspace CLI Skills: `core` for discovery and Worktrees, `doc` and `sheet` for requirements and plans, and `html-view` for the prototype. Each agent can read the other’s accessible material and Issue feedback; people retain the final delivery decision.

Web SDK supplies the content models, editors and Headless operations; Server SDK supports collaboration, versions and Worktrees; AI SDK supplies content operations and inspection. Workspace adds the project, identity, Issues, repository views and publishing workflow. Reuse that composition to build a product lab, research workspace or internal delivery hub.
