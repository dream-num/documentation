## 容量评估

需根据实际业务规模评估容量需求。若需求较大，Docker Compose 部署方式可能不适用。特别说明：

- **exchange worker**（导入导出服务）为计算密集型服务，处理导入导出任务时可能在短时间内占用大量 CPU 与内存，尤其是导入大文档时。需评估导入导出需求，为其分配合适的 CPU 与内存资源。
- **collaboration-server**（协同引擎）为有状态的 Node 服务，在同时打开较多文档编辑时会占用较多内存。需评估所需实例数及每个实例的内存配置。若有编辑超大表格（大于 500 万单元格）的需求，建议每个实例至少配置 8 GB 内存。

此外，自 `v0.15.0` 起引入的协同编辑分层调度，需统计使用场景中表格的规模分布（文档与幻灯片不参与分层调度），以判断是否需配置分层调度。若需要，还需评估集群等级数量及各等级处理的表格规模（单元格总数、导入耗时等指标）。具体配置说明见对应部署平台的配置文档。

### 协同编辑资源需求计算

若绝大部分为小文档，协同服务可选择 2c4g 规格；否则建议选择 4c8g 规格。不建议继续增加单实例协同服务的规格，以免造成 CPU 资源浪费。

- 单实例协同服务（2c4g / 4c8g）可支持约 1100 / 1200 篇小规模文档的并发编辑，按编辑保存 QPS 计算约为 360 / 400。
- 单 universer 服务（2c4g / 4c8g）可支持约 1200 / 2200 篇小规模文档的并发编辑，按编辑保存 QPS 计算约为 400 / 730。

### 多人协同资源需求计算

多人协同时，除编辑保存消耗资源外，协同消息广播对 CPU 资源的需求更为显著。协同消息广播由 universer 服务完成，不影响 collaboration-server 的资源占用。

2c4g × 2 的配置可支持向 1400 人每秒推送 10 次编辑操作。平均而言，1 核 CPU 最高可支持每秒 3500 次协同广播。

协同广播 QPS 计算公式为：

```
协同广播 QPS = 编辑保存 QPS × (活跃用户数 / 活跃文档数 − 1)
```

其中减去 1 是因为向自身的推送已计入编辑保存 QPS 中。
