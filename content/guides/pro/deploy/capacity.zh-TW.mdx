## 容量評估

需根據實際業務規模評估容量需求。若需求較大，Docker Compose 部署方式可能不適用。特別說明：

- **exchange worker**（匯入匯出服務）為計算密集型服務，處理匯入匯出任務時可能在短時間內佔用大量 CPU 與記憶體，尤其是匯入大文件時。需評估匯入匯出需求，為其分配合適的 CPU 與記憶體資源。
- **collaboration-server**（協同引擎）為有狀態的 Node 服務，在同時開啟較多文件編輯時會佔用較多記憶體。需評估所需實例數及每個實例的記憶體配置。若有編輯超大表格（大於 500 萬儲存格）的需求，建議每個實例至少配置 8 GB 記憶體。

此外，自 `v0.15.0` 起引入的協同編輯分層排程，需統計使用場景中表格的規模分布（文件與簡報不參與分層排程），以判斷是否需配置分層排程。若需要，還需評估叢集等級數量及各等級處理的表格規模（儲存格總數、匯入耗時等指標）。具體配置說明見對應部署平台的配置文件。

### 協同編輯資源需求計算

若絕大部分為小文件，協同服務可選擇 2c4g 規格；否則建議選擇 4c8g 規格。不建議繼續增加單實例協同服務的規格，以免造成 CPU 資源浪費。

- 單實例協同服務（2c4g / 4c8g）可支援約 1100 / 1200 篇小規模文件的併發編輯，按編輯儲存 QPS 計算約為 360 / 400。
- 單 universer 服務（2c4g / 4c8g）可支援約 1200 / 2200 篇小規模文件的併發編輯，按編輯儲存 QPS 計算約為 400 / 730。

### 多人協同資源需求計算

多人協同時，除編輯儲存消耗資源外，協同訊息廣播對 CPU 資源的需求更為顯著。協同訊息廣播由 universer 服務完成，不影響 collaboration-server 的資源佔用。

2c4g × 2 的配置可支援向 1400 人每秒推送 10 次編輯操作。平均而言，1 核心 CPU 最高可支援每秒 3500 次協同廣播。

協同廣播 QPS 計算公式為：

```
協同廣播 QPS = 編輯儲存 QPS × (活躍使用者數 / 活躍文件數 − 1)
```

其中減去 1 是因為向自身的推送已計入編輯儲存 QPS 中。

### 容量需求計算器

可使用下方的計算器，根據實際業務參數快速估算所需的資源配置。輸入活躍文件數、儲存頻率、協同比例等參數後，計算器將自動輸出編輯 QPS、協同廣播 QPS 以及推薦的 Node 服務、Universer 和資料庫配置。
