## Bereitstellungskonfiguration

### So ändern Sie die Bereitstellungskonfiguration

Die Standardbereitstellungskonfiguration von Univer befindet sich im Helm-Diagramm `values.yaml`, [klicken zum Anzeigen](https://github.com/dream-num/helm-charts/blob/main/charts/univer-stack/values.yaml). Wenn Sie die Konfiguration ändern müssen, müssen Sie die Dateien in den Diagrammen nicht bearbeiten. Erstellen Sie einfach eine neue `values.yaml`-Datei und schreiben Sie die Konfigurationselemente, die Sie ändern müssen, hinein. Geben Sie bei der Installation über den Befehl `helm install` diese Datei `values.yaml` an. Die benutzerdefinierte Konfiguration überschreibt dann die Standardkonfiguration. Nicht spezifizierte Konfigurationselemente verwenden die Standardwerte. Spezifische Helm-Befehlsanweisungen finden Sie in den Bereitstellungsschritten unten.

### Konfigurationsdetails

#### Identitätsauthentifizierung und Berechtigungsverwaltung aktivieren

Die Bedeutung der relevanten Konfigurationselemente wurde bereits in [Integration mit Ihrem System über USIP](/guides/pro/usip) erläutert und wird hier nicht wiederholt. Um es zu aktivieren, können Sie auf die folgende Konfiguration zurückgreifen:

```yaml title="values.yaml"
universer:
  config:
    usip:
      enabled: true # Set to true to enable USIP
      uri:
        userinfo: 'https://your-domain/usip/userinfo'
        collaborators: 'https://your-domain/usip/collaborators'
        role: 'https://your-domain/usip/role'
        credential: 'https://your-domain/usip/credential'
        unitEditTime: 'https://your-domain/usip/unit-edit-time'

      # apikey is optional
      apikey: ''
    auth:
      permission:
        enableObjInherit: false
        customerStrategies: ''
```

#### Univer Event Publishing aktivieren

Die Bedeutung der relevanten Konfigurationselemente wurde bereits in [Integration mit Ihrem System über Univer Event Sync](/guides/pro/event-sync) erläutert und wird hier nicht wiederholt. Um es zu aktivieren, können Sie auf die folgende Konfiguration zurückgreifen:

```yaml title="values.yaml"
universer:
  config:
    rabbitmq:
      eventSync: true # Set to true to enable
```

#### Selbstverwaltete Infrastrukturkomponenten verwenden

##### RDS

**Bitte beachten Sie**: Da die von Univer verwendete Temporal-Komponente GaussDB und DamengDB nicht unterstützt, installiert Univer PostgreSQL separat für Temporal, wenn Sie sich für eine dieser Datenbanken entscheiden. Temporal speichert Workflow-Status von Import-/Exportaufgaben in der Datenbank und bezieht keine Dokumentdaten mit ein. Selbst wenn es verloren geht, schlägt es nur bei unvollständigen Import-/Exportaufgaben fehl und hat keine weiteren Auswirkungen.

###### Verwenden Sie PostgreSQL-kompatibles RDS

```yaml title="values.yaml"
postgresql:
  enabled: false # Disable Univer's built-in database

universer:
  config:
    database:
      driver: postgresql # Set to postgresql for PostgreSQL-compatible databases
      host: your-database-host
      port: your-database-port
      dbname: univer # Univer database init scripts use this name by default; keep it consistent if changed
      username: postgres # Grant select, insert, update, delete permissions
      password: postgres
      sslMode: disable # Supported values: disable, require, verify-ca, verify-full; set to require / verify-ca / verify-full to enable SSL

temporal: # temporal uses the database
  server:
    config:
      persistence:
        default:
          driver: sql # Fixed to sql
          sql:
            driver: postgres12 # postgres 12 or above required
            host: your-database-host
            port: your-database-port
            database: temporal # Univer database init scripts use this name by default; keep it consistent if changed
            user: postgres # Grant select, insert, update, delete permissions
            password: postgres

        visibility:
          driver: sql
          sql:
            driver: postgres12 # postgres 12 or above required
            host: your-database-host
            port: your-database-port
            database: temporal_visibility # Univer database init scripts use this name by default; keep it consistent if changed
            user: postgres # Grant select, insert, update, delete permissions
            password: postgres
```

#### Tiered Collaborative Editing Scheduling Configuration

Eingeführt seit `v0.15.0`, standardmäßig deaktiviert und muss zur Aktivierung manuell konfiguriert werden. Das System entscheidet anhand der Gesamtzellenzahl der Arbeitsmappe und der tatsächlichen Importzeit, für welche Ebene des Collaboration-Service-Clusters die Planung geplant werden soll. Bei neu importierten Arbeitsmappen basiert die Planung auf der Importzeit; Bei Arbeitsmappen, die auf andere Weise oder nach der Generierung eines neuen Snapshots erstellt wurden, basiert die Planung auf der Gesamtzellenzahl. Nach jeder Snapshot-Erstellung werden die relevanten Metrikdaten in der Datenbank gespeichert und die Planungsrichtlinie aktualisiert.

Der Kern der mehrstufigen Planung besteht darin, den Kollaborationsdienst als mehrere Cluster bereitzustellen und anhand von Regeln anzugeben, welcher Cluster Tabellenkalkulationen unterschiedlicher Größenordnung verarbeitet. Die Datenstruktur der Regelkonfiguration lautet wie folgt:

```yaml
unitRoutingConf:
  tiers:
    - tierName: normal
      enable: true
      upgradeCellsThreshold: 0
      downgradeCellsThreshold: 0
      upgradeImportTimeThreshold: 0
    - tierName: large
      enable: true
      upgradeCellsThreshold: 1000
      downgradeCellsThreshold: 900
      upgradeImportTimeThreshold: 10
    - tierName: huge
      enable: true
      upgradeCellsThreshold: 10000
      downgradeCellsThreshold: 9000
      upgradeImportTimeThreshold: 60
```

Beschreibung:

- `tiers`: Beschreibt Informationen zu jedem Cluster; Theoretisch können beliebig viele Cluster konfiguriert werden.
- `enable`: Legt fest, ob dieser Cluster aktiviert werden soll; Wird auf `false` gesetzt und der Cluster wird ignoriert.
- `upgradeCellsThreshold`: Gibt die Gesamtzahl der Blattzellen an, die für die Planung für diesen Cluster erforderlich ist.
- `downgradeCellsThreshold`: Wenn das Blatt derzeit für diesen Cluster geplant ist, kann es nur dann auf einen Cluster niedrigerer Ebene herabgestuft werden, wenn die Gesamtzellenzahl unter diesen Wert fällt. Dadurch wird ein häufiges Wechseln bei Blättern vermieden, deren Maßstab nahe der Ebenengrenze liegt.
- `upgradeImportTimeThreshold`: Für neu importierte Blätter ohne Statistiken zur Gesamtzellzahl wird diese Konfiguration für die Planung verwendet. Der Mechanismus ist derselbe wie bei `upgradeCellsThreshold`, außer dass die Metrik die tatsächliche Importzeit ist.

Sie müssen sicherstellen, dass in mindestens einem Cluster alle Metrikanforderungen auf 0 gesetzt sind, damit jedes Blatt geplant werden kann.

Planungsbeispiele unter der Beispielkonfiguration oben:

- Arbeitsmappe1 hat nach der Erstellung eine anfängliche Zellenanzahl von 0 und wird für den normalen Cluster geplant.
- Wenn Arbeitsmappe1 bearbeitet wird und die Wenn die Gesamtzellenzahl 1000 erreicht, wird sie für den großen Cluster geplant.
- Wenn die Gesamtzellenzahl von Arbeitsmappe1 auf 999 sinkt, weil sie immer noch über dem Herabstufungsschwellenwert von 900 liegt, bleibt sie für den großen Cluster geplant.
- Wenn die Gesamtzellenzahl von Arbeitsmappe1 weiter auf 899 sinkt, wird sie wieder auf den normalen Cluster herabgestuft.
- Arbeitsmappe2 wird mit einer tatsächlichen Zeit von 61 Sekunden importiert, was mehr ist Der Riese-Cluster-Schwellenwert von 60 Sekunden liegt bei 60 Sekunden, sodass er für den Riesigen Cluster geplant wird.

Wenn eine feinere Steuerung der Clusterebene erforderlich ist, passen Sie die Orchestrierung der Diagramme an, um tatsächlich die entsprechende Ebene der `collaboration-server`-Dienstcluster bereitzustellen, und konfigurieren Sie dann die Planungs-Routing-Tabelle (Array `tiers`) wie oben beschrieben.

Bitte konfigurieren Sie unter K8s `unitRoutingConf` in den Helm-Werten selbst.

## Bereitstellungs-SOP

Nachdem Sie die erforderliche Konfiguration ermittelt haben, können Sie Univer-Back-End-Dienste gemäß den folgenden Schritten bereitstellen.

### K8s-Bereitstellungs-SOP

Bitte beachten Sie bei der Bereitstellung mit K8s: Wenn es benutzerdefinierte Konfigurationsänderungen gibt, müssen Sie die Version der benutzerdefinierten Konfigurationsdatei verwalten `values.yaml` selbst, da nachfolgende Upgrade-Vorgänge weiterhin die vollständige benutzerdefinierte Konfiguration erfordern. Es wird empfohlen, Git oder andere Versionsverwaltungstools zu verwenden.

1. Bereiten Sie die Konfigurationsdatei `values.yaml` vor (überspringen Sie diesen Schritt, wenn keine Änderungen erforderlich sind).
2. Bereiten Sie die Lizenzdateien `license.txt` und `licenseKey.txt` vor.
3. Wenn Sie sich für die Verwendung von selbstverwaltetem RDS entscheiden, laden Sie [Datenbankinitialisierungsskript](https://release-univer.oss-cn-shenzhen.aliyuncs.com/releases/latest/univer-server-sql-latest.tar.gz) herunter und führen Sie die RDS-Initialisierung durch, einschließlich Universer und Temporal. Bei Verwendung von GaussDB oder DamengDB ist keine zeitliche Initialisierung erforderlich.
4. Führen Sie den Helm-Installationsbefehl mit Ihrer `values.yaml`-Datei und Ihren Lizenzdateien aus:
   - Wenn der Bereitstellungsserver auf das öffentliche Internet zugreifen kann:
     ```shell
     helm install -n univer --create-namespace \
         -f your-own-values.yaml-path \
         --set global.istioNamespace="univer" \
         --set-file universer.license.licenseV2=your-license.txt-path \
         --set-file universer.license.licenseKeyV2=your-licenseKey.txt-path \
         univer-stack \
         oci://univer-acr-registry.cn-shenzhen.cr.aliyuncs.com/helm-charts/univer-stack \
         --version target-version

     # After success, run the following two commands to restart services to complete sidecar injection
     kubectl rollout restart -n univer deployment/collaboration-server
     kubectl rollout restart -n univer deployment/universer
     ```
Wenn Sie die konfigurierten Observability-Komponenten von Univer bereitstellen müssen, installieren Sie sie mit dem folgenden Befehl:
     ```bash
     helm upgrade --install -n univer-observability --create-namespace \
         --set global.univerNamespace="univer" \
         univer-observability \
         oci://univer-acr-registry.cn-shenzhen.cr.aliyuncs.com/helm-charts/univer-observability
     ```

Parameter Beschreibung:
     - `--set global.univerNamespace="univer"`: Legt den Namensraum des zu beobachtenden Univer-Clusters auf `"univer"` fest.
   - Wenn der Bereitstellungsserver nicht auf das öffentliche Internet zugreifen kann:
     - [Klicken Sie hier, um](//releases/univer-server/download) das von Univer bereitgestellte All-in-One-Offline-Installationspaket für K8s herunterzuladen.
     - Laden Sie das Offline-Paket hoch Installationspaket auf den Bereitstellungsserver und extrahieren Sie es.
     - Geben Sie das extrahierte Verzeichnis ein und führen Sie Folgendes aus:
       ```shell
       export REGISTER=XXXX # Your private image registry
       export NAMESPACE=XXX # The image namespace to upload to
       docker login $REGISTER
       bash load-image.sh --registry $REGISTER --namespace $NAMESPACE
       ```
     - Nach Erfolg werden die Dateien `values.yaml` und `values-observability.yaml` im aktuellen Verzeichnis generiert; Ändern Sie sie nach Bedarf:
       - `values.yaml`: Univer-Dienstkonfigurationsdatei
       - `values-observability.yaml`: Konfigurationsdatei der Observability-Überwachungskomponente für Univer-Dienste
     - Führen Sie dann die folgenden Befehle zur Installation aus:
       ```shell
       helm install -n univer --create-namespace \
           -f your-own-values.yaml-path \
           --set global.istioNamespace="univer" \
           --set-file universer.license.licenseV2=your-license.txt-path \
           --set-file universer.license.licenseKeyV2=your-licenseKey.txt-path \
           univer-stack \
           univer-stack-xxxx.tgz # Change to the corresponding chart package in the current directory after extraction

       # After success, run the following two commands to restart services to complete sidecar injection
       kubectl rollout restart -n univer deployment/collaboration-server
       kubectl rollout restart -n univer deployment/universer
       ```
     - Wenn Sie die konfigurierten Observability-Komponenten von Univer bereitstellen müssen, installieren Sie sie mit dem folgenden Befehl:
       ```bash
       helm upgrade --install -n univer-observability --create-namespace \
           --set global.univerNamespace="univer" \
           -f your-own-values-observability.yaml-path \
           univer-observability \
           univer-observability-xxxx.tgz
       ```

Parameterbeschreibung:
       - `--set global.univerNamespace="univer"`: Legt den Namespace des zu beobachtenden Univer-Clusters auf `"univer"` fest.

Parameterbeschreibungen:

- `-n univer`: Gibt den Cluster-Namespace als `univer` an; kann nach Bedarf geändert werden, aber merken Sie sich diesen Wert, da er für nachfolgende Upgrades weiterhin benötigt wird.
- `univer-stack`: Der Name der Helm-Version; kann nach Bedarf geändert werden, aber merken Sie sich diesen Wert, da er für nachfolgende Upgrades weiterhin benötigt wird.
- `--version target-version`: Gibt die Bereitstellungsversion an; Wechsel zur Zielversion; oder lassen Sie dieses Element weg, um automatisch die neueste Version auszuwählen.
- `-f your-own-values.yaml-path`: Gibt den Pfad der benutzerdefinierten Konfigurationsdatei an `values.yaml`; Stellen Sie sicher, dass der Pfad korrekt ist.
- `--set-file universer.license.licenseV2=your-license.txt-path`: Gibt den Pfad der extrahierten `license.txt`-Datei an.
- `--set-file universer.license.licenseKeyV2=your-licenseKey.txt-path`: Gibt den Pfad der extrahierten `licenseKey.txt`-Datei an.

5. Regressionstests abschließen.
