## Архитектура развёртывания и сервисы

![Архитектура развёртывания и сервисы](./index/deploy-arch.png)

### История изменений

- Начиная с `v0.13.0` добавлен сервис `collaboration-helper`, который асинхронно выполняет ресурсоёмкие для CPU задачи, например создаёт снимки.
- Начиная с `v0.15.0` используется многоуровневая диспетчеризация совместного редактирования. Операции с электронными таблицами разного размера направляются в разные кластеры сервисов совместной работы, поэтому крупные таблицы меньше влияют на обработку таблиц обычного размера.

### Описание сервисов

- **collaboration-server**: серверный движок совместного редактирования, который использует тот же алгоритм OT, что и клиентская часть.
- **collaboration-helper**: выполняет ресурсоёмкие для CPU задачи совместной работы, например создаёт снимки, и тем самым обеспечивает плавное совместное редактирование. Добавлен в `v0.13.0`.
- **universer**: обрабатывает запросы на операции с документами, хранит данные документов и рассылает сообщения совместной работы.
- **exchange worker**: выполняет вычислительные задачи импорта и экспорта документов. Это ресурсоёмкий сервис с высокими требованиями к объёму памяти.

<Callout>
  collaboration-server — сервис с сохранением состояния. Запросы на редактирование одного документа обрабатываются одним и тем же экземпляром collaboration-server, что сокращает накладные расходы на загрузку данных и повышает общую производительность.
  Поэтому при обращении к collaboration-server для обработки операций редактирования universer добавляет уровень маршрутизации на основе консистентного хеширования.
</Callout>

### Описание компонентов

- **RDS**: реляционная база данных для хранения метаданных документов, настроек разрешений и других данных.
- **Object Storage**: объектное хранилище для содержимого документов, включая изображения и фрагменты данных.
- **Redis**: кеш со сведениями об участниках совместной работы над открытыми документами, который также используется для ограничения частоты запросов к API.
- **RabbitMQ**: очередь сообщений, через которую сервисы universer обмениваются сообщениями совместной работы, предназначенными для рассылки.
- **Temporal**: движок выполнения рабочих процессов с открытым исходным кодом. Univer использует его для управления асинхронными процессами импорта и экспорта документов.

## Подготовка к развёртыванию

Разобравшись с основной архитектурой серверных сервисов Univer, перед развёртыванием в рабочей среде оцените следующие аспекты.

### Выбор способа развёртывания

Сейчас Univer поддерживает два способа развёртывания:

- **Развёртывание с Docker Compose**
  Docker Compose поддерживает развёртывание только на одном сервере, поэтому масштабировать систему можно преимущественно вертикально. **Горизонтальное масштабирование не поддерживается.** Этот вариант подходит для небольших систем без команды, способной сопровождать Kubernetes.

- **Развёртывание в стандартной Kubernetes-совместимой среде**
  Этот способ рекомендуется, если у вас уже есть кластер Kubernetes, совместимый со стандартными паттернами K8s. Univer поддерживает горизонтальное масштабирование, а развёртывание в K8s обеспечивает наилучшую масштабируемость.

### Аутентификация пользователей и проверка разрешений

В конфигурации Univer аутентификация и проверка разрешений по умолчанию отключены. Решите, нужны ли они с учётом требований вашей системы. Подробнее см. в разделе [Интеграция с вашей системой через USIP](/guides/pro/usip).

### Выбор инфраструктурных компонентов

Как показано на схеме архитектуры выше, Univer зависит от MQ, Redis, RDS и Object Storage. В установочный пакет Univer входят распространённые версии этих компонентов с открытым исходным кодом.

Univer также позволяет использовать компоненты, которыми вы управляете самостоятельно. Для рабочей среды такой вариант **настоятельно рекомендуется** по следующим причинам:

- Упрощается сопровождение системы
- Данные хранятся безопаснее
- Система работает стабильнее

Это особенно важно для RDS и Object Storage, где хранятся данные документов. Если использовать встроенные версии Univer, повреждение накопителя физического сервера может привести к безвозвратной потере данных. Если собственной инфраструктуры хранения нет, выберите сервисы публичного облачного провайдера. Если доступны только встроенные компоненты хранения Univer, регулярно создавайте резервные копии данных, желательно раз в сутки.

Если вы выбрали компоненты под собственным управлением, убедитесь, что они полностью соответствуют требованиям Univer. Требования к каждому компоненту приведены ниже.

#### MQ

Компонент должен быть полностью совместим с AMQP/AMQPS. Сейчас рекомендуется RabbitMQ. В установочном пакете Univer используется официальный образ `rabbitmq:3-management`.

#### Redis

Компонент должен поддерживать все команды Redis. В установочном пакете Univer используется официальный образ `bitnami/redis:7.0.15-debian-11-r3`.

Сейчас Univer использует команды Redis `GET`, `MGET`, `SET`, `SETNX`, `DEL`, `EXISTS`, `EXPIRE`, `HSET`, `HGET`, `HDEL`, `HGETALL`, `HLEN`, `SCAN`, `Pipeline`, `EVAL`, `EVALSHA`. Убедитесь, что ваш компонент Redis поддерживает перечисленные команды. При соблюдении требований совместимости можно использовать распределённую версию Redis.

#### RDS

Сейчас поддерживаются PostgreSQL 16.1, MySQL 8.0, GaussDB и DamengDB. Выберите одну из этих баз данных или совместимую альтернативу. В установочном пакете Univer используется официальный образ `postgres:16.1`.

Обратите внимание: сейчас Univer не поддерживает распределённые базы данных, в которых требуется шардирование по полям таблиц. Распределённую базу данных нельзя использовать, если она не полностью совместима со способом доступа к односерверной базе. Даже с полностью совместимыми распределёнными базами данных, такими как TiDB, следует соблюдать осторожность: текущий генератор идентификаторов Univer создаёт идентификаторы с последовательным ростом, поэтому запросы могут сосредоточиться на одном узле и создать узкое место в производительности.

#### Object Storage

Компонент должен быть совместим с API AWS S3. В установочном пакете Univer используется официальный образ `bitnami/minio:2024.8.3-debian-12-r1`.

#### Компоненты наблюдаемости

Для дальнейшей эксплуатации и сопровождения серверных сервисов Univer решите, будете ли вы использовать встроенные компоненты наблюдаемости Univer или подключитесь к существующей системе. Сейчас Univer предоставляет метрики Prometheus, панели мониторинга Grafana и журналы сервисов. Инструкции по подключению см. в [руководстве SRE](/guides/pro/sre-manual).

Если у вас нет системы наблюдаемости или её сложно интегрировать, рекомендуется включить встроенные компоненты наблюдаемости Univer.
