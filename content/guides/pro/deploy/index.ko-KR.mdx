## 배포 아키텍처 및 서비스

![배포 아키텍처 및 서비스](./index/deploy-arch.png)

### 발전 과정

- `v0.13.0`부터 비동기로 실행되는 CPU 집약적 작업(예: 스냅샷 생성)을 처리하기 위해 `collaboration-helper` 서비스가 추가되었습니다.
- `v0.15.0`부터 계층형 협업 편집 스케줄링이 도입되었습니다. 규모가 서로 다른 스프레드시트의 작업을 각각 다른 협업 서비스 클러스터로 라우팅하여 대규모 스프레드시트가 일반 규모의 스프레드시트에 미치는 영향을 줄입니다.

### 서비스 소개

- **collaboration-server**: 프런트엔드와 동일한 OT 알고리즘을 구현하는 백엔드 협업 편집 엔진입니다.
- **collaboration-helper**: 협업 중 CPU 집약적 작업(예: 스냅샷 생성)을 처리하여 원활한 협업 편집을 보장합니다. 참고: `v0.13.0`부터 도입되었습니다.
- **universer**: 문서 작업 요청을 처리하고 문서 데이터를 유지하며 협업 메시지 브로드캐스트를 담당합니다.
- **exchange worker**: 문서 가져오기/내보내기 계산 작업을 실행합니다. 많은 메모리를 필요로 하는 연산 집약적 서비스입니다.

<Callout>
  collaboration-server는 상태 저장 서비스입니다. 동일한 문서의 편집 요청은 같은 collaboration-server 인스턴스에서 처리되므로 데이터 로딩 오버헤드가 줄고 전반적인 성능이 향상됩니다.
  따라서 universer는 편집 작업을 처리하기 위해 collaboration-server를 호출할 때 일관된 해시 라우팅 계층을 추가합니다.
</Callout>

### 컴포넌트 소개

- **RDS**: 문서 메타데이터, 권한 구성 등을 저장하는 관계형 데이터베이스입니다.
- **Object Storage**: 이미지, 데이터 청크 등 문서 콘텐츠 데이터를 저장하는 객체 스토리지입니다.
- **Redis**: 온라인 문서 공동 작업자 및 API 요청 속도 제한을 위한 캐시입니다.
- **RabbitMQ**: universer 서비스가 브로드캐스트해야 하는 협업 메시지를 교환할 때 사용하는 메시지 큐입니다.
- **Temporal**: 오픈 소스 워크플로 실행 엔진입니다. Univer는 문서 가져오기/내보내기의 비동기 워크플로를 관리하는 데 사용합니다.

## 배포 전 준비

Univer 백엔드 서비스의 기본 아키텍처를 파악한 후 프로덕션에 배포하기 전에 다음 항목을 평가해야 합니다.

### 배포 방식 선택

Univer는 현재 두 가지 배포 방식을 제공합니다.

- **Docker Compose 배포**
  Docker Compose는 단일 머신 배포만 지원하며 주로 수직으로 확장합니다. **수평 확장은 지원하지 않습니다.** Kubernetes 운영 역량이 없고 사용 규모가 비교적 작은 환경에 적합합니다.

- **표준 Kubernetes 호환 배포**
  이미 Kubernetes 클러스터를 운영하고 있고 표준 K8s 패턴과 호환된다면 이 방식을 권장합니다. Univer는 수평 확장을 지원하며 K8s 배포가 가장 뛰어난 확장성을 제공합니다.

### 사용자 신원 인증 및 권한 검증

Univer 설치 구성은 기본적으로 신원 인증과 권한 검증을 활성화하지 않습니다. 실제 비즈니스 요구 사항에 따라 활성화 여부를 결정해야 합니다. 자세한 내용은 [USIP를 통해 시스템과 통합하기](/guides/pro/usip)를 참고하세요.

### 인프라 컴포넌트 선택

위 시스템 배포 아키텍처와 같이 Univer가 의존하는 인프라 컴포넌트에는 MQ, Redis, RDS, Object Storage가 있습니다. Univer 설치 패키지에는 각 컴포넌트의 일반적인 오픈 소스 버전이 포함되어 있습니다.

Univer는 자체 관리 컴포넌트로 전환하는 것도 지원하며, 다음과 같은 이유로 프로덕션 환경에서는 이를 **적극 권장**합니다.

- 시스템 유지 관리 용이
- 안전한 데이터 저장 보장
- 안정적인 시스템 운영 보장

문서 데이터를 저장하는 RDS와 Object Storage에는 특히 중요합니다. Univer 내장 버전을 사용하면 물리적 머신의 스토리지 손상으로 데이터가 영구적으로 손실될 수 있습니다. 자체 스토리지 인프라가 없다면 퍼블릭 클라우드 공급업체가 제공하는 서비스를 선택하는 것이 좋습니다. Univer 내장 스토리지 컴포넌트만 사용할 수 있다면 데이터를 정기적으로, 가급적 하루에 한 번 백업해야 합니다.

자체 관리 컴포넌트를 사용한다면 Univer의 요구 사항과 완벽하게 호환되는지 확인하세요. 각 컴포넌트의 요구 사항은 다음과 같습니다.

#### MQ

AMQP/AMQPS와 완벽하게 호환되어야 하며 현재는 RabbitMQ를 권장합니다. Univer 설치 패키지에서 사용하는 공식 이미지는 `rabbitmq:3-management`입니다.

#### Redis

모든 Redis 명령과 호환되어야 합니다. Univer 설치 패키지에서 사용하는 공식 이미지는 `bitnami/redis:7.0.15-debian-11-r3`입니다.

현재 Univer가 사용하는 Redis 명령은 `GET`, `MGET`, `SET`, `SETNX`, `DEL`, `EXISTS`, `EXPIRE`, `HSET`, `HGET`, `HDEL`, `HGETALL`, `HLEN`, `SCAN`, `Pipeline`, `EVAL`, `EVALSHA`입니다. Redis 컴포넌트가 위 명령과 호환되는지 확인하세요. 호환성 요구 사항을 충족한다면 분산형 Redis도 사용할 수 있습니다.

#### RDS

현재 PostgreSQL 16.1, MySQL 8.0, GaussDB, DamengDB를 지원합니다. 이 데이터베이스 중 하나 또는 호환되는 대안을 선택할 수 있습니다. Univer 설치 패키지에서 사용하는 공식 이미지는 `postgres:16.1`입니다.

현재 Univer는 테이블 필드를 기준으로 샤딩해야 하는 분산 데이터베이스를 지원하지 않습니다. 분산 데이터베이스가 단일 머신 데이터베이스의 접근 방식과 완벽하게 호환되지 않으면 사용할 수 없습니다. 또한 TiDB처럼 완벽하게 호환되는 분산 데이터베이스를 사용할 때도 주의해야 합니다. 현재 Univer의 ID 생성기는 점차 증가하는 ID를 생성하므로 요청이 동일한 노드에 집중되어 성능 병목 현상이 발생할 수 있습니다.

#### Object Storage

AWS S3 API와 호환되어야 합니다. Univer 설치 패키지에서 사용하는 공식 이미지는 `bitnami/minio:2024.8.3-debian-12-r1`입니다.

#### 관측성 컴포넌트

향후 Univer 백엔드 서비스를 운영하고 유지 관리할 때 Univer에 통합된 관측성 컴포넌트를 사용할지, 기존 관측성 시스템에 연결할지 결정해야 합니다. Univer는 현재 Prometheus 메트릭, Grafana 대시보드 및 서비스 로그를 제공합니다. 연결에 대한 자세한 내용은 [SRE 매뉴얼](/guides/pro/sre-manual)을 참고하세요.

관측성 시스템이 없거나 통합하기 어렵다면 Univer 내장 관측성 컴포넌트를 활성화하는 것이 좋습니다.
