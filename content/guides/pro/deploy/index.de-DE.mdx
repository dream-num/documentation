## Bereitstellungsarchitektur und -dienste

![Bereitstellungsarchitektur und -dienste](./index/deploy-arch.png)

### Entwicklungsverlauf

- Seitdem `v0.13.0`, der Dienst `collaboration-helper` wurde hinzugefügt, um asynchron ausgeführte CPU-intensive Aufgaben (z. B. Snapshot-Generierung) zu verarbeiten.
- Seit `v0.15.0` wurde eine abgestufte gemeinsame Bearbeitungsplanung eingeführt, um Vorgänge an Tabellenkalkulationen unterschiedlichen Maßstabs an verschiedene Cluster von Kollaborationsdiensten weiterzuleiten und so die Auswirkungen großer Tabellenkalkulationen im normalen Maßstab zu reduzieren Tabellenkalkulationen.

### Service-Einführung

- **Collaboration-Server**: Die Back-End-Engine für die kollaborative Bearbeitung, die denselben OT-Algorithmus wie das Front-End implementiert.
- **collaboration-helper**: Verantwortlich für die Abwicklung rechenintensiver Aufgaben während der Zusammenarbeit (z. B. Snapshot-Erstellung), um eine reibungslose gemeinsame Bearbeitung sicherzustellen. Hinweis: eingeführt seit `v0.13.0`.
- **universer**: Behandelt Dokumentoperationsanfragen, pflegt Dokumentdaten und ist für die Übertragung gemeinsamer Nachrichten verantwortlich.
- **Exchange Worker**: Verantwortlich für die Ausführung von Dokumentenimport-/-exportberechnungsaufgaben; Es handelt sich um einen rechenintensiven Dienst mit hohem Speicherbedarf.

<Callout>
Collaboration-Server ist ein zustandsbehafteter Dienst. Bearbeitungsanfragen für dasselbe Dokument werden innerhalb derselben Collaboration-Server-Instanz verarbeitet, was den Datenladeaufwand reduziert und die Gesamtleistung verbessert.
Daher fügt Universer beim Aufruf des Collaboration-Servers eine Ebene des konsistenten Hash-Routings hinzu, um Bearbeitungsvorgänge zu verarbeiten.
</Callout>

### Komponenteneinführung

- **RDS**: Relationale Datenbank, die zum Speichern von Dokumentmetadaten, Berechtigungskonfigurationen usw. verwendet wird.
- **Objektspeicher**: Objektspeicher, der zum Speichern von Dokumentinhaltsdaten, einschließlich Bildern und Daten, verwendet wird Chunks usw.
- **Redis**: Cache für Online-Dokumentmitarbeiter und API-Ratenbegrenzung.
- **RabbitMQ**: Nachrichtenwarteschlange, die für Universer-Dienste verwendet wird, um kollaborative Nachrichten auszutauschen, die gesendet werden müssen.
- **Temporal**: Open-Source-Workflow-Ausführungs-Engine; Univer verwendet es, um den asynchronen Workflow des Dokumentenimports/-exports zu verwalten.

## Vorbereitung vor der Bereitstellung

Nachdem Sie die grundlegende Architektur der Univer-Back-End-Dienste verstanden haben, sollten die folgenden Punkte vor der Produktionsbereitstellung bewertet werden:

### Auswahl der Bereitstellungsmethode

Univer bietet derzeit zwei Bereitstellungsmethoden:

- **Docker Compose-Bereitstellung**
Docker Compose unterstützt nur die Bereitstellung auf einer Maschine und die Skalierung erfolgt hauptsächlich vertikal. **Horizontale Skalierung wird nicht unterstützt.** Sie eignet sich für Szenarien ohne Kubernetes-O&M-Funktionen und mit relativ geringem Nutzungsumfang.

- **Standard-Kubernetes-kompatible Bereitstellung**
Wenn Sie bereits einen Kubernetes-Cluster betreiben und dieser mit Standard-K8s-Mustern kompatibel ist, wird diese Methode empfohlen. Univer unterstützt horizontale Skalierung und die K8s-Bereitstellung bietet die beste Skalierbarkeit.

### Benutzeridentitätsauthentifizierung und Berechtigungsvalidierung

Die Installationskonfiguration von Univer aktiviert standardmäßig keine Identitätsauthentifizierung und Berechtigungsvalidierung. Sie müssen anhand der tatsächlichen Geschäftsanforderungen entscheiden, ob Sie es aktivieren möchten. Weitere Informationen finden Sie unter [Integration mit Ihrem System über USIP](/guides/pro/usip).

### Auswahl der Infrastrukturkomponenten

Wie in der Systembereitstellungsarchitektur oben gezeigt, umfassen die abhängigen Infrastrukturkomponenten von Univer MQ, Redis, RDS und Object Storage. Das Installationspaket von Univer enthält gängige Open-Source-Versionen der entsprechenden Komponenten.

Gleichzeitig unterstützt Univer den Wechsel zu selbstverwalteten Komponenten, und es wird aus folgenden Gründen **dringend empfohlen**, dies in Produktionsumgebungen zu tun:

- Erleichtert die Systemwartung
- Gewährleistet die Sicherheit der Datenspeicherung
- Gewährleistet einen stabilen Systembetrieb

Dies gilt insbesondere für RDS und Object Storage, die Dokumentdaten speichern. Wenn Sie die integrierten Versionen von Univer verwenden, kann eine Beschädigung des physischen Maschinenspeichers zu dauerhaftem Datenverlust führen. Wenn Sie keine eigene Speicherinfrastruktur haben, empfiehlt es sich, Dienste von Public-Cloud-Anbietern zu wählen. Wenn Sie nur die integrierten Speicherkomponenten von Univer verwenden können, sichern Sie die Daten regelmäßig, vorzugsweise einmal täglich.

Wenn Sie sich für die Verwendung selbstverwalteter Komponenten entscheiden, stellen Sie sicher, dass diese vollständig mit den Anforderungen von Univer kompatibel sind. Die Anforderungen für jede Komponente lauten wie folgt:

#### MQ

Muss vollständig kompatibel mit AMQP/AMQPS sein; Derzeit wird RabbitMQ empfohlen. Das offizielle Image, das im Installationspaket von Univer verwendet wird, ist `rabbitmq:3-management`.

#### Redis

Muss mit allen Redis-Befehlen kompatibel sein. Das offizielle Image, das im Installationspaket von Univer verwendet wird, ist `bitnami/redis:7.0.15-debian-11-r3`.

Zu den derzeit von Univer verwendeten Redis-Befehlen gehören: `GET`, `MGET`, `SET`, `SETNX`, `DEL`, `EXISTS`, `EXPIRE`, `HSET`, `HGET`, `HDEL`, `HGETALL`, `HLEN`, `SCAN`, `Pipeline`, `EVAL`, `EVALSHA`. Stellen Sie sicher, dass die Redis-Komponente mit den oben genannten Befehlen kompatibel ist. Unter der Voraussetzung der Meeting-Kompatibilität kann auch eine verteilte Version von Redis verwendet werden.

#### RDS

Derzeit angepasst für PostgreSQL 16.1, MySQL 8.0, GaussDB und DamengDB. Sie können eine der oben genannten Datenbanken oder eine kompatible Alternative wählen. Das offizielle Image, das im Installationspaket von Univer verwendet wird, ist `postgres:16.1`.

Bitte beachten Sie, dass Univer derzeit keine verteilten Datenbanken unterstützt, die eine Aufteilung nach Tabellenfeldern erfordern. Wenn eine verteilte Datenbank nicht vollständig mit der Zugriffsmethode einer Einzelmaschinendatenbank kompatibel ist, kann sie nicht verwendet werden. Wenn Sie außerdem eine vollständig kompatible verteilte Datenbank wie TiDB verwenden, sollten Sie ebenfalls vorsichtig sein – der aktuelle ID-Generator von Univer erzeugt tendenziell inkrementierende IDs, was dazu führen kann, dass sich Anfragen auf denselben Knoten konzentrieren und Leistungsengpässe entstehen.

#### Objektspeicher

Muss mit der AWS S3-API kompatibel sein. Das offizielle Image, das im Installationspaket von Univer verwendet wird, ist `bitnami/minio:2024.8.3-debian-12-r1`.

#### Beobachtbarkeitskomponenten

Wenn Sie anschließend die Back-End-Dienste von Univer betreiben und warten, müssen Sie entscheiden, ob Sie die integrierten Observability-Komponenten von Univer verwenden oder eine Verbindung zu einem vorhandenen Observability-System herstellen möchten. Univer bietet derzeit Prometheus-Metriken, Grafana-Dashboards und Serviceprotokolle. Einzelheiten zur Verbindung finden Sie im [SRE-Handbuch](/guides/pro/sre-manual).

Wenn Sie kein Observability-System haben oder die Integration schwierig ist, wird empfohlen, die integrierten Observability-Komponenten von Univer zu aktivieren.
