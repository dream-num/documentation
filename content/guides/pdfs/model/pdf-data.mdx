## IPdfUnitData

`IPdfUnitData` is the snapshot persisted for a single `UNIVER_PDF` unit. The schema is `univer-pdf-unit`, the current schema version is `1`, and revision numbers start at `1`.

| Property            | Type                                          | Purpose                                                            |
| ------------------- | --------------------------------------------- | ------------------------------------------------------------------ |
| `schema`            | `'univer-pdf-unit'`                           | Stable identifier for the PDF unit schema                          |
| `schemaVersion`     | `1`                                           | Current PDF unit schema version                                    |
| `id`                | `string`                                      | Identity shared by storage, collaboration, resources, and export   |
| `rev`               | `number`                                      | Authoritative revision of the unit                                 |
| `name`              | `string`                                      | PDF name shown to users                                            |
| `sourceDocumentRef` | `IPdfSourceDocumentRef`                       | Immutable provenance of the imported PDF artifact                  |
| `document`          | `IPdfDocument`                                | Imported baseline, or the baseline of a blank document             |
| `editState`         | `IPdfDurableEditState`                        | Accepted and persisted editing intent                              |
| `documentShell?`    | `IPdfDocumentShell`                           | Small page directory and fragment index for block-backed PDFs      |
| `fragmentIndex?`    | `IPdfUnitFragmentIndex`                       | Logical mapping from pages and shared data to stored fragments     |
| `resourceBindings?` | `Record<string, PdfDurableResourceBinding>`   | Durable native or Univer-managed resource bindings                 |
| `fragmentBindings?` | `Record<string, IPdfFragmentArtifactBinding>` | Runtime file bindings for independently loaded fragments           |
| `capabilityReport?` | `IPdfCapabilityReport`                        | Import and runtime decisions about supported actions and fallbacks |
| `metadata?`         | `Record<string, PdfJsonValue>`                | Application or integration metadata                                |

## Baseline and edit layer

The imported `document` is an immutable baseline. Editing never rewrites it in place. Text replacements, inserted objects, page changes, source suppressions, and managed resources are recorded in `editState`, which is then projected over the baseline for rendering and export.

Separating the two layers preserves the provenance of native PDF content and lets exporters decide which source operations to copy, suppress, or replace.

<Callout type="warning" title="Choose the correct view">
  `pdf.getDocument()` returns the imported baseline. `pdf.save()` returns the complete unit snapshot with its durable edit state. Advanced integrations can obtain the current projection from `pdf.getModel().getMaterializedDocument()`.
</Callout>

## Create and persist a snapshot

```ts
const pdf = univerAPI.createPdf({ name: 'Untitled contract' })
const page = pdf.getPageByIndex(0)

page?.insertTextBox({
  text: 'Draft',
  left: 36,
  top: 36,
})

const snapshot = pdf.save()
await applicationStorage.save(snapshot.id, snapshot)
```

Restore the complete snapshot through the Facade:

```ts
const snapshot = await applicationStorage.load('pdf-unit-id')
const pdf = univerAPI.createPdf(snapshot)
```

After the unit is running, do not modify a snapshot object. Use Facade methods or registered commands instead, so that validation, undo and redo, collaboration, and export intent remain consistent.

## Block-backed PDFs

Large PDFs, or PDFs stored remotely, can use `documentShell`, `fragmentIndex`, and `fragmentBindings`. The shell keeps page sizes, order, labels, and block IDs available before any page body is loaded. Providers materialize page fragments and shared fragments when the UI needs them.

These fields are exchange and storage contracts. Application code normally obtains them from the PDF exchange or collaboration services and persists them unchanged.
