Permission control in Univer determines what a user may do on a workbook, a worksheet, or a range. When a user attempts an operation without the required permission, Univer stops the operation and reports the missing permission. Protecting a range, for example, controls whether collaborators can edit, view, copy, or filter content inside it.

<Callout type="warning">
Your service must persist protection rules and collaborator changes, return the current user’s permissions, and pass request failures back to the caller. A mock that returns an empty list is not a persistence layer. In collaboration, the backend must also check read, JOIN, and mutation permissions itself; see [Identity and authorization](/server/collaboration/identity-and-authorization). Protection in the UI and hidden shadows do not replace server authorization.

[Permission Service Integration](#authorization-service)
</Callout>

## Core Concepts

- Scope: Permissions apply at three levels: workbook, worksheet, and range.
- Permission Points: Each feature has one permission point, and changing its value enables or disables that feature.
- Protection Rules: A worksheet or a range needs a protection rule before its permission points can be set.

<Callout type="info">
Local, non-persistent permissions can be changed through permission points. For persistence, see [Permission Service Integration](#authorization-service).

In collaborative editing, updating a permission point also updates the server state:
  - `false`: The permission point requires at least the `owner` role
  - `true`: The permission point requires at least the `reader` role
</Callout>

## Basic Example

Before using the `allowedUsers` examples, replace `user1` and `user2` with real collaborator IDs returned by your authorization service.

The examples below show the usual way to set permissions at each of the three levels: workbook, worksheet, and range.

### Workbook Permissions Code Example

Set workbook-level permissions directly through the [Facade API](/guides/sheets/getting-started/facade).

The example below disables editing for the whole workbook. To control another feature, replace the permission point with the matching one; see the [workbook permission points list](#workbook-point):

```typescript
const fWorkbook = univerAPI.getActiveWorkbook()
if (!fWorkbook) throw new Error('No active workbook')
const workbookPermission = fWorkbook.getWorkbookPermission()

// Set the workbook to be non-editable
await workbookPermission.setPoint(univerAPI.Enum.WorkbookPermissionPoint.Edit, false)
```

Workbook permission points can be set directly, without creating a protection rule first.

### Worksheet Permissions Code Example

Worksheet and range permissions can be set through the Facade API or through commands. This example sets the worksheet edit permission. To control another feature, replace the permission point with the matching one; see the [worksheet permission points list](#worksheet-point):

```typescript
const fWorkbook = univerAPI.getActiveWorkbook()
if (!fWorkbook) throw new Error('No active workbook')
const fWorksheet = fWorkbook.getActiveSheet()
const worksheetPermission = fWorksheet.getWorksheetPermission()

// Create worksheet protection, allow specified users to edit
const permissionId = await worksheetPermission.protect({
  allowedUsers: ['user1', 'user2'],
  name: 'My Worksheet Protection',
})

// To set permission points, you must first protect the worksheet
await worksheetPermission.setPoint(univerAPI.Enum.WorksheetPermissionPoint.Edit, false)
```

#### Delete Worksheet Permissions

```typescript
const fWorkbook = univerAPI.getActiveWorkbook()
if (!fWorkbook) throw new Error('No active workbook')
const fWorksheet = fWorkbook.getActiveSheet()
const worksheetPermission = fWorksheet.getWorksheetPermission()

// Remove worksheet protection
await worksheetPermission.unprotect()
```

### Custom Range Permissions Code Example

Range permissions can be set in the same two ways: through the API or through commands. The example below uses the range edit permission. Other range features require a different permission point; see the [list of permission points - Range](#range-point) for details.

```typescript
const fWorkbook = univerAPI.getActiveWorkbook()
if (!fWorkbook) throw new Error('No active workbook')
const fWorksheet = fWorkbook.getActiveSheet()
const fRange = fWorksheet.getRange('A1:B2')
const rangePermission = fRange.getRangePermission()

// Set range protection permission, allow specified users to edit but not allow others to view
const rule = await rangePermission.protect({
  name: 'My protected range',
  allowViewByOthers: false,
  allowedUsers: ['user1', 'user2'],
})
console.log(rule)

// To set permission points, you must first create a range protection rule.
await rule.setPoint(univerAPI.Enum.RangePermissionPoint.Edit, false)
await rule.setPoint(univerAPI.Enum.RangePermissionPoint.View, true)
```

#### Delete Range Protection Permissions

```typescript
const fWorkbook = univerAPI.getActiveWorkbook()
if (!fWorkbook) throw new Error('No active workbook')
const fWorksheet = fWorkbook.getActiveSheet()
const fRange = fWorksheet.getRange('A1:B2')
const rangePermission = fRange.getRangePermission()

// delete all rules within the range
await rangePermission.unprotect()

// Or delete specific rules within the range
const rules = await rangePermission.listRules()
if (rules.length > 0) {
  await rules[0].remove()
}
```

## Common tasks [#permission-tasks]

### Set a workbook to read-only

```typescript
const fWorkbook = univerAPI.getActiveWorkbook()
if (!fWorkbook) throw new Error('No active workbook')
const permission = fWorkbook.getWorkbookPermission()
await permission.setMode('viewer')
console.log(permission.getSnapshot())
```

### Manage protected ranges

```typescript
const fWorkbook = univerAPI.getActiveWorkbook()
if (!fWorkbook) throw new Error('No active workbook')
const fWorksheet = fWorkbook.getActiveSheet()
const permission = fWorksheet.getWorksheetPermission()

const createdRules = await permission.protectRanges([
  {
    ranges: [fWorksheet.getRange('A1:B2')],
    options: { name: 'Public area', allowViewByOthers: true },
  },
  {
    ranges: [fWorksheet.getRange('C3:D4')],
    options: { name: 'Private area', allowViewByOthers: false, allowedUsers: ['user1'] },
  },
])
console.log(createdRules)

const rules = await permission.listRangeProtectionRules()
const firstRule = rules[0]
if (firstRule) {
  await firstRule.updateRanges([fWorksheet.getRange('A1:B3')])
}
```

### Diagnose cell permissions

```typescript
const fWorkbook = univerAPI.getActiveWorkbook()
if (!fWorkbook) throw new Error('No active workbook')
const permission = fWorkbook.getActiveSheet().getWorksheetPermission()
console.log(permission.debugCellPermission(0, 0))
```

## Protected Range Shadow Strategy [#permission-ui]

Use `non-editable` to distinguish the protected areas the current user can edit from those they cannot. Editable areas receive no shadow, areas with editing disabled keep their shadow, and non-viewable ranges stay masked.

The setting affects only how range and worksheet protection is displayed. It does not create protection rules, does not change edit or view permissions, and does not add shadows to unprotected areas. Configure the protection rules and the current user’s permissions first, as described above.

| Strategy | Display behavior |
| --- | --- |
| `true` / `'always'` | Show shadows for all protected areas (default). |
| `'non-editable'` | Hide shadows on editable protected areas; keep them on non-editable areas. |
| `'non-viewable'` | Show shadows only on non-viewable protected areas. |
| `false` / `'none'` | Hide all protection shadows; permission checks still apply. |

## Update permission UI with the Facade API [#permission-ui-api]

### Protected Range Shadow Strategy [#protected-range-shadow-api]

The Facade API below changes existing workbooks in the current Univer instance. In plugin mode, import `@univerjs/sheets-ui/facade` first; the Sheets Core preset already includes that module.

```typescript
// Set to only show shadows for non-editable ranges
univerAPI.setProtectedRangeShadowStrategy('non-editable')

// Get the current protected range shadow display strategy
console.log(univerAPI.getProtectedRangeShadowStrategy())

// Subscribe to changes in the protected range shadow strategy
const subscription = univerAPI.getProtectedRangeShadowStrategy$().subscribe((strategy) => {
  console.log('Global strategy changed to:', strategy)
  // Update UI or perform other actions
})

// Later, unsubscribe to clean up
subscription.unsubscribe()
```

## Permission Service Integration [#permission-integration]

### Extended usage

To check permissions inside your own plugin, work with the permission points directly.

The example below uses `WorkbookEditablePermission`. Other permission points follow the same pattern.

```typescript
import { IPermissionService } from '@univerjs/core'
import { WorkbookEditablePermission } from '@univerjs/sheets'

class YourService {
  constructor(@IPermissionService private _permissionService: IPermissionService) {
  }

  setWorkbookNotEditable() {
    this._permissionService.updatePermissionPoint(new WorkbookEditablePermission('unitId').id, false)
  }

  setWorkbookEditable() {
    this._permissionService.updatePermissionPoint(new WorkbookEditablePermission('unitId').id, true)
  }
}
```

[List of permission points](#point-list)

### How to Extend Permission Points

For custom permission points, implement `IPermissionPoint` and register it with the permission service:

```typescript
import type { IPermissionPoint } from '@univerjs/core'
import { IPermissionService, PermissionStatus } from '@univerjs/core'
import { UnitAction, UnitObject } from '@univerjs/protocol'

export class CustomPermissionPoint implements IPermissionPoint {
  type = UnitObject.Unkonwn // your type
  subType = UnitAction.View // your subType
  status = PermissionStatus.INIT
  value = true // Default value
  id: string
  constructor(unitId: string, subUnitId: string, customId: string) {
    // The id must be unique within `IPermissionService`.
    this.id = `${unitId}.${subUnitId}.${customId}`
  }
}

class YourService {
  constructor(@IPermissionService private _permissionService: IPermissionService) {
    this._init()
  }

  _init() {
    this._permissionService.addPermissionPoint(new CustomPermissionPoint('unitId', 'subUnitId', 'my-id'))
  }
}

// How to use it elsewhere
class ConsumeService {
  constructor(@IPermissionService private _permissionService: IPermissionService) {
  }

  doSomething() {
    const point = this._permissionService.getPermissionPoint(new CustomPermissionPoint('unitId', 'subUnitId', 'my-id').id)
    console.log(point?.value)
  }

  bindEvent() {
    // This returns an RxJS observable that lets you listen for permission changes
    const point$ = this._permissionService.getPermissionPoint$(new CustomPermissionPoint('unitId', 'subUnitId', 'my-id').id)
    console.log(point$)
  }
}
```

### Integrating a Third-Party Authorization Service (Advanced) [#authorization-service]

Implement [IAuthzIoService](https://github.com/dream-num/univer/blob/dev/packages/core/src/services/authz-io/type.ts) in your application and connect its permission, role, and collaborator methods to your backend. The example assumes `./authorization-service` exports the implementation as `YourAuthzService`. Register it before creating any workbooks, and keep the other initialization options and plugin registrations.

```typescript
import { IAuthzIoService, Univer } from '@univerjs/core'
import { YourAuthzService } from './authorization-service'

const univer = new Univer({
  override: [[IAuthzIoService, { useClass: YourAuthzService }]],
})
```

Your authz service must persist protection rules and collaborator changes, return the current user’s permissions, and surface request failures. A mock that returns empty lists persists nothing. In collaboration, the backend must still check read, JOIN, and mutation permissions itself; see [Identity and authorization](/server/collaboration/identity-and-authorization). UI protection and hidden shadows are not a substitute for server authorization.

### Collaborator Management

<Callout>
  Collaborator management belongs to your application and its permission service. Connect your own user and ACL model, and enforce read, JOIN, and edit policies on the server; see [identity and authorization](/server/collaboration/identity-and-authorization). The frontend APIs below require a matching permission-service implementation; they do not configure server authorization.
</Callout>

- Get the collaborator list

```typescript
const fWorkbook = univerAPI.getActiveWorkbook()
if (!fWorkbook) throw new Error('No active workbook')
const workbookPermission = fWorkbook.getWorkbookPermission()

const collaborators = await workbookPermission.listCollaborators()
console.log(collaborators)
```

- Add collaborators

```typescript
const fWorkbook = univerAPI.getActiveWorkbook()
if (!fWorkbook) throw new Error('No active workbook')
const workbookPermission = fWorkbook.getWorkbookPermission()

// Add multiple collaborators at once
await workbookPermission.setCollaborators([
  {
    user: { userID: 'user1', name: 'John Doe', avatar: 'https://...' },
    role: univerAPI.Enum.UnitRole.Editor,
  },
  {
    user: { userID: 'user2', name: 'Jane Smith', avatar: '' },
    role: univerAPI.Enum.UnitRole.Reader,
  },
])

// Add a single collaborator
await workbookPermission.addCollaborator(
  { userID: 'user1', name: 'John Doe', avatar: 'https://...' },
  univerAPI.Enum.UnitRole.Editor,
)
```

- Update collaborator roles

```typescript
const fWorkbook = univerAPI.getActiveWorkbook()
if (!fWorkbook) throw new Error('No active workbook')
const workbookPermission = fWorkbook.getWorkbookPermission()

await workbookPermission.updateCollaborator(
  { userID: 'user1', name: 'John Doe Updated', avatar: 'https://...' },
  univerAPI.Enum.UnitRole.Reader,
)
```

- Remove collaborators

```typescript
const fWorkbook = univerAPI.getActiveWorkbook()
if (!fWorkbook) throw new Error('No active workbook')
const workbookPermission = fWorkbook.getWorkbookPermission()

// Remove multiple collaborators
await workbookPermission.removeCollaborators(['user1', 'user2'])

// Remove a single collaborator
await workbookPermission.removeCollaborator('user1')
```
