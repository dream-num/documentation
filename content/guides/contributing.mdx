Thank you for your interest in contributing to Univer! This guide will help you get started.

## Code of Conduct

We are committed to providing a friendly, safe, and welcoming environment for all contributors. Please be respectful and constructive in all interactions.

## How to Contribute

### Reporting Bugs

Before creating a bug report, please:

1. Search [existing issues](https://github.com/dream-num/univer/issues) to avoid duplicates
2. Use the latest stable version to verify the bug still exists
3. Collect relevant information: browser version, Node.js version, error messages

When reporting, include:

- A clear, descriptive title
- Steps to reproduce the issue
- Expected vs actual behavior
- A minimal reproduction (CodeSandbox, StackBlitz, or GitHub repo)
- Screenshots or screen recordings if applicable

### Suggesting Features

Feature requests are welcome! Please open a discussion first to gather feedback from the community and maintainers.

### Contributing Code

#### Development Setup

1. Fork and clone the repository:
   ```bash
   git clone https://github.com/YOUR_USERNAME/univer.git
   cd univer
   ```

2. Install dependencies:
   ```bash
   pnpm install
   ```

3. Build the project:
   ```bash
   pnpm build
   ```

4. Run tests:
   ```bash
   pnpm test
   ```

#### Project Structure

```
packages/
  core/           # Core infrastructure (DI, command system, lifecycle)
  design/         # Design system and base styles
  engine-render/  # Canvas rendering engine
  engine-formula/ # Formula calculation engine
  sheets/         # Spreadsheet data model and core logic
  sheets-ui/      # Spreadsheet UI components
  docs/           # Document data model
  docs-ui/        # Document UI components
  slides/         # Presentation data model
  ui/             # Shared UI framework
examples/         # Integration examples (React, Vue, Angular, etc.)
```

#### Writing a Plugin

Univer is built on a plugin architecture. To add new functionality:

1. Create a new package under `packages/` or a standalone repository
2. Implement the plugin class extending `Plugin`
3. Register commands, services, and controllers in `onStarting`
4. Add facade extensions if exposing public APIs
5. Write tests and documentation

See the [Custom Plugin Tutorial](/guides/recipes/tutorials/custom-plugin) for a step-by-step guide.

#### Commit Convention

We use [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>(<scope>): <subject>

<body>

<footer>
```

Common types:

- `feat`: New feature
- `fix`: Bug fix
- `docs`: Documentation changes
- `style`: Code style changes (formatting, semicolons, etc.)
- `refactor`: Code refactoring
- `perf`: Performance improvements
- `test`: Test additions or fixes
- `chore`: Build process or auxiliary tool changes

Example:
```
feat(sheets): add support for custom number formats

Closes #1234
```

#### Pull Request Process

1. Create a feature branch from `dev`
2. Make your changes with clear, focused commits
3. Add or update tests as needed
4. Ensure `pnpm lint` and `pnpm test` pass
5. Update documentation if your changes affect public APIs
6. Open a Pull Request against the `dev` branch
7. Fill out the PR template with a clear description

### Contributing Documentation

Documentation improvements are highly valued. To edit docs:

1. Documentation lives in the [documentation repository](https://github.com/dream-num/documentation)
2. Each page has a corresponding `.mdx` file
3. Follow the existing style and formatting
4. Update all language variants if applicable (en-US, zh-CN, zh-TW, ja-JP)
