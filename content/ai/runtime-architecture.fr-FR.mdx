Lorsqu'une commande CLI s'exécute, la partie chère n'est généralement pas l'analyse d'arguments. Elle transforme un Unit[^document-unit] en un Univer live qui peut être lu et écrit : création de Univer, installation de plugins, ouverture du moteur de collaboration, chargement du point de contrôle, application de changements et attente de formules pour terminer le calcul.

Deux fonctionnalités Runtime[^live-runtime] effectuent ce travail, et cette page couvre les deux:

- `@univer-cli/univer-collaboration-runtime` charge une unité et l'actionne dans le processus actuel;
- `@univer-cli/univer-collaboration-runtime-pool` place les Runtimes dans les travailleurs et loue, réutilise et les retire par identité de l'unité.

Un Worker Runtime survit à travers les invocations de CLI seulement quand un processus de longue durée le possède. Dans cette architecture, ce propriétaire est un démon local.

## Trois cycles de vie

La réutilisation dépend de la séparation de trois vies :

| Objet | Création | Fin | Possède |
| --- | --- | --- | --- |
| Processus CLI | Sur chaque commande | Après la sortie du résultat | Arguments, une requête, formatage de sortie |
| Processus Daemon | Première requête ou démarrage direct | Arrêt, redémarrage de mise à niveau ou crash | Pool Runtime, handlers métier, socket local |
| Worker Runtime | Première rencontre d’une clé par le pool | Éviction TTL/LRU[^runtime-cache], invalidation, arrêt du daemon ou crash Worker | Un Worker, un handle backend, une Unit chargée et son état collaboratif |

Une règle de propriété régit la conception : **l'ICL fait un appel, le démon possède la piscine, la piscine possède les travailleurs, et chaque travailleur possède un Runtime.**

<Mermaid chart={"flowchart LR\n  CLI1[Appel CLI 1<br/>éphémère] -->|Requête JSON| D[Daemon<br/>propriétaire durable]\n  CLI2[Appel CLI 2<br/>éphémère] -->|Requête JSON| D\n  CLIN[Appel CLI N<br/>éphémère] -->|Requête JSON| D\n\n  D --> P[Pool Collaboration Runtime]\n  P -->|key: Unit A| WA[Worker A]\n  P -->|key: Unit B| WB[Worker B]\n  WA --> RA[Runtime A<br/>Unit A chargée]\n  WB --> RB[Runtime B<br/>Unit B chargée]\n  RA --> BA[Backend A]\n  RB --> BB[Backend B]\n  BA --> DS[(Serveur collaboratif<br/>ou autre source)]\n  BB --> DS"} />

Le démon n'avance que les requêtes JSON que l'application définit. Les snapshots, les modifications et les blocs sont lus par le backend à l'intérieur du Worker, de sorte qu'ils ne passent jamais par le CLI ou le démon.

## Étape 1 : charger un Runtime à chaque commande

L'implémentation la plus simple crée `@univer-cli/univer-collaboration-runtime` à l'intérieur d'une action Commander et la ferme lorsque l'opération se termine :

```ts
const runtime = await runtimeFactory.load(unitId, unitType);

try {
  const pulled = await runtime.pull();
  if (pulled.status === "conflict") throw new Error(pulled.conflict.message);

  const execution = await runtime.execute({ mode: "write", code });
  let commit = await runtime.commit();
  if (commit.status === "pull-required") {
    const repulled = await runtime.pull();
    if (repulled.status === "conflict") throw new Error(repulled.conflict.message);
    commit = await runtime.commit();
  }
  return { execution, commit };
} finally {
  await runtime.close();
}
```

`runtimeFactory` vient de `createUniverCollaborationRuntimeFactory()`. De la charge à la clôture, un Runtime est lié à exactement une Unité et conserve la révision actuelle de l'Unité, les mutations en attente, les changements en attente et l'état de conflit. L'appelant doit également vérifier l'état final du commit : seul `confirmed` et `nothing-to-commit` signifient que l'opération est terminée.

Un appel `load()` fait plus que lire un fichier. Il effectue les étapes suivantes dans l'ordre :

1. Ouverture du backend collaboratif fourni par l’application ;
2. Création de headless Univer et installation de la collaboration ;
3. Chargement d’UnitData ou d’un point de contrôle Snapshot ;
4. Rejeu des modifications portées par le point de contrôle ;
5. Récupération et rejeu de l’écart jusqu’à la dernière révision distante ;
6. Attente de l’application des derniers résultats des modules de formules installés ;
7. Retour d’un Runtime prêt pour `execute()`, `pull()` et `commit()`.

Une invocation unique complète se produit comme suit :

<Mermaid chart={"sequenceDiagram\n  autonumber\n  actor User as Utilisateur\n  participant CLI as Processus CLI\n  participant RT as Collaboration Runtime\n  participant U as headless Univer\n  participant B as Backend\n\n  User->>CLI: Exécuter la commande\n  CLI->>CLI: Démarrer Node.js, charger les modules, analyser les arguments\n  CLI->>RT: factory.load(unitId, unitType)\n  RT->>B: Ouvrir et lire point de contrôle / modifications\n  RT->>U: Créer Univer, installer les plugins, charger et rejouer Unit\n  RT->>U: Attendre les formules\n  RT-->>CLI: Runtime prêt\n  CLI->>RT: pull()\n  CLI->>RT: execute()\n  opt Opération d’écriture\n    CLI->>RT: commit()\n    RT->>B: Soumettre les modifications\n  end\n  CLI->>RT: close()\n  RT->>B: Fermer le handle backend\n  RT->>U: Libérer Univer\n  CLI-->>User: Afficher et quitter"} />

La propriété est directe ici, et une défaillance ne laisse aucun état derrière, de sorte que cet arrangement convient aux commandes à basse fréquence et aux tâches ponctuelles. Le coût est que la prochaine commande CLI démarre un nouveau processus Node.js et répète l'ensemble de la séquence de chargement, de sorte qu'il ne peut pas réutiliser la Univer ou l'unité indique que la commande précédente a été construite.

## Étape 2 : héberger le Runtime dans un pool de Workers

`@univer-cli/univer-collaboration-runtime-pool` maintient un processus Worker séparé et Collaboration Runtime pour chaque clé résidente. L'application fournit une entrée Worker; le moteur, les identifiants et Univer sont tous créés à l'intérieur du Worker:

```ts title="collaboration-worker.ts"
import { defineUniverCollaborationRuntimeWorker } from "@univer-cli/univer-collaboration-runtime-pool";

export default defineUniverCollaborationRuntimeWorker({
  async createRuntime(init: { unitId: string; unitType: number }) {
    return createRuntimeFromApplicationInit(init);
  },
});
```

L'entrée Worker doit pointer vers un fichier ESM JavaScript construit. `init` est envoyé au Worker uniquement sur une création froide, et il doit être compatible avec un clone structuré.

L'appelant n'a pas besoin de concevoir une couche Runtime RPC séparée. Le bail permet déjà d'obtenir les API publiques, y compris `getState()`, `execute()`, `fetch()`, `pull()`, `commit()` et `exportUnitData()` :

```ts
import { createUniverCollaborationRuntimePool } from "@univer-cli/univer-collaboration-runtime-pool";

const pool = createUniverCollaborationRuntimePool({
  entry: new URL("./collaboration-worker.js", import.meta.url),
});

const lease = await pool.acquire({
  key: targetKey,
  init: { unitId, unitType },
});

try {
  await lease.pull();
  const result = await lease.execute({ mode: "read", code });
  console.log(result.value);
} catch (error) {
  await lease.invalidate();
  throw error;
} finally {
  await lease.release();
}
```

`key` identifie quel Runtime réutiliser; ce n'est pas seulement un argument de requête. La même clé doit toujours signifier la même unité, la même chaîne d'état de collaboration, et une sémantique d'initialisation compatible. Une unité simple et un brouillon Worktree doivent utiliser des clés différentes même lorsqu'ils partagent le même `unitId`.

La piscine a quatre comportements qui déterminent la réutilisation:

- Un seul bail contient une clé à la fois. Les demandes simultanées attendent dans l'ordre de FIFO, de sorte que deux appels ne peuvent pas modifier simultanément le même état en direct;
- `release()` retourne un Runtime de confiance au cache inactif, où la prochaine requête pour cette clé peut la réutiliser;
- `invalidate()` marque l'état comme n'étant plus digne de confiance. Le Worker et son Runtime sont détruits, et la demande suivante effectue une charge froide;
- TTL et LRU peuvent évincer les Runtimes inactifs. Délais dépassés, crashes Worker et erreurs de protocole invalident aussi l’instance.

Si le pool lui-même vit à l'intérieur d'un processus CLI à courte durée de vie, cependant, la réutilisation ne peut toujours pas franchir les limites des commandes :

<Mermaid chart={"flowchart LR\n  subgraph C1[Appel CLI 1]\n    P1[Pool 1] --> W1[Worker A] --> R1[Runtime A]\n  end\n\n  X1[La CLI quitte] -.->|Le pool ferme et son Worker quitte| C1\n\n  subgraph C2[Appel CLI 2]\n    P2[Nouveau Pool 2] --> W2[Nouveau Worker A] --> R2[Runtime A rechargé]\n  end\n\n  X1 --> C2"} />

Les travailleurs assurent l'isolement des processus pour le Runtime, le leasing exclusif et la résiliation en cas d'échec. Pour réutiliser les travailleurs à travers les invocations CLI, le pool a encore besoin d'un propriétaire qui survive à toute commande.

## Étape 3 : confier le pool au Daemon

Le démon est un processus local sur demande Node.js. Le CLI l'appelle à travers une socket Unix ou une pipe nommée Windows. Quitter le CLI ne met pas fin au démon, de sorte que sa piscine, les travailleurs, et les Runtimes inactif restent en vie.

Créer le pool une fois dans l'entrée du démon, puis acquérir un bail dans chaque gestionnaire d'entreprise:

```ts title="daemon-entry.ts"
import { createDaemonServer, DAEMON_SOCKET_ENV } from "@univer-cli/daemon";
import { createUniverCollaborationRuntimePool } from "@univer-cli/univer-collaboration-runtime-pool";

const socketPath = process.env[DAEMON_SOCKET_ENV];
if (!socketPath) throw new Error(`${DAEMON_SOCKET_ENV} is required`);

const pool = createUniverCollaborationRuntimePool({
  entry: new URL("./collaboration-worker.js", import.meta.url),
  cache: { idleTtlMs: 5 * 60_000, maxEntries: 20 },
});

const server = createDaemonServer({
  identity: { id: "my-cli", version: "1.0.0" },
  socketPath,
  onShutdown: () => pool.close(),
});

server.handle("unit.execute", async (payload) => {
  const input = parseExecuteRequest(payload);
  const lease = await pool.acquire({
    key: input.targetKey,
    init: { unitId: input.unitId, unitType: input.unitType },
  });

  try {
    const pulled = await lease.pull();
    if (pulled.status === "conflict") throw new Error(pulled.conflict.message);

    const execution =
      input.mode === "read"
        ? await lease.execute({ mode: "read", code: input.code })
        : await lease.execute({ mode: "write", code: input.code });
    const commit = input.mode === "write" ? await commitWithPull(lease) : null;
    return { commitStatus: commit?.status ?? null, value: execution.value };
  } catch (error) {
    await lease.invalidate();
    throw error;
  } finally {
    await lease.release();
  }
});

await server.listen();
```

L'application définit `parseExecuteRequest()` et les règles `targetKey`. Le démon fournit le transport local et la gestion du cycle de vie seulement; il ne comprend pas les unités, les Runtimes, ou le protocole de collaboration. La fermeture du démon doit appeler `pool.close()`, si inactif et actif Travailleurs ont un propriétaire final clair. Dans cet exemple, `commitWithPull()` gère la séquence de traction et de commit après `pull-required` puis vérifie le statut de commit final. Toute erreur non gérée invalide le bail actuel, ce qui maintient l'exemple prudent.

Une commande CLI ordinaire envoie maintenant une demande d'affaires au démon :

```ts
import { createDaemonClient } from "@univer-cli/daemon";

const client = createDaemonClient({
  entry: new URL("./daemon-entry.js", import.meta.url),
  identity: { id: "my-cli", version: "1.0.0" },
  socketPath,
});

const result = await client.request("unit.execute", {
  targetKey,
  unitId,
  unitType,
  mode,
  code,
});
```

Lorsque la socket n'existe pas, le client démarre l'entrée de démon configuré, attend l'identité et le protocole poignée de main, puis envoie la requête. Si un démon compatible est déjà en cours d'exécution, le client la réutilise directement.

## Étape 4 : comparer première requête et suivantes

Le premier accès à une clé suit le chemin du froid : le démon peut avoir besoin de démarrer, et le bassin doit créer un Worker et un Runtime.

<Mermaid chart={"sequenceDiagram\n  autonumber\n  participant CLI as Premier appel CLI\n  participant D as Daemon\n  participant P as Pool Runtime\n  participant W as Worker A\n  participant R as Runtime A\n  participant B as Backend\n\n  CLI->>D: unit.execute(target A)\n  Note over CLI,D: Démarrer le daemon si le socket est absent\n  D->>P: acquire(key A, init)\n  P->>W: Créer le Worker et charger son entrée\n  W->>R: createRuntime(init)\n  R->>B: Ouvrir le backend, lire point de contrôle / modifications\n  R->>R: Créer Univer, charger Unit, attendre les formules\n  R-->>P: Runtime prêt\n  P-->>D: Lease A\n  D->>R: pull → execute → commit\n  D->>P: release()\n  Note over P,R: Worker A et Runtime A restent en cache inactif\n  D-->>CLI: Résultat JSON\n  Note over CLI: La CLI quitte, daemon / Worker restent actifs"} />

L'accès ultérieur à la même clé suit le chemin chaud. Le processus CLI recommence, mais la charge de Runtime chère n'est pas répétée:

<Mermaid chart={"sequenceDiagram\n  autonumber\n  participant CLI as Appel CLI suivant\n  participant D as Daemon actif\n  participant P as Pool Runtime\n  participant R as Runtime A chargé\n\n  CLI->>D: unit.execute(target A)\n  D->>P: acquire(key A, init)\n  P-->>D: Cache trouvé, renvoyer Lease A\n  D->>R: pull()\n  Note over R: Synchroniser les changements distants pendant l’inactivité\n  D->>R: execute()\n  opt Opération d’écriture\n    D->>R: commit()\n  end\n  D->>P: release()\n  D-->>CLI: Résultat JSON\n  Note over CLI,R: La CLI quitte, Runtime A reste actif"} />

La réutilisation s'applique à un Runtime en direct qui a déjà été créé et chargé. Il ne contourne pas la cohérence de collaboration. Après l'acquisition d'un bail, l'appelant devrait normalement appeler `pull()`; après `commit()`, il devrait inspecter le statut final et manipuler `pull-required`, `retry`, `unknown` ou `conflict`.

## Coûts supprimés et conservés

| Coût | Chargement direct à chaque appel | Daemon + pool Worker |
| --- | --- | --- |
| Démarrage CLI, arguments, sortie | Chaque fois | Chaque fois |
| Aller-retour JSON par socket local | Aucun | Chaque fois |
| Démarrage daemon et modules | Aucun | Première requête ou redémarrage |
| Démarrage Worker et entrée | Aucun Worker | Création à froid par clé |
| Création Univer et plugins | Chaque fois | Création à froid par clé |
| Point de contrôle, rejeu initial, attente des formules | Chaque fois | Création à froid par clé |
| `pull()` des changements pendant l’inactivité | Chaque fois | Généralement encore nécessaire à chaque fois |
| `execute()` et `commit()` | Chaque fois | Chaque fois |
| Mémoire inactive, handle backend et processus Worker | Libérés à la sortie | Conservés jusqu’à éviction, invalidation ou arrêt du daemon |

Réutiliser la mémoire résidente et Worker compte pour une latence de démarrage plus faible sur les appels ultérieurs. Set `idleTtlMs`, `maxEntries` , le timeout ouvert , et les timeouts d'opération des événements de pool et de latence mesurée , plutôt que de conserver chaque unité indéfiniment .

## Concurrence, échecs et arrêt

Quatre règles décrivent le comportement du système :

1. **Demandes simultanées pour la même clé d'attente.** Un Runtime en direct appartient à un bail à la fois, de sorte que les appels interleaved ne peuvent pas modifier l'état de collaboration.
2. **Des clés différentes s’exécutent en parallèle dans des Workers différents.** Chaque clé résidente coûte un Worker et un Runtime propres.
3. **Seul un état de confiance peut être réutilisé.** Appelez `release()` après une opération réussie et les mutations locales ont été effacées. Appelez `invalidate()` après une panne, un crash ou une erreur de protocole, ou chaque fois que l'application ne peut pas confirmer l'état local.
4. **La responsabilité de l'arrêt est dirigée vers le bas.** Le CLI remplit une demande; démon stopdown appelle `pool.close()`; le pool résilie les travailleurs et ferme leurs Runtimes et leurs moteurs.

Pour les commandes à basse fréquence où la latence unique est acceptable, l'utilisation directe de `@univer-cli/univer-collaboration-runtime` est l'option la plus simple. Combinez le démon avec `@univer-cli/univer-collaboration-runtime-pool` uniquement lorsque les mesures montrent que le chargement répété est le coût dominant et que l'application peut accepter un processus résident et son utilisation de mémoire.

[^document-unit]: Une Unit est une instance de document, par exemple un classeur ou un document texte. Une feuille appartient à un classeur et ne constitue pas une Unit distincte.

[^live-runtime]: Ici, Runtime désigne l’instance Univer active et les ressources nécessaires pour manipuler une Unit chargée, et non l’exécutable Node.js ou un instantané enregistré.

[^runtime-cache]: Le TTL évince un Runtime inactif à l’expiration de sa durée de vie ; le LRU évince les moins récemment utilisés quand la capacité est limitée. Ces règles libèrent les ressources sans supprimer la Unit persistée.
