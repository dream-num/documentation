Cuando un comando CLI funciona, la parte costosa generalmente no es el análisis de argumentos. Está convirtiendo un Unit[^document-unit] en un Univer vivo que se puede leer y escribir: crear Univer, instalar plugins, abrir la colaboración backend, cargar el control, aplicar cambios, y esperar a que las fórmulas terminen de calcular.

Dos capacidades Runtime[^live-runtime] realizan este trabajo, y esta página cubre ambas:

- `@univer-cli/univer-collaboration-runtime` carga una Unidad y opera en ella en el proceso actual;
- `@univer-cli/univer-collaboration-runtime-pool` coloca Tiempos de ejecución en los trabajadores y arrenda, reutiliza y los retira por identidad de unidad.

Un Worker Runtime sobrevive a través de invocaciones CLI sólo cuando un proceso de larga vida lo posee. En esta arquitectura, ese propietario es un daemon local.

## Tres ciclos de vida

Reutilizar depende de mantener tres vidas separadas:

| Objeto | Creación | Fin | Posee |
| --- | --- | --- | --- |
| Proceso CLI | En cada comando | Después de imprimir el resultado | Argumentos, una solicitud y formato de salida |
| Proceso Daemon | Primera solicitud o inicio directo | Parada, reinicio por actualización o fallo | Pool Runtime, handlers de negocio y socket local |
| Worker Runtime | Primer encuentro de una clave en el pool | Expulsión TTL/LRU[^runtime-cache], invalidación, cierre daemon o fallo Worker | Un Worker, un handle backend, una Unit cargada y estado colaborativo |

Una regla de propiedad gobierna el diseño: **el CLI hace una llamada, el daemon posee la piscina, la piscina es dueña de Trabajadores, y cada Trabajador posee un Runtime.**

<Mermaid chart={"flowchart LR\n  CLI1[Invocación CLI 1<br/>breve] -->|Solicitud JSON| D[Daemon<br/>propietario duradero]\n  CLI2[Invocación CLI 2<br/>breve] -->|Solicitud JSON| D\n  CLIN[Invocación CLI N<br/>breve] -->|Solicitud JSON| D\n\n  D --> P[Pool Collaboration Runtime]\n  P -->|key: Unit A| WA[Worker A]\n  P -->|key: Unit B| WB[Worker B]\n  WA --> RA[Runtime A<br/>Unit A cargada]\n  WB --> RB[Runtime B<br/>Unit B cargada]\n  RA --> BA[Backend A]\n  RB --> BB[Backend B]\n  BA --> DS[(Servidor colaborativo<br/>u otra fuente)]\n  BB --> DS"} />

El daemon sólo adelanta las peticiones JSON que la aplicación define. instantáneas, cambios y bloques son leídos por el backend dentro del Worker, por lo que nunca pasan por el CLI o el daemon.

## Paso 1: cargar Runtime en cada orden

La implementación más simple crea `@univer-cli/univer-collaboration-runtime` dentro de una acción Commander y la cierra cuando la operación completa:

```ts
const runtime = await runtimeFactory.load(unitId, unitType);

try {
  const pulled = await runtime.pull();
  if (pulled.status === "conflict") throw new Error(pulled.conflict.message);

  const execution = await runtime.execute({ mode: "write", code });
  let commit = await runtime.commit();
  if (commit.status === "pull-required") {
    const repulled = await runtime.pull();
    if (repulled.status === "conflict") throw new Error(repulled.conflict.message);
    commit = await runtime.commit();
  }
  return { execution, commit };
} finally {
  await runtime.close();
}
```

`runtimeFactory` viene de `createUniverCollaborationRuntimeFactory()`. De carga a cierre, un Runtime está obligado a exactamente una Unidad y mantiene la revisión actual de la Unidad, mutaciones pendientes, cambios en espera, y estado de conflicto. El callador también debe comprobar el estado de compromiso final: sólo `confirmed` y `nothing-to-commit` significan que la operación ha terminado.

Una llamada `load()` hace más que leer un archivo. Realiza los siguientes pasos para:

1. Abrir el backend colaborativo de la aplicación;
2. Crear headless Univer e instalar colaboración;
3. Cargar UnitData o un punto de control Snapshot;
4. Reproducir sus cambios;
5. Obtener y reproducir el intervalo hasta la última revisión remota;
6. Esperar la aplicación de los resultados más recientes de los módulos de fórmulas instalados;
7. Devolver un Runtime listo para `execute()`, `pull()` y `commit()`.

Una invocación completa procede de la siguiente manera:

<Mermaid chart={"sequenceDiagram\n  autonumber\n  actor User as Usuario\n  participant CLI as Proceso CLI\n  participant RT as Collaboration Runtime\n  participant U as headless Univer\n  participant B as Backend\n\n  User->>CLI: Ejecutar comando\n  CLI->>CLI: Iniciar Node.js, cargar módulos, analizar argumentos\n  CLI->>RT: factory.load(unitId, unitType)\n  RT->>B: Abrir y leer punto de control / cambios\n  RT->>U: Crear Univer, instalar plugins, cargar y reproducir Unit\n  RT->>U: Esperar fórmulas\n  RT-->>CLI: Runtime listo\n  CLI->>RT: pull()\n  CLI->>RT: execute()\n  opt Operación de escritura\n    CLI->>RT: commit()\n    RT->>B: Enviar cambios\n  end\n  CLI->>RT: close()\n  RT->>B: Cerrar handle backend\n  RT->>U: Liberar Univer\n  CLI-->>User: Imprimir y salir"} />

La propiedad es directa aquí, y un fallo no deja ningún estado atrás, por lo que este arreglo se adapta a comandos de baja frecuencia y tareas de un solo paso. El costo es que el siguiente comando CLI inicia un nuevo proceso Node.js y repite toda la secuencia de carga, por lo tanto no puede reutilizar el Univer e Unit declara que el comando anterior construido.

## Paso 2: alojar Runtime en un pool de Workers

`@univer-cli/univer-collaboration-runtime-pool` mantiene un proceso independiente de Trabajador y Collaboration Runtime para cada llave residente. La aplicación proporciona una entrada de Trabajador; el backend, credenciales y Univer son todas creadas dentro del Trabajador:

```ts title="collaboration-worker.ts"
import { defineUniverCollaborationRuntimeWorker } from "@univer-cli/univer-collaboration-runtime-pool";

export default defineUniverCollaborationRuntimeWorker({
  async createRuntime(init: { unitId: string; unitType: number }) {
    return createRuntimeFromApplicationInit(init);
  },
});
```

La entrada de Worker debe apuntar a un archivo JavaScript ESM construido. `init` es enviado al Trabajador sólo en una creación fría, y debe ser compatible con clon estructurado.

El callador no necesita diseñar una capa RPC Runtime separada. El contrato de arrendamiento ya proxie las API públicas, incluyendo `getState()`, `execute()`, `fetch()`, `pull()`, `commit()`, y `exportUnitData()`:

```ts
import { createUniverCollaborationRuntimePool } from "@univer-cli/univer-collaboration-runtime-pool";

const pool = createUniverCollaborationRuntimePool({
  entry: new URL("./collaboration-worker.js", import.meta.url),
});

const lease = await pool.acquire({
  key: targetKey,
  init: { unitId, unitType },
});

try {
  await lease.pull();
  const result = await lease.execute({ mode: "read", code });
  console.log(result.value);
} catch (error) {
  await lease.invalidate();
  throw error;
} finally {
  await lease.release();
}
```

`key` identifica qué Runtime reutilizar; no es simplemente un argumento de consulta. La misma clave siempre debe significar la misma Unidad, la misma cadena del estado de colaboración, y semántica de inicialización compatible. Una unidad simple y un borrador Worktree deben usar diferentes claves incluso cuando comparten el mismo `unitId`.

La piscina tiene cuatro comportamientos que determinan la reutilización:

- Sólo un contrato de arrendamiento tiene una llave a la vez. Las solicitudes simultáneas esperan en orden FIFO, por lo que dos llamadas no pueden modificar el mismo estado en vivo simultáneamente;
- `release()` devuelve un tiempo de ejecución confiable al caché de ocio, donde la siguiente solicitud para esa clave puede reutilizarla;
- `invalidate()` marca el estado como ya no confiable. El trabajador y su tiempo de ejecución son destruidos, y la siguiente petición realiza una carga fría;
- TTL y LRU pueden expulsar Runtimes inactivos. Tiempos agotados, fallos Worker y errores de protocolo también invalidan la instancia.

Si la piscina vive dentro de un proceso CLI de corta duración, sin embargo, la reutilización todavía no puede cruzar los límites del comando:

<Mermaid chart={"flowchart LR\n  subgraph C1[Invocación CLI 1]\n    P1[Pool 1] --> W1[Worker A] --> R1[Runtime A]\n  end\n\n  X1[La CLI termina] -.->|El pool cierra y su Worker termina| C1\n\n  subgraph C2[Invocación CLI 2]\n    P2[Nuevo Pool 2] --> W2[Nuevo Worker A] --> R2[Runtime A recargado]\n  end\n\n  X1 --> C2"} />

Los trabajadores proporcionan aislamiento de proceso para el tiempo de ejecución, arrendamiento exclusivo y terminación en el fracaso. Para reutilizar a los trabajadores a través de las invocaciones CLI, la piscina todavía necesita un propietario que sobrevive cualquier comando individual.

## Paso 3: usar Daemon como propietario duradero

El daemon es un proceso local Node.js a pedido. El CLI lo llama a través de un socket Unix o una tubería llamada Windows. Salir el CLI no termina el daemon, por lo que su piscina, los trabajadores y los tiempos de ejecución ociosos permanecen vivos.

Crear la piscina una vez en la entrada de daemon, luego adquirir un contrato de arrendamiento en cada manejador de negocios:

```ts title="daemon-entry.ts"
import { createDaemonServer, DAEMON_SOCKET_ENV } from "@univer-cli/daemon";
import { createUniverCollaborationRuntimePool } from "@univer-cli/univer-collaboration-runtime-pool";

const socketPath = process.env[DAEMON_SOCKET_ENV];
if (!socketPath) throw new Error(`${DAEMON_SOCKET_ENV} is required`);

const pool = createUniverCollaborationRuntimePool({
  entry: new URL("./collaboration-worker.js", import.meta.url),
  cache: { idleTtlMs: 5 * 60_000, maxEntries: 20 },
});

const server = createDaemonServer({
  identity: { id: "my-cli", version: "1.0.0" },
  socketPath,
  onShutdown: () => pool.close(),
});

server.handle("unit.execute", async (payload) => {
  const input = parseExecuteRequest(payload);
  const lease = await pool.acquire({
    key: input.targetKey,
    init: { unitId: input.unitId, unitType: input.unitType },
  });

  try {
    const pulled = await lease.pull();
    if (pulled.status === "conflict") throw new Error(pulled.conflict.message);

    const execution =
      input.mode === "read"
        ? await lease.execute({ mode: "read", code: input.code })
        : await lease.execute({ mode: "write", code: input.code });
    const commit = input.mode === "write" ? await commitWithPull(lease) : null;
    return { commitStatus: commit?.status ?? null, value: execution.value };
  } catch (error) {
    await lease.invalidate();
    throw error;
  } finally {
    await lease.release();
  }
});

await server.listen();
```

La aplicación define `parseExecuteRequest()` y las reglas `targetKey`. El daemon sólo proporciona transporte local y gestión del ciclo de vida; no entiende Unidades, Tiempos de ejecución, o el protocolo de colaboración. Cerrar el daemon debe llamar `pool.close()`, por lo que los trabajadores activos y ociosos tienen un dueño final claro. En este ejemplo, `commitWithPull()` maneja la secuencia de atracción y compromiso después de `pull-required` y comprueba el estado de compromiso final.

Un comando CLI ordinario envía ahora una solicitud de negocio al daemon:

```ts
import { createDaemonClient } from "@univer-cli/daemon";

const client = createDaemonClient({
  entry: new URL("./daemon-entry.js", import.meta.url),
  identity: { id: "my-cli", version: "1.0.0" },
  socketPath,
});

const result = await client.request("unit.execute", {
  targetKey,
  unitId,
  unitType,
  mode,
  code,
});
```

Cuando el socket no existe, el cliente comienza la entrada de daemon configurada, espera el apretón de manos de identidad y protocolo, y luego envía la solicitud. Si un daemon compatible ya está funcionando, el cliente la reutiliza directamente.

## Paso 4: comparar primera solicitud y siguientes

El primer acceso a una clave sigue el camino frío: el daemon puede tener que empezar, y la piscina debe crear un Worker y un Runtime.

<Mermaid chart={"sequenceDiagram\n  autonumber\n  participant CLI as Primera invocación CLI\n  participant D as Daemon\n  participant P as Pool Runtime\n  participant W as Worker A\n  participant R as Runtime A\n  participant B as Backend\n\n  CLI->>D: unit.execute(target A)\n  Note over CLI,D: Iniciar daemon si falta el socket\n  D->>P: acquire(key A, init)\n  P->>W: Crear Worker y cargar entrada\n  W->>R: createRuntime(init)\n  R->>B: Abrir backend, leer punto de control / cambios\n  R->>R: Crear Univer, cargar Unit, esperar fórmulas\n  R-->>P: Runtime listo\n  P-->>D: Lease A\n  D->>R: pull → execute → commit\n  D->>P: release()\n  Note over P,R: Worker A y Runtime A quedan en caché inactiva\n  D-->>CLI: Resultado JSON\n  Note over CLI: La CLI termina, daemon / Worker siguen vivos"} />

El acceso posterior a la misma llave sigue el camino caliente. El proceso CLI comienza de nuevo, pero la carga de Runtime costosa no se repite:

<Mermaid chart={"sequenceDiagram\n  autonumber\n  participant CLI as Invocación CLI posterior\n  participant D as Daemon activo\n  participant P as Pool Runtime\n  participant R as Runtime A cargado\n\n  CLI->>D: unit.execute(target A)\n  D->>P: acquire(key A, init)\n  P-->>D: Acierto de caché, devolver Lease A\n  D->>R: pull()\n  Note over R: Sincronizar cambios remotos durante la inactividad\n  D->>R: execute()\n  opt Operación de escritura\n    D->>R: commit()\n  end\n  D->>P: release()\n  D-->>CLI: Resultado JSON\n  Note over CLI,R: La CLI termina, Runtime A sigue vivo"} />

Reutilización se aplica a un Runtime en vivo que ya ha sido creado y cargado. No evita la coherencia de la colaboración. Después de adquirir un contrato de arrendamiento, el llamante normalmente debe llamar a `pull()`; después de `commit()`, debe inspeccionar el estado final y manejar `pull-required`, `retry`, `unknown`, o `conflict`.

## Costes que desaparecen y permanecen

| Coste | Cargar directamente cada vez | Daemon + pool Worker |
| --- | --- | --- |
| Inicio CLI, argumentos, salida | Cada vez | Cada vez |
| Solicitud/respuesta JSON por socket | Ninguno | Cada vez |
| Inicio daemon y módulos | Ninguno | Primera solicitud o reinicio |
| Inicio Worker y entrada | Sin Worker | Creación fría por clave |
| Crear Univer e instalar plugins | Cada vez | Creación fría por clave |
| Punto de control, cambios iniciales, espera de fórmulas | Cada vez | Creación fría por clave |
| `pull()` de cambios durante inactividad | Cada vez | Normalmente cada vez |
| `execute()` y `commit()` | Cada vez | Cada vez |
| Memoria inactiva, handle backend, proceso Worker | Liberados al salir | Retenidos hasta expulsión, invalidación o cierre daemon |

Reuse trades de memoria residente y Worker cuenta para una menor latencia de inicio en llamadas posteriores. Set `idleTtlMs`, `maxEntries` , el tiempo libre , y el tiempo de funcionamiento de los eventos de la piscina y latencia medida , en lugar de retener cada unidad indefinidamente .

## Concurrencia, fallos y cierre

Cuatro reglas describen el comportamiento del sistema:

1. **Solicitudes simultáneas para la misma espera clave.** A live Runtime pertenece a un contrato de arrendamiento a la vez, por lo que las llamadas entrelazadas no pueden modificar el estado de colaboración.
2. **Claves distintas trabajan en paralelo en Workers distintos.** Cada clave residente requiere su propio Worker y Runtime.
3. **Sólo el estado de confianza puede ser reutilizado.** Call `release()` después de que una operación tenga éxito y se hayan despejado las mutaciones locales. Llame a `invalidate()` tras un tiempo, un accidente o un error de protocolo, o cuando la aplicación no pueda confirmar el estado local.
4. **La responsabilidad de desactivación fluye hacia abajo.** El CLI completa una petición; el cierre de daemon llama `pool.close()`; la piscina termina a los trabajadores y cierra sus Runtimes y backends.

Para comandos de baja frecuencia donde la latencia de una sola vacante es aceptable, usando `@univer-cli/univer-collaboration-runtime` directamente es la opción más simple. Combine el daemon con `@univer-cli/univer-collaboration-runtime-pool` sólo cuando las mediciones muestran que la carga repetida es el costo dominante y la aplicación puede aceptar un proceso de residencia y su uso de memoria.

[^document-unit]: Una Unit es una instancia de documento, como un libro de cálculo o un documento de texto. Una hoja forma parte de un libro y no es una Unit independiente.

[^live-runtime]: Aquí, Runtime es la instancia activa de Univer y los recursos necesarios para operar sobre una Unit cargada, no el ejecutable de Node.js ni una instantánea guardada.

[^runtime-cache]: TTL retira un Runtime inactivo al vencer su tiempo de vida; LRU retira los menos usados recientemente cuando falta capacidad. Liberan recursos sin eliminar la Unit persistida.
