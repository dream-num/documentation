Когда запускается команда CLI, дорогостоящая часть обычно не является анализом аргументов. Она превращает Unit[^document-unit] в живой Univer, который можно читать и писать: создание Univer , установка плагинов, открытие бэкэнда совместной работы, загрузка контрольной точки, применение наборов изменений и ожидание формул для завершения вычислений.

Две возможности Runtime[^live-runtime] выполняют эту работу, и эта страница охватывает оба:

- `@univer-cli/univer-collaboration-runtime` загружает блок и работает на нем в текущем процессе;
- `@univer-cli/univer-collaboration-runtime-pool` размещает время выполнения в рабочих и арендует, повторно использует и удаляет их по идентификатору блока.

Рабочее время выполнения выживает через вызовы CLI только тогда, когда ему принадлежит долгоживущий процесс. В этой архитектуре этот владелец является местным демоном.

## Три жизненных цикла

Повторное использование зависит от разделения трех жизней:

| Объект | Создание | Завершение | Владеет |
| --- | --- | --- | --- |
| Процесс CLI | В каждой командной строке | После вывода результата | Аргументы, один запрос, форматирование вывода |
| Процесс Daemon | Первый запрос или прямой запуск | Остановка, перезапуск обновления, сбой | Пул Runtime, бизнес-обработчики, локальный socket |
| Worker Runtime | Первое появление ключа в пуле | TTL/LRU[^runtime-cache]-вытеснение, инвалидирование, остановка daemon, сбой Worker | Один Worker, дескриптор backend, загруженная Unit и её состояние |

Одно правило владения управляет дизайном: **CLI делает один звонок, демон владеет бассейном, бассейн владеет рабочими, и каждый рабочий владеет временем выполнения.**

<Mermaid chart={"flowchart LR\n  CLI1[Вызов CLI 1<br/>короткоживущий] -->|JSON-запрос| D[Daemon<br/>долговечный владелец]\n  CLI2[Вызов CLI 2<br/>короткоживущий] -->|JSON-запрос| D\n  CLIN[Вызов CLI N<br/>короткоживущий] -->|JSON-запрос| D\n\n  D --> P[Пул Collaboration Runtime]\n  P -->|key: Unit A| WA[Worker A]\n  P -->|key: Unit B| WB[Worker B]\n  WA --> RA[Runtime A<br/>Unit A загружена]\n  WB --> RB[Runtime B<br/>Unit B загружена]\n  RA --> BA[Backend A]\n  RB --> BB[Backend B]\n  BA --> DS[(Сервер совместной работы<br/>или другой источник)]\n  BB --> DS"} />

Демон пересылает только запросы JSON, которые определяет приложение. Снимки, заменители и блоки считываются бэкэндом внутри Работника, поэтому они никогда не проходят через CLI или демон.

## Шаг 1: загрузка Runtime для каждой команды

Простейшая реализация создает `@univer-cli/univer-collaboration-runtime` внутри действия Commander и закрывает его при завершении операции:

```ts
const runtime = await runtimeFactory.load(unitId, unitType);

try {
  const pulled = await runtime.pull();
  if (pulled.status === "conflict") throw new Error(pulled.conflict.message);

  const execution = await runtime.execute({ mode: "write", code });
  let commit = await runtime.commit();
  if (commit.status === "pull-required") {
    const repulled = await runtime.pull();
    if (repulled.status === "conflict") throw new Error(repulled.conflict.message);
    commit = await runtime.commit();
  }
  return { execution, commit };
} finally {
  await runtime.close();
}
```

`runtimeFactory` происходит от `createUniverCollaborationRuntimeFactory()`. От загрузки до закрытия Runtime привязан к точно одному блоку и сохраняет текущий пересмотр этого блока, ожидая мутаций, ожидая изменений и состояния конфликта. Абонент также должен проверить окончательный статус совершения: только `confirmed` и `nothing-to-commit` означают, что операция завершена.

Звонок `load()` делает больше, чем чтение файла. Он выполняет следующие шаги в порядке:

1. Открывает backend совместной работы приложения;
2. Создаёт headless Univer и устанавливает совместную работу;
3. Загружает UnitData или контрольную точку Snapshot;
4. Воспроизводит изменения из контрольной точки;
5. Получает и воспроизводит промежуток до актуальной удалённой ревизии;
6. Ждёт применения последних результатов установленных модулей формул;
7. Возвращает Runtime с `execute()`, `pull()` и `commit()`.

Полное одноразовое обращение происходит следующим образом:

<Mermaid chart={"sequenceDiagram\n  autonumber\n  actor User as Пользователь\n  participant CLI as Процесс CLI\n  participant RT as Collaboration Runtime\n  participant U as headless Univer\n  participant B as Backend\n\n  User->>CLI: Выполнить команду\n  CLI->>CLI: Запустить Node.js, загрузить модули, разобрать аргументы\n  CLI->>RT: factory.load(unitId, unitType)\n  RT->>B: Открыть и прочитать точку / изменения\n  RT->>U: Создать Univer, плагины, загрузить и воспроизвести Unit\n  RT->>U: Дождаться формул\n  RT-->>CLI: Runtime готов\n  CLI->>RT: pull()\n  CLI->>RT: execute()\n  opt Операция записи\n    CLI->>RT: commit()\n    RT->>B: Отправить изменения\n  end\n  CLI->>RT: close()\n  RT->>B: Закрыть дескриптор backend\n  RT->>U: Освободить Univer\n  CLI-->>User: Вывести результат и выйти"} />

Собственность здесь прямая, и отказ не оставляет состояния позади, поэтому эта компоновка подходит для низкочастотных команд и разовых задач.Стоимость в том, что следующая команда CLI запускает новый процесс Node.js и повторяет всю последовательность загрузки, поэтому она не может повторно использовать Univer, а блок заявляет, что предыдущая команда построена.

## Шаг 2: размещение Runtime в пуле Workers

`@univer-cli/univer-collaboration-runtime-pool` поддерживает отдельный процесс Worker и Collaboration Runtime для каждого ключа резидента. Приложение обеспечивает запись Worker; бэкэнд, учетные данные и Univer создаются внутри Worker:

```ts title="collaboration-worker.ts"
import { defineUniverCollaborationRuntimeWorker } from "@univer-cli/univer-collaboration-runtime-pool";

export default defineUniverCollaborationRuntimeWorker({
  async createRuntime(init: { unitId: string; unitType: number }) {
    return createRuntimeFromApplicationInit(init);
  },
});
```

Запись Рабочего должна указывать на построенный файл JavaScript ESM. `init` отправляется Работнику только на холодном творении, и он должен быть совместим со структурированным клоном.

Абоненту не нужно проектировать отдельный уровень Runtime RPC. В аренде уже прокси-серверы общедоступных API, включая `getState()`, `execute()`, `fetch()`, `pull()`, `commit()` и `exportUnitData()`:

```ts
import { createUniverCollaborationRuntimePool } from "@univer-cli/univer-collaboration-runtime-pool";

const pool = createUniverCollaborationRuntimePool({
  entry: new URL("./collaboration-worker.js", import.meta.url),
});

const lease = await pool.acquire({
  key: targetKey,
  init: { unitId, unitType },
});

try {
  await lease.pull();
  const result = await lease.execute({ mode: "read", code });
  console.log(result.value);
} catch (error) {
  await lease.invalidate();
  throw error;
} finally {
  await lease.release();
}
```

`key` определяет, какое время выполнения использовать повторно; это не просто аргумент запроса. Один и тот же ключ всегда должен означать один и тот же блок, одну и ту же цепочку состояния совместной работы и совместимую семантику инициализации. Простой блок и проект Worktree должны использовать разные ключи, даже если они имеют один и тотже `unitId`.

Бассейн имеет четыре типа поведения, которые определяют повторное использование:

- Одновременная аренда ключа выполняется только по одному запросу, поэтому два вызова не могут изменить одно и то же состояние одновременно.
- `release()` возвращает доверенное время выполнения в пустой кэш, где следующий запрос на этот ключ может повторно использовать его;
- `invalidate()` отмечает состояние как более ненадежное.Рабочий и его время выполнения уничтожаются, а следующий запрос выполняет холодную нагрузку;
- Простаивающие Runtimes вытесняются по TTL/LRU. Тайм-ауты, сбои Worker и ошибки протокола также инвалидируют экземпляр.

Однако, если сам бассейн живет в недолговечном процессе CLI, повторное использование все еще не может пересечь командные границы.

<Mermaid chart={"flowchart LR\n  subgraph C1[Вызов CLI 1]\n    P1[Pool 1] --> W1[Worker A] --> R1[Runtime A]\n  end\n\n  X1[CLI завершается] -.->|Пул закрывается вместе с Worker| C1\n\n  subgraph C2[Вызов CLI 2]\n    P2[Новый Pool 2] --> W2[Новый Worker A] --> R2[Runtime A загружен заново]\n  end\n\n  X1 --> C2"} />

Рабочие обеспечивают изоляцию процесса для Runtime, эксклюзивную аренду и прекращение на отказ. Для повторного использования работников через вызовы CLI, пул все еще нуждается в владельце, который переживет любую одну команду.

## Шаг 3: Daemon как долговечный владелец

Демон — это локальный процесс Node.js по требованию. CLI вызывает его через гнездо Unix или трубку с именем Windows. Выход CLI не прекращает демон, поэтому его пул, рабочие и простояющие Runtimes остаются в живых.

Создайте бассейн один раз в входе демона, а затем приобретите аренду в каждом бизнес-обработчике:

```ts title="daemon-entry.ts"
import { createDaemonServer, DAEMON_SOCKET_ENV } from "@univer-cli/daemon";
import { createUniverCollaborationRuntimePool } from "@univer-cli/univer-collaboration-runtime-pool";

const socketPath = process.env[DAEMON_SOCKET_ENV];
if (!socketPath) throw new Error(`${DAEMON_SOCKET_ENV} is required`);

const pool = createUniverCollaborationRuntimePool({
  entry: new URL("./collaboration-worker.js", import.meta.url),
  cache: { idleTtlMs: 5 * 60_000, maxEntries: 20 },
});

const server = createDaemonServer({
  identity: { id: "my-cli", version: "1.0.0" },
  socketPath,
  onShutdown: () => pool.close(),
});

server.handle("unit.execute", async (payload) => {
  const input = parseExecuteRequest(payload);
  const lease = await pool.acquire({
    key: input.targetKey,
    init: { unitId: input.unitId, unitType: input.unitType },
  });

  try {
    const pulled = await lease.pull();
    if (pulled.status === "conflict") throw new Error(pulled.conflict.message);

    const execution =
      input.mode === "read"
        ? await lease.execute({ mode: "read", code: input.code })
        : await lease.execute({ mode: "write", code: input.code });
    const commit = input.mode === "write" ? await commitWithPull(lease) : null;
    return { commitStatus: commit?.status ?? null, value: execution.value };
  } catch (error) {
    await lease.invalidate();
    throw error;
  } finally {
    await lease.release();
  }
});

await server.listen();
```

Приложение определяет `parseExecuteRequest()` и правила `targetKey`. Демон обеспечивает только местный транспорт и управление жизненным циклом; он не понимает Units, Runtimes или протокола совместной работы. Отключение демона должно вызывать `pool.close()`, поэтому праздные и активные Рабочие имеют четкого конечного владельца. В этом примере `commitWithPull()` обрабатывает последовательность тяги и совершения после `pull-required` а также проверяет окончательный статус совершения. Любая необработанная ошибка аннулирует текущую аренду, что сохраняет пример консервативным.

Обычная команда CLI теперь отправляет один бизнес-запрос демону:

```ts
import { createDaemonClient } from "@univer-cli/daemon";

const client = createDaemonClient({
  entry: new URL("./daemon-entry.js", import.meta.url),
  identity: { id: "my-cli", version: "1.0.0" },
  socketPath,
});

const result = await client.request("unit.execute", {
  targetKey,
  unitId,
  unitType,
  mode,
  code,
});
```

Когда розетка не существует, клиент запускает настроенный вход демона, ждет идентификации и рукопожатия протокола, а затем отправляет запрос.Если совместимый демон уже запущен, клиент повторно использует его напрямую.

## Шаг 4: первый и последующие запросы

Первый доступ к ключу следует холодному пути: демону, возможно, придется начать, а бассейн должен создать Рабочего и Время выполнения.

<Mermaid chart={"sequenceDiagram\n  autonumber\n  participant CLI as Первый вызов CLI\n  participant D as Daemon\n  participant P as Пул Runtime\n  participant W as Worker A\n  participant R as Runtime A\n  participant B as Backend\n\n  CLI->>D: unit.execute(target A)\n  Note over CLI,D: Запустить daemon при отсутствии socket\n  D->>P: acquire(key A, init)\n  P->>W: Создать Worker и загрузить вход\n  W->>R: createRuntime(init)\n  R->>B: Открыть backend, прочитать точку / изменения\n  R->>R: Создать Univer, загрузить Unit, дождаться формул\n  R-->>P: Runtime готов\n  P-->>D: Lease A\n  D->>R: pull → execute → commit\n  D->>P: release()\n  Note over P,R: Worker A и Runtime A остаются в кеше ожидания\n  D-->>CLI: JSON-результат\n  Note over CLI: CLI завершается, daemon / Worker остаются живы"} />

Последующий доступ к одному и тому же ключу следует горячим путем. Процесс CLI начинается снова, но дорогостоящая нагрузка Runtime не повторяется:

<Mermaid chart={"sequenceDiagram\n  autonumber\n  participant CLI as Следующий вызов CLI\n  participant D as Работающий Daemon\n  participant P as Пул Runtime\n  participant R as Загруженный Runtime A\n\n  CLI->>D: unit.execute(target A)\n  D->>P: acquire(key A, init)\n  P-->>D: Попадание в кеш, вернуть Lease A\n  D->>R: pull()\n  Note over R: Синхронизировать удалённые изменения за время простоя\n  D->>R: execute()\n  opt Операция записи\n    D->>R: commit()\n  end\n  D->>P: release()\n  D-->>CLI: JSON-результат\n  Note over CLI,R: CLI завершается, Runtime A остаётся жив"} />

Повторное использование относится к уже созданному и загруженному реальному времени выполнения. Он не обходится без согласованности сотрудничества. После приобретения аренды абонент должен обычно звонить `pull()`; после `commit()` он должен проверить окончательный статус и обращаться с `pull-required`, `retry` , `unknown` или `conflict`.

## Какие затраты исчезают и остаются

| Затраты | Прямая загрузка каждый раз | Daemon + пул Worker |
| --- | --- | --- |
| Запуск CLI, аргументы, вывод | Каждый раз | Каждый раз |
| JSON-запрос/ответ по локальному socket | Нет | Каждый раз |
| Запуск daemon и загрузка модулей | Нет | Первый запрос или перезапуск |
| Запуск Worker и загрузка входа | Нет Worker | Холодное создание по ключу |
| Создание Univer и установка плагинов | Каждый раз | Холодное создание по ключу |
| Контрольная точка, начальные изменения, ожидание формул | Каждый раз | Холодное создание по ключу |
| `pull()` изменений за время простоя | Каждый раз | Обычно нужен каждый раз |
| `execute()` и `commit()` | Каждый раз | Каждый раз |
| Память простоя, дескриптор backend, Worker | Освобождаются с командой | Хранятся до вытеснения, инвалидирования или остановки daemon |

Повторное использование обменов резидентной памятью и рабочими учитывает более низкую задержку запуска на более поздних вызовах. Установите `idleTtlMs`, `maxEntries` , тайм-аут и тайм-Ауты работы от событий пула и измеренной задержки, а не сохраняйте каждый блок на неопределенный срок.

## Конкурентность, сбои и остановка

Четыре правила описывают поведение системы:

1. **Параллельные запросы на одно и то же ключевое ожидание.** Живое время выполнения принадлежит одной аренде за раз, поэтому переплетенные звонки не могут изменить состояние совместной работы.
2. **Разные ключи работают параллельно в разных Workers.** Каждый резидентный ключ требует отдельного Worker и Runtime.
3. **Только доверенное государство можно использовать повторно.** Позвоните `release()` после того, как операция увенчалась успехом, и местные мутации были очищены. Позвоните в `invalidate()`, после тайм-аута, сбоя или ошибки протокола, или когда приложение не может подтвердить локальное состояние.
4. **Ответственность за остановку течет вниз.** CLI выполняет один запрос; отключение демона вызывает `pool.close()`; пул прекращает работу сотрудников и закрывает их время выполнения и бэкэнды.

Для низкочастотных команд, где допустима разовая задержка, использование `@univer-cli/univer-collaboration-runtime` напрямую является самым простым вариантом.Объедините демон с `@univer-cli/univer-collaboration-runtime-pool` только тогда, когда измерения показывают, что повторная загрузка является доминирующей стоимостью, и приложение может принять постоянный процесс и его использование памяти.

Полный список — в [каталоге пакетов](/ai/packages).

[^document-unit]: Unit — экземпляр документа, например рабочая книга или текстовый документ. Лист является частью книги, а не отдельной Unit.

[^live-runtime]: Здесь Runtime — работающий экземпляр Univer и ресурсы для операций с загруженной Unit, а не исполняемый файл Node.js или сохранённый снимок документа.

[^runtime-cache]: TTL удаляет неактивный Runtime из кэша по истечении срока жизни; LRU при нехватке места вытесняет давно не использованные экземпляры. Это освобождает ресурсы, но не удаляет сохранённую Unit.
